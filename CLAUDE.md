# atelier-api

Fastify + Postgres API. Plain JavaScript, ESM, no TypeScript.

## Conventions

- `src/config.js` — `loadConfig(env)` validates env vars, throws with clear message; server exits 1 on failure. Add new env vars here + `.env.example`.
- `src/db.js` — `createPool(databaseUrl)` returns pg Pool. Inject the pool into `buildApp({ pool })`; never import a global pool (keeps tests isolated).
- `src/app.js` — `buildApp()` builds the Fastify instance without listening. Tests use `app.inject()` (no port binding needed).
- **CORS covers TWO browser apps and must name both origins AND every write method.** `buildApp({ storeBaseUrl, crmBaseUrl })` → `@fastify/cors` with `credentials: true`, an exact-match origin allowlist and an explicit `methods` list. Guarded by `test/cors.test.js`. Three traps, each of which has actually broken the product:
  - **The CRM is a second origin.** Storefront islands fetch browser :4321 → api :3001; the CRM fetches :5273 → api :3001. Only the storefront was allow-listed, so *every* CRM call — including sign-in — was blocked by the browser. `CRM_BASE_URL` (→ `config.crmBaseUrl`) is the second entry.
  - **`methods` MUST be spelled out.** @fastify/cors defaults to `GET,HEAD,POST`, so a `PATCH`/`PUT` is refused at the preflight and **never reaches this server**. Every admin edit is a PATCH and shipping rates are a PUT, so the default silently broke every write in both browser apps — while curl and `app.inject()` (neither of which preflights) kept passing. Any CORS assertion made with `inject` alone is worthless for methods; only a real browser preflight proves it.
  - **The allowlist is closed, never reflected.** `origin: true` (echo whatever asked) plus `credentials: true` would let any site drive the API with a logged-in staff cookie. An unknown origin gets `storeBaseUrl` back, which the browser then rejects.
- `src/server.js` — only entry point that listens/exits.
- Config objects frozen (`Object.freeze`); immutable updates house style.

## Migrations

- `migrate:create` emits a CommonJS template (`exports.up`) — rewrite to ESM (`export const up/down`) because this package is `"type": "module"`.
- Tests run migrations themselves via the programmatic runner: `import runner from 'node-pg-migrate'` with `{ databaseUrl, dir: 'migrations', direction: 'up', migrationsTable: 'pgmigrations', log: () => {} }`. Runner returns the array of applied migrations — empty array proves a re-run is a no-op.
- `vitest.config.js` sets `fileParallelism: false` — the runner takes a Postgres advisory lock, so parallel test files throw "Another migration is already running". Keep it serialized.
- Schema: one `inventory` row per colourway (`colourway_id` unique). Check constraints: `products.product_type IN ('fabric','finished_good')`, `inventory.unit IN ('metres','units')`. Upsert targets for the seed: `brands.slug`, `products.slug`, `colourways.sku`, `collections (brand_id, slug)` — all unique.
- Commerce schema: `users.role IN ('customer','trade','backoffice','director')` (default `customer`), `orders.kind IN ('checkout','order_request','backorder_request')`, `orders.status IN ('requested','confirmed','paid','shipped','declined')`. `order_lines.colourway_id` is `ON DELETE RESTRICT` (commerce records survive catalogue cleanup); `orders.user_id` is `SET NULL` (guest orders keep `guest_email`). Shipping seed upsert key: `shipping_rates (zone, threshold_qty)` unique.

## Seed

- `npm run seed` (`src/seed/run.js`) — idempotent import of the atelier-app catalogue. `src/seed/catalogue-data.js` is a pure transform layer (no DB) importing vendored snapshots from `src/seed/data/` (`{realCatalogue,atelier,suppliers,pricing}.js` plus their internal deps `fx/discounts/fabricutDesigns.js` — Node-safe pure data copied from the CRM repo's `atelier-app/src/data/`; re-copy when the catalogue changes). `src/seed/seed.js` `runSeed(pool)` does the upserts in one transaction.
- Upsert semantics: brands/collections/products/colourways use `ON CONFLICT … DO UPDATE`; **inventory and shipping_rates use `DO NOTHING`** — they become live operational data after first seed (reservations, admin-edited rates) and a reseed must not clobber them.
- Products carry no SKU; the SKU lives on `colourways` (finished goods get one colourway carrying the product SKU). Fabric product slug = slugify(`${brand} ${design}`), e.g. `pierre-frey-atlas`.
- House brand `Atelier Textiles NZ` (slug `atelier-textiles-nz`) is the only `is_international=false` brand; only its finished goods have `retail_price_cents` (indicative values in `HOUSE_RETAIL_PRICE_CENTS`). All fabrics + international finished goods have null retail price (FR-3). It is **also the only `trade_only=false` house** — the one library a signed-out visitor may browse (see "Two independent gates" under Catalogue). `trade_only` is written on INSERT only, so a CRM change to it survives every reseed.
- **Three seed-owned brand files that a `./data/` re-copy must NOT overwrite.** `src/seed/data/brand-websites.js` (`BRAND_WEBSITES`, slug → the house's own site), `src/seed/data/represented-houses.js` (`REPRESENTED_HOUSES`) and `src/seed/data/brand-stories.js` (`BRAND_STORIES`, slug → the house description). The first two hold the client's roster of 4 Aug 2026 and supersede any earlier researched values — do not "correct" an entry back, raise it instead. realCatalogue.js only knows houses with products or designs behind them, so a house Atelier represents but holds nothing from could never reach `brands`; `buildBrandRows()` appends the represented-only ones LAST and skips any slug the catalogue already produced, so the two can never both emit one slug (which would make the brands upsert hit the same conflict key twice). Their `currency` is the SUPPLIER's invoicing currency (the suppliers.js rule — Jim Thompson is Thailand but USD), defaulted from the region where no invoice is on file; nothing renders it until the house has a product. 41 brand rows: 27 stocked + 14 represented.
- **`BRAND_STORIES` fills blanks only.** `toBrandRow()` reads realCatalogue.js's own story FIRST and falls back to the map, so the snapshot stays the source of record for every house it describes; the map covers the eighteen it says nothing about (the 14 represented-only houses plus Brochier, Trend, Vervain and Atelier's own entry), written from each house's website. **State a founding year only where a source confirms it** — the storefront's `foundedYear()` parses "Founded YYYY" straight out of this text into the "est. YYYY" meta, so a guessed date surfaces as fact; a house without one shows its country alone, which is what the design degrades to. Guarded by a seed test asserting no brand is left without a description. Caveat: `upsertBrands` writes `story = EXCLUDED.story` unconditionally (unlike `website_url`), so a story staff edit in the CRM does NOT survive a reseed — pre-existing for every snapshot-described house, not introduced by the map.
- **A roster change needs a migration, not just a seed edit.** `website_url` is `COALESCE(brands.website_url, EXCLUDED.website_url)` on purpose, so a URL staff typed in the CRM outlives every reseed — which also means a reseed can never *change* a URL that is already set. `migrations/1786060800000_client-house-roster.js` is the one-off correction that applied the roster to already-seeded databases (inserts the 14 houses `ON CONFLICT DO NOTHING`, then overwrites `website_url` for all 39), and `1786075200000_house-descriptions.js` does the same for the descriptions (`WHERE story IS NULL`, so a CRM edit made in between survives). Both inline their own copy of the data rather than importing the seed files — see below. It inlines its own copy of the data rather than importing the seed files: a migration is a record of what ran, and one importing a file that later changes would rewrite its own past. The COALESCE contract still stands for every reseed after it.
- `hex_tones` jsonb: pass `JSON.stringify(array)` as the query param — pg maps raw JS arrays to Postgres arrays, not jsonb.
- Shipping tiers: `threshold_qty` is the tier floor (0 and 20 per zone); a quote picks the highest threshold <= qty.

## Supplier price lists

- Two-step pipeline: `npm run convert:pricing` (`scripts/convert-price-lists.js`, Node with no dependencies) turns the per-brand template drops in `incoming/pricing-templates/` (gitignored) into the universal file `src/seed/data/price-lists.json`; `npm run import:pricing` (`src/seed/import-price-lists.js` → `src/seed/price-lists.js`) upserts it into `price_list_items`.
- All templates share one 14-column layout (Date Effective … Freight Rate). Converter normalises: item type → `category` (`fabric|wallpaper|trimming|accessory`), pack type → `unit` (`metre|yard|roll|piece`), currency names → ISO (`EUR|USD|GBP`), d/m/Y and Excel-serial dates → ISO, float noise rounded to 4dp. CSVs are sniffed strict UTF-8 (BOM tolerated) then `cp1252` then latin-1 (≈28 files are cp1252); XLSX read from the zip directly. Supplier name comes from the filename prefix (title-cased, `SUPPLIER_OVERRIDES` for JV/JWall/C&C), not the `Product Range` column (which holds range names like "MISSONI WALL COVERING").
- Converter fails loudly (file:line list, writes nothing) on unmappable values; **skips** rows with wholesale rate 0 (price-on-application items, reported to stderr) and exact duplicate rows (keep-first).
- **Both converters were Python until they were ported to Node (no dependencies), and the port is pinned to byte-identical output** — `src/seed/data/price-lists.json` is committed, so a formatting drift shows up as an 8 MB diff rather than a bug. `scripts/lib/` is the shared machinery: `zip.js` (central directory + `inflateRawSync`; ZIP64 throws), `xml.js`, `xlsx.js`, `text.js` (encoding sniff + CSV), `python-format.js`. Four traps the port had to reproduce, all guarded by `test/converters.test.js`:
  - **`json.dumps` is not `JSON.stringify`.** Python separates with `", "`/`": "`, writes a float as `115.0` not `115`, and switches to exponent notation at 1e16 with a two-digit exponent (`1e+16`). `python-format.js` reproduces `repr(float)`, `format(x, 'g')` and both `dumps` shapes; every number these converters emit came from a Python float, so ints never appear.
  - **D365 writes `<x:row>`, Excel writes `<row>`.** Python's ElementTree resolved namespaces for free; the tag scanner resolves the document's prefix once from the root element and matches through it. Matching a bare tag name silently finds nothing — which reads as "not a dynamic worksheet export", not as a parser bug.
  - **An XML parser normalises literal CRLF in text content to LF** (XML 1.0 §2.11) before anything downstream sees it. Multi-line addresses and comment fields carry CRLF, so skipping this changes thousands of rows. A character reference (`&#13;`) is not literal and must survive, hence normalise-then-expand-entities.
  - **`Number()` is far looser than `float()`** — `''` is 0, `'0x10'` is 16. `parseNumber` is regex-gated so a malformed cell surfaces as a reported error instead of a plausible zero.
- Cross-checked against `~/Documents/atelier-platform-demo` docs (Verum build spec REQ "price-list import templates", Action-List 13–15 Jul): the 14-column set matches the ratified template; `code_normalized` implements decision 6 (uniform code format, raw kept for traceability); unit vocabulary matches decision 7 (`metre|yard|roll|piece|hide|panel` — hide/panel have no template rows yet). `duty_class`/`freight_class` letters are stored **raw, uninterpreted**: the broker's duty table (A10) and a freight class→rate table are still owed — the CRM's `/import` wizard applies a 7% duty placeholder downstream; do NOT bake placeholders into this table. Pattern-match text stays embedded in `vertical_repeat` (corpus too messy for an enum: "Repetable", "HD", "V x 70H"…; definitive field list still owed from Charlotte).
- Upsert key `(supplier, category, code)`, `ON CONFLICT … DO UPDATE` — unlike inventory, a re-import is how new season rates land, so freshest wins; rows absent from later files are kept. `wholesale_rate` stays `numeric(12,4)` in the **supplier's currency** (not NZD cents — the pricing waterfall converts downstream). Whole import is one transaction, chunked `unnest` batches; `validatePriceListItems` rejects the batch before any SQL (also catches duplicate keys, which would break multi-row upsert).
- `repeat` is a Postgres non-reserved word but quoted `"repeat"` in SQL anyway. Guarded by `test/price-lists.test.js`, which also validates the committed JSON (19.5k items, 40 suppliers).

## Legacy D365 staging

- Two-step pipeline mirroring the price-list one: `npm run convert:legacy` (`scripts/convert-d365-exports.js`, Node with no dependencies) turns the Dynamics worksheet exports in `incoming/data-exports/` (gitignored) into `incoming/data-exports/normalized/*.json`; `npm run import:legacy` (`src/seed/import-legacy.js` → `src/seed/legacy-import.js`) upserts them into the eleven `legacy_*` tables (product_prices, stock_items, item_locations, accounts, contacts, sales_orders, sales_invoices, purchase_orders, purchase_invoices, reserves, cuttings). Full column audit and data findings in `docs/d365-export-analysis.md`.
- Adding an entity means three edits in lockstep: `ENTITIES` in the converter, a `createTable` in a migration, and a `LEGACY_TABLES` entry (the column map drives the `unnest` casts, so a missing/misnamed column fails the whole import rather than silently nulling).
- Columns pulled from a **related** entity export as `<relationship-guid>.<logical_name>` (e.g. `5c5e1693-….atelier_code`). The GUID changes if the view is rebuilt, so the column map accepts a `*.atelier_code` suffix wildcard; a bare logical name always takes precedence.
- **All four transaction entities are header-only** (sales orders, sales invoices, purchase orders, purchase invoices) — roll-up totals, no lines. There is no export path for the detail rows, so **line-item import is shelved**: legacy sales history stays header-grain and product-grain historical reporting is out of scope. Revenue by customer/owner/period still works off the 7,002 invoice headers.
- **D365 item codes are composed at sales-order time, not catalogued**: `{supplier's colour code}[ {YY}{SUPPLIER_TOKEN}]` (e.g. `F3518-003 23PF`). 74.5% carry the suffix, 62 tokens, years 11–26. The token is the **supplier**, not the brand (`CF` = Colefax & Fowler + Jane Churchill), so the token set doubles as the supplier↔brand roll-up A13 wants. Consequence: Product Prices is the catalogue spine (19,327 designs) and Stock Items is the transacted subset (7,611) — a colourway only exists once sold. The item code's numeric part is the supplier's colour code and does **not** match the price-list code, so never join those on code.
- **Lookup columns export as the target's display name, which destroys the key.** `legacy_stock_items.product_price_list` is the price row's Description: only 52% of stock items resolve to exactly one price row (796 ambiguous, 1,780 no match, 1,064 unset). Same for `legacy_item_locations.item` (7,611 items share 6,315 names). The fix is a related **code** column, as Reserves/Cuttings already have — those join at 88–92%. Re-export those two views before attempting any stock↔price mapping.
- `legacy_reserves` (not the stock item's free-text `Reserve` note) is the source of reserved quantity.
- Portal identity columns on `contact` (`adx_identity_*`, incl. the password hash) are dropped at conversion alongside the supplier bank details.
- **Staging is deliberately separate from the live tables and nothing maps into them yet.** The A1/A2/A3 definitions (cost source, what counts as a sale, stock authority) are unsettled; Atelier runs live on D365 until cutover so the import must re-run; and `orders`/`order_lines` are owned by the Stripe webhook + admin-orders state machine — injecting historic orders there would desync `qty_reserved`.
- Exports must stay **dynamic** worksheets. Each embeds `<entity>:<sig>:<logical_name>=<Display Name>&…` in `sheet.xml` (data is on `sheet2.xml`), so columns are matched by **D365 logical name, never display name or position** — a renamed or reordered view cannot corrupt the import, and a missing required column fails the whole run. Dynamic exports also carry the record GUID and a row checksum; a static export carries neither.
- Upsert key is the D365 GUID → re-import is idempotent and refreshes in place; rows absent from a later export are kept. `validateLegacyRecords` runs before any SQL and rejects duplicate GUIDs (a multi-row upsert cannot hit the same conflict key twice) and unknown columns. `raw` jsonb holds every non-empty source column by logical name — `JSON.stringify` it before binding (pg maps a raw object to a record, not jsonb).
- **Consent polarity trap**: D365 renders `donotemail=false` as the word **"Allow"** and `donotsendmm=false` as **"Send"**. Staging columns keep the source attribute's polarity and name (`do_not_*`, TRUE = do not contact); a column named `send_marketing_materials` would invert every row. Guarded by `test/legacy-import.test.js`.
- Supplier bank-account columns are dropped at conversion time and never reach the database. Normalised JSON lives under `incoming/` (gitignored), not `src/seed/data/`, because accounts and orders are client PII.
- Timestamps are `timestamp` (no zone): the export writes Excel serials rendered in the exporting user's local time, so tagging them UTC would shift every date by the NZ offset.

### Getting the exports onto a server (`push:legacy`)

- **A deploy can never carry this data.** `incoming/` is gitignored (client PII), so `npm run import:legacy` on a server finds an empty directory and the CRM's Orders/Clients/Price-lists screens sit at `total: 0` — 200-with-no-rows, which reads as "broken app" rather than "no data". That is exactly what happened on staging: migrations applied, routes deployed, zero rows.
- `npm run push:legacy` (`src/seed/push-legacy.js`) runs on the workstation that HAS the files and streams them to a remote API: `ATELIER_API_PASSWORD='…' npm run push:legacy -- --api https://api.example.com --email <director>`. Options `--dir`, `--batch` (default 1000), `--only <entity>`, `--dry-run`, `--cookie` (skip sign-in). Password comes from the environment by preference — argv is visible in shell history and `ps`.
- The receiving end is `POST /admin/legacy/import/:entity` (`src/routes/admin-legacy-import.js`), **director-only** — backoffice may browse the staging tables but not bulk-write them. `:entity` uses the export/table names (`product_prices`, `sales_orders`), NOT the read routes' URL vocabulary (`prices`, `sales-orders`).
- **Batching is what makes this work without server access.** The corpus is 125 MB of JSON but ~12 MB gzipped; at 1000 records a batch the largest request is **403 KB compressed** (accounts, the fattest rows), under nginx's 1 MB default `client_max_body_size`. So no nginx edit, no SSH, no panel — an HTTPS session cookie is the whole channel. Raising the batch size past ~2000 breaks that guarantee.
- Body is gzip (`application/gzip`, parsed as a Buffer by a parser **encapsulated in this plugin** — same posture as the Stripe webhook; if it leaked to the root instance every JSON route would start receiving Buffers). A plain JSON array is accepted too, for a hand-made curl. `decodeImportPayload` (`src/legacy/import-payload.js`) caps the DECOMPRESSED size at 32 MB — a gzip bomb is cheap to build, so the compressed body limit alone is not a defence — and rejects batches over 5000 records.
- Status codes: 400 malformed (bad gzip, not an array, empty, unknown entity), 413 oversized batch, 422 field-level (`validateLegacyRecords`: bad GUID, unknown column, duplicate GUID inside one batch), 403 backoffice, 401 anonymous.
- Idempotent and resumable: each batch is one transaction upserting on the D365 GUID, so an interrupted push is re-run, not repaired. The client retries transport failures and 5xx three times with backoff and fails fast on 4xx (retrying a rejected batch only burns the rate-limit bucket, 600 / 10 min).
- `LEGACY_ENTITY_ORDER` (`src/seed/legacy-entities.js`) is shared by the local CLI and the push so both land the catalogue spine (product prices, stock) first. Guarded by `test/legacy-import-api.test.js` (22 tests); verified end to end by pushing all 55,877 records into an empty database over HTTP.

## Trade client portal (`/account/*`)

- The approved-trade client's own view: dashboard, sample history, invoice record, price lists, account manager. `src/routes/account.js`, read models in `src/trade-accounts/` + `src/account/summary.js`. **Every route is `requireRole('trade')` and nothing else** — `GRANTING_ROLES.trade` is `['trade']` and `effectiveRole` collapses an unapproved trade account to `customer`, so that one preHandler already means "approved trade, not a customer, not staff". Staff are excluded deliberately (they have the CRM and `/admin/legacy/*`, unscoped); re-deriving the predicate per handler is how the archived-user and CORS-methods regressions happened. All routes opt into `config.rateLimit` — the limiter is `global: false`, so a route without it is unmetered.
- **`users` is a login (a person); a trade client is a company.** Nothing joined them, so `trade_accounts` + `trade_account_users` (migration `1786248000000_trade-accounts.js`) is the link, deliberately **outside** the `legacy_*` namespace: `importLegacyEntity` upserts every mapped column to EXCLUDED, so anything stored on a legacy row would be destroyed by the next `npm run import:legacy`.
- **The key is the D365 GUID; the NAME is a snapshot.** The transaction exports carry the customer as the target's **display name**, not a key (`legacy_sales_invoices.customer` is text), so `trade_accounts.legacy_customer_name` is snapshotted at link time and is what the reads match on. **Account names are not unique** — 866 rows, 865 distinct names ("Peter Kedgley Architects" twice, 2 invoices between them) — and a name-equality predicate returns the UNION of every account sharing it, i.e. cross-client disclosure by construction.
- **The collision check is LIVE, in `VIEWER_CTE`, not the stored flag.** `name_is_ambiguous` is computed once at link time, but `npm run import:legacy` re-runs until cutover — upserting `legacy_accounts.name` and inserting new rows — so the flag can be falsified afterwards. Two drifts, both closed by the CTE's join to `legacy_accounts`: a NEW account appearing with an already-linked company's name (its invoices would join straight onto that viewer while the flag still said false), and a linked account being RENAMED with its old name later taken by someone else (here the collision count is legitimately 1, so recomputing the flag would not help — requiring the snapshot to still equal the LINKED GUID's current name is what does). `toClientTradeAccount`'s `linked` is the live `resolves`, so the dashboard can never promise history the reads will refuse. The stored flag remains the CRM's warning. Verified against the real corpus: the colliding link reports `coverage.invoices: 2` to staff and serves the client `linked: false` and zero rows; both drift cases are regression-tested.
- **`UNIQUE (user_id)` on `trade_account_users`** — one login, one company. Without it a back-office mis-click links a person to a second firm and a single-row viewer query starts returning a non-deterministic one (intermittent cross-company disclosure). Several logins per company IS allowed and is the common case (the trade application collects a design contact and an accounts contact).
- **The scoping key is never a function argument.** `VIEWER_CTE` (`src/trade-accounts/viewer.js`) derives it inside SQL from `$1 = the authenticated user id`, the same posture as `/orders/mine`. No read model here accepts a customer name — a helper that did is one a future route could bind from a query param. An unlinked or ambiguous viewer resolves to zero rows, so the reads **fail closed** rather than degrading to `= ''` (which matches every legacy row with an empty customer field).
- Linking is **manual, backoffice, and never automatic** (`/admin/trade-accounts`, `src/trade-accounts/admin-trade-accounts.js`). **No screen calls those routes yet** — they belong on the CRM's Users → Applicants tab, which is another repo — so `trade_accounts` and `trade_account_users` are registered as editable AdminJS resources as the stopgap. Without one of the two, nothing can create a link and the samples/invoices/account-manager panels are unreachable for every client. `GET /admin/trade-accounts/suggestions` ranks candidates by exact account email then name — suggestions only. An auto-link on email match is the tempting shortcut and is wrong: 171 contact emails are shared by 2-4 contacts and 385 are free-mail, so it would eventually show one designer another's invoices. `GET /admin/trade-accounts/:id` carries `coverage` (invoice + cutting counts) because a link resolving to zero is almost certainly the wrong company, and this is the only place a human sees that before the client does.
- **Invoices are header-only, forever, and carry no payment state.** All four D365 transaction entities export header-grain and line import is shelved, and `status_reason` is 'Sent to Xero' on all 7,002 rows — a dispatch state, not a payment one — while FR-8 forbids calling Xero. So the screen is an invoice **record**, never a statement: no balance, no aging, no "paid" badge. `POST /account/invoices/:id/copy-request` is what replaces the missing PDF (mails the back office + the client). Its `:id` is **re-resolved through the caller's own scoped query** — a D365 GUID is not a secret, and without that check the back office would receive "client X wants invoice <guid>" with no way to tell it was not theirs, and would post it. A non-owned id is **404, not 403** (403 confirms existence).
- Sample history is `legacy_cuttings`, not `legacy_reserves`. The staged export starts 2025-04-08 and has no due-back date, so the panel says what window it is showing rather than implying it is everything. **`legacy_cuttings.comments` is NOT served** — it looks client-safe and is not: 1,757 of 1,886 rows carry one and they are the back office's scratchpad, holding staff names, handling instructions and in several current rows a third party's name, email, phone or home address. Serving it would put one client's contact details in another client's JSON.
- **Account manager is a staff-set field on `trade_accounts`, never derived from `legacy_accounts.owner`** — 72% of that column is a shared login ('Atelier Sales' 491, 'Showroom #' 135) and A6 (salesperson vs owner vs account holder) is still open. Null degrades to a generic showroom contact block.
- **`GET /orders/mine` is now paged** (`page`/`limit`, `{ orders, meta }`). It used to return every order a user had ever placed plus every line of all of them, which the dashboard then sliced to three — and a long-standing trade client is exactly the account that breaks that. Order lines now also carry `slug`/`product_type`/`brand_name`/`colourway_name`/`lead_time`, which is what reorder needs.
- **Client price lists are the SELL side and must never touch `price_list_items`** (`src/pricing/trade-price-lists.js`). That table is Atelier's BUY side — 19.5k supplier rates, mostly discount-inclusive, so the rate IS the net cost; divide it into the trade price and the margin falls out, and the lists are the maisons' confidential documents. Do not widen the guard on `/admin/price-list-items`, do not reuse `toPriceListItem` (no field-level redaction), and do not point the portal at `/admin/legacy/prices` (its `:guid` route returns the whole `raw` jsonb, bypassing every column whitelist). The client list is built from `products.trade_price_cents` alone — cost-free by construction — and `test/price-list-exposure.test.js` asserts all of it, parameterised over every `LEGACY_ENTITIES` route plus a property check that no client-facing key matches `/wholesale|landed|duty|freight|cost|margin|markup|credit_limit|payment_terms/`.
- **Price lists ship DISABLED** (`TRADE_PRICE_LISTS_ENABLED`, off unless exactly `'true'`; the routes are simply not registered, so a probe 404s). `trade_price_cents` is still the demo snapshot — 8 of 12 seeded fabrics share NZ$187.76, no finished good has one — and a per-house list is a document a designer quotes a job from. Turning it on is a decision about the numbers.
- CSV export escapes RFC 4180 **and** neutralises formula lead-ins (`= + - @ TAB CR` get an apostrophe): every column is staff-typed free text via `PATCH /admin/products` and the file is built to open in Excel, where `=HYPERLINK`/`=WEBSERVICE` exfiltrate. The `Content-Disposition` filename comes from the brand **slug** (`[a-z0-9-]` by construction), so nothing typed can reach the header.
- Guarded by `test/account-portal.test.js` (20), `test/trade-accounts.test.js` (18), `test/price-list-exposure.test.js` (15). The portal fixture gives two different legacy accounts **the same name** — the regression the ambiguity flag exists to prevent, which a fixture with distinct names would pass anyway.

## Auth

- Sessions are **stateless signed cookies**: cookie `atelier_session` holds the user id, signed by `@fastify/cookie` with `COOKIE_SECRET` (required env var, 32+ chars; `buildApp({ pool, cookieSecret })` throws without it). No sessions table — logout only clears the client cookie.
- `src/auth/session.js` — `setSessionCookie(reply, userId)` / `clearSessionCookie(reply)` / `readSessionUserId(request)` (returns user id or null; use this for US-006 middleware). Cookie flags: HttpOnly, Secure, SameSite=Lax, path=/, 30-day maxAge.
- `src/auth/passwords.js` — argon2id via `hashPassword`/`verifyPassword` (never throws on malformed hash, returns false). `getDummyHash()` is verified against for unknown emails so login timing doesn't enumerate accounts.
- Rate limiting: `@fastify/rate-limit` registered `global: false`; routes opt in via `config: { rateLimit: { max, timeWindow } }`. Login AND register share 10 per 15 min per IP (register is limited because each attempt runs a memory-hard argon2 hash and 409s enumerate emails). The limiter store is per app instance and per route — tests that spend attempts need their own `buildApp()`.
- Fastify's bundled Ajv has **no `format: 'email'`** — body schemas use `EMAIL_PATTERN` regex instead. Schema violations return 400 (Fastify default), not 422.
- Responses use snake_case fields matching DB columns; `password_hash` is never selected into a response — always select via `PUBLIC_USER_COLUMNS` from `src/auth/user-columns.js` (single source of truth, do not redefine locally).
- Guards (`src/auth/guards.js`): `buildApp` decorates `app.guards = createGuards(pool)`; protect routes with `{ preHandler: app.guards.requireAuth }` or `app.guards.requireRole('trade'|'backoffice'|'director'|'customer')`. `requireAuth` loads the user from DB per request and sets `request.user`; 401 when no/invalid session or user deleted. `requireRole` returns 403; unknown role name throws at registration time. Role semantics: unapproved trade collapses to `customer` (`effectiveRole`), `director` passes `backoffice` checks, `requireRole('trade')` is approved-trade ONLY (backoffice/director do NOT get trade capability — deliberate, revisit if staff need trade-pricing views).
- `POST /auth/trade-application` = register with `role='trade'` (`trade_approved` stays false via DB default) **plus the full atelier.co.nz trade-account form** in a required `application` object (body schema is structural only; `validateTradeApplication` in `src/users/trade-applications.js` returns the field-level 422s with `application.<field>` paths). `submitTradeApplication` creates the user AND the `trade_applications` row in one transaction — a duplicate email (409) leaves no orphan form. Same rate limit bucket rules as register. The form is reviewed in the CRM's Users → Applicants tab (`GET /admin/trade-applications`(`/:id`), backoffice, read-only — `src/routes/admin-trade-applications.js`); each application embeds the applicant's live `user` state via LEFT JOIN because approval state is NEVER stored on the application: `users.trade_approved` stays the single source of truth, flipped only via `PATCH /admin/users/:id { trade_approved: true }`. `trade_applications.user_id` is `ON DELETE SET NULL` (business record survives account removal — test cleanups must delete applications before users or they orphan). Approval is manual and silent: nothing notifies the applicant. **A pending trade account cannot authenticate at all**: the application sets no session cookie, `/auth/login` answers **403** "awaiting review" (checked only AFTER the argon2 verify, so without the right password it stays the generic 401 — no enumeration), and `SESSION_USER_CONDITION` (`src/auth/user-columns.js`, = active AND NOT pending-trade) is what `/auth/me` + `guards.loadSessionUser` filter on, so revoking approval kills a live session exactly like archiving does. Guarded by `test/trade-applications.test.js`; the shared valid-form fixture lives in `test/helpers/trade-application-fixture.js`.
- **`/admin/users` is the account admin the CRM drives** (`src/routes/admin-users.js` + `src/users/admin-users.js`, backoffice-only). `GET` filters by `role`, by `segment` (`clients` = customer+trade, `staff` = backoffice+director — the coarse split the CRM navigates by; passing both intersects), by free-text `q`, and `include_archived`. `PATCH` writes `role`/`trade_approved`/`name`/`email` from a frozen whitelist. **`email` is editable on purpose**: it is what the client signs in with, and a typo taken down over the phone otherwise leaves an account nobody can reach and no way to fix it short of SQL. It is lower-cased in `updateUser` (not the route) because every auth path looks the address up in lower case, and a collision is the same 409 create answers with. Two self-protection guards live in the handlers (they need `request.user`): you cannot change your own `role`, and you cannot archive yourself. **A patch that moves a role off `trade` also clears `trade_approved`** — the flag only means anything on a trade row, so demoting an approved account used to strand a `true` nothing displays, and re-promoting it months later handed back trade pricing AND every trade-only house with no review. Enforced in `updateUser`, not in a screen, so it holds for the CRM, the AdminJS panel and any future caller; an explicit `trade_approved: true` in the same body loses, because the role is the stronger statement and the two together are a contradiction rather than an instruction.
- **Every auth path must exclude archived accounts.** `archived_at` is a soft delete (orders reference the row), so the account is still fully loginable unless the query says otherwise — archiving from the CRM used to leave the session cookie live, let the old password back in, and keep serving trade pricing. `ACTIVE_USER_CONDITION` in `src/auth/user-columns.js` is the single source of truth for the clause; it is applied in exactly three places (`/auth/login`, `/auth/me`, `guards.loadSessionUser` — which covers `requireAuth`, `requireRole` AND `loadOptionalUser`, so an archived trade user drops to anonymous on the public catalogue) plus `src/admin/authenticate.js` for the panel. (`/auth/me` and `loadSessionUser` actually apply `SESSION_USER_CONDITION`, which embeds it and adds the pending-trade exclusion — see the trade-application bullet.) The back-office `src/users/admin-users.js` queries deliberately do NOT use it — staff must be able to list and restore archived rows. Login and panel login **select** `archived_at` rather than filtering in SQL: filtering would return before the argon2 verify and make "archived" measurably faster than "wrong password". Both answer with the same generic 401. Guarded by `test/auth.test.js`, `test/guards.test.js`, `test/admin-panel.test.js`.
- Behind a reverse proxy set `TRUST_PROXY` (→ `config.trustProxy` → Fastify `trustProxy`) or per-IP rate limiting collapses to one shared bucket. Use the proxy address form (`TRUST_PROXY=127.0.0.1` for same-host nginx), not `true` — `true` trusts client-supplied `X-Forwarded-For` wholesale. Still deferred from the security review: @fastify/helmet, account-keyed login backoff.

## Catalogue (public)

- `GET /catalogue/products` (`src/routes/catalogue.js` + `src/catalogue/products.js`) — public product list, `show_on_website = true` only, paginated (`page`, `limit`; defaults 1/20, max 100). Response: `{ products: [...], meta: { total, page, limit, sort } }`.
- Filters are exact-match strings whitelisted in `FILTER_COLUMNS` (`application`, `composition`, `width`, `price_band`, `lead_time`, `product_type`, `collection`) plus `brand` (matches `brands.slug`). Filter *names* map to trusted columns; filter *values* always go through parameterized placeholders — never interpolate a value into SQL. Unknown query params are simply ignored (the whitelist controls what filters), not rejected.
- **Merchandising fields** (added so the storefront grid is a real shopping grid, not a spec table), all built by one `LEFT JOIN LATERAL` colourway rollup: `image_url` (first colourway image in name order, falling back to the product's `hi_res_asset_url`, else null), `in_stock` (`bool_or` over the colourways' `qty_available - qty_reserved > 0`; no colourways or no inventory rows → false), `colourway_count` (true count) and `colourways` (up to `CARD_SWATCH_LIMIT` = 6 `{ name, sku, hex_tones }` for the card swatch strip). The rollup is an aggregate subquery, so it always yields one row — `cw` is never null.
- **Search**: `q` is a single free-text term ILIKE-matched against product name, house name, composition, application, and (via EXISTS) every colourway name/SKU. `%`/`_`/`\` in the term are escaped and the SQL carries `ESCAPE '\'`, so searching `100%` finds a literal percent. A blank/whitespace term is ignored, not treated as "match nothing". `q` narrows the count query too, so `meta.total` is the search total.
- **Sort**: `sort` ∈ `name` (default) | `price_asc` | `price_desc` | `newest`, mapped through the trusted `SORT_ORDERS` table — never interpolate the raw value. Price sorts order on `DISPLAY_PRICE` (`CASE WHEN b.is_international THEN NULL ELSE p.retail_price_cents END`), **not** the raw column: ordering on a price the shopper is not allowed to see would leak it. Hidden/absent prices sort `NULLS LAST` in both directions.
- Pricing (FR-3), enforced in `toPublicProduct`: international brands (`is_international = true`) get `price_hidden: true` and **no** `retail_price_cents` field; domestic brands get `retail_price_cents` only when non-null, `price_hidden: false`.
- Fastify querystring validation with `additionalProperties: false` does NOT reject unknown params here (extra keys pass through), but `enum`/type constraints (`product_type`, `sort`) DO 400. Rely on the code whitelist for filter safety, not on schema strictness for unknown keys.
- `GET /catalogue/products/:slug` (`src/catalogue/product-detail.js`) — public product detail, `show_on_website = true` only (else 404). Response `{ product }`: list fields + `hi_res_asset_url` + `colourways: [{ name, sku, hex_tones, image_url, in_stock }]`. `in_stock = qty_available - qty_reserved > 0`; a colourway with **no** inventory row (LEFT JOIN → nulls) is out of stock. pg returns `numeric` columns as strings — coerce with `Number()` before arithmetic.
- **Trade pricing** (`trade_price_cents`, integer NZD cents on `products`): added by the `1784605289852_trade-price-cents` migration; precomputed at seed for **fabrics only** from the vendored `src/seed/data/pricing.js` `tradeUnit(design)` (`Math.round(unit * 100)`); finished goods stay null. **Both** the list and detail endpoints reveal it, and only to approved trade users (`effectiveRole(user) === 'trade'`) — never to anonymous/customer/backoffice. (The list used to omit it entirely; that made a signed-in trade shopper see "sign in for trade pricing" on every card in the grid.) `price_hidden` is independent: an international house hides its retail price from everyone, trade included, while still showing the trade figure.
- Optional-auth pattern for public routes that show extra fields to logged-in users: `app.guards.loadOptionalUser(request)` returns the user or null and never blocks (unlike `requireAuth`). Route derives `includeTrade` from it and passes it into the read model; the read model is the single gate that adds the field. Both catalogue routes use it.
- `GET /catalogue/brands` → `{ brands: [{ slug, name, country, currency, is_international, story, website_url }] }` (all brands, alpha). `GET /catalogue/brands/:slug` → `{ brand: { ...brand, collections: [{ slug, name }] } }`, 404 if unknown (`src/catalogue/brands.js`). `website_url` (migration `1785715200000`) is the house's own site, rendered by the storefront brand page as an outbound link; admin create/PATCH validate it via `websiteUrlFrom` — absolute http(s) only, else 422, so a `javascript:` URL can never reach a public href; explicit null clears it. Seed source is `src/seed/data/brand-websites.js` — **seed-owned, not a vendored snapshot** (a re-copy of `src/seed/data/` must not overwrite it), URLs verified against the live sites before entry — and the brand upsert applies it with `COALESCE(brands.website_url, EXCLUDED.website_url)`: it fills blanks only, a CRM-entered URL survives every reseed (guarded by `test/seed.test.js`).

### Two independent gates — trade PRICE vs trade VISIBILITY

- **`includeTrade` is who may see a price; `includeTradeOnly` is whose products exist at all.** They cover different sets of people and conflating them is the trap: `includeTrade` (FR-3, `trade_price_cents`) is **approved trade ONLY** — staff deliberately never receive it. `includeTradeOnly` (`src/catalogue/visibility.js`, `canSeeTradeCatalogue`) is approved trade **plus backoffice/director**, because the back office has to be able to check the real storefront against what it published. A pending trade application is `effectiveRole` `customer` for both, so an applicant sees exactly what a signed-out visitor sees. `viewerGates(user)` in `src/routes/catalogue.js` resolves the session once and derives both.
- **`brands.trade_only`** (migration `1786161600000_brand-trade-only`, `NOT NULL DEFAULT true`) is the flag. A signed-out visitor browses only houses with `trade_only = false`; the seed opens exactly one, `atelier-textiles-nz` (Atelier's own workroom), and closes all 40 represented maisons. **The default is closed on purpose** — a house created in the CRM mid-negotiation must fail to "not published yet", never to "accidentally published" — and `POST /admin/brands` defaults it to `true` for the same reason.
- **The seed writes it on INSERT only.** `trade_only` is absent from `upsertBrands`'s `ON CONFLICT DO UPDATE` set list (unlike `is_international`, which refreshes), so opening or closing a house in the CRM is operational data that survives every reseed — same posture as inventory and shipping rates, and for the same reason: a reseed silently pulling a maison off the public site would be invisible until someone noticed the grid had shrunk. The migration is what applied the initial values to already-seeded databases.
- **Where the predicate is applied**: the listing and both SKU-resolving transactional paths use it as a WHERE clause (`PUBLIC_BRAND_CONDITION`, `b.trade_only = false`) — a closed house's product must vanish, not read as brandless. **The detail endpoint deliberately does NOT**: it fetches the row, then answers **403** `{ error, message, trade_only: true }` carrying nothing about the product. 404 would be a lie (the URL is shareable and the design is real) and, worse, the storefront's SSR fetch carries no session cookie — so a trade customer's own product page would 404 in the HTML and only appear after the island rehydrated. 404 still means the slug genuinely does not exist.
- **The gate closes the transactional paths too, or it is cosmetic.** The cart and the order request take a bare SKU, so `validateCheckoutLines` and `resolveLine` both apply it; a non-entitled caller gets the **same 422 as an unknown SKU** (a refusal must not confirm what exists). Consequence to know: the guest order-request flow (FR-5/FR-6) now reaches the open houses only. The **Stripe webhook deliberately does NOT apply it** — it re-resolves the cart with its own query, and a session that has already been paid must always produce an order; re-gating there would drop a paid order on the floor if a house were closed between checkout and the callback.
- **Houses and collections stay public for everyone.** `/catalogue/brands`(`/:slug`) lists every maison — the directory is Atelier's marketing and closing it would gut `/brands` for signed-out visitors — and each brand now carries `trade_only` so the storefront can label it and offer the application. Collections are listed for everyone too; only `product_count` moves, counting what THIS viewer can reach (0 for a guest on a represented house) so a tile never promises twelve designs and opens on none.
- `meta.trade_gated` on the listing tells the storefront which of the two libraries it is looking at — without it, the public subset is presented as if it were the whole catalogue. Guarded by `test/trade-catalogue.test.js` (22 tests: the four viewers × listing / detail / brands / collections / order request / checkout / admin PATCH).
- **Every catalogue test fixture must set `trade_only = false`** or it models a house no anonymous request can see; the column defaults closed and 64 tests failed on the migration alone until the fixtures said so.

### Collections (brand → collection → product)

- The hierarchy is `brands 1—N collections 1—N products`, but a product's **brand is a direct FK** (`products.brand_id` NOT NULL), not inherited through the collection; `products.collection_id` is nullable (`ON DELETE SET NULL`). A product with no collection is normal, not broken — **the seed never assigns one**, so every seeded product starts uncollected and membership is staff-assigned in the CRM. `admin-products.js` `requireCollectionInBrand` 422s a collection belonging to another house.
- **A collection slug is unique per brand, never globally** (`collections_brand_id_slug_unique`), so every single-collection lookup is brand-scoped: `GET /catalogue/brands/:slug/collections/:collectionSlug` → `{ collection: { slug, name, product_count, brand } }`, 404 otherwise (`src/catalogue/collections.js`). The house param stays named `slug` because Fastify's router rejects two different parameter names in the same path position — renaming it would break `/catalogue/brands/:slug`.
- `GET /catalogue/collections?brand=` → `{ collections: [...] }` (brand name, then collection name). Unknown brand → **empty list, not 404** — same posture as a product filter that matches nothing. `product_count` counts only reachable products (visible, unarchived, unarchived house), so a non-zero count always yields a non-empty grid.
- Collections carry **tile editorial**: `description` + `image_url` (migration `1785801600000`), seeded from the vendored atelier.co.nz snapshot (`realCatalogue.collections` `description`/`src` — the first seed dropped these) and exposed on both public collection endpoints and the admin reads. `PATCH /admin/collections/:id` now takes any of `name`/`description`/`image_url` (`minProperties: 1`; name no longer required); `image_url` goes through the same http(s)-only `websiteUrlFrom` gate as the brand website (it lands in a public `<img src>`), 422 otherwise. Collection **display names drop the snapshot's redundant house prefix** (`collectionDisplayName`: "Pierre Frey | Cappuccino" → "Cappuccino"; a letterless remainder like "2024" keeps the full name) while the **slug still derives from the full snapshot title** — it is the `(brand_id, slug)` upsert key and changing it on a reseed would duplicate every already-seeded collection.
- **Neither collection route returns products.** The grid is `GET /catalogue/products?brand=&collection=`, so filtering, sorting, paging and the trade-price gate stay in one read model. `collection` alone (no `brand`) matches every house using that slug — pair the two.
- Both product read models expose `collection: { slug, name } | null` via a `LEFT JOIN collections col ON col.id = p.collection_id AND col.archived_at IS NULL`. **The archived check lives in the join condition, not the WHERE clause**: archiving a collection is a soft delete of the grouping only (see `setCollectionArchived`), so its products keep selling and simply read as uncollected — and the `collection` filter can never match an archived collection. The join is in the count query too, or `meta.total` would ignore the filter.
- Guarded by `test/catalogue-collections.test.js` (15 tests), whose fixture gives two houses the *same* collection slug — the regression that brand-scoping exists to prevent.

## Shipping

- `GET /shipping/quote?zone=&qty=` (`src/routes/shipping.js` + `src/shipping/rates.js`) — public flat-rate quote. `getShippingQuote` picks the highest tier whose `threshold_qty` floor is `<= qty` for the zone. Response `{ zone, qty, threshold_qty, rate_cents }`. Unknown zone (no rows) → 400 with a clear message; missing/invalid `zone`/`qty` → 400 by schema (Fastify coerces the querystring `qty` to a number). Boundary rule: at `qty == threshold` the higher tier applies (`<=`).
- `PUT /admin/shipping-rates` (backoffice) — body `{ rates: [{ zone, threshold_qty, rate_cents }] }`; `upsertShippingRates` upserts on `(zone, threshold_qty)` in one transaction (edit rate or add a tier without redeploy) and returns the full `{ rates }` list. Note: seed inserts rates `DO NOTHING`, so admin edits here are the mutation path and survive reseeds.

## Checkout (Stripe)

- `POST /checkout/session` (`src/routes/checkout.js` + `src/checkout/checkout.js`) — B2C card checkout for finished goods (FR-4). Body `{ lines: [{ sku, qty }], zone }`; **no prices accepted from the client** (`additionalProperties: false` on line items). `validateCheckoutLines` resolves each SKU server-side and rejects with **422**: fabric products (`product_type = 'fabric'`), goods with `retail_price_cents = null`, hidden/unknown SKUs, and insufficient stock (`qty_available - qty_reserved < qty`, pg-numeric strings coerced). Unknown shipping zone → **400**.
- Stripe line items use inline `price_data` (currency/`product_data.name`/`unit_amount` from the DB), never pre-created Price IDs. A shipping line item is appended from `getShippingQuote(zone, totalQty)`. The cart (`[{ sku, qty }]` only) + zone + shipping_cents go into `session.metadata` so the **US-011 webhook** rebuilds the order — this endpoint creates **no** order row. `client_reference_id`/`customer_email` are set when logged in (`loadOptionalUser` — guests allowed). Returns `{ url, session_id }`.
- **Delivery details are collected at Stripe**, not by the store: `shipping_address_collection: { allowed_countries: SHIPPING_COUNTRIES }` (`['NZ']` — the shipping-rate tiers only price the three NZ zones, so no other country may be offered), `phone_number_collection`, `billing_address_collection: 'auto'`. Deliberately **no `shipping_options`** — our own zone tiers price the freight as a line item, and Stripe adding its own would double-charge. The webhook persists what was collected (below).
- A **mixed-currency cart is rejected with 422** before any Stripe call: one session charges in one currency (and the shipping line is priced in it), so picking a winner would silently mis-charge. The insufficient-stock 422 names the SKU **and** how many remain, so the store can tell the shopper what to change.
- **Stripe is injected**, not imported globally: `buildApp({ ..., stripe, storeBaseUrl })`. `src/server.js` builds the real client from `STRIPE_SECRET_KEY` (optional env — checkout returns **503** when unset, so the rest of the API boots without it). Tests pass a stub whose `checkout.sessions.create` records params — no SDK/network. Secret comes from env only; `test/checkout.test.js` greps `src/` for an `sk_(live|test)_` literal and asserts none (the pattern is built from fragments so it never self-matches).
- `GET /checkout/session/:id` (public) — the store success page (US-019) verifies a completed session. `retrieveCheckoutSession({ stripe }, id)` calls `stripe.checkout.sessions.retrieve(id)` and returns only non-sensitive fields `{ order_number: 'WEB-<id>', paid, amount_total_cents, currency, email }` (no line items/prices). Unknown/failed retrieve → **404**; stripe unset → **503**. `order_number` is deterministic so the success page shows it without waiting for the async webhook to create the order row. Test stub adds a `retrieve` method alongside `create`.
- Errors are thrown as `Object.assign(new Error(msg), { statusCode })`; Fastify serializes `{ statusCode, error, message }`, so handlers stay thin.

## Webhooks (Stripe)

- `POST /webhooks/stripe` (`src/routes/webhooks.js` + `src/webhooks/stripe-webhook.js`) — records completed payments as paid orders (FR-4). Verifies the signature with `stripe.webhooks.constructEvent(rawBody, sig, STRIPE_WEBHOOK_SECRET)`; invalid signature → **400**. On `checkout.session.completed`: inserts an order (`kind='checkout'`, `status='paid'`) with lines and decrements `inventory.qty_available`. Other event types are recorded but create no order. Returns `{ received: true, duplicate }`.
- **Raw body**: signature verification needs the exact bytes, so the webhook plugin registers its own `addContentTypeParser('application/json', { parseAs: 'buffer' }, …)`. Content-type parsers are **encapsulated** — this only affects the webhook plugin; every other route keeps normal JSON parsing. `request.body` is a Buffer here.
- **Idempotency**: the `webhook_events` table (migration `1784606400000`, PK `event_id`) is the ledger. `processStripeEvent` opens one transaction, claims the event with `INSERT … ON CONFLICT (event_id) DO NOTHING`; `rowCount === 0` → replay → rollback and return `{ duplicate: true }` (creates nothing). Order creation + inventory decrement + ledger claim all commit together.
- **Money is re-resolved server-side**, never read from the payload: the cart (`[{ sku, qty }]`) lives in `session.metadata.cart`, zone in `metadata.zone`, shipping in `metadata.shipping_cents` (all stashed by US-010 checkout). Line prices come from a fresh DB lookup by SKU (`retail_price_cents`). `order_number = WEB-${session.id}` (stable per session). `user_id` from `client_reference_id` (int), else `guest_email` from `customer_details.email`/`customer_email`.
- **Delivery details are persisted** onto the order (`orders.shipping_address` jsonb + `orders.contact_phone`, migration `1785283200000_order-delivery-details`) by `deliveryDetails(session)`. Stripe moved the address to `session.collected_information.shipping_details` in newer API versions, so it reads **both** that and the legacy top-level `session.shipping_details` — an API-version bump must not silently start dropping addresses. Absent sub-fields are recorded as explicit nulls; a session with nothing collected stores null, not `{}`. jsonb because it is a verbatim purchase-time snapshot, never something we query into. Without this the back office had a paid order and no address to ship it to.
- **Config**: `STRIPE_WEBHOOK_SECRET` (optional env → `config.stripeWebhookSecret`) injected as `buildApp({ ..., stripeWebhookSecret })`. Webhook returns **503** when stripe or the secret is unset. Tests inject a stub whose `webhooks.constructEvent` re-parses the raw body into an event when the signature header matches a sentinel, else throws — no SDK/network.

## Order requests (fabric / backorder)

- `POST /orders/request` (`src/routes/orders.js` + `src/orders/order-request.js`) — a customer or guest asks the back office to cut and invoice fabric (FR-5/FR-6). Body `{ lines: [{ sku, qty_metres, cut_requirements? }], contact?: { name, email, phone }, accepted_lead_time? }`. Public (guests allowed via `loadOptionalUser`). Returns **201** `{ order: { id, order_number, kind, status, lines } }`.
- **Two-layer validation**: the body schema is structural only (empty `lines`/missing `sku` → **400**). `qty_metres > 0` and email validity are checked in the handler via `validateOrderRequestInput`, which returns **422** `{ message, errors: [{ field, message }] }` with field paths like `lines[0].qty_metres` / `contact.email`. Guests must supply `contact.email`; logged-in users fall back to their session email (order gets `user_id`, `guest_email` stays null).
- **Availability decides the kind**: for every line, `available = qty_available - qty_reserved` (pg-numeric strings coerced). All lines in stock → `kind='order_request'`, `order_number` `REQ-…`. Any line short → requires `accepted_lead_time=true` (else **422** "accept the quoted lead time"); then `kind='backorder_request'`, `order_number` `BO-…`. Both create `status='requested'`.
- **Reservation**: in one transaction each line increments `inventory.qty_reserved` by `qty_metres` (backorder lines reserve too — committed demand). The colourway row is locked `FOR UPDATE OF c` — the inventory row is the nullable side of the LEFT JOIN and **can't** be locked directly ("FOR UPDATE cannot be applied to the nullable side of an outer join"), so locking the colourway serialises concurrent same-SKU requests. Unknown/hidden SKU → **422**.
- Pricing is deliberately **0** on request lines (`unit_price_cents = 0`); the invoice amount is set manually by the back office at confirmation (US-014), not by the client. `contact` name/phone are stored in `orders.notes`.

## Order history + guest lookup

- `GET /orders/mine` (`src/routes/orders.js` + `src/orders/order-history.js`) — auth (`requireAuth`), returns `{ orders: [...] }` newest first, each with `lines`. Ownership is enforced in SQL (`WHERE user_id = request.user.id`), never in the handler, so one user can never read another's orders.
- `GET /orders/lookup?order_number=&email=` — public guest lookup. Returns `{ order }` only when order number AND email match; email matches either `guest_email` or the placing user's `users.email` (case-insensitive `lower()`). No match → **404** (never a 400/enumeration signal). Both query params required by schema (missing → 400).
- Order shape (`toOrder`): `id, order_number, kind, status, subtotal_cents, shipping_cents, total_cents, shipping_zone, xero_invoice_ref, shipping_address, created_at, lines`. Lines carry `sku, product_name, qty, unit_price_cents, cut_requirements`. Internal columns (`stripe_session_id`, `guest_email`) are not exposed. Lines are batch-loaded for all order ids in one query (`ol.order_id = ANY($1::int[])`) then grouped — no N+1.

## Back-office order management

- `src/routes/admin-orders.js` + `src/orders/admin-orders.js` (US-014, FR-7). All routes `requireRole('backoffice')` (director inherits). Handlers stay thin; the state machine + reservation logic live in the module.
- **Lifecycle** (order-request / backorder kinds): `requested --confirm--> confirmed --mark-paid--> paid --ship--> shipped`; `requested|confirmed --decline--> declined`. Any other transition throws **409** via `requireStatus`. `confirm` stores `xero_invoice_ref` from the body (manual Xero, no API call).
- **Reservation model**: only `RESERVING_KINDS` (`order_request`, `backorder_request`) touch inventory here; `checkout` orders arrived paid + already-decremented and hold no reservation (`reserves(kind)` guards every inventory write). `reservation_state` per order = `held` (requested/confirmed/paid) → `converted` (shipped: `qty_reserved -=`, `qty_available -=`) or `released` (declined: `qty_reserved -=`). `ship`/`decline` update inventory with a single `UPDATE inventory i ... FROM order_lines ol WHERE ol.order_id=$1 AND i.colourway_id=ol.colourway_id` (no per-line loop). A colourway with no inventory row (short backorder) reserved nothing, so the join simply matches nothing.
- **Endpoints**: `GET /admin/orders?status=` (optional enum filter → 400 on unknown), `GET /admin/orders/:id` (404), `PATCH /admin/orders/:id` (body `{ lines: [{ id, qty }] }` — edits qtys, adjusts held reservation by delta; **only** requested/confirmed, else 409), `POST .../confirm|mark-paid|ship|decline`. `:id` is an integer param (Fastify coerces; non-numeric → 400).
- Every mutation runs through `withOrderTxn(pool, id, fn)`: `BEGIN`, `SELECT ... FOR UPDATE` the order (404 if missing), run `fn`, `COMMIT`, then return the fresh order via `getAdminOrder`. Admin order shape exposes internal fields customers don't see (`guest_email`, `notes`, `shipping_address`, `contact_phone`, per-line `colourway_id` + `inventory` snapshot + `reserved_qty`).
- **Test gotcha**: register shares a rate-limit bucket (10 / 15 min / IP). Register staff/customer **once** in `beforeAll` and keep them; per-test `beforeEach` cleans only orders + brand fixtures, never users (re-registering each test 429s and yields no cookie). pg `numeric` qty comes back like `'10.00'` — compare with `Number()`, not string equality.

## Back-office catalogue admin

- `src/routes/admin-catalogue.js` + `src/catalogue/admin-brands.js` (brands + collections) + `src/catalogue/admin-products.js` (products + colourways). All routes `requireRole('backoffice')`. **The client is the CRM, not the storefront** — the storefront's admin islands were deleted in its `6d1e1df` ("move back-office admin out of the storefront") and the screens now live in `atelier-crm` (`src/screens/Admin*.jsx`), calling these endpoints cross-origin from :5273. Nothing to do with the AdminJS panel at `/panel`, which stays as the raw fallback.
- **Endpoints**: `GET|POST /admin/brands`, `PATCH /admin/brands/:id`; `GET|POST /admin/collections` (`?brand_id=` filter, `brand_id` in the create body), `PATCH /admin/collections/:id` (name only); `GET|POST /admin/products` (`?brand_id=`), `GET|PATCH /admin/products/:id`; `POST /admin/products/:id/colourways`, `PATCH /admin/colourways/:id`. Admin reads are separate from the public catalogue ones because they include `id` and unhidden-only filtering does not apply (staff see `show_on_website = false` rows).
- **Slugs are server-generated on create and immutable after** — they are public storefront URLs and the EmDash brand-page match key, so a rename must not break links. `slugFrom` (exported from `admin-brands.js`) wraps `src/seed/slugify.js`: whitespace-only input makes slugify throw and punctuation-only returns `''`; both become **422**, never a 500 or an empty slug. Product slug follows the seed convention in `src/seed/catalogue-data.js` — fabric = `slugify(\`${brand.name} ${name}\`)` using the brand **name** (not its slug), finished good = `slugify(name)`.
- **`product_type` is immutable too** (the colourway's inventory `unit` was derived from it), and creates take no inline colourways — add them one at a time via the nested route.
- **`trade_only` is editable per house** (create + PATCH), because whether a maison appears on the public storefront is a commercial decision the office makes, not a property of the vendored catalogue. Create defaults it to `true`. See the visibility gate under Catalogue (public).
- **SKUs are typed by staff, not generated.** The CRM's Brand-Product-Colour generator lives only in the demo app and was deliberately not ported; the API just enforces uniqueness. `sku` *is* editable via PATCH (typo fixes are safe — `order_lines` reference `colourway_id`, never the sku).
- **Duplicates are detected by the database, never pre-checked** (a pre-check races and would still need the handler): `rethrowConflict` maps pg `23505` to a **409** keyed on `error.constraint` (`brands_slug_key`, `collections_brand_id_slug_unique`, `products_slug_key`, `colourways_sku_key`; unknown constraint degrades the message, never the status).
- **Colourway create is the one transaction**: BEGIN → `SELECT product_type` (404 if the product is gone) → INSERT colourway → `INSERT INTO inventory (…) VALUES ($1, 0, 0, $2) ON CONFLICT (colourway_id) DO NOTHING` → COMMIT, unit from `UNIT_BY_PRODUCT_TYPE` (`fabric → metres`, `finished_good → units`). A duplicate SKU rolls the whole thing back, so a failed create leaves no orphan colourway. `hex_tones` must be `JSON.stringify`'d (same trap as the seed).
- `buildUpdate(input, columns)` builds every PATCH's SET clause from a **frozen in-code column whitelist** — column names are never user input, values are always `$n` placeholders. `Object.hasOwn` keeps an explicit `null` (clears `collection_id`) distinct from an absent key (leaves it alone).
- Status codes: 400 schema (incl. empty PATCH via `minProperties: 1`), 404 unknown `:id`, 409 duplicates, 422 business rules (unknown `brand_id`/`collection_id`, a collection belonging to another brand, unsluggable name).
- **Gotcha — `additionalProperties: false` does not reject unknown body keys.** Fastify's bundled Ajv runs `removeAdditional: true`, so extra keys are silently *stripped*, not 400'd (same family as the querystring note under Catalogue). Immutability still holds where it counts: on PATCH the stripped body becomes `{}` and `minProperties` produces the 400, and on create a client-supplied `slug` is discarded so the server's wins. Do not rely on schema strictness to reject a field — leave it out of the whitelist.
- Guarded by `test/admin-catalogue.test.js` (63 tests). Same rate-limit gotcha as admin orders: register the two users **once** in `beforeAll`; fixtures are namespaced `admin-cat-test-*` so cleanup deletes brands by slug prefix and cascades.

### Panel security invariants (each one fixed a confirmed exploit — do not regress)

- **Guard matches paths exactly, never by regex/substring.** `registerSessionGuard` compares `url.split('?')[0]` against an exact set of public asset paths. It previously used upstream's `request.url.match(assetPath)` — an *unanchored regex over path+query*, so `?x=/frontend/assets/icomoon.css` on any panel URL skipped auth entirely (unauthenticated read of every user's `password_hash`, and an unauthenticated `role=director` self-promotion). The same bug is still live upstream in `@adminjs/fastify`'s `withProtectedRoutesHandler` — do not copy it back.
- **Session id is regenerated on login.** `await request.session.regenerate()` runs before `session.set('adminUser', …)`, so a pre-auth session id can never become an authenticated one. Read `redirectTo` *before* regenerating — regenerate swaps in a fresh session and drops it. (Hence `redirectTo` is stored via `session.set`, not as a loose property.)
- **`password_hash` is stripped at the query layer** (`src/admin/redacted-resource.js`), not merely `isVisible: false`. AdminJS's `isVisible` is a UI flag only — `BaseRecord.toJSON` serialises `params` verbatim, so a "hidden" column still ships in every list/show JSON payload. `RedactedSqlResource` narrows the SELECT and strips hidden columns from create/update. `count()` is deliberately left alone (narrowing its select would produce an invalid non-grouped aggregate).
- **CORS never covers the panel.** `@fastify/cors` is a fastify-plugin, so it **hoists to the root instance** — registering it in a child scope does *not* keep it off the panel (verified). app.js therefore uses a `delegator` that returns `{ origin: false }` for `isAdminPanelPath(request.url)`. Without this, any script on the storefront origin could read and drive the panel with a logged-in staff cookie. The delegator also covers the CORS-registered wildcard `OPTIONS *` route, which a route-membership check could not.
- **Panel session cookie uses a separate signing key** (`src/admin/session-secret.js`): HMAC-derived from `COOKIE_SECRET`, or `ADMIN_SESSION_SECRET` when set. `@fastify/session` and `@fastify/cookie` both default to HMAC-SHA256, so sharing a key means a value signed for one verifies under the other.
- **Origin guard stands in for CSRF tokens.** AdminJS's React frontend can't carry a token we mint, so `registerOriginGuard` (onRequest) rejects state-changing methods — and `GET /panel/logout` — when `Sec-Fetch-Site` is anything but `same-origin`/`none`, or `Origin` doesn't match `Host`. `same-site` is treated as cross-origin (a sibling subdomain is a different origin). Host comparison **normalises both sides under the origin's scheme** so an explicit default port still matches, and compares host only, not scheme — behind a TLS-terminating proxy without `TRUST_PROXY` the request looks like http while the browser reports https, and rejecting that would block every write. A missing `Origin` is allowed (same-origin navigations and non-browser clients omit it; browsers always send it on cross-origin writes). `test/admin-panel.test.js` guards both directions — the foreign origin is rejected *and* a same-origin write still succeeds.
- Known-vulnerable transitive deps ship with the adminjs frontend bundle (`@tiptap/extension-link` XSS, `react-router`, `i18next-http-backend`). No `richtext` property is configured, so the tiptap surface isn't reachable, and `npm audit fix --force` only offers a breaking downgrade to `adminjs@6` — track upstream for a patched `adminjs@7.x` instead.

## Foundations

The shared delete/archive lifecycle module, `src/lifecycle/`. Every hard delete in this API goes through it.

- **The schema will not stop a destructive delete.** Of the 13 FK edges between the live (non-`legacy_*`) tables exactly ONE is RESTRICT (`order_lines_colourway_id_fkey`); eight CASCADE and four SET NULL. `DELETE FROM brands WHERE id = <a stocked house>` raises nothing and destroys its collections, products, colourways and inventory while returning success — and SET NULL is worse because it is invisible: deleting a user SET NULLs their whole order history into anonymous guest orders with no `guest_email`, silently. So the module **probes first**; the pg 23503 catch is a backstop for the grandchild race and for a future RESTRICT FK whose registry entry someone forgot, never the primary defence.
- **`deleteOrExplain(pool, entityName, id, ctx)` returns its refusal — it never throws it.** Fastify's error serializer emits exactly `{ statusCode, error, message }` and drops custom properties, so a thrown error cannot carry `blockers`, which is the entire point of the 409. Result is `{ deleted: true, entity, id }` or `{ deleted: false, status: 404|403|409, error, message, blockers: [{ relation, label, count, capped }], archivable }`. `replyDelete(reply, result)` sends it; success is **200 `{ deleted: { entity, id } }`**, not 204, because every route here returns a JSON envelope and the CRM's `useMutation` names the result in its toast.
- **Transaction order is `BEGIN` → lock → guard → probe → `DELETE` → `COMMIT`**, and the lock must be `SELECT … FOR UPDATE`, **never `FOR NO KEY UPDATE`**. Postgres takes `FOR KEY SHARE` on a referenced row whenever a transaction inserts a row pointing at it; `FOR KEY SHARE` conflicts with `FOR UPDATE` and with nothing weaker, so the weaker mode would leave the check-then-delete window wide open. Probes and the DELETE share the transaction. No SERIALIZABLE — it would add 40001 retries nothing here handles. Guarded by a stub-pool test asserting the statement order and the lock text.
- **Probes count archived rows.** An archived product still blocks its house: archiving is not deletion, and skipping archived rows would let a delete quietly destroy the archive. All of an entity's probes run as ONE `UNION ALL` round trip, each `LIMIT 101`; past 100 hits a blocker reports `{ count: 100, capped: true }` and the message renders "100+ products" rather than counting 19,000 rows to answer a question whose answer is already "no".
- **Registry keys are code literals used at route registration — never a path parameter.** `requireEntity` throws a plain `Error` (a 500) for an unknown name rather than answering 404, so a caller that ever wired `:entity` from the URL fails loudly instead of letting a client probe which names exist. `assertEntity` runs at import time over every entry (probe body matches `/^SELECT 1 FROM [a-z_ ]/` with exactly one `$1`, relation/table/column match `/^[a-z][a-z0-9_]*$/`, relations unique within an entity), so a malformed probe stops the server booting instead of reaching SQL.
- **`archivable` is a property of the entity, not the row.** `inventory` and `shipping_rates` have no `archived_at` column, so their refusals must not offer "archive instead". Check the column exists before adding an entry with `archivable: true`.
- **`inventory`'s `idColumn` is `colourway_id`, not `id`.** The table has both (`id` is the PK, `colourway_id` is UNIQUE) and every existing caller — `/admin/inventory/:colourwayId`, the order state machine — addresses stock by colourway. An entry keyed on `id` would look right and address the wrong row.
- Guards are for rules that are not "something still points at this", and return `{ status, message }` or null: reserved stock blocks its `inventory` row (409); the last `shipping_rates` tier for a zone is 409, because a zone with no tiers makes `getShippingQuote` answer 400 and stops checkout there; a self-delete is **403** from `ctx.user.id`, not 409 — nothing references the row, the caller simply may not.
- Adding an entity is one registry entry; the tables for suppliers and samples do not exist yet, so those entries belong to the workstreams that create them (the safety test asserts every declared table exists in `information_schema.columns`).
- **`setArchived(db, entityName, id, archived, options)` (`src/lifecycle/archive.js`) is the single soft-archive write**, and takes `db` — a pool *or* an open client — so a caller can join it to its own transaction. `setOrderArchived` does exactly that: its terminal-state guard and the write must be one transaction or a concurrent transition slips between them. All eight helpers (`setBrandArchived`, `setCollectionArchived`, `setProductArchived`, `setColourwayArchived`, `setPriceListItemArchived`, `setOrderArchived`, `setUserArchived`, `setEnquiryArchived`) delegate to it and keep their own wrapper, because three different return conventions are in play (throw 404 / return null / re-fetch through a joined read model) and each one's existing tests assert its shape. What was actually duplicated is four lines: the `now()`/`NULL` fragment, the WHERE on the id column, the RETURNING projection and "no row means unknown id". `extraSets`/`alias`/`from`/`filter`/`returning` cover the rest and are frozen code literals, same posture as `buildUpdate`'s column whitelists.
- **`order` is in the registry `archivable: true, deletable: false`.** It has to be there for `setArchived` to reach it, and it must never be hard-deleted: CASCADE would take its lines, the delete would not release `qty_reserved` (permanently corrupting stock), and the row carries `xero_invoice_ref` and `stripe_session_id`. `deleteOrExplain` resolves through `requireDeletableEntity` and throws for it. **The normal protection is absence** — `requireEntity` throws on an unknown name, so `order_lines`, `webhook_events`, trade applications, trade accounts and every `legacy_*` table need no entry at all. Only reach for `deletable: false` when an entity must be in the registry for another reason.
- Every column constant used as a RETURNING projection (`BRAND_COLUMNS`, `ROW_COLUMNS`, `USER_READ_COLUMNS`, `ENQUIRY_COLUMNS`) is unqualified, so it is only valid while the statement has no alias — the collection wrapper passes a fully qualified projection because its `FROM brands b` join forces one.
- **Fixture cleanup order matters**: delete `orders` before `brands`. `order_lines.colourway_id` is the one RESTRICT edge, so a brand cascade cannot get past it and the cleanup itself 23503s.
- Guarded by `test/lifecycle-delete.test.js` (23 tests): real-database behaviour plus a stub `pool` (`{ connect: async () => client }` logging SQL text) for the statement order, the lock mode and the 23503 branch, whose real-world trigger is a race. `test/lifecycle-archive.test.js` (7) covers `setArchived`'s own contract. `test/lifecycle-registry.test.js` (79) covers the registry: probe shape, `assertEntity` actually rejecting 14 malformed synthetic entries, agreement with `information_schema` (including `archivable` in **both** directions against the `archived_at` column), and a source scan asserting every `deleteOrExplain`/`setArchived` call outside `src/lifecycle/` passes a **single-quoted literal**.
### CI

- `.github/workflows/ci.yml` runs `npm run lint` then `npm test` on every pull request into `august-6th-updates`, with `permissions: contents: read` so the job token cannot push, tag or write to `main`. **No typecheck step — there is no TypeScript in this repo**; a template that adds one is wrong.
- **The job needs a real Postgres and two env vars.** There are no database mocks here: every suite runs the migrations through node-pg-migrate against a live server, so the workflow declares a `postgres:14` service (pinned to match local Homebrew — a newer server would let a query through CI that fails in production) with a `pg_isready` healthcheck, or the first migration races startup and the connection-refused reads as a code fault. `DATABASE_URL` and a throwaway 32-character `COOKIE_SECRET` are set in `env:`, because `loadConfig` throws without either and nothing in the suite can build an app.
- **Node 22, not 20**: node-pg-migrate `require()`s the ESM migration files, which is only unflagged from 22.12 (and 20.19). That is the same `ExperimentalWarning` the local test run prints.
- `npm ci` cannot be rehearsed from a worktree on the dev machine — every worktree's `node_modules` is a symlink to the main checkout, so running it would rebuild the shared tree and break every other loop. The first PR run is what proves that step.

- **The registry is not an authorisation boundary.** `requireEntity` throwing on an unknown name proves nothing: `'brand'` and `'user'` are both known, so an entity name derived from a path parameter would still let a client pick which table gets written to or deleted from. The scan demands a literal for that reason, and it carries its own "did I find any call sites at all" assertion — a regex that silently matches nothing passes every per-site check vacuously.

## Pricing template

- **v2 is a strict superset of the 14 v1 columns**, in the same order, with `Supplier`, `Brand`, `Pattern Match` and `Duty Percent` appended. That is what lets one template be universal without breaking a single existing drop. Migration `1786334400000_price-list-template-v2.js` adds the storage: `brand_name text`, `pattern_match text`, `duty_percent numeric(6,3)`, `template_version text NOT NULL DEFAULT 'v1'`. (`Supplier` already had a column — v2 only changes where its value comes from.)
- **`brand_name` is TEXT and deliberately NOT a foreign key to `brands`.** Supplier spelling does not reliably match the 41 houses ("Colefax & Fowler" vs "Colefax and Fowler"), and an FK would fail a whole 2,000-row import over one naming difference. Do not "fix" it into a reference.
- **`duty_percent` stays NULL until a real file carries a real number.** The broker's duty table (A10) is still owed; the CRM's `/import` wizard applies its 7% placeholder downstream and that placeholder must never be baked into this ledger. It carries no range CHECK on purpose — nobody has stated the legitimate range, and a guessed CHECK is exactly the mistake the old freight-class set was.
- **`duty_class` and `freight_class` are a single uppercase letter (`~ '^[A-Z]$'`), still stored raw and uninterpreted.** The original sets (`'A'`–`'E'` for freight, nothing for duty) encoded a guess about a broker table nobody has, so the first `F` from a supplier would have rejected the client's own file as if it were a bug in ours. A Postgres CHECK passes on NULL, so widening needed no backfill across the 19.5k rows. `src/seed/price-lists.js`'s `FREIGHT_CLASSES`/`DUTY_CLASSES` are the narrower application-layer gate and are widened separately.
- **Only `freight_class` is a widen. `duty_class` is a NEW constraint and is therefore `NOT VALID`.** Every existing `freight_class` already satisfied `IN ('A'..'E')`, a subset of `^[A-Z]$`, so re-adding that one validates the table and cannot fail. `duty_class` had **no** CHECK from the day the table was created and `POST`/`PATCH /admin/price-list-items` accepted 200 characters of free text into it, which the CRM still renders as a plain input — so a database with real back-office use can hold a staff-typed note like "Pending broker confirmation", and a validating constraint aborts the entire migration on it (`23514 … is violated by some row`, reproduced on a scratch database). `NOT VALID` enforces the shape on every INSERT and UPDATE from here on and leaves existing rows alone; a fresh database is unaffected either way. Validating it is a second migration, after somebody audits the column — the letters are stored raw and uninterpreted, so nothing reads a legacy value in the meantime.
- **`template_version` records which header row a row came in through, and has no CHECK.** The accepted set lives in the code registry, not the schema — pinning it here would make every new template a migration. It is the converter's verdict written down, never a cell read from the file: **the header row IS the version** (a version cell can be misdeclared by deleting a column, whereas a header mismatch fails loudly).
- **A missing key in an `unnest` batch binds an explicit NULL, which DEFEATS a column DEFAULT.** So any importer path that writes `template_version` must `COALESCE` it, or a v1 row violates the NOT NULL it was supposed to default into.
- **`src/seed/data/price-lists.json` is regenerated in its own commit, converter unchanged.** The committed 8 MB file is byte-pinned; a converter change and a data refresh in one commit make the diff unreviewable — a reviewer facing 19.5k rewritten lines cannot tell a rate refresh from a mapper bug. `test/price-lists.test.js`'s regeneration tripwire is what enforces it: the committed file's FIRST record must carry none of the four v2 keys and must keep `mapV1`'s exact key order, so a v2 mapper that wrote `brand_name: null` onto v1 rows (or reordered a key) and regenerated the file fails immediately rather than at review. The first record stays a v1 one — it sorts first on `(supplier, category, code)` — so a genuine v2 drop landing later does not falsify it.
- Widening a class check: node-pg-migrate names an inline column `check:` constraint `<table>_<column>_check`, so `dropConstraint` then `addConstraint` under the **same** name.
- **The accepted layouts live in `scripts/lib/price-template.js`, not in the converter.** `TEMPLATES` is a frozen array of `{ version, header, map }`; `matchTemplate(headerRow)` returns the first entry matching **exactly on length and labels** (labels lowercased and whitespace-collapsed first), else null. `scripts/convert-price-lists.js` keeps only the file walk, the supplier name (`SUPPLIER_OVERRIDES`, `FILENAME_PATTERN`), the dedupe and the write. Adding v3 is one more entry, not a rewrite.
- **Matching is exact on length because a newer template starts with an older one's columns.** The old check sliced the header to 14 cells before comparing, so any longer header matched v1 by its first 14 — which would silently import a v2 file as v1 and drop its new columns. A header that matches no entry produces the same loud `file:line: unexpected header [...]` error as before, now suffixed `; accepted: <version> [...]` for every registered template, and the converter writes nothing.
- **`normaliseHeader` drops trailing EMPTY header cells before matching.** A CSV header line ending in a comma yields a blank 15th field and Excel emits blank cells too; counting one would fail a real drop over a stray comma. A blank cell declares no column so it cannot disambiguate two templates — a *named* extra column still changes the length and still fails.
- **`mapV1` is the converter's original `normaliseRow` MOVED, not rewritten** — same emitted key order, same `cleanMeasure`/`round4`/`generalFormat` calls, same comments. The 19.5k committed rows were produced by it, so any edit to what it emits is an 8 MB diff. Its private helpers (`parseDate`/`parseInteger`/`isoDate`/`cleanMeasure`) and the item-type, pack, currency, freight and duty vocabularies moved with it.
- **`mapV2` delegates the shared fourteen columns to `mapV1` and appends its own keys after them.** `mapV1` bounds its own read to `V1_HEADER.length`, so it maps a v2 row unchanged; overriding one input is `mapV1(row, { ...context, supplier })`. Re-listing the shared columns in a second mapper is how the byte-pin would rot.
- **The Supplier CELL wins over the filename, which is now only a fallback.** The filename was the most fragile input in the pipeline — a rename silently renamed a supplier, and one file could only ever hold one. `parseFilename` therefore returns `{ supplier: null }` instead of throwing, and the converter fails a file loudly only when the template has no Supplier column of its own (`template.header.includes('supplier')` — no per-template flag needed). A v2 row with neither is a row-level `file:line: empty supplier and none in the filename`.
- **v2-only keys are OMITTED on v1 rows, never written as null**, and the reason is commented at `mapV1`'s return: all 19.5k committed records were written without them, so adding `brand_name: null` to each is a total 8 MB diff for no information. Absent key and explicit null are the same to the importer — except `template_version`, whose `NOT NULL DEFAULT` a bound NULL defeats, hence the COALESCE there. Do not "tidy" them into explicit nulls.
- **`duty_percent` is rounded to 3dp, the scale of `numeric(6,3)`, so the JSON says exactly what the database will hold.** A non-numeric cell fails the row loudly; nothing else is checked — no legitimate range has been stated, and guessing one is the mistake the old freight-class set already was. Consequence to know: a value ≥ 1000 passes the converter and overflows at import.
- **Anything that compares two converter output rows must compare key COUNTS too.** `sameExceptSource` iterated only the first row's keys, so a v2 row would have been dropped as an "exact duplicate" of a thinner v1 row carrying the same `(supplier, category, code)`. A real clash must surface as a conflict, not a silent keep-first.
- **The importer's COALESCE lives in the SELECT, and that is why the unnest rowset is named.** `src/seed/price-lists.js` builds `INSERT … SELECT COALESCE(b."template_version", 'v1'), b."…" FROM unnest($1::text[], …) AS b("template_version", "…")`. `SELECT *` cannot wrap one column, and the alias list is generated from the same `COLUMNS` array as the INSERT list so the two can never drift out of order. `duty_percent` joins `wholesale_rate` as `numeric` in `COLUMN_TYPES`; everything else is `text` or `date`.
- **The importer validates the v2 fields by TYPE and says nothing about range.** `brand_name`, `pattern_match` and `template_version` go through `optionalText` (absent or null is normal — a v1 row omits them — but a present value must be a non-empty string, since the converter turns a blank cell into null and never `''`). `duty_percent` only has to be a finite number, so a value ≥ 1000 passes here and overflows `numeric(6,3)` at the INSERT: loud, and deliberate until the broker's table arrives.
- **`template_version` is deliberately not enum-checked in the importer either.** The accepted set is the converter's registry in `scripts/lib/price-template.js`; an older API importing a newer converter's file must still store the row rather than reject a template it has not heard of. The schema has no CHECK for the same reason. (An earlier note here claimed `src/seed/` *cannot* import from `scripts/`. It can — same package, plain relative specifier, no bundler and no `files` field — and since the vocabulary module below, it does. `template_version` is still not enum-checked, for the reason above rather than a mechanical one.)
- **A later v1 file for a key already imported from a v2 one CLEARS the v2 fields** and sets `template_version` back to `v1`, because the upsert still sets every non-key column to `EXCLUDED`. That is this table's freshest-wins contract applied uniformly — the upsert key is unchanged at `(supplier, category, code)` — not an oversight. Giving just these four columns a quieter `COALESCE(EXCLUDED.x, price_list_items.x)` rule is a product decision, not a tidy-up.
- **The dedupe key inside `validatePriceListItems` is joined with literal NUL bytes**, which most editors and file readers render as spaces. An exact-string edit anchored on that line will fail to match; anchor on a neighbouring line. `sed -n '70,80p' src/seed/price-lists.js | cat -et` shows them as `^@`.
- **The pipeline's vocabularies live once, in `scripts/lib/price-template.js`, and every layer imports them** — the converter, `src/seed/price-lists.js` and `src/routes/admin-price-lists.js` (whose `CATEGORY_ENUM`/`UNIT_ENUM`/`CURRENCY_ENUM` are now spreads of the shared sets). They were hand-copied into three files and had drifted: all three still refused a freight class the column CHECK had been widened to accept. `src/` importing from `scripts/` is deliberate and works — same package, relative specifier, no bundler; the only cost is that `xlsx.js`/`zip.js`/`xml.js` load with it, and they are pure function modules.
- **STORED set versus INPUT map is the distinction that keeps the byte-pin safe.** `CATEGORIES`/`UNITS`/`CURRENCIES` are what the column CHECKs accept; `CATEGORY_BY_ITEM_TYPE`/`UNIT_BY_PACK`/`CURRENCY_MAP` are what a template CELL may say. Adding an input alias can only turn a cell that used to fail the whole run into one that maps — it can never change what an already-mapped cell produces — so `price-lists.json` is safe from it by construction. `assertStorable(map, stored, what)` runs at module load and throws if any alias maps outside the stored set, which is what stops an alias quietly widening storage; `scripts/convert-price-lists.js` wraps its own `CATEGORY_BY_FILE_TOKEN` in it for the same reason.
- **Adding a currency is four edits in lockstep**, each failing at a different layer if missed: the DB CHECK on `price_list_items.currency` (a migration), `CURRENCIES`, `CURRENCY_MAP`, and `CURRENCY_ENUM` in `src/routes/admin-price-lists.js` — which now derives from `CURRENCIES`, so the last two are one edit. ISO codes (`eur`/`usd`/`gbp`) are accepted as INPUT ALIASES for the long names only; the stored set is **not** widened by them. `p/hide` and `p/panel` were added to `UNIT_BY_PACK` the same way — both units have been in the CHECK since the table was created (platform decision 7) with no template rows yet.
- **`duty_class` and `freight_class` are one exported predicate now, not three copied sets.** `CLASS_LETTER = /^[A-Z]$/` + `isClassLetter` are used by `mapV1`, by `optionalClassLetter` in the importer's validator, and by the admin write schema (`pattern: CLASS_LETTER.source` — a JSON-Schema `pattern` only applies to strings, so an explicit null still clears the column). `duty_class` was free text up to 200 characters at the admin boundary and is now one uppercase letter, which turns what would have been an opaque 23514 into a 400. The letters are still stored raw and uninterpreted.
- **A converter that fails loudly and writes nothing is its own corpus proof.** The committed `price-lists.json` exists, therefore no source row ever carried a value the old vocabulary lacked — so widening a vocabulary cannot change a committed byte. Verified against the committed 19,514 records anyway: units are `metre,piece,roll,yard` (no hide or panel row exists), currencies `EUR,GBP,USD`, freight classes `A`–`E`, duty classes `A` or null.
- **The corpus is not in a worktree.** `incoming/` is gitignored, so `incoming/pricing-templates/` exists only in the main checkout and `npm run convert:pricing` cannot run from a worktree at all. Verify a converter change by running it against a hand-made fixture into a scratch path — `node scripts/convert-price-lists.js <in-dir> <out.json>`, filename matching `^(.+?)(?:\s+(FABRIC|WPPR|TRIMMING))?\s+PL\b` — and compare a record against a line of the committed JSON. The `convert:pricing && git diff --exit-code` gate is a main-checkout step before merge.
- **v1 output is byte-pinned at the unit level, in `test/price-template.test.js`'s `byte pin` block: `dumps(mapV1(row))` against a hardcoded string.** Every other assertion in that file compares OBJECTS, and an object comparison is blind to exactly the two drifts that cost 8 MB — a reordered key and a float printed as `115` instead of `115.0`. The pinned string is line 2 of `src/seed/data/price-lists.json` verbatim (the converter writes one record per line), reproduced from the cells that made it, so the pin is the committed bytes rather than a description of them. Do not reformat those strings.
- **The Python-faithful float formatting stays, and is not a portability wart to clean up.** All 19.5k committed records were produced by `json.dumps` over Python floats, so `repr(float)`/`format(x, 'g')`/`", "` separators are what the file IS; swapping in `JSON.stringify` rewrites every line. `scripts/lib/python-format.js` is guarded by `test/converters.test.js` and now pinned end-to-end through `mapV1`.
- **v2 rows carry no such history — their bytes are pinned to this Node implementation instead.** No Python ever wrote one, so the v2 pin fixes the shape going forward (v1's keys first and unchanged, the four appended after them, non-ASCII written raw under `ensure_ascii=False`) rather than reproducing anything.

## Colour files

- The supplier colour spreadsheets in `incoming/colour-files/` (gitignored, the client's only copy, read-only) become the colourway catalogue — brand, design, supplier colour code, colour name — with 2026 rates as a secondary output. `npm run convert:colour` (`scripts/convert-colour-files.js`) drives it, over `scripts/lib/colour-sheet.js` (the shared row-extraction harness) and `scripts/lib/colour-adapters/` (the registry). Dependency-free, same posture as the two existing converters.
- **Per-supplier adapters, not one universal parser.** Eighteen files, eighteen layouts: several carry more than one brand, one spans ten sheets, and one is a PDF with no extraction path. The registry is keyed by **filename prefix**; each entry declares the sheets to read and, per sheet, a column map of the adapter's own field names onto the labels the supplier printed.
- **The header row is located by MATCHING LABELS, never by a fixed index, and the column map is the label set it is matched on** — so the map and the recognition rule are one declaration and cannot disagree. Across the corpus the header lands on rows 1, 2, 3, 4, 77, 98, 104, 105 and 106 (Jim Thompson hangs a banner row above its; Perennials starts two blank rows in; the five US houses sharing a terms-and-conditions preamble bury theirs a hundred rows down). A fixed index is right for one file and silently wrong for the rest: it reads a sentence of boilerplate as a column name and then every data row as a mismatch, which looks like "the supplier changed the file" rather than a bug here. `HEADER_SCAN_LIMIT` (250) bounds the scan so a file whose header is genuinely absent fails at once instead of reading a 20,000-row sheet to reach the same verdict; a failure names the labels never seen ANYWHERE in the window, which is what distinguishes a renamed column from a header below the bound.
- **A label the matched header carries TWICE aborts the sheet.** `select` would otherwise have to pick one of the two columns, and picking silently is how a whole file imports off the wrong cell. The check runs only on a row that otherwise matches — running it earlier would abort on any preamble row that happens to repeat a label. Jim Thompson's FABRIC sheet is the live case: it repeats `H`, `V`, `CM.` and `IN.`, so an adapter must declare the unambiguous labels instead.
- **A worksheet is addressed by NAME, never by `sheet<N>.xml`.** The number is the order the sheets were created in, not the order they appear in, and C&C Milano's only sheet is `sheet.xml` with no number. `worksheetPaths` resolves `xl/workbook.xml` through `xl/_rels/workbook.xml.rels`, accepting a `Target` either relative to `xl/` or absolute from the package root (C&C Milano writes the absolute form).
- **The `x:` element prefix is not a D365 quirk.** C&C Milano's supplier-written workbook root is `<x:workbook>` where Excel's is `<workbook>`, so the prefix is resolved with `namespacePrefix()` — matching a bare tag name finds nothing, which reads as "empty workbook" rather than as a parser bug. The same holds for the attribute prefix: `r:id` is read from whatever `xmlns:…="…/relationships"` declares.
- **A DECLARED `unsupported` entry is not the same as an UNKNOWN file.** A declared refusal (the de Le Cuona PDF) is a decision someone recorded, and is reported without failing the run. An unknown filename is a drop nobody has looked at: it is listed on stderr and exits non-zero, because a silently skipped file looks exactly like one that imported cleanly. `.DS_Store` and other dot-prefixed entries are filtered — macOS writes them into any folder it opens.
- `assertAdapter`/`assertRegistry` run at import over every entry (same posture as the lifecycle registry's `assertEntity` and `price-template.js`'s `assertStorable`), so a malformed adapter stops the converter starting rather than surfacing as a mis-mapped column thousands of rows in. Two fields declaring the same label is rejected — it is a typo far more often than an intention, and afterwards it is invisible. `selectAdapter(adapters, filename)` is the pure longest-prefix-wins lookup and `matchAdapter` binds it to the registry; the longest prefix wins so a seasonal drop needing its own layout (`Jim Thompson … 2026 - SS'26`) is not shadowed by the annual one.
- **Never join the supplier colour code to `price_list_items.code`.** The D365 item code's numeric part is the supplier's colour code and does not match the price-list code — same rule as the legacy staging section states.
- **A record is `{ brand, design, designCode, colourCode, colourName }`** (`scripts/lib/colour-adapters/records.js`). `designCode` is the fifth field on purpose: it is the code the supplier's PRICE list keys on (Maria Flora's pattern number, Perennials' quality, `NH-AFTERALLTOO`), so keeping it is what lets the rate output be emitted without re-reading every workbook. It is **not** the colour code, and neither may be joined to `price_list_items.code`.
- **One row is not one colourway.** A sheet declares its columns and, where the layout needs it, a `row(values)` mapper returning one record, an array of them, or nothing for a row it declines. Madeaux prints one row per design and names that design's colours inside a cell ("100% Linen\nColours: 01 Stone, 02 Straw, 03 Marine"), so its mapper returns three; a section banner or a note returns none. A row that should have mapped and could not **throws**, carrying `file:sheet:row` — declining a row and failing to map one must never look the same.
- **Two skip rules live in the reader, not in an adapter**: a fully blank row, and a row that repeats the header — every declared cell equalling its own label. `openSheet` matches the FIRST header row, so each later copy arrives as a data row; both Liberty sheets repeat theirs once and Madeaux repeats its four times under the section banners.
- **A sheet must name its `brand`, and `assertSheet` enforces the rest at import**: `row` must be a function, and a sheet WITHOUT a mapper must declare exactly the record's own fields including all of `design`/`colourCode`/`colourName` — because there the selected cells *are* the record, so a stray column silently yields nothing and a missing one silently yields a blank field. A sheet with a mapper may select whatever it needs (Jean Monro's RSC reads a description it never emits).
- **The supplier's spelling of a house is not the catalogue's, and no adapter may invent one.** "Mariaflora" is `Maria Flora` and "Liberty" is `Liberty London`; a mapped spelling comes from a declared alias table and an unmapped one passes through RAW for the import to report. Maria Flora's single sheet carries two houses (1,088 Mariaflora, 353 Filippo Uecher), so its brand comes off the row, not the sheet.
- **Jean Monro's workbook is three houses, and one of them is unnamed.** JM is Jean Monro; NH is Nicky Haslam (identified from the price list's own `NH-…` codes, e.g. `NH-AFTERALLTOO` "AFTER ALL TOO"); **RSC is unidentified** — nothing in this repo names it — so the token is emitted verbatim and reported as an unknown house rather than guessed at. The three sheets also disagree about what a column MEANS: `name` is the design on JM and the colour on NH and RSC, which is the sharpest case in the corpus for a column map being per sheet.
- **Where a design has to be derived, derive it against the file's own redundancy and measure it.** NH has no design column at all, and RSC's sits in an unlabelled cell. NH's design comes off the item code, which the sheet itself splits across three unlabelled cells for its first 102 rows and leaves blank for the last 50; RSC's is the description cut at the colour. Both were diffed against those cells over the whole sheet — 0 disagreements on 102 and 87 rows — before being shipped. The price list is the corpus to identify an unlabelled prefix against; when nothing matches, that is an answer too.
- **Declare the sheets that hold stock and no others.** Perennials Wallcoverings reprints all four of its type sheets in `ALL SKUS` (41+23+75+81 = 220 exactly), so declaring them too would emit every wallcovering twice; the fabrics file is the opposite, `Fabrics` and `Trims ` being disjoint. **`Trims ` really does end in a space** — a sheet is addressed by name, so the space is declared. Liberty's two sheets overlap without either containing the other (54 codes only in "Sheet1 (2)", 217 only in "Sheet1"), so both are read and the overlap is reconciled downstream.
- **All eighteen drops are claimed: seventeen workbooks and one declared refusal, 47,082 colourways.** `node scripts/convert-colour-files.js` exits 0 over the whole corpus. Largest readings: Colefax 9,065, Pierre Frey 5,998, Trend 6,039, JV 4,917 across nine sheets, Stroheim 3,883, S Harris 3,870, Jim Thompson 3,320, Clarence House 2,540, C&C Milano 1,686, Maria Flora 1,441, Liberty 1,277.
- **A brand LETTER is a code, not a spelling, and an unknown one must fail.** Colefax Group puts four houses in one sheet keyed by `C`/`J`/`L`/`M`, and the map was measured rather than read off the filename: each letter's design names were looked up in `price-lists.json` and C matches "Colefax & Fowler" on 678 of its 691 designs, J "Jane Churchill" 332/338, L "Larsen" 347/361, M "Manuel Canovas" 278/288, with no other supplier above 42. Passing an unmapped letter through the way an unmapped house NAME is passed through would file stock under a house called "X", so `colefax.js` throws instead.
- **A colourway SKU that is `<design code><colour suffix>` gives the design code up by subtraction, and the price list is what proves the split.** Colefax's stock number (hyphen on most rows, slash on 1,750), Jim Thompson's article code (three digits) and the five Fabricut houses' fabric number (two digits) all split, and the derived design code is what the supplier's price list keys on: 9,015 of 9,065 Colefax rows, 2,839 of 3,320 Jim Thompson rows (the other 481 are Fox Linton, which has its own supplier rows) and 97%+ of each Fabricut file. Measure a split rule this way before shipping it — and none of these codes may be joined to `price_list_items.code` in SQL; the corpus is evidence, not a key.
- **Clarence House, S. Harris, Stroheim, Trend and Vervain are one Fabricut layout in five files**, which is why they are one module. Their shared terms-and-conditions preamble puts the header on row 98, 104, 106, 105 and 77 — five files, one layout, five header rows, the corpus's plainest argument for locating a header by label. Only `All Colors` is declared: `Pattern Only` is the same rows without the fabric number and the colour name, so it holds designs, not colourways. Each file carries exactly one house today and the house still comes off the row, so a Fabricut export that ever carries two cannot be misfiled.
- **A row that is not stock is not a row that failed to map.** Every large file mixes non-stock rows into its stock sheets, and each is declined by a stated, measured property: Jannelli & Volpi's 239 sample books, swatches and colour cards (told apart only by `SALES UNIT`, since they carry item codes and design names like any other row), C&C Milano's 587 `Camp.` sample cuttings and its three dictionary rows (rows 2–4 translate the Italian header into English, French and German, and print the product type out where a data row numbers it), and CO.DE's 45 substrate price rows (the only rows in that file with no item code). Anything else a mapper cannot map still throws.
- **Jannelli & Volpi names no colours at all.** `ITEM` is the colourway's code and `DESIGN` the design's name; `6570` and `6571` are both "RIBBON GRASS" and the file says nothing about how they differ — the price list agrees, repeating the design as its description. So those 4,917 records carry an **empty `colourName`**, deliberately, and `FAM` is the collection's code rather than the design's so there is no design code either. Nine of its ten sheets are declared (`ACCESSORIES` is a different layout holding thirteen display items); `JV Contract` is declared and empty this year, which is worth reading rather than assuming. Six of its eight houses have no catalogue row, and two of those are spelt two ways inside the one file (`DESIGN LICENSE`/`DESIGN LICENCE`, `ALTAGAMMA`/`ALTAGAMMA MODERN LIVING`) — both spellings are emitted as found, because choosing between them is naming a house.
- **Jim Thompson keeps its colour names on a sheet of its own.** `FABRIC`, `WALLPAPER` and `THROWS` are the priced sheets and name no colour; `CODE LIST` carries `OFFICIAL COLOUR NAME` and every one of the 2,922 fabric and 392 wallpaper codes, so that is the sheet declared and the rates story has to join the two. The spring drop is a strict subset of the annual one (all 221 codes, same colour names) and orders the same labels differently — code before name in one, after in the other — which is what the longest-prefix rule and the label map are both for.
- **Pierre Frey's colour name is a subtraction that 318 rows resist.** The file names no colour on its own: `Name SKU available` runs the design and the colour together. 5,680 of 5,998 SKU names start with their own design name and give the colour up by subtraction, and 299 of those ARE the design name (the supplier named no colour, so the record carries none). The remaining 318 abbreviate the design instead of repeating it — "GR CORAIL RAY 2CH BLEU BL 4" for "LE GRAND CORAIL - Rayure 2 chemins" — and the SKU name is emitted whole rather than cut at a guess. Four of its five houses are spelt exactly as the catalogue spells them, accent included; Le Manach has no catalogue row and passes through raw.
- **`npm run convert:colour` writes `incoming/colour-files/normalized/colourways.json`** — gitignored, beside the drops, never `src/seed/data/`, the same rule the D365 exports follow (these are the client's own catalogue and price files, not repo data). A row is `{ supplier, brand, design, design_code, colour_code, colour_name, source_file, source_sheet, source_row }`, one per line. The provenance triple is the one thing that cannot be recovered later: a row that turns out to be wrong is a row somebody has to find in a supplier's spreadsheet. Serialisation is plain `JSON.stringify`, **not** `lib/python-format.js` — that module exists to reproduce the bytes a Python converter once wrote for the committed `price-lists.json`, and this file has no such history to pin. The converter walk filters to FILES (`withFileTypes` + `isFile()`), or a second run meets the `normalized/` directory it wrote and reports it as a drop nobody has mapped.
- **A row that cannot be mapped aborts THAT FILE, and any aborted file means the WHOLE RUN writes nothing.** A half-written catalogue is worse than none — the missing houses read as houses the supplier stopped carrying, not as a converter that gave up. Every bad row of the file is listed as `file:sheet:row` (50 printed, the count always in full), because a supplier who renamed one column usually renamed three and a converter that dies on the first is fixed one release per row. A sheet that will not OPEN is recorded the same way and the remaining sheets are still read.
- **One classification path, two views over it.** `sheetReadings` decides what every data row IS — `record`, `skip` (with its reason) or `error` (already carrying `file:sheet:row`) — and never throws; `sheetColourways` is the strict view that throws on the first error, so a caller wanting only records cannot walk past one, and `reading.js` is the counting view the converter uses. Writing the lenient reader as a second implementation of the same rules is how the two drift apart.
- **A declined row states WHY, and the reason names a KIND of row.** `skip(reason)` (`colour-adapters/records.js`); an empty reason throws. "1,604 rows skipped" is a number nobody can account for, where "587 sample cutting, 262 sample sold by the unit, 45 substrate price, 684 blank" is a file someone can check. The reader owns two reasons no adapter should have to declare (`blank row`, `repeats the header`) and a third bucket for a mapper that declines by returning nothing — counted, never absorbed, because the summary is only trustworthy while **rows in = colourways out + skips + errors** per sheet.
- **An exact repeat is dropped keep-first; a CLASH is reported and both rows kept.** 1,159 of the 47,082 colourways are exact repeats (Liberty's two overlapping sheets, Jim Thompson's spring subset, Maria Flora's 73 reprints) and dropping them chooses nothing. Seven rows share a house, design and colour code with a *different* name — the supplier's own two spellings, six Madeaux section reprints ("Blue Grass"/"Bluegrass") and Maria Flora's Filigrana 102 ("Lino"/"Linen") — and dropping one of those would choose, on an identity key nothing has ratified: the colourway SKU's shape is the import's decision. The run names both rows and their coordinates instead.
- **Whole-corpus reading:** 18 files, 17 read + 1 declared refusal, 48,384 rows in, 47,082 colourways out, 1,604 skipped, 1,159 exact duplicates dropped, **45,923 written** (12 MB, 15 suppliers, 37 brand spellings). `design_code` is empty for Jannelli & Volpi, C&C Milano, Liberty and Madeaux; `colour_name` is empty for all 4,917 JV records and 299 Pierre Frey ones.
- Guarded by `test/colour-files.test.js`. **No test may read `incoming/`** (gitignored, and absent on CI): every fixture is a real xlsx built in memory — a genuine deflated zip of genuine SpreadsheetML — so the harness inflates and scans for real. Each adapter's fixture is its file's own header row and first data rows transcribed cell for cell, trailing spaces and embedded newlines included; the C&C Milano workbook shape (`x:` prefix, absolute unnumbered target) has its own, because it is the one file that would have failed silently.

### The rates these files carry (the second output)

- **These drops are price lists as well as colour lists, and the rate output IS the universal pricing template** — not a shape of its own. `npm run convert:colour` writes `incoming/colour-files/normalized/rates.csv`: the v2 header row from `scripts/lib/price-template.js` and one row per rate, so the rates go on through `npm run convert:pricing` and the same vocabularies, code normalisation, dedupe and importer as every other supplier drop. Verified end to end — the office's own converter reads all 15,611 rows with no errors and `validatePriceListItems` accepts every one. `scripts/lib/colour-adapters/rate-template.js` owns the shape; `rates.js` owns the reader.
- **`assertTemplateHeader` runs at module load** and fails the converter if `RATE_HEADER` ever stops matching a registered template — the header row is what declares the version, so a drift would otherwise surface as "unexpected header" a whole pipeline away, in a file nobody edited. **`verifyRates` then runs every emitted row through the template's own mapper before anything is written**, so an unmappable item type, an unknown pack, a code that normalises to nothing or a rate that is not a number fails here rather than in the office's hands. Being in the template's shape is a measurement, not a claim.
- **Nothing is invented into `Duty Rate`, `Freight Rate` or `Duty Percent`.** All three are emitted EMPTY across all 15,611 rows, and would be carried RAW if a supplier's own sheet ever stated one: the broker's duty table (A10) and the freight class table are still owed, and a placeholder written here would be indistinguishable from a rate a supplier quoted. Same rule as the price-list converter's.
- **Rate sheets are declared apart from colourway sheets, in `adapter.rateSheets`, and read in their own pass.** Most files price on the very sheet the colourways come off and declare it twice, because the two outputs want different cells (a rate wants the unit, the width and the composition) and are grained differently — a rate is usually the DESIGN's, a colourway always the colour's. Jim Thompson settles the argument: its `CODE LIST` names every colourway and prices none, while `FABRIC`, `WALLPAPER` and `THROWS` price every article code and name no colour.
- **A rate sheet's declared constants are validated against the SHARED vocabularies at import** (`assertRateSheet` → `CURRENCY_MAP`, `CATEGORY_BY_ITEM_TYPE`, `UNIT_BY_PACK`), so an adapter cannot declare an item type or a pack the pricing converter would then refuse. A sheet must also declare a `wholesale` column; where a file prices two ways (Perennials' yard/roll, Jim Thompson's metre/selling-unit) that is the common case and the mapper reaches for the other column by name.
- **A row with no usable rate is skipped and counted, never defaulted to zero.** The reader owns three verdicts: an empty cell or `N/A` is "no rate stated"; a zero is "rate of zero, price on application" (the same reading `convert-price-lists.js` gives it — writing it would make the office quote nothing for a fabric); anything that is not a number at all is a row this converter cannot map and throws with `file:sheet:row`. An adapter that KNOWS a legitimate non-numeric form declines it explicitly with a reason — Madeaux states two rates in one cell for its 13 grasscloth wallpapers.
- **`(supplier, category, code)` is the ledger's ratified upsert key, so a code priced two ways gets NO rate.** Unlike a colourway clash, where both rows are kept because the SKU's shape is still the import's decision, one key is one row: keeping the first decides silently and keeping both makes the pricing converter refuse the whole file. 230 codes end up there (Pierre Frey prices 25 designs by the metre and by the piece at one amount; JV lists 203 items twice at different prices), each printed with every coordinate. A repeat that agrees on the money and differs only in a colourway's own cell simply collapses onto the first, counted separately.
- **The supplier cell is the spelling the office already files that house under, and it comes from a DECLARED table measured against `price-lists.json`.** A house that invoices Atelier directly is its own supplier even when its colourways arrive inside a distributor's workbook: Nicky Haslam's 17 rows are not Jean Monro's, Colefax Group's four letters are four suppliers, Pierre Frey's five houses are five (and the office spells Braquenié without its accent, S. Harris without its point). An unmapped house falls back to the drop's supplier rather than opening a new one, and the Brand column always keeps the file's own spelling — that is what the template's two columns are for.
- **The committed price list verifies the whole extraction, not just a code.** 14,914 of the 15,611 emitted rates land on a row the office already holds under the same supplier, category and code, and 10,634 of those carry the identical rate. Read it as evidence and never write it from here.
- **Jannelli & Volpi's DEALER PRICE is exactly twice what the office's ledger holds** for five of its six houses (3,939 rows at a ratio of 2.000; Missoni's 323 match to the cent), and CO.DE and JV Fabrics quote a PUBLIC price with no dealer column at all. The ledger is discount-inclusive, so these rows are emitted as the file states them and flagged — applying a discount here would be inventing exactly the placeholder the duty columns are kept empty for.
- **Liberty's two sheets price differently and the ledger decides between them**: of the 119 designs in both, all 119 agree with `DISTRIBUTOR PRICE` and only the 29 coincidences agree with `PRICE £ EX VAT`, so only `Sheet1` is a rate sheet and the 19 designs found solely in "Sheet1 (2)" get no rate.
- **A sectioned sheet reprints its header with columns RENAMED and sometimes SHIFTED.** Liberty's wallpaper section writes `WALLPAPER NAME`/`PAPER TYPE` and inserts `ROLL DIMENSIONS` after the width, so every later cell moves by one — nothing past the width may be declared there, or a repeat measurement lands in the fibre content. Madeaux relabels its price column per section (`Export/m`, `Export/ Roll`, `Export`). Neither row is caught by the shared "repeats the header" rule, which needs every declared cell to equal its own label, so each adapter declines it by the one label its sections do not change.
- `rates.csv` is written beside `colourways.json` under `incoming/` and is never dropped into `incoming/pricing-templates/` by anything here. Copying it there and running `npm run convert:pricing` regenerates the committed `src/seed/data/price-lists.json` — an 8 MB diff, and the office's decision to make.

### Landing the colourways in the catalogue (`import:colour`)

- `npm run import:colour` (`src/seed/import-colourways.js` → `src/seed/colourways-import.js`) reads the normalised file and lands it as **one product per (house, design) and one colourway per row**, plus a zeroed `inventory` row. Two-step pipeline, same shape as the pricing and D365 ones; pass a path argument to read a scratch file instead of `incoming/colour-files/normalized/colourways.json`.
- **A house is resolved by SLUG against `brands`, and an unresolved one is REPORTED, never created.** Slug rather than name because the catalogue's own identity key is the slug and it absorbs the spellings that differ only in accent or point ("S. Harris" → `s-harris`, "Braquenié" → `braquenie`) while still refusing a genuinely different name ("Colefax & Fowler" and "Colefax and Fowler" do not collide into one house by accident). Measured over the corpus: **22 of the 37 brand spellings resolve, carrying 38,064 of the 45,923 rows; 15 spellings covering 7,823 rows have no catalogue row** — Jannelli & Volpi's six houses, C & C Milano, Perennials, Le Manach, Fox Linton, Nicky Haslam, BILL BENSLEY X JIM THOMPSON and Jean Monro's unidentified RSC. Each is a naming decision the office owes; their rows stay in the normalised file and land on the next run once somebody adds the house.
- **The colourway SKU is `<brand slug>-<design>-<supplier colour code>`, uppercased, every part slugified.** Nothing shorter is unique — Madeaux and Maria Flora number colours per design ("01", "102"), so a code alone repeats across designs — and the office's own Brand-Product-Colour generator lives in the CRM demo app and was deliberately never ported. Slugifying every part is what makes the key stable under the supplier's own re-casing: Liberty writes one colourway "Deco Scallop"/"Pewter" on one sheet and "DECO SCALLOP"/"PEWTER" on the other, and 28 of the corpus's 35 repeated SKUs are exactly that. Measured: 38,064 rows, 38,064 distinct SKUs, and **zero collisions with the 34 demo SKUs the seed already holds**.
- **One SKU is one colourway, so a repeat collapses onto the first row — but a repeat and a CONFLICT are counted apart.** Where the two rows name the colour the same thing modulo casing and spacing it is only counted (28 rows); where they genuinely disagree it is reported with both names and both `file:sheet:row` coordinates (7 rows — the six Madeaux section reprints and Maria Flora's Filigrana 102, exactly the seven the converter's clash report names). The catalogue can hold one name per SKU and nothing has ratified which, so the run says so rather than choosing quietly.
- **Products are `INSERT … ON CONFLICT DO NOTHING`, not DO UPDATE.** This file knows a design's name and nothing else, so composition, width, the trade price and `show_on_website` belong to the seed or to a person in the CRM; writing EXCLUDED over them would replace a catalogue entry with a thinner one and re-capitalise a house-styled name into the supplier's ALL CAPS. That costs a select-back (DO NOTHING returns no row for a slug that was already there) and buys an import that provably changes nothing on a re-run. The product slug follows the seed's own fabric convention — slugify of brand name plus design name — on the **catalogue's** spelling of the house, so a design the seed already holds is joined rather than duplicated.
- **Colourways upsert on the SKU exactly as the seed does**, minus `hex_tones` and `image_url` — this file cannot speak for a swatch somebody uploaded, so an import never blanks one. Inventory is `INSERT … DO NOTHING` at zero, like the seed and the admin colourway create: stock is live operational data from the first run on. The unit comes from the product's OWN `product_type` (read back, not assumed), so a colourway landing on an existing finished good stocks in `units` rather than `metres`.
- **Every product this importer creates is a `fabric`.** `products.product_type` is CHECKed to `fabric|finished_good`, and a wallpaper or a trimming is nearer the first than the second — it is cut, priced and stocked by length. The type is immutable on an existing product (the inventory unit was derived from it), which the DO NOTHING already guarantees.
- **A row is DECLINED with a stated reason; a malformed BATCH is rejected before any SQL.** Emptiness is a decline — a house with no catalogue row, a row carrying no design or no colour code (Liberty prints exactly one, whose design, colour code and name are all "-") — and each reason names a KIND of row, so the summary reads "7,823 house not in the catalogue, 1 no design name" rather than a number nobody can account for. A missing coordinate or a non-string field is malformed and throws with `file:sheet:row` before a connection is even taken, the same posture as `validateLegacyRecords` and `validatePriceListItems`. Rows in = colourways out + skipped + repeats + conflicts, exactly, and the whole corpus balances.
- **The supplier colour code is NEVER joined to `price_list_items.code`** — the D365 item code's numeric part is the supplier's colour code and does not match the price list's. Nothing in the importer reads or writes that table, and a stub-pool test asserts it by logging every statement the import issues. The `design_code` the file carries (what the supplier's own price list keys on) has no column to land in and is deliberately dropped rather than squeezed into one that means something else.
- The whole import is one transaction in chunked `unnest` batches: either the catalogue gains every colourway or it gains none, because a half-imported house looks exactly like a house the supplier stopped carrying. Guarded by `test/colour-files.test.js` (114 tests), which covers the plan purely, the statement order and the price-list abstinence through a stub pool, and the real database behaviour — idempotency proved by comparing every catalogue row before and after a second run, plus `inventoryCreated: 0`.
