# atelier-api

Fastify + Postgres API. Plain JavaScript, ESM, no TypeScript.

## Conventions

- `src/config.js` — `loadConfig(env)` validates env vars, throws with clear message; server exits 1 on failure. Add new env vars here + `.env.example`.
- `src/db.js` — `createPool(databaseUrl)` returns pg Pool. Inject the pool into `buildApp({ pool })`; never import a global pool (keeps tests isolated).
- `src/app.js` — `buildApp()` builds the Fastify instance without listening. Tests use `app.inject()` (no port binding needed).
- **CORS covers TWO browser apps and must name both origins AND every write method.** `buildApp({ storeBaseUrl, crmBaseUrl })` → `@fastify/cors` with `credentials: true`, an exact-match origin allowlist and an explicit `methods` list. Guarded by `test/cors.test.js`. Three traps, each of which has actually broken the product:
  - **The CRM is a second origin.** Storefront islands fetch browser :4321 → api :3001; the CRM fetches :5273 → api :3001. Only the storefront was allow-listed, so *every* CRM call — including sign-in — was blocked by the browser. `CRM_BASE_URL` (→ `config.crmBaseUrl`) is the second entry.
  - **`methods` MUST be spelled out.** @fastify/cors defaults to `GET,HEAD,POST`, so a `PATCH`/`PUT` is refused at the preflight and **never reaches this server**. Every admin edit is a PATCH and shipping rates are a PUT, so the default silently broke every write in both browser apps — while curl and `app.inject()` (neither of which preflights) kept passing. Any CORS assertion made with `inject` alone is worthless for methods; only a real browser preflight proves it.
  - **The allowlist is closed, never reflected.** `origin: true` (echo whatever asked) plus `credentials: true` would let any site drive the API with a logged-in staff cookie. An unknown origin gets `storeBaseUrl` back, which the browser then rejects.
- `src/server.js` — only entry point that listens/exits.
- Config objects frozen (`Object.freeze`); immutable updates house style.

## Migrations

- `migrate:create` emits a CommonJS template (`exports.up`) — rewrite to ESM (`export const up/down`) because this package is `"type": "module"`.
- Tests run migrations themselves via the programmatic runner: `import runner from 'node-pg-migrate'` with `{ databaseUrl, dir: 'migrations', direction: 'up', migrationsTable: 'pgmigrations', log: () => {} }`. Runner returns the array of applied migrations — empty array proves a re-run is a no-op.
- `vitest.config.js` sets `fileParallelism: false` — the runner takes a Postgres advisory lock, so parallel test files throw "Another migration is already running". Keep it serialized.
- Schema: one `inventory` row per colourway (`colourway_id` unique). Check constraints: `products.product_type IN ('fabric','finished_good')`, `inventory.unit IN ('metres','units')`. Upsert targets for the seed: `brands.slug`, `products.slug`, `colourways.sku`, `collections (brand_id, slug)` — all unique.
- Commerce schema: `users.role IN ('customer','trade','backoffice','director')` (default `customer`), `orders.kind IN ('checkout','order_request','backorder_request')`, `orders.status IN ('requested','confirmed','paid','shipped','declined')`. `order_lines.colourway_id` is `ON DELETE RESTRICT` (commerce records survive catalogue cleanup); `orders.user_id` is `SET NULL` (guest orders keep `guest_email`). Shipping seed upsert key: `shipping_rates (zone, threshold_qty)` unique.

## Seed

- `npm run seed` (`src/seed/run.js`) — idempotent import of the atelier-app catalogue. `src/seed/catalogue-data.js` is a pure transform layer (no DB) importing vendored snapshots from `src/seed/data/` (`{realCatalogue,atelier,suppliers,pricing}.js` plus their internal deps `fx/discounts/fabricutDesigns.js` — Node-safe pure data copied from the CRM repo's `atelier-app/src/data/`; re-copy when the catalogue changes). `src/seed/seed.js` `runSeed(pool)` does the upserts in one transaction.
- Upsert semantics: brands/collections/products/colourways use `ON CONFLICT … DO UPDATE`; **inventory and shipping_rates use `DO NOTHING`** — they become live operational data after first seed (reservations, admin-edited rates) and a reseed must not clobber them.
- Products carry no SKU; the SKU lives on `colourways` (finished goods get one colourway carrying the product SKU). Fabric product slug = slugify(`${brand} ${design}`), e.g. `pierre-frey-atlas`.
- House brand `Atelier Textiles NZ` (slug `atelier-textiles-nz`) is the only `is_international=false` brand; only its finished goods have `retail_price_cents` (indicative values in `HOUSE_RETAIL_PRICE_CENTS`). All fabrics + international finished goods have null retail price (FR-3).
- `hex_tones` jsonb: pass `JSON.stringify(array)` as the query param — pg maps raw JS arrays to Postgres arrays, not jsonb.
- Shipping tiers: `threshold_qty` is the tier floor (0 and 20 per zone); a quote picks the highest threshold <= qty.

## Supplier price lists

- Two-step pipeline: `npm run convert:pricing` (`scripts/convert-price-lists.py`, Python stdlib only) turns the per-brand template drops in `incoming/pricing-templates/` (gitignored) into the universal file `src/seed/data/price-lists.json`; `npm run import:pricing` (`src/seed/import-price-lists.js` → `src/seed/price-lists.js`) upserts it into `price_list_items`.
- All templates share one 14-column layout (Date Effective … Freight Rate). Converter normalises: item type → `category` (`fabric|wallpaper|trimming|accessory`), pack type → `unit` (`metre|yard|roll|piece`), currency names → ISO (`EUR|USD|GBP`), d/m/Y and Excel-serial dates → ISO, float noise rounded to 4dp. CSVs are sniffed `utf-8-sig` then `cp1252` (≈28 files are cp1252); XLSX read from the zip directly (no openpyxl). Supplier name comes from the filename prefix (title-cased, `SUPPLIER_OVERRIDES` for JV/JWall/C&C), not the `Product Range` column (which holds range names like "MISSONI WALL COVERING").
- Converter fails loudly (file:line list, writes nothing) on unmappable values; **skips** rows with wholesale rate 0 (price-on-application items, reported to stderr) and exact duplicate rows (keep-first).
- Cross-checked against `~/Documents/atelier-platform-demo` docs (Verum build spec REQ "price-list import templates", Action-List 13–15 Jul): the 14-column set matches the ratified template; `code_normalized` implements decision 6 (uniform code format, raw kept for traceability); unit vocabulary matches decision 7 (`metre|yard|roll|piece|hide|panel` — hide/panel have no template rows yet). `duty_class`/`freight_class` letters are stored **raw, uninterpreted**: the broker's duty table (A10) and a freight class→rate table are still owed — the CRM's `/import` wizard applies a 7% duty placeholder downstream; do NOT bake placeholders into this table. Pattern-match text stays embedded in `vertical_repeat` (corpus too messy for an enum: "Repetable", "HD", "V x 70H"…; definitive field list still owed from Charlotte).
- Upsert key `(supplier, category, code)`, `ON CONFLICT … DO UPDATE` — unlike inventory, a re-import is how new season rates land, so freshest wins; rows absent from later files are kept. `wholesale_rate` stays `numeric(12,4)` in the **supplier's currency** (not NZD cents — the pricing waterfall converts downstream). Whole import is one transaction, chunked `unnest` batches; `validatePriceListItems` rejects the batch before any SQL (also catches duplicate keys, which would break multi-row upsert).
- `repeat` is a Postgres non-reserved word but quoted `"repeat"` in SQL anyway. Guarded by `test/price-lists.test.js`, which also validates the committed JSON (19.5k items, 40 suppliers).

## Legacy D365 staging

- Two-step pipeline mirroring the price-list one: `npm run convert:legacy` (`scripts/convert-d365-exports.py`, Python stdlib only) turns the Dynamics worksheet exports in `incoming/data-exports/` (gitignored) into `incoming/data-exports/normalized/*.json`; `npm run import:legacy` (`src/seed/import-legacy.js` → `src/seed/legacy-import.js`) upserts them into the eleven `legacy_*` tables (product_prices, stock_items, item_locations, accounts, contacts, sales_orders, sales_invoices, purchase_orders, purchase_invoices, reserves, cuttings). Full column audit and data findings in `docs/d365-export-analysis.md`.
- Adding an entity means three edits in lockstep: `ENTITIES` in the converter, a `createTable` in a migration, and a `LEGACY_TABLES` entry (the column map drives the `unnest` casts, so a missing/misnamed column fails the whole import rather than silently nulling).
- Columns pulled from a **related** entity export as `<relationship-guid>.<logical_name>` (e.g. `5c5e1693-….atelier_code`). The GUID changes if the view is rebuilt, so the column map accepts a `*.atelier_code` suffix wildcard; a bare logical name always takes precedence.
- **All four transaction entities are header-only** (sales orders, sales invoices, purchase orders, purchase invoices) — roll-up totals, no lines. There is no export path for the detail rows, so **line-item import is shelved**: legacy sales history stays header-grain and product-grain historical reporting is out of scope. Revenue by customer/owner/period still works off the 7,002 invoice headers.
- **D365 item codes are composed at sales-order time, not catalogued**: `{supplier's colour code}[ {YY}{SUPPLIER_TOKEN}]` (e.g. `F3518-003 23PF`). 74.5% carry the suffix, 62 tokens, years 11–26. The token is the **supplier**, not the brand (`CF` = Colefax & Fowler + Jane Churchill), so the token set doubles as the supplier↔brand roll-up A13 wants. Consequence: Product Prices is the catalogue spine (19,327 designs) and Stock Items is the transacted subset (7,611) — a colourway only exists once sold. The item code's numeric part is the supplier's colour code and does **not** match the price-list code, so never join those on code.
- **Lookup columns export as the target's display name, which destroys the key.** `legacy_stock_items.product_price_list` is the price row's Description: only 52% of stock items resolve to exactly one price row (796 ambiguous, 1,780 no match, 1,064 unset). Same for `legacy_item_locations.item` (7,611 items share 6,315 names). The fix is a related **code** column, as Reserves/Cuttings already have — those join at 88–92%. Re-export those two views before attempting any stock↔price mapping.
- `legacy_reserves` (not the stock item's free-text `Reserve` note) is the source of reserved quantity.
- Portal identity columns on `contact` (`adx_identity_*`, incl. the password hash) are dropped at conversion alongside the supplier bank details.
- **Staging is deliberately separate from the live tables and nothing maps into them yet.** The A1/A2/A3 definitions (cost source, what counts as a sale, stock authority) are unsettled; Atelier runs live on D365 until cutover so the import must re-run; and `orders`/`order_lines` are owned by the Stripe webhook + admin-orders state machine — injecting historic orders there would desync `qty_reserved`.
- Exports must stay **dynamic** worksheets. Each embeds `<entity>:<sig>:<logical_name>=<Display Name>&…` in `sheet.xml` (data is on `sheet2.xml`), so columns are matched by **D365 logical name, never display name or position** — a renamed or reordered view cannot corrupt the import, and a missing required column fails the whole run. Dynamic exports also carry the record GUID and a row checksum; a static export carries neither.
- Upsert key is the D365 GUID → re-import is idempotent and refreshes in place; rows absent from a later export are kept. `validateLegacyRecords` runs before any SQL and rejects duplicate GUIDs (a multi-row upsert cannot hit the same conflict key twice) and unknown columns. `raw` jsonb holds every non-empty source column by logical name — `JSON.stringify` it before binding (pg maps a raw object to a record, not jsonb).
- **Consent polarity trap**: D365 renders `donotemail=false` as the word **"Allow"** and `donotsendmm=false` as **"Send"**. Staging columns keep the source attribute's polarity and name (`do_not_*`, TRUE = do not contact); a column named `send_marketing_materials` would invert every row. Guarded by `test/legacy-import.test.js`.
- Supplier bank-account columns are dropped at conversion time and never reach the database. Normalised JSON lives under `incoming/` (gitignored), not `src/seed/data/`, because accounts and orders are client PII.
- Timestamps are `timestamp` (no zone): the export writes Excel serials rendered in the exporting user's local time, so tagging them UTC would shift every date by the NZ offset.

## Auth

- Sessions are **stateless signed cookies**: cookie `atelier_session` holds the user id, signed by `@fastify/cookie` with `COOKIE_SECRET` (required env var, 32+ chars; `buildApp({ pool, cookieSecret })` throws without it). No sessions table — logout only clears the client cookie.
- `src/auth/session.js` — `setSessionCookie(reply, userId)` / `clearSessionCookie(reply)` / `readSessionUserId(request)` (returns user id or null; use this for US-006 middleware). Cookie flags: HttpOnly, Secure, SameSite=Lax, path=/, 30-day maxAge.
- `src/auth/passwords.js` — argon2id via `hashPassword`/`verifyPassword` (never throws on malformed hash, returns false). `getDummyHash()` is verified against for unknown emails so login timing doesn't enumerate accounts.
- Rate limiting: `@fastify/rate-limit` registered `global: false`; routes opt in via `config: { rateLimit: { max, timeWindow } }`. Login AND register share 10 per 15 min per IP (register is limited because each attempt runs a memory-hard argon2 hash and 409s enumerate emails). The limiter store is per app instance and per route — tests that spend attempts need their own `buildApp()`.
- Fastify's bundled Ajv has **no `format: 'email'`** — body schemas use `EMAIL_PATTERN` regex instead. Schema violations return 400 (Fastify default), not 422.
- Responses use snake_case fields matching DB columns; `password_hash` is never selected into a response — always select via `PUBLIC_USER_COLUMNS` from `src/auth/user-columns.js` (single source of truth, do not redefine locally).
- Guards (`src/auth/guards.js`): `buildApp` decorates `app.guards = createGuards(pool)`; protect routes with `{ preHandler: app.guards.requireAuth }` or `app.guards.requireRole('trade'|'backoffice'|'director'|'customer')`. `requireAuth` loads the user from DB per request and sets `request.user`; 401 when no/invalid session or user deleted. `requireRole` returns 403; unknown role name throws at registration time. Role semantics: unapproved trade collapses to `customer` (`effectiveRole`), `director` passes `backoffice` checks, `requireRole('trade')` is approved-trade ONLY (backoffice/director do NOT get trade capability — deliberate, revisit if staff need trade-pricing views).
- `POST /auth/trade-application` = register with `role='trade'` (`trade_approved` stays false via DB default) **plus the full atelier.co.nz trade-account form** in a required `application` object (body schema is structural only; `validateTradeApplication` in `src/users/trade-applications.js` returns the field-level 422s with `application.<field>` paths). `submitTradeApplication` creates the user AND the `trade_applications` row in one transaction — a duplicate email (409) leaves no orphan form. Same rate limit bucket rules as register. The form is reviewed in the CRM's Users → Applicants tab (`GET /admin/trade-applications`(`/:id`), backoffice, read-only — `src/routes/admin-trade-applications.js`); each application embeds the applicant's live `user` state via LEFT JOIN because approval state is NEVER stored on the application: `users.trade_approved` stays the single source of truth, flipped only via `PATCH /admin/users/:id { trade_approved: true }`. `trade_applications.user_id` is `ON DELETE SET NULL` (business record survives account removal — test cleanups must delete applications before users or they orphan). Approval is manual and silent: nothing notifies the applicant. **A pending trade account cannot authenticate at all**: the application sets no session cookie, `/auth/login` answers **403** "awaiting review" (checked only AFTER the argon2 verify, so without the right password it stays the generic 401 — no enumeration), and `SESSION_USER_CONDITION` (`src/auth/user-columns.js`, = active AND NOT pending-trade) is what `/auth/me` + `guards.loadSessionUser` filter on, so revoking approval kills a live session exactly like archiving does. Guarded by `test/trade-applications.test.js`; the shared valid-form fixture lives in `test/helpers/trade-application-fixture.js`.
- **Every auth path must exclude archived accounts.** `archived_at` is a soft delete (orders reference the row), so the account is still fully loginable unless the query says otherwise — archiving from the CRM used to leave the session cookie live, let the old password back in, and keep serving trade pricing. `ACTIVE_USER_CONDITION` in `src/auth/user-columns.js` is the single source of truth for the clause; it is applied in exactly three places (`/auth/login`, `/auth/me`, `guards.loadSessionUser` — which covers `requireAuth`, `requireRole` AND `loadOptionalUser`, so an archived trade user drops to anonymous on the public catalogue) plus `src/admin/authenticate.js` for the panel. (`/auth/me` and `loadSessionUser` actually apply `SESSION_USER_CONDITION`, which embeds it and adds the pending-trade exclusion — see the trade-application bullet.) The back-office `src/users/admin-users.js` queries deliberately do NOT use it — staff must be able to list and restore archived rows. Login and panel login **select** `archived_at` rather than filtering in SQL: filtering would return before the argon2 verify and make "archived" measurably faster than "wrong password". Both answer with the same generic 401. Guarded by `test/auth.test.js`, `test/guards.test.js`, `test/admin-panel.test.js`.
- Behind a reverse proxy set `TRUST_PROXY` (→ `config.trustProxy` → Fastify `trustProxy`) or per-IP rate limiting collapses to one shared bucket. Use the proxy address form (`TRUST_PROXY=127.0.0.1` for same-host nginx), not `true` — `true` trusts client-supplied `X-Forwarded-For` wholesale. Still deferred from the security review: @fastify/helmet, account-keyed login backoff.

## Catalogue (public)

- `GET /catalogue/products` (`src/routes/catalogue.js` + `src/catalogue/products.js`) — public product list, `show_on_website = true` only, paginated (`page`, `limit`; defaults 1/20, max 100). Response: `{ products: [...], meta: { total, page, limit, sort } }`.
- Filters are exact-match strings whitelisted in `FILTER_COLUMNS` (`application`, `composition`, `width`, `price_band`, `lead_time`, `product_type`, `collection`) plus `brand` (matches `brands.slug`). Filter *names* map to trusted columns; filter *values* always go through parameterized placeholders — never interpolate a value into SQL. Unknown query params are simply ignored (the whitelist controls what filters), not rejected.
- **Merchandising fields** (added so the storefront grid is a real shopping grid, not a spec table), all built by one `LEFT JOIN LATERAL` colourway rollup: `image_url` (first colourway image in name order, falling back to the product's `hi_res_asset_url`, else null), `in_stock` (`bool_or` over the colourways' `qty_available - qty_reserved > 0`; no colourways or no inventory rows → false), `colourway_count` (true count) and `colourways` (up to `CARD_SWATCH_LIMIT` = 6 `{ name, sku, hex_tones }` for the card swatch strip). The rollup is an aggregate subquery, so it always yields one row — `cw` is never null.
- **Search**: `q` is a single free-text term ILIKE-matched against product name, house name, composition, application, and (via EXISTS) every colourway name/SKU. `%`/`_`/`\` in the term are escaped and the SQL carries `ESCAPE '\'`, so searching `100%` finds a literal percent. A blank/whitespace term is ignored, not treated as "match nothing". `q` narrows the count query too, so `meta.total` is the search total.
- **Sort**: `sort` ∈ `name` (default) | `price_asc` | `price_desc` | `newest`, mapped through the trusted `SORT_ORDERS` table — never interpolate the raw value. Price sorts order on `DISPLAY_PRICE` (`CASE WHEN b.is_international THEN NULL ELSE p.retail_price_cents END`), **not** the raw column: ordering on a price the shopper is not allowed to see would leak it. Hidden/absent prices sort `NULLS LAST` in both directions.
- Pricing (FR-3), enforced in `toPublicProduct`: international brands (`is_international = true`) get `price_hidden: true` and **no** `retail_price_cents` field; domestic brands get `retail_price_cents` only when non-null, `price_hidden: false`.
- Fastify querystring validation with `additionalProperties: false` does NOT reject unknown params here (extra keys pass through), but `enum`/type constraints (`product_type`, `sort`) DO 400. Rely on the code whitelist for filter safety, not on schema strictness for unknown keys.
- `GET /catalogue/products/:slug` (`src/catalogue/product-detail.js`) — public product detail, `show_on_website = true` only (else 404). Response `{ product }`: list fields + `hi_res_asset_url` + `colourways: [{ name, sku, hex_tones, image_url, in_stock }]`. `in_stock = qty_available - qty_reserved > 0`; a colourway with **no** inventory row (LEFT JOIN → nulls) is out of stock. pg returns `numeric` columns as strings — coerce with `Number()` before arithmetic.
- **Trade pricing** (`trade_price_cents`, integer NZD cents on `products`): added by the `1784605289852_trade-price-cents` migration; precomputed at seed for **fabrics only** from the vendored `src/seed/data/pricing.js` `tradeUnit(design)` (`Math.round(unit * 100)`); finished goods stay null. **Both** the list and detail endpoints reveal it, and only to approved trade users (`effectiveRole(user) === 'trade'`) — never to anonymous/customer/backoffice. (The list used to omit it entirely; that made a signed-in trade shopper see "sign in for trade pricing" on every card in the grid.) `price_hidden` is independent: an international house hides its retail price from everyone, trade included, while still showing the trade figure.
- Optional-auth pattern for public routes that show extra fields to logged-in users: `app.guards.loadOptionalUser(request)` returns the user or null and never blocks (unlike `requireAuth`). Route derives `includeTrade` from it and passes it into the read model; the read model is the single gate that adds the field. Both catalogue routes use it.
- `GET /catalogue/brands` → `{ brands: [{ slug, name, country, currency, is_international, story, website_url }] }` (all brands, alpha). `GET /catalogue/brands/:slug` → `{ brand: { ...brand, collections: [{ slug, name }] } }`, 404 if unknown (`src/catalogue/brands.js`). `website_url` (migration `1785715200000`) is the house's own site, rendered by the storefront brand page as an outbound link; admin create/PATCH validate it via `websiteUrlFrom` — absolute http(s) only, else 422, so a `javascript:` URL can never reach a public href; explicit null clears it. Seed source is `src/seed/data/brand-websites.js` — **seed-owned, not a vendored snapshot** (a re-copy of `src/seed/data/` must not overwrite it), URLs verified against the live sites before entry — and the brand upsert applies it with `COALESCE(brands.website_url, EXCLUDED.website_url)`: it fills blanks only, a CRM-entered URL survives every reseed (guarded by `test/seed.test.js`).

### Collections (brand → collection → product)

- The hierarchy is `brands 1—N collections 1—N products`, but a product's **brand is a direct FK** (`products.brand_id` NOT NULL), not inherited through the collection; `products.collection_id` is nullable (`ON DELETE SET NULL`). A product with no collection is normal, not broken — **the seed never assigns one**, so every seeded product starts uncollected and membership is staff-assigned in the CRM. `admin-products.js` `requireCollectionInBrand` 422s a collection belonging to another house.
- **A collection slug is unique per brand, never globally** (`collections_brand_id_slug_unique`), so every single-collection lookup is brand-scoped: `GET /catalogue/brands/:slug/collections/:collectionSlug` → `{ collection: { slug, name, product_count, brand } }`, 404 otherwise (`src/catalogue/collections.js`). The house param stays named `slug` because Fastify's router rejects two different parameter names in the same path position — renaming it would break `/catalogue/brands/:slug`.
- `GET /catalogue/collections?brand=` → `{ collections: [...] }` (brand name, then collection name). Unknown brand → **empty list, not 404** — same posture as a product filter that matches nothing. `product_count` counts only reachable products (visible, unarchived, unarchived house), so a non-zero count always yields a non-empty grid.
- Collections carry **tile editorial**: `description` + `image_url` (migration `1785801600000`), seeded from the vendored atelier.co.nz snapshot (`realCatalogue.collections` `description`/`src` — the first seed dropped these) and exposed on both public collection endpoints and the admin reads. `PATCH /admin/collections/:id` now takes any of `name`/`description`/`image_url` (`minProperties: 1`; name no longer required); `image_url` goes through the same http(s)-only `websiteUrlFrom` gate as the brand website (it lands in a public `<img src>`), 422 otherwise. Collection **display names drop the snapshot's redundant house prefix** (`collectionDisplayName`: "Pierre Frey | Cappuccino" → "Cappuccino"; a letterless remainder like "2024" keeps the full name) while the **slug still derives from the full snapshot title** — it is the `(brand_id, slug)` upsert key and changing it on a reseed would duplicate every already-seeded collection.
- **Neither collection route returns products.** The grid is `GET /catalogue/products?brand=&collection=`, so filtering, sorting, paging and the trade-price gate stay in one read model. `collection` alone (no `brand`) matches every house using that slug — pair the two.
- Both product read models expose `collection: { slug, name } | null` via a `LEFT JOIN collections col ON col.id = p.collection_id AND col.archived_at IS NULL`. **The archived check lives in the join condition, not the WHERE clause**: archiving a collection is a soft delete of the grouping only (see `setCollectionArchived`), so its products keep selling and simply read as uncollected — and the `collection` filter can never match an archived collection. The join is in the count query too, or `meta.total` would ignore the filter.
- Guarded by `test/catalogue-collections.test.js` (15 tests), whose fixture gives two houses the *same* collection slug — the regression that brand-scoping exists to prevent.

## Shipping

- `GET /shipping/quote?zone=&qty=` (`src/routes/shipping.js` + `src/shipping/rates.js`) — public flat-rate quote. `getShippingQuote` picks the highest tier whose `threshold_qty` floor is `<= qty` for the zone. Response `{ zone, qty, threshold_qty, rate_cents }`. Unknown zone (no rows) → 400 with a clear message; missing/invalid `zone`/`qty` → 400 by schema (Fastify coerces the querystring `qty` to a number). Boundary rule: at `qty == threshold` the higher tier applies (`<=`).
- `PUT /admin/shipping-rates` (backoffice) — body `{ rates: [{ zone, threshold_qty, rate_cents }] }`; `upsertShippingRates` upserts on `(zone, threshold_qty)` in one transaction (edit rate or add a tier without redeploy) and returns the full `{ rates }` list. Note: seed inserts rates `DO NOTHING`, so admin edits here are the mutation path and survive reseeds.

## Checkout (Stripe)

- `POST /checkout/session` (`src/routes/checkout.js` + `src/checkout/checkout.js`) — B2C card checkout for finished goods (FR-4). Body `{ lines: [{ sku, qty }], zone }`; **no prices accepted from the client** (`additionalProperties: false` on line items). `validateCheckoutLines` resolves each SKU server-side and rejects with **422**: fabric products (`product_type = 'fabric'`), goods with `retail_price_cents = null`, hidden/unknown SKUs, and insufficient stock (`qty_available - qty_reserved < qty`, pg-numeric strings coerced). Unknown shipping zone → **400**.
- Stripe line items use inline `price_data` (currency/`product_data.name`/`unit_amount` from the DB), never pre-created Price IDs. A shipping line item is appended from `getShippingQuote(zone, totalQty)`. The cart (`[{ sku, qty }]` only) + zone + shipping_cents go into `session.metadata` so the **US-011 webhook** rebuilds the order — this endpoint creates **no** order row. `client_reference_id`/`customer_email` are set when logged in (`loadOptionalUser` — guests allowed). Returns `{ url, session_id }`.
- **Delivery details are collected at Stripe**, not by the store: `shipping_address_collection: { allowed_countries: SHIPPING_COUNTRIES }` (`['NZ']` — the shipping-rate tiers only price the three NZ zones, so no other country may be offered), `phone_number_collection`, `billing_address_collection: 'auto'`. Deliberately **no `shipping_options`** — our own zone tiers price the freight as a line item, and Stripe adding its own would double-charge. The webhook persists what was collected (below).
- A **mixed-currency cart is rejected with 422** before any Stripe call: one session charges in one currency (and the shipping line is priced in it), so picking a winner would silently mis-charge. The insufficient-stock 422 names the SKU **and** how many remain, so the store can tell the shopper what to change.
- **Stripe is injected**, not imported globally: `buildApp({ ..., stripe, storeBaseUrl })`. `src/server.js` builds the real client from `STRIPE_SECRET_KEY` (optional env — checkout returns **503** when unset, so the rest of the API boots without it). Tests pass a stub whose `checkout.sessions.create` records params — no SDK/network. Secret comes from env only; `test/checkout.test.js` greps `src/` for an `sk_(live|test)_` literal and asserts none (the pattern is built from fragments so it never self-matches).
- `GET /checkout/session/:id` (public) — the store success page (US-019) verifies a completed session. `retrieveCheckoutSession({ stripe }, id)` calls `stripe.checkout.sessions.retrieve(id)` and returns only non-sensitive fields `{ order_number: 'WEB-<id>', paid, amount_total_cents, currency, email }` (no line items/prices). Unknown/failed retrieve → **404**; stripe unset → **503**. `order_number` is deterministic so the success page shows it without waiting for the async webhook to create the order row. Test stub adds a `retrieve` method alongside `create`.
- Errors are thrown as `Object.assign(new Error(msg), { statusCode })`; Fastify serializes `{ statusCode, error, message }`, so handlers stay thin.

## Webhooks (Stripe)

- `POST /webhooks/stripe` (`src/routes/webhooks.js` + `src/webhooks/stripe-webhook.js`) — records completed payments as paid orders (FR-4). Verifies the signature with `stripe.webhooks.constructEvent(rawBody, sig, STRIPE_WEBHOOK_SECRET)`; invalid signature → **400**. On `checkout.session.completed`: inserts an order (`kind='checkout'`, `status='paid'`) with lines and decrements `inventory.qty_available`. Other event types are recorded but create no order. Returns `{ received: true, duplicate }`.
- **Raw body**: signature verification needs the exact bytes, so the webhook plugin registers its own `addContentTypeParser('application/json', { parseAs: 'buffer' }, …)`. Content-type parsers are **encapsulated** — this only affects the webhook plugin; every other route keeps normal JSON parsing. `request.body` is a Buffer here.
- **Idempotency**: the `webhook_events` table (migration `1784606400000`, PK `event_id`) is the ledger. `processStripeEvent` opens one transaction, claims the event with `INSERT … ON CONFLICT (event_id) DO NOTHING`; `rowCount === 0` → replay → rollback and return `{ duplicate: true }` (creates nothing). Order creation + inventory decrement + ledger claim all commit together.
- **Money is re-resolved server-side**, never read from the payload: the cart (`[{ sku, qty }]`) lives in `session.metadata.cart`, zone in `metadata.zone`, shipping in `metadata.shipping_cents` (all stashed by US-010 checkout). Line prices come from a fresh DB lookup by SKU (`retail_price_cents`). `order_number = WEB-${session.id}` (stable per session). `user_id` from `client_reference_id` (int), else `guest_email` from `customer_details.email`/`customer_email`.
- **Delivery details are persisted** onto the order (`orders.shipping_address` jsonb + `orders.contact_phone`, migration `1785283200000_order-delivery-details`) by `deliveryDetails(session)`. Stripe moved the address to `session.collected_information.shipping_details` in newer API versions, so it reads **both** that and the legacy top-level `session.shipping_details` — an API-version bump must not silently start dropping addresses. Absent sub-fields are recorded as explicit nulls; a session with nothing collected stores null, not `{}`. jsonb because it is a verbatim purchase-time snapshot, never something we query into. Without this the back office had a paid order and no address to ship it to.
- **Config**: `STRIPE_WEBHOOK_SECRET` (optional env → `config.stripeWebhookSecret`) injected as `buildApp({ ..., stripeWebhookSecret })`. Webhook returns **503** when stripe or the secret is unset. Tests inject a stub whose `webhooks.constructEvent` re-parses the raw body into an event when the signature header matches a sentinel, else throws — no SDK/network.

## Order requests (fabric / backorder)

- `POST /orders/request` (`src/routes/orders.js` + `src/orders/order-request.js`) — a customer or guest asks the back office to cut and invoice fabric (FR-5/FR-6). Body `{ lines: [{ sku, qty_metres, cut_requirements? }], contact?: { name, email, phone }, accepted_lead_time? }`. Public (guests allowed via `loadOptionalUser`). Returns **201** `{ order: { id, order_number, kind, status, lines } }`.
- **Two-layer validation**: the body schema is structural only (empty `lines`/missing `sku` → **400**). `qty_metres > 0` and email validity are checked in the handler via `validateOrderRequestInput`, which returns **422** `{ message, errors: [{ field, message }] }` with field paths like `lines[0].qty_metres` / `contact.email`. Guests must supply `contact.email`; logged-in users fall back to their session email (order gets `user_id`, `guest_email` stays null).
- **Availability decides the kind**: for every line, `available = qty_available - qty_reserved` (pg-numeric strings coerced). All lines in stock → `kind='order_request'`, `order_number` `REQ-…`. Any line short → requires `accepted_lead_time=true` (else **422** "accept the quoted lead time"); then `kind='backorder_request'`, `order_number` `BO-…`. Both create `status='requested'`.
- **Reservation**: in one transaction each line increments `inventory.qty_reserved` by `qty_metres` (backorder lines reserve too — committed demand). The colourway row is locked `FOR UPDATE OF c` — the inventory row is the nullable side of the LEFT JOIN and **can't** be locked directly ("FOR UPDATE cannot be applied to the nullable side of an outer join"), so locking the colourway serialises concurrent same-SKU requests. Unknown/hidden SKU → **422**.
- Pricing is deliberately **0** on request lines (`unit_price_cents = 0`); the invoice amount is set manually by the back office at confirmation (US-014), not by the client. `contact` name/phone are stored in `orders.notes`.

## Order history + guest lookup

- `GET /orders/mine` (`src/routes/orders.js` + `src/orders/order-history.js`) — auth (`requireAuth`), returns `{ orders: [...] }` newest first, each with `lines`. Ownership is enforced in SQL (`WHERE user_id = request.user.id`), never in the handler, so one user can never read another's orders.
- `GET /orders/lookup?order_number=&email=` — public guest lookup. Returns `{ order }` only when order number AND email match; email matches either `guest_email` or the placing user's `users.email` (case-insensitive `lower()`). No match → **404** (never a 400/enumeration signal). Both query params required by schema (missing → 400).
- Order shape (`toOrder`): `id, order_number, kind, status, subtotal_cents, shipping_cents, total_cents, shipping_zone, xero_invoice_ref, shipping_address, created_at, lines`. Lines carry `sku, product_name, qty, unit_price_cents, cut_requirements`. Internal columns (`stripe_session_id`, `guest_email`) are not exposed. Lines are batch-loaded for all order ids in one query (`ol.order_id = ANY($1::int[])`) then grouped — no N+1.

## Back-office order management

- `src/routes/admin-orders.js` + `src/orders/admin-orders.js` (US-014, FR-7). All routes `requireRole('backoffice')` (director inherits). Handlers stay thin; the state machine + reservation logic live in the module.
- **Lifecycle** (order-request / backorder kinds): `requested --confirm--> confirmed --mark-paid--> paid --ship--> shipped`; `requested|confirmed --decline--> declined`. Any other transition throws **409** via `requireStatus`. `confirm` stores `xero_invoice_ref` from the body (manual Xero, no API call).
- **Reservation model**: only `RESERVING_KINDS` (`order_request`, `backorder_request`) touch inventory here; `checkout` orders arrived paid + already-decremented and hold no reservation (`reserves(kind)` guards every inventory write). `reservation_state` per order = `held` (requested/confirmed/paid) → `converted` (shipped: `qty_reserved -=`, `qty_available -=`) or `released` (declined: `qty_reserved -=`). `ship`/`decline` update inventory with a single `UPDATE inventory i ... FROM order_lines ol WHERE ol.order_id=$1 AND i.colourway_id=ol.colourway_id` (no per-line loop). A colourway with no inventory row (short backorder) reserved nothing, so the join simply matches nothing.
- **Endpoints**: `GET /admin/orders?status=` (optional enum filter → 400 on unknown), `GET /admin/orders/:id` (404), `PATCH /admin/orders/:id` (body `{ lines: [{ id, qty }] }` — edits qtys, adjusts held reservation by delta; **only** requested/confirmed, else 409), `POST .../confirm|mark-paid|ship|decline`. `:id` is an integer param (Fastify coerces; non-numeric → 400).
- Every mutation runs through `withOrderTxn(pool, id, fn)`: `BEGIN`, `SELECT ... FOR UPDATE` the order (404 if missing), run `fn`, `COMMIT`, then return the fresh order via `getAdminOrder`. Admin order shape exposes internal fields customers don't see (`guest_email`, `notes`, `shipping_address`, `contact_phone`, per-line `colourway_id` + `inventory` snapshot + `reserved_qty`).
- **Test gotcha**: register shares a rate-limit bucket (10 / 15 min / IP). Register staff/customer **once** in `beforeAll` and keep them; per-test `beforeEach` cleans only orders + brand fixtures, never users (re-registering each test 429s and yields no cookie). pg `numeric` qty comes back like `'10.00'` — compare with `Number()`, not string equality.

## Back-office catalogue admin

- `src/routes/admin-catalogue.js` + `src/catalogue/admin-brands.js` (brands + collections) + `src/catalogue/admin-products.js` (products + colourways). All routes `requireRole('backoffice')`. **The client is the CRM, not the storefront** — the storefront's admin islands were deleted in its `6d1e1df` ("move back-office admin out of the storefront") and the screens now live in `atelier-crm` (`src/screens/Admin*.jsx`), calling these endpoints cross-origin from :5273. Nothing to do with the AdminJS panel at `/panel`, which stays as the raw fallback.
- **Endpoints**: `GET|POST /admin/brands`, `PATCH /admin/brands/:id`; `GET|POST /admin/collections` (`?brand_id=` filter, `brand_id` in the create body), `PATCH /admin/collections/:id` (name only); `GET|POST /admin/products` (`?brand_id=`), `GET|PATCH /admin/products/:id`; `POST /admin/products/:id/colourways`, `PATCH /admin/colourways/:id`. Admin reads are separate from the public catalogue ones because they include `id` and unhidden-only filtering does not apply (staff see `show_on_website = false` rows).
- **Slugs are server-generated on create and immutable after** — they are public storefront URLs and the EmDash brand-page match key, so a rename must not break links. `slugFrom` (exported from `admin-brands.js`) wraps `src/seed/slugify.js`: whitespace-only input makes slugify throw and punctuation-only returns `''`; both become **422**, never a 500 or an empty slug. Product slug follows the seed convention in `src/seed/catalogue-data.js` — fabric = `slugify(\`${brand.name} ${name}\`)` using the brand **name** (not its slug), finished good = `slugify(name)`.
- **`product_type` is immutable too** (the colourway's inventory `unit` was derived from it), and creates take no inline colourways — add them one at a time via the nested route.
- **SKUs are typed by staff, not generated.** The CRM's Brand-Product-Colour generator lives only in the demo app and was deliberately not ported; the API just enforces uniqueness. `sku` *is* editable via PATCH (typo fixes are safe — `order_lines` reference `colourway_id`, never the sku).
- **Duplicates are detected by the database, never pre-checked** (a pre-check races and would still need the handler): `rethrowConflict` maps pg `23505` to a **409** keyed on `error.constraint` (`brands_slug_key`, `collections_brand_id_slug_unique`, `products_slug_key`, `colourways_sku_key`; unknown constraint degrades the message, never the status).
- **Colourway create is the one transaction**: BEGIN → `SELECT product_type` (404 if the product is gone) → INSERT colourway → `INSERT INTO inventory (…) VALUES ($1, 0, 0, $2) ON CONFLICT (colourway_id) DO NOTHING` → COMMIT, unit from `UNIT_BY_PRODUCT_TYPE` (`fabric → metres`, `finished_good → units`). A duplicate SKU rolls the whole thing back, so a failed create leaves no orphan colourway. `hex_tones` must be `JSON.stringify`'d (same trap as the seed).
- `buildUpdate(input, columns)` builds every PATCH's SET clause from a **frozen in-code column whitelist** — column names are never user input, values are always `$n` placeholders. `Object.hasOwn` keeps an explicit `null` (clears `collection_id`) distinct from an absent key (leaves it alone).
- Status codes: 400 schema (incl. empty PATCH via `minProperties: 1`), 404 unknown `:id`, 409 duplicates, 422 business rules (unknown `brand_id`/`collection_id`, a collection belonging to another brand, unsluggable name).
- **Gotcha — `additionalProperties: false` does not reject unknown body keys.** Fastify's bundled Ajv runs `removeAdditional: true`, so extra keys are silently *stripped*, not 400'd (same family as the querystring note under Catalogue). Immutability still holds where it counts: on PATCH the stripped body becomes `{}` and `minProperties` produces the 400, and on create a client-supplied `slug` is discarded so the server's wins. Do not rely on schema strictness to reject a field — leave it out of the whitelist.
- Guarded by `test/admin-catalogue.test.js` (63 tests). Same rate-limit gotcha as admin orders: register the two users **once** in `beforeAll`; fixtures are namespaced `admin-cat-test-*` so cleanup deletes brands by slug prefix and cascades.

## Transactional email (US-015)

- `src/email/` is a self-contained module. `templates.js` — pure `renderTemplate(name, data) → { subject, text }` for the six lifecycle templates (`request_received`, `backoffice_new_request`, `checkout_receipt`, `order_confirmed`, `payment_received`, `shipped`); `TEMPLATE_NAMES` lists them; unknown name throws. Templates do no I/O, so they unit-test directly.
- `mailer.js` — `createMailer({ transport, from, backofficeEmail, log })` returns `{ send({ template, to, data }), backofficeEmail }`. **`send` never throws**: a delivery failure is logged and returned as `{ ok: false, error }` so a mail problem can't fail the API request that triggered it. Transport is injected (dependency-injection, same as Stripe/pool).
- `transport.js` — `createMailTransport(config)` builds a nodemailer transport: real SMTP when `SMTP_HOST` is set, otherwise **`jsonTransport`** (captures + serialises the message, sends nothing) so dev/test never send real mail. Tests inject their own capture transport (`{ sent: [], sendMail }`) — no nodemailer needed.
- `recipients.js` — `resolveOrderRecipient(db, { guest_email, user_id })`: guest email wins (no query); otherwise looks up `users.email`; null when neither. `db` may be a pool or an open client.
- `notifications.js` — the trigger layer. `notifyRequestReceived(mailer, { order, customerEmail })` (US-012: customer ack + back-office alert), `notifyCheckoutReceipt(mailer, db, order)` (US-011), `notifyOrderTransition(mailer, db, order)` (US-014: maps `order.status` `confirmed→order_confirmed` / `paid→payment_received` / `shipped→shipped`, any other status is a no-op). **Every helper is a no-op when `mailer` is null** and never throws.
- Wiring: `buildApp({ ..., mailer })` (default null) passes the mailer into `orderRoutes`, `adminOrderRoutes`, `webhookRoutes`. Triggers: `POST /orders/request` → `notifyRequestReceived`; webhook after a *fresh* paid order (`result.order` truthy, i.e. not a replay) → `notifyCheckoutReceipt`; admin `confirm`/`mark-paid`/`ship` handlers → `notifyOrderTransition` (NOT `patch`/`decline` — patch could keep status `confirmed` and re-send). `processStripeEvent` now returns `user_id`/`guest_email`/`total_cents` on `result.order` so the receipt needs no extra query.
- Config/env: `SMTP_HOST`/`SMTP_PORT`/`SMTP_SECURE`/`SMTP_USER`/`SMTP_PASS` (all optional), `EMAIL_FROM`, `BACKOFFICE_EMAIL` (non-secret defaults). `server.js` builds the transport+mailer; `buildApp` in tests gets `mailer` only when a test needs to observe sends (existing suites pass no mailer → null → no-op, unchanged).

## Admin panel (AdminJS)

- **The panel fails soft.** `buildApp` wraps the whole registration in try/catch: a failure logs and leaves `/panel` unmounted, but the JSON API keeps serving. It was unguarded once and took production down with a 502 on *every* route — the panel has boot-time failure modes the API does not share (missing adminjs deps after a deploy without `npm ci`, an unwritable cwd during `NODE_ENV=production` component bundling, `@adminjs/sql` throwing on any table without a primary key). A back-office screen must never be able to stop the shop. Guarded by `test/admin-panel.test.js` ("still serves the API when the panel fails to start"). `.adminjs/` is gitignored AND in the ESLint `ignores` — it is generated at boot and linting it fails.
- AdminJS v7 CRUD panel at **`/panel`** (`src/admin/panel.js`), enabled via `buildApp({ adminPanel: { databaseUrl, sessionSecret } })` — `server.js` always passes it; tests don't get it unless they opt in. The adminjs import tree is heavy (rollup/babel), so app.js loads it with a dynamic `import()` only when the option is set, inside an encapsulated register scope — its session/form-body/multipart parsers never touch the JSON API routes.
- **The prefix is `/panel`, deliberately not `/admin`** (`src/admin/paths.js` is the single source of truth). `/admin/*` is the JSON API the CRM's back-office screens call cross-origin, so the panel must be distinguishable from it by an exact prefix test — see the CORS note below.
- **Do not switch to `buildAuthenticatedRouter`** from `@adminjs/fastify`: it registers `@fastify/cookie` itself and collides with buildApp's registration (Fastify decorators are single-shot even across scopes → `FST_ERR_DEC_ALREADY_PRESENT`). `panel.js` recreates its small auth layer (session, guard preHandler, login/logout) on top of the public `buildRouter` export — the upstream handlers aren't deep-importable (exports map only exposes `.`).
- Login: HTML form at `/panel/login`, `src/admin/authenticate.js` — argon2 verify with dummy-hash timing guard (same posture as `/auth/login`), roles `backoffice`/`director` only, rate-limited 10/15 min. Sessions are `@fastify/session` with the **memory store** — a server restart logs everyone out (acceptable; re-login). Cookie `adminjs_session`, `path=/panel`, `secure: 'auto'` (production needs `TRUST_PROXY` set so the forwarded proto is seen, already required for rate limiting).
- Resources (`src/admin/resources.js`): brands/collections/products/colourways/inventory/shipping_rates/price_list_items/users editable; **orders, order_lines, webhook_events read-only** — the `/admin/orders` JSON API state machine owns them and raw edits would desync `qty_reserved`. `users`: `new` disabled (accounts only via register endpoints).
- `@adminjs/sql` introspects **all** tables at boot and throws if any lacks a primary key; it also opens its own knex pool — `panel.js` destroys it in an `onClose` hook (tests hang on open handles otherwise).
- Production: with `NODE_ENV=production` adminjs bundles user components at boot (writes `.adminjs/` in cwd — needs write perms); we have none, so `ADMIN_JS_SKIP_BUNDLE=true` is a valid opt-out. Guarded by `test/admin-panel.test.js`.

### Panel security invariants (each one fixed a confirmed exploit — do not regress)

- **Guard matches paths exactly, never by regex/substring.** `registerSessionGuard` compares `url.split('?')[0]` against an exact set of public asset paths. It previously used upstream's `request.url.match(assetPath)` — an *unanchored regex over path+query*, so `?x=/frontend/assets/icomoon.css` on any panel URL skipped auth entirely (unauthenticated read of every user's `password_hash`, and an unauthenticated `role=director` self-promotion). The same bug is still live upstream in `@adminjs/fastify`'s `withProtectedRoutesHandler` — do not copy it back.
- **Session id is regenerated on login.** `await request.session.regenerate()` runs before `session.set('adminUser', …)`, so a pre-auth session id can never become an authenticated one. Read `redirectTo` *before* regenerating — regenerate swaps in a fresh session and drops it. (Hence `redirectTo` is stored via `session.set`, not as a loose property.)
- **`password_hash` is stripped at the query layer** (`src/admin/redacted-resource.js`), not merely `isVisible: false`. AdminJS's `isVisible` is a UI flag only — `BaseRecord.toJSON` serialises `params` verbatim, so a "hidden" column still ships in every list/show JSON payload. `RedactedSqlResource` narrows the SELECT and strips hidden columns from create/update. `count()` is deliberately left alone (narrowing its select would produce an invalid non-grouped aggregate).
- **CORS never covers the panel.** `@fastify/cors` is a fastify-plugin, so it **hoists to the root instance** — registering it in a child scope does *not* keep it off the panel (verified). app.js therefore uses a `delegator` that returns `{ origin: false }` for `isAdminPanelPath(request.url)`. Without this, any script on the storefront origin could read and drive the panel with a logged-in staff cookie. The delegator also covers the CORS-registered wildcard `OPTIONS *` route, which a route-membership check could not.
- **Panel session cookie uses a separate signing key** (`src/admin/session-secret.js`): HMAC-derived from `COOKIE_SECRET`, or `ADMIN_SESSION_SECRET` when set. `@fastify/session` and `@fastify/cookie` both default to HMAC-SHA256, so sharing a key means a value signed for one verifies under the other.
- **Origin guard stands in for CSRF tokens.** AdminJS's React frontend can't carry a token we mint, so `registerOriginGuard` (onRequest) rejects state-changing methods — and `GET /panel/logout` — when `Sec-Fetch-Site` is anything but `same-origin`/`none`, or `Origin` doesn't match `Host`. `same-site` is treated as cross-origin (a sibling subdomain is a different origin). Host comparison **normalises both sides under the origin's scheme** so an explicit default port still matches, and compares host only, not scheme — behind a TLS-terminating proxy without `TRUST_PROXY` the request looks like http while the browser reports https, and rejecting that would block every write. A missing `Origin` is allowed (same-origin navigations and non-browser clients omit it; browsers always send it on cross-origin writes). `test/admin-panel.test.js` guards both directions — the foreign origin is rejected *and* a same-origin write still succeeds.
- Known-vulnerable transitive deps ship with the adminjs frontend bundle (`@tiptap/extension-link` XSS, `react-router`, `i18next-http-backend`). No `richtext` property is configured, so the tiptap surface isn't reachable, and `npm audit fix --force` only offers a breaking downgrade to `adminjs@6` — track upstream for a patched `adminjs@7.x` instead.
