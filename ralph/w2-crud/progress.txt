- **The MAY-touch list is a collision guard, not a scope definition.** Its purpose is that two
  concurrent workstreams never edit the same lines. A file no epic owns (here `src/routes/contact.js`
  and `test/contact.test.js`) carries no collision risk, so the epic's own story table — which is
  what assigns the work — wins over the list's silence. The MUST-NOT-touch list is the real fence and
  it is explicit about who owns what; treat an omission there as permission and an entry there as a
  wall. Epic 2's "Owns these files" line says "other Wave 2 epics must not touch them" — a protection
  list, not an exhaustive statement of W2's surface.
- **Check `git log --oneline` the moment the worktree behaves oddly — two iterations can be live in
  it at once.** It happened on US-004: a second run committed the story while this one was writing
  it. The tells are all cheap to spot and all mean the same thing — an `Edit` refused with "File has
  been modified since read" on a file you had not touched, a path *disappearing* from `git status`
  mid-task (it was committed underneath you), `prd.json` already reading `passes: true` with a
  timestamp you did not write. When it happens: do NOT `git checkout -- <file>` anything you did not
  personally write (it discards their in-flight work), stage by explicit pathspec rather than `-A`,
  and gate the commit on the single test file you touched — a full-suite result is uninterpretable
  while someone else has source files open.
- **A row mapper that grows a second `extra` argument breaks every `rows.map(toX)` call site**, and
  breaks it silently: `map` passes the index as the second argument and `{ ...1 }` is `{}`, so the
  output is accidentally correct today and wrong the moment `extra` is used for anything a number
  could satisfy. `toProduct(row, extra)` in `admin-products.js` was already the house pattern for a
  detail read that adds children/counts to a list shape; when copying it, convert the sibling call
  sites to `rows.map((row) => toX(row))` in the same edit. Only `src/catalogue/admin-brands.js` was
  affected — `brands.js`/`collections.js` (W7's) have their own local mappers.
- **A single-row admin read never filters on `archived_at`.** `getAdminProduct` does not, and the
  restore screen is why: the row a caller asks for by id is one they already know exists, and a 404
  there reads as "someone deleted it" rather than "it is archived". Filtering belongs on the LIST
  (`include_archived`), never on the by-id read. The same applies to the children a detail read
  embeds — `getAdminProduct` returns every colourway, archived included, each carrying its own
  `archived_at` for the screen to style.
- **A paginated admin list is a settled shape — copy it, do not redesign it.** Module exports
  `DEFAULT_PAGE`/`DEFAULT_LIMIT`/`MAX_LIMIT` and a `list…` returning `{ items, total }`; the route
  imports the three constants, spends them as schema `default`/`maximum`, and builds the envelope
  `{ <plural>: items, meta: { total, page, limit } }`. `MAX_LIMIT` as the schema `maximum` is what
  makes an over-large `limit` a 400 rather than a silent clamp. The CRM's `readList(body, key)`
  takes the array's key as an argument precisely because this API has no single one, so `items` vs
  `colourways` is a free choice — match the sibling routes in the same file.
- **A LIST filters `archived_at`; a by-id read never does.** The two halves of the same rule: the
  list hides archived rows behind `include_archived`, and the detail read returns them, because the
  restore screen reads a row back after archiving it. What a list must NOT do is filter on a
  *parent's* archive flag — archiving a product does not archive its colourways, so a list that
  hid them would disagree with the product detail (which returns every child) about which rows
  exist.
- **A standalone list of a child entity has to carry its parents' names, or the screen is unusable.**
  A colourway row is a SKU, a colour name and an id; nothing on it says which design or house it
  belongs to, and the entire point of browsing it outside its parent is not knowing that already.
  The pattern is a second `…_CONTEXT_COLUMNS` + `…_CONTEXT_FROM` pair beside the narrow select, fed
  to the mapper's `extra` argument — so the rows embedded in a parent's detail read keep the narrow
  shape (they already sit under their parent) and only the standalone reads pay for the joins.
- **A PATCH with exactly ONE editable column takes `required`, not `minProperties: 1`.** The house
  PATCH shape (whitelist + `minProperties: 1` + `buildUpdate`) exists to pick some-of-many; with one
  column there is nothing to pick, and the two rules answer differently when Ajv's
  `removeAdditional` strips the immutable keys a client sent. `{ zone, threshold_qty }` becomes `{}`,
  which `minProperties` was evaluated BEFORE the strip and therefore lets through — the handler then
  builds an empty SET clause, which is invalid SQL. `required: ['rate_cents']` makes that same body a
  400. Write the UPDATE inline too: a one-column `buildUpdate` call is indirection over a literal.
- **The identity key of a row is not always its id.** `shipping_rates` is addressed by `id` for PATCH
  and DELETE but keyed on `(zone, threshold_qty)` — the quote resolves against the pair and the seed
  upserts on it — so moving either column is a delete plus a create, never an edit. When a table has
  both, the id belongs in the read projection (nothing else can address a row for a single-row
  write) and the key columns belong out of every PATCH whitelist. Assert the strip explicitly: a
  PATCH body carrying the key must come back with the key unchanged.
- **A single-row POST beside a bulk PUT must 409 rather than upsert.** The bulk path is "make this
  table so" and upserting is its whole point; a create is a statement that the row is new, so a
  collision is a mistyped key, and silently overwriting a live row hides it. Same table, two write
  paths, deliberately different conflict behaviour.
- **A fixture is only namespaced by its SKU/slug/email, never by its human-readable name — so
  search for it by the namespaced value.** The test database holds the seeded catalogue as well as
  the fixtures, and a colour or design name is exactly the kind of word the real catalogue also
  uses: `?q=Jade` returned the fixture plus two seeded rows, while `?q=Velvet` in the same file
  happens to be unique today and will stop being so the moment the colour files land. Assert on
  `q=<the prefixed SKU>`, or on `.toContain`, never on an exact array of everything a display name
  matches. Same family as US-006's rule about an unfiltered `meta.total`.
- **A value the API derives rather than accepts must be derived from ONE exported map.** `unit` is
  computed by `unitFor` in `src/catalogue/admin-products.js` and now imported by the inventory
  admin instead of being copied; two maps would eventually disagree about a colourway created
  through one path and re-stocked through the other, and the disagreement would be a silently
  redenominated quantity rather than an error. Export the helper (which carries the 422), not the
  object.
- **A mid-transaction race is reproducible deterministically by wrapping the pool, not by timing.**
  `deleteOrExplain` only uses `connect()`/`query()`/`release()`, so `{ connect: async () => ({
  query, release }) }` around a real client can run arbitrary work on another connection when a
  chosen statement is about to execute. That is how the 23503 backstop gets exercised against the
  real database instead of a stub that just throws the error code. Applies to any check-then-write
  in this codebase.
- **`useCrudScreen` replaces a CRM screen's list fetch, its `status`/`loadError` pair and its
  `useToast` — but NOT its `useMutation` when the screen holds a SECOND list.** The kit binds
  `mutation` to *its* list's reload, so a screen like AdminBrands (houses + collections) or
  AdminProducts (list + an expanded detail read) builds a combined `reload` and calls `useMutation`
  itself with `crud.toast.flash`, leaving `crud.mutation` unused. Everything else comes from the
  kit: `crud.list.rows/status/error/total`, `crud.remove.ask(row)` on the button, and
  `<ConfirmDialog {...crud.remove.dialog} />` at the foot of the screen. A screen must not import
  `apiDelete`, `attemptDelete`, `describeBlockers` or `deleteDialog`.
- **The dialog's "Archive instead" ALWAYS archives; it is not the row's Archive/Restore toggle.**
  It appears only on a *refused* delete, so pointing it at the toggle would answer the refusal by
  restoring an already-archived row — putting it back on the website in response to a request to
  remove it. Keep them as two functions (`archiveTogglePath` / `archiveInsteadPath`), not one with
  a flag. And `useCrudScreen` shows the button only when `archive !== null` AND the API said
  `archivable`, so an archivable entity whose screen forgets the option renders a Cancel-only 409.
- **An unpaged admin endpoint must be given a limit ABOVE its row count, never the kit's default
  25.** `/admin/brands` and `/admin/products` return the whole list with no `meta` (`readList`
  falls back to the row count) and declare no `page` param, which Fastify's Ajv silently strips
  rather than rejecting — so a `totalPages` of 2 would advertise a page that can never be fetched.
  Check whether the endpoint actually pages before wiring a screen: `meta` in the envelope is the
  tell, and `MAX_LIMIT` in the module is the second.
- **With no jsdom, an acceptance criterion about how a SCREEN is composed is provable only by
  reading the file.** "Uses `useCrudScreen`", "adds no bespoke dialog or paginator" and "does not
  re-implement the flow" are all `readFileSync(new URL('./Screen.jsx', import.meta.url))` plus
  `toContain`/`not.toContain` — the idiom `src/admin/useCrudScreen.test.js` already uses on the kit.
  It is the only test of a `.jsx` this repo can have, and it costs nothing.
- **Only the permanent verb is drawn `tone="danger"`.** Archive was red while it was the most
  destructive thing on a row; with a real Delete beside it, two red buttons claim the reversible
  action is as grave as the irreversible one. Archive/Restore becomes neutral on every screen that
  gains a Delete.
- **A CRM screen holding a SECOND list is usually a screen that has not been written yet.** The
  tell is exactly the workaround `useCrudScreen` forces: a combined `reload` and a hand-rolled
  `useMutation`, because the kit binds `mutation` to *its* list. AdminBrands carried collections
  that way; splitting them out gave them a filter, a create form, a Delete and a detail read, and
  left AdminBrands taking `crud.mutation` straight from the kit. Read the "second list keeps its own
  useMutation" rule as a description of a debt, not a pattern to copy.
- **A child whose key is unique per PARENT must never be identified by that key once it is listed
  across all parents.** A collection slug is unique per house (`collections_brand_id_slug_unique`),
  and so is its display name in practice — the seed strips the house prefix off the vendored titles,
  so a catalogue-wide list genuinely shows several "Cappuccino"s. React keys and every path stay on
  `id`, the parent becomes a column, and anything naming a row to a person names the parent with it
  (`describeCollection` → `Cappuccino (Pierre Frey)`), because the delete dialog's "Delete
  “Cappuccino”?" is otherwise a question three houses can answer. Same rule for any future
  cross-parent list of a per-parent-unique child.
- **A filter another screen LINKS INTO belongs in the URL, not in `useState`.** `useSearchParams` is
  the whole implementation (`const brandFilter = searchParams.get('brand_id') ?? ''`), and it fixes
  two things state cannot: a link clicked while the target screen is already mounted does not
  remount it, so state would silently ignore it; and the back button would not undo the filter. The
  kit needs no change — `filters` is rebuilt each render and `useAdminList` keys on the serialised
  query.
- **A source-scan assertion must not match the file's own prose.** `expect(source).not.toContain(
  'useMutation')` failed on a comment *explaining* when a screen calls `useMutation` — the scan sees
  comments. Assert the positive (`toContain('crud.mutation')`) where the negative would be tripped by
  a sentence, and keep negative scans to symbols a screen would never merely discuss. The general
  form: scan for the **token a screen could only have by doing the thing** — a path fragment
  (`'/archive'`), an import name, a call shape — never for the English word, which the file has to
  be free to use while explaining itself.
- **A screen whose entity is NOT archivable passes `useCrudScreen` no `archive` option, and that is
  the entire handling.** `shipping_rates` and `inventory` have no `archived_at` column, so the API's
  refusal carries `archivable: false`; the kit requires that AND a supplied action, so a Cancel-only
  409 dialog is already the right rendering. There is nothing to branch on, and the only mistake
  available is inventing a second button for an endpoint that does not exist. Read it as the mirror
  of US-009's rule (an archivable entity whose screen forgets the option renders a Cancel-only 409
  *wrongly*): the same dialog is correct here and a bug there, and which one it is comes from the
  entity, not the screen.
- **An advance warning derived from rows already on screen is not the forbidden pre-flight.** The kit
  bans a second "can I delete this" GET because it races the delete and the 409 is authoritative — it
  does not ban reading what the list already returned. Grouping the loaded tiers to mark a zone's
  only tier, or reading a `product_count` off a detail the screen already holds, costs no request
  and is the only warning staff get before a refusal.
- **Check the read model's projection before trusting `useCrudScreen`'s default delete path.** It is
  `` `${path}/${row.id}` ``, and `inventory` has no `id` in its public shape — one row per colourway,
  every caller addresses it by colourway — so the default builds
  `DELETE /admin/inventory/undefined`. That is what the `deletePath` option is for, and the same
  question applies to any entity whose URL key is not its primary key.
- **Deleting the row a list is keyed on removes the way back to it, so the create has to ship in the
  same story.** A colourway whose stock row is deleted vanishes from `GET /admin/inventory`
  altogether; a screen that only lists inventory can never show it again. The fix is a second
  endpoint that still sees the row — `GET /admin/colourways` reports `inventory: null` for exactly
  those — not a cleverer query against the list's own. Ask "what does this list stop showing after a
  successful delete" before wiring one.
- **A screen composing the kit may override a `remove.dialog` prop after spreading it; that is
  composition, not re-implementation.** `useCrudScreen` discards a delete's response body, so an API
  that qualifies its own success (`DELETE /admin/price-list-items/:id` returns a `warning` saying the
  next import re-creates the row) cannot reach the toast — and a caveat that lands after the deletion
  is not a caveat. Rewrite the **ask** step's body instead, keyed on `confirmLabel`: it is `'Delete'`
  while the dialog is still asking and `null` once the API has refused, and a refusal's body is the
  API's own sentence, which must never be overwritten. Re-implementing `deleteDialog` would be the
  violation; passing a later prop is not.
- **The dialog's name for a row must identify it across the WHOLE list it appears in.** The general
  form of US-010's collection rule: a key unique within a parent, or within an identity tuple, names
  several rows once the list spans all of them. A price-list `code` is unique only within
  `(supplier, category)`, so `describeRate` leads with the supplier; an account is named by `email`
  (unique by constraint) and never by `name` (nullable, freely duplicated). Ask what the row's real
  uniqueness constraint is, not what looks like a name.
- **A control bound to server truth needs no revert when its write fails.** `useMutation`
  deliberately does not reload on error, and once a list belongs to `useAdminList` a `<select
  value={row.role}>` re-renders from the unchanged row by itself — so the `load()`-to-undo that a
  hand-rolled screen needed becomes dead weight. The rule only holds while the control reads the row
  rather than a draft; an editor holding a draft still has to re-seed it.
- **A negative source scan for "this screen does X nowhere" must name the one token that opens X.**
  `not.toContain('Delete')` and `not.toContain('ConfirmDialog')` both fail against a header comment
  explaining *why* a screen has neither. `remove.ask` is the only entry point into the kit's delete
  flow, so its absence is the criterion; `'<ConfirmDialog'` (with the angle bracket) is the rendered
  form the prose cannot accidentally contain. Third instance of the same trap — see US-010's
  `useMutation` and US-011's `/archive`.

  and the row holds the Xero reference and the Stripe session id), so there is no endpoint to wire.
  The screen takes `list`, `toast` and `mutation` and renders no `<ConfirmDialog>` and no Delete
  button. Its Archive stays `tone="danger"` — alone among the live screens, and by the same rule
  rather than as an exception: only the most permanent verb on a row is red, and on an order archive
  is it.
- **What the 42 new tests assert:** `pageCount(866, UNPAGED_LIST_LIMIT) === 1` against
  `pageCount(866, 25) === 35`, and `RATE_LIST_LIMIT` inside the endpoint's `MAX_LIMIT` of 200; each
  filter builder through `buildListQuery` (an unset filter never becoming `status=` / `role=`, which
  the enums answer with a list-killing 400); `stockDeletePath` addressing by colourway **with an
  explicit assertion that the row has no `id`**; `describeRate` telling two suppliers' rows with the
  same code apart, and `describeAccount` preferring email over name; `needsStockRow` separating "no
  row" from "a row at zero"; `withDeleteCaveat` rewriting the ask, leaving a refusal untouched and
  mutating nothing. Then the source scans: all five screens contain `useCrudScreen` and
  `<Pagination`; the four delete screens contain `remove.ask` and `<ConfirmDialog` and none of
  `apiDelete`/`attemptDelete`/`describeBlockers`/`deleteDialog`/`role="dialog"`; none of the five
  keeps `useToast`, `loadError` or `useState('loading')`; AdminOrders has no `remove.ask`, no
  `<ConfirmDialog` and no rendered `Delete` label, and still has `/archive`; AdminStock has no
  `/archive` (not archivable) and does have `stockDeletePath`; and all five former paginator screens
  contain `<Pagination` and neither `Math.ceil(` nor `Previous`.
- **Learnings:**
  - Patterns: check the read model's projection before trusting the kit's default delete path; a
    delete removes the way back to its own row, so the create ships with it; overriding a
    `remove.dialog` prop after spreading is composition; a dialog name must be unique across the
    whole list; a control bound to server truth needs no revert; a negative source scan must name
    the one token that opens the behaviour. All six promoted to `## Codebase Patterns` above.
  - Gotcha: `clientAccountsQuery` returned a **querystring** and `useAdminList` wants a **filters
    object**, so it became `clientAccountsFilters` and its seven tests now assert through
    `buildListQuery`. Any screen-local query builder written before W1 landed has the same shape
    mismatch; converting it is the conversion.
  - Gotcha: `useMutation` does not reload on failure, which is correct and was previously papered
    over. `UserManagement` called `load()` to revert a refused PATCH; with the row owned by the hook
    the `<select>` reverts by itself, and the extra reload was hiding the fact that the control was
    already bound to server truth.
  - Gotcha: the drafts effect on AdminStock must key on `crud.list.rows`, which `useAdminList` holds
    in state — a stable identity between renders. Keyed on anything rebuilt per render it would
    loop, and with no jsdom nothing in this repo would catch it.
  - Gotcha: `readList` falls back to the row count when there is no `meta`, so `crud.list.total` is
    the right source for every "N shown" counter — including on the three unpaged endpoints, where
    it equals `rows.length` by construction.
  - Context: the new pure half is `src/screens/adminLists.js` (beside `adminCatalogue.js`,
    `adminShipping.js` and `clientAccounts.js`); the kit it composes is `src/admin/useCrudScreen.js`,
    `useAdminList.js`, `list.js`, `Pagination.jsx`, `ConfirmDialog.jsx` and `deleteFlow.js`. The
    API routes behind the deletes are `DELETE /admin/inventory/:colourwayId` (US-008),
    `/admin/price-list-items/:id` (US-003) and `/admin/users/:id` (US-004); `POST /admin/inventory`
    and `GET /admin/colourways` (US-006) are what the restock panel calls.
