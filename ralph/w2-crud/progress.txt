- **W1 IS on this branch now** (api `2b75fae`/`560c13b`, crm `74fd824`), superseding the three
  BLOCKED entries below — they were written before the merge and are kept as the audit trail, not
  as current fact. `atelier-api/src/lifecycle/` (`registry.js`, `delete.js`, `archive.js`) and
  `atelier-crm/src/admin/` (`list.js`, `useAdminList.js`, `Pagination.jsx`, `ConfirmDialog.jsx`,
  `deleteFlow.js`, `useCrudScreen.js`) all exist, and `src/lib/api.js` has `apiDelete`. A human
  cleared the `BLOCKED:` prefixes in prd.json in the same commit, so US-001..003 are live again.
- **The registry already carries every W2 entity.** `LIFECYCLE_ENTITIES` in
  `src/lifecycle/registry.js` ships entries for brand, collection, product, colourway, inventory,
  price_list_item, user, shipping_rate, contact_enquiry and order — with the probes, guards and
  `archivable` flags architecture.md § *Delete policy* specifies. So a W2 delete story is **routes
  and tests only**: two `app.delete` handlers piping `deleteOrExplain` into `replyDelete`. Do not
  add a registry entry (the file is W1's), and check what is already there before scoping the work
  — epics.md's "Registry entries + DELETE routes" line overstates what is left to do.
- Story pick order is by `priority`, so a blocked low-priority story does not stop the loop — it is
  marked BLOCKED and the next iteration moves down the list.
- **A story's file footprint is the ROUTE file plus the DOMAIN module it calls.** `src/routes/*` is
  thin by house rule, so the logic always lands in `src/<domain>/`. Owning `admin-price-lists.js`
  the route says nothing about `src/pricing/admin-price-lists.js` the module. Check both against the
  MAY-touch list before starting, and check each entity separately when a story names two.
- **Re-verify a shared blocker; do not inherit it from this log.** A previous entry recording
  "dependency absent" is a statement about the branch at that moment, and another workstream can
  land it in between. Two commands settle it in seconds — `ls atelier-api/src` for `lifecycle/`,
  `ls atelier-crm/src/admin` for the CRUD kit — and they are cheaper than either blocking a story
  that has become implementable or building on one that has not arrived. This is exactly what
  happened: three stories were blocked on a dependency that landed the same day.
- **The DELETE route shape, once, for every remaining delete story.** Handler is a one-liner:
  `async (request, reply) => replyDelete(reply, await deleteOrExplain(pool, '<entity>',
  request.params.id, { user: request.user }))`, with `{ preHandler: backoffice, schema: { params:
  idParamsSchema } }`. Three fixed points: the entity name must be a **single-quoted literal**
  (`test/lifecycle-registry.test.js` scans `src/` and fails on an expression — the registry is not
  an authorisation boundary, so a `:entity` param would let a client pick the table); `ctx.user`
  comes from `request.user`, which the role guard has already loaded; and the result is *returned*,
  never thrown, because Fastify's error serializer drops `blockers` off a thrown error.
- **CORS already lists DELETE** (`allowedMethods` in `src/app.js`, guarded by `test/cors.test.js`).
  A new DELETE route needs no CORS change — but note the preflight is the only place this is
  provable; `app.inject()` does not preflight.
- **`sprint-status.yaml` can lag prd.json.** Story pick reads prd.json only, so a stale `blocked`
  in the yaml does not stall the loop; fix your own story's line and leave the others.
- **A test fixture that reaches commerce must be cleaned up before its brand.** `cleanupFixtures`
  in `test/admin-catalogue.test.js` deletes brands by slug prefix and relies on CASCADE; the one
  RESTRICT edge in the schema (`order_lines.colourway_id`) stops that cascade dead, so an order
  fixture makes the *cleanup itself* raise 23503 in the NEXT test's `beforeEach`. Delete orders by
  order-number prefix first (their lines cascade). Same rule for any future fixture that inserts
  into `orders`.
- **A mid-transaction race is reproducible deterministically by wrapping the pool, not by timing.**
  `deleteOrExplain` only uses `connect()`/`query()`/`release()`, so `{ connect: async () => ({
  query, release }) }` around a real client can run arbitrary work on another connection when a
  chosen statement is about to execute. That is how the 23503 backstop gets exercised against the
  real database instead of a stub that just throws the error code. Applies to any check-then-write
  in this codebase.

- **What the tests actually assert**, against the acceptance criteria:
  - *Order lines block with a named count.* A product whose colourway carries an order line comes
    back 409 with `{ relation: 'order_lines', label: 'order lines', count: 1, capped: false }`, and
    both the product and the colourway still exist. The probe reaches the grandchild through the
    colourway — nothing about the product row itself says it has been sold.

    reads "colourways holding stock", the colourway-level one "units of stock on hand"; those labels
    are W1's and the CRM will render them verbatim.
  - *Colourways and zero-quantity inventory cascade as owned children.* Deleting a never-sold
    product returns 200 and its colourway and stock row are gone; its house is untouched. Deleting a
    colourway takes its stock row and leaves the product.
  - *The 23503 backstop produces the same 409 shape.* See the note below — this one is the reason
    the story is more than a copy of US-001.
  - Plus 401 anonymous, 403 customer (row still present in both), 404 unknown id with `blockers: []`.
- **The backstop test is a real race, not a stubbed error code.** The probes cover `order_lines` for
  both entities, so no ordinary request can reach the 23503 path — the only way in is the grandchild
  window delete.js documents: the transaction locks the PRODUCT, so an order line inserted against
  one of its existing colourways after the probes have run is not stopped by anything. The test
  reproduces that deterministically by passing `deleteOrExplain` a pool wrapper whose `query` runs
  the insert on a second connection when the statement is about to be `DELETE FROM products`.
  Postgres serialises the insert against the cascade's delete of the colourway, the RESTRICT edge
  fires, and the catch re-answers it as a 409. The test then runs the ordinary probe path over the
  same product and asserts `Object.keys` equality plus `probed.message === backstop.message` modulo
  `1+` vs `1` — which is what "the same 409 shape" means, rather than two hand-written expectations
  that could drift apart.
- **Learnings:**
  - Pattern: the pool-wrapper technique for reproducing a mid-transaction race, and the
    delete-orders-before-brands cleanup rule — both promoted to `## Codebase Patterns` above.
  - Gotcha: "samples" appears in this story's first acceptance criterion, and **there is no samples
    table** — no migration creates one (E4 US-001 does, and is `pending`), and W1's registry
    entries for product and colourway carry no samples probe. Nothing was stubbed for it: a probe
    against a non-existent relation would fail the registry's `information_schema` safety test.
    Whoever lands E4 must add that probe to the two registry entries and a test here; until then the
    criterion is unmeetable, not unmet.
  - Gotcha: `constraintBlockers` reports `count: 1, capped: true` — a "1+", because pg says a row
    exists and nothing about how many. A CRM dialog that renders `count` without honouring `capped`
    will tell staff there is exactly one order line when there may be a hundred.
  - Gotcha: the delete of an order line's colourway is refused, but the delete of its ORDER is not
    gated here at all — `orders` is `deletable: false` in the registry and cleanup relies on the
    order cascade taking its lines. That is why the fixture cleanup works and why no test tries to
    delete a colourway by deleting its order first.
  - Context: the probe bodies for both entities are `src/lifecycle/registry.js` lines ~208-254; the
    23503 mapping is `CONSTRAINT_BLOCKERS` in `src/lifecycle/delete.js`, keyed on
    `order_lines_colourway_id_fkey` — the only RESTRICT edge in the schema
    (`migrations/1784603440195_users-orders-shipping-schema.js`).
- **Needs human verification:** none for this story on its own — no screen calls these yet. Carry
  forward to W2-US-009 (AdminProducts wiring): a real cross-origin DELETE preflight from the CRM at
  :5273, which `app.inject()` cannot prove, and the 409 dialog rendering both blocker labels
  ("colourways holding stock" / "units of stock on hand") and the `capped` "+" suffix.
