# Ralph progress log — Atelier — August 6th updates — W3 Suppliers

## Codebase Patterns

General, reusable findings only. A Ralph iteration reads this block FIRST, before anything else.
Story-specific detail belongs in the per-story entries below, not here.

- **Migration timestamps**: latest pre-W3 migration is `1786248000000_trade-accounts.js`. W3 starts at
  `1786334400000` and steps by 86400000 per story, so concurrent workstreams do not collide on a name.
- **`npm run migrate` twice is the no-op proof**: the second run prints "No migrations to run!". The
  programmatic runner (`runner({ databaseUrl, dir: 'migrations', direction: 'up', migrationsTable:
  'pgmigrations', log: () => {} })`) returns `[]` — that is the assertion every schema test makes.
- **Migration test template** is `test/schema.test.js` / `test/commerce-schema.test.js`: run migrations in
  `beforeAll`, `createPool`, assert `information_schema.tables`, assert the re-run is `[]`, then one
  `rejects.toThrow(/<constraint_name>/)` per invariant. Constraint names are what the assertions match, so
  they are part of the contract (`suppliers_name_key`, `suppliers_discount_method_check`).
- **Partial-index house style**: archivable tables get `<table>_archived_at_live_idx` with
  `where: 'archived_at IS NULL'`; an optional-but-unique column gets `unique: true` +
  `where: '<col> IS NOT NULL'` so NULLs stay repeatable.
- **Fixture cleanup order is FK order.** Delete `price_list_items` (SET NULL) and `brands` (RESTRICT)
  before `suppliers`, or the supplier delete 23503s inside cleanup and every later test sees leftovers.
- **`brands` is served to anonymous visitors** — a schema test asserting no `brands` column matches
  `/wholesale|landed|duty|freight|cost|margin|markup|discount|credit_limit|payment_terms/` is cheap and is
  the same vocabulary `test/price-list-exposure.test.js` polices at the response layer.
- **Any `brands` fixture needs `trade_only = false`**, including one created purely to exercise an FK —
  the column is `NOT NULL DEFAULT true`.
- **pg parses `numeric[]` into JS NUMBERS but a scalar `numeric` into a STRING.** The house rule
  "coerce numeric with `Number()`" is about the scalar case only; an array column arrives already
  numeric, so a test asserting `['0.4000']` fails against `[0.4]`. Code that reads both shapes must
  coerce defensively rather than assume either.
- **A CHECK constraint cannot contain a subquery**, so per-element validation of an array column is
  impossible in SQL. What IS expressible is an ordinary immutable function call —
  `array_position(col, NULL) IS NULL` catches a NULL element (which would otherwise null the whole
  computed result). Element ranges have to be enforced in the module that reads them.
- **A "must be exactly one of these two columns" invariant is a plain CHECK**, e.g.
  `a IS NULL OR cardinality(b) = 0`. Cheaper and more durable than a precedence rule each reader
  re-implements, and it fails at write time where the typo is.
- **An inline column `check:` is auto-named `<table>_<column>_check` by Postgres**, whether it is
  written in a `createTable` column or an `addColumns` one — node-pg-migrate emits an unnamed
  `CHECK (...)` and the server names it. So a `rejects.toThrow(/<table>_<column>_check/)` assertion
  works without an explicit `addConstraint`, and `pg_get_constraintdef(oid)` finds it by that name.
- **Two tables that must share a vocabulary should be asserted against EACH OTHER, not against a
  literal.** `pg_get_constraintdef` renders an IN list as `= ANY (ARRAY['x'::text, …])`, so the
  allowed values parse straight back out with `/'([^']+)'::text/g`. A drift between two such CHECKs
  never throws — it just stops matching — so nothing else would catch it.
- **Adding a column to a read model's whitelist is INERT unless the route's schema also lists it.**
  Fastify's Ajv runs `removeAdditional: true`, so a key absent from the route's `properties` is
  stripped from the body/querystring before the handler sees it. `FILTER_COLUMNS`
  (`src/catalogue/products.js`) and `PRODUCT_UPDATE_COLUMNS` (`src/catalogue/admin-products.js`)
  are each gated by a schema in a route file — `src/routes/catalogue.js` and
  `src/routes/admin-catalogue.js` respectively. Both edits are needed or neither is worth making.
- **The admin module template is `src/pricing/admin-price-lists.js`**, and every back-office read
  model in this repo is the same five parts: `DEFAULT_PAGE`/`DEFAULT_LIMIT`/`MAX_LIMIT`, a private
  `httpError`, a `rethrowConflict` keyed on `error.constraint`, a frozen `*_UPDATE_COLUMNS` fed to
  `buildUpdate`, and a `to<Entity>` mapper returning a frozen object. The list returns
  `{ <plural>, total }` — the ROUTE builds the meta envelope, never the module.
- **A local `escapeLike` is duplicated per module on purpose** (`admin-users.js`,
  `admin-price-lists.js`, and now `admin-suppliers.js`). It always pairs with an explicit
  `ESCAPE '\'` in the SQL — the clause is not optional, and the term is otherwise a wildcard.
- **`Number(null)` is 0, which reads as "free" for any rate column.** Every nullable numeric a read
  model coerces needs `value == null ? null : Number(value)`; the blanket "coerce with `Number()`"
  rule silently turns "no discount recorded" into "100% off".
- **An exposure test asserts BOTH directions or it rots.** A suite that only asserts a field is
  absent from `/catalogue/*` keeps passing after the admin read model quietly stops returning it.
  Pair every absence assertion with one that the back-office model DOES carry the field, and scan
  the raw response BODY for the fixture's secret values as well as its keys — a renamed column
  passes a key scan while still shipping the value.
- **Use the bare table name, not an alias, when a query needs a correlated EXISTS.** An unqualified
  `*_COLUMNS` projection constant is only valid while the statement has no alias, so
  `FROM suppliers ... WHERE supplier_aliases.supplier_id = suppliers.id` keeps one constant usable
  in the SELECT, the INSERT RETURNING and the UPDATE RETURNING alike.
- **`test/suppliers-terms.test.js`'s source scan is a plain `source.includes(table)`, so a COMMENT
  naming `supplier_brand_terms` outside `src/suppliers/` fails it** — the scan cannot tell prose
  from a join. Describe those tables by role ("the per-brand commercial terms") anywhere else.
- **Fastify validates the body BEFORE the preHandler runs**, so a guard test that posts a body the
  schema rejects gets a 400 and proves nothing about the guard. Send a valid body where the route
  takes one and none where it does not; `app.inject` with a payload on GET/DELETE is also its own
  hazard (an empty JSON body is `FST_ERR_CTP_EMPTY_JSON_BODY`).
- **A route-level enum duplicating a database CHECK is the house pattern** (`CATEGORY_ENUM` in
  `admin-price-lists.js`), because without it a bad value reaches the CHECK and a 23514 surfaces as
  a 500 rather than a 400. Export the enum and assert it against the live `pg_get_constraintdef`,
  or the boundary copy and the database drift with nothing raising.
- **A DELETE refusal is a RETURN VALUE, and the route must pipe it through `replyDelete`.** Fastify's
  error serializer emits `{ statusCode, error, message }` and drops every custom property, so a
  thrown error cannot carry `blockers` or `archivable` — the two fields the CRM dialog needs.
- **A registry probe is needed most where the FK is SET NULL, not where it is RESTRICT.** RESTRICT at
  least refuses; SET NULL succeeds, reports 200 and silently unlinks every child. Both edges out of
  a new entity need a probe, and the SET NULL one is the load-bearing half.
- **Split any backfill/import into a PURE planner and a thin apply layer, and make its sources
  injectable.** The planner takes the sources plus whatever the database already holds and emits
  desired state keyed by NAME; the apply layer resolves names to ids. That is what lets the
  real-corpus assertions run with zero writes to the SHARED test database, while the SQL is
  exercised against small prefixed fixtures with an injected source — without it a test run
  creates the real production rows and every later suite sees them.
- **"Re-running changes nothing" is a per-statement guard, not a hope.** `ON CONFLICT (k) DO UPDATE
  SET c = COALESCE(t.c, EXCLUDED.c), … WHERE (t.c, …) IS DISTINCT FROM (COALESCE(t.c, EXCLUDED.c),
  …)` fills only NULLs AND does nothing when there is nothing to fill, so `updated_at` does not
  creep on every run. Build the SET list and the row comparison from ONE frozen column constant so
  they cannot drift. `RETURNING id, (xmax = 0) AS inserted` then separates a created row from an
  enriched one — but with that WHERE an untouched conflicting row returns nothing at all, so ids
  for the rest need a second `WHERE name = ANY($1::text[])`.
- **An array column that differs per row cannot go through `unnest`** (the arrays would have to be
  ragged), so a table with one forces a row-at-a-time insert loop. Fine at a couple of dozen rows;
  it is not an optimisation someone should collapse.
- **Distinct display names can slugify to the same slug** (`C & C Milano` and `C&C Milano` are both
  `c-c-milano`), which is a 23505 mid-transaction. Any code generating slugs in bulk must detect
  the collision against both the planned and the stored slugs and report it, the same way an
  unsluggable name is reported rather than defaulted.

- **Learnings:**
  - Pattern: split a backfill into a PURE planner and a thin apply layer. The planner takes the
    sources plus whatever the database already holds and emits desired state keyed by NAME; the
    apply layer resolves names to ids. That is what lets the real-corpus assertions (19.5k rates,
    the two unmatched spellings, the currency conflict) run with zero writes to the shared test
    database, while the SQL is exercised against small prefixed fixtures with an INJECTED
    snapshot — otherwise a test run creates the nine real houses and every later suite sees them.
  - Pattern: "re-running changes nothing" is a per-statement guard, not a hope. `ON CONFLICT (k)
    DO UPDATE SET c = COALESCE(t.c, EXCLUDED.c), ... WHERE (t.c, ...) IS DISTINCT FROM
    (COALESCE(t.c, EXCLUDED.c), ...)` fills only NULLs AND does nothing when there is nothing to
    fill, so `updated_at` does not creep on every run. Build both the SET list and the row
    comparison from one frozen column constant so they cannot drift.
  - Pattern: `RETURNING id, (xmax = 0) AS inserted` separates a created row from an updated one in
    a single upsert. With the WHERE above, an untouched conflicting row returns NOTHING, so the
    ids for the rest have to be read back with a second `WHERE name = ANY($1::text[])`.
  - Gotcha: a row-per-item array column cannot go through `unnest` (the arrays would have to be
    ragged), so `discount_chain` forces the terms insert to be a row-at-a-time loop. Fine at
    two dozen rows; do not "optimise" it into a single statement.
  - Gotcha: `existingSuppliers`/`existingAliases` build one index and the SUPPLIER NAME must win
    over an alias, per the AC's own "matching name then alias". Consequence a reader will trip on:
    adding an alias alone does NOT merge two live supplier rows — the duplicate has to go first.
  - Gotcha: a planner that only plans what a source names will not enrich an existing supplier no
    source mentions. That is correct, but it means a plan's `suppliers` list is not "every
    supplier in the database" and a test asserting otherwise is wrong (cost one red test here).
  - Gotcha: two spellings can slugify to the same slug (`C & C Milano` and `C&C Milano` are both
    `c-c-milano`), which would be a 23505 on `suppliers_slug_key` mid-transaction. Detect it in the
    planner, skip the second and report the pair; an unsluggable name (punctuation only) takes the
    same path rather than defaulting a slug.
  - Context: the snapshot's catch-all tier is the literal `'All other collections'` in
    `resolveDiscount` (`src/seed/data/discounts.js`). The backfill translates it into `is_fallback`,
    which is exactly why the string never has to reach the schema.
