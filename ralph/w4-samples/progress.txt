# Ralph progress log — Atelier — August 6th updates — W4 Samples

## Codebase Patterns

General, reusable findings only. A Ralph iteration reads this block FIRST, before anything else.
Story-specific detail belongs in the per-story entries below, not here.

- **The allowed migration glob is `migrations/*samples*`, so every migration this workstream
  writes must contain the literal string "samples"** — `..._sample-loans.js` does NOT match and
  would be an out-of-bounds file. Name them `..._samples-loans.js`, `..._samples-orders.js`.
- **`atelier_w4` was migrated BEFORE it was seeded**, so any migration that seeds by UPDATE matched
  nothing and its effect is missing from this database while the code is correct. That is how
  `test/featured-rank.test.js` was already failing on a clean checkout (all `featured_rank` NULL).
  Repair is to re-run the migration's OWN exported statements against the database
  (`1786593600000_featured-rank.js` exports `FEATURED_BRANDS`/`brandFeatureSql` for exactly this),
  never to edit another workstream's test. If a suite fails before you have written a line, prove
  it is pre-existing by moving your new files aside and re-running — do not assume either way.
- **`npx vitest run <one file>` is denied at the tool level; `npm test` is the only way to run
  tests.** Budget for the whole suite (~30 s, 52 files) on every check.
- **A source scan that bans a token must not ban it in prose too.** Ban the literal column names
  (`qty_available`, `qty_reserved`) plus the table in a SQL position
  (`/(?:INTO|FROM|JOIN|UPDATE)\s+inventory\b/i`), so a comment may still explain WHY samples are
  not inventory. And assert the scanned file list is non-empty — a scan that matches nothing
  passes every per-file check vacuously.
- **A concurrency invariant held by a partial unique index is testable without stubbing pg**, and
  the shape is reusable for any check-then-write here: take TWO clients off the pool, `BEGIN` both,
  INSERT on the first, start the second INSERT as a PENDING promise (do not await it), sleep ~50 ms
  so it actually reaches the lock wait, `COMMIT` the first, then await the rejection. Without the
  sleep the two statements may simply run in sequence — the assertion still passes, but it has
  stopped testing contention. `client.release()` in a `finally`, and `ROLLBACK` the aborted
  transaction.
- **`rethrowConflict` is EXPORTED from `src/catalogue/admin-brands.js` and is the house 23505 -> 409
  mapper for the whole API.** An unrecognised `error.constraint` degrades the MESSAGE and never the
  status, so a domain that has no message table yet can already prove its duplicate answers 409.
- **A prefix cleanup must match every name the suite WRITES, not just the ones it inserts.** A test
  that renames a fixture (`${PREFIX} Name` → `${PREFIX} Name Ltd`) leaks the row past a
  hyphen-anchored `${PREFIX}-%` pattern, and a fixture carrying a LITERAL unique value (a uuid, a
  guid) then 23505s on the next run — so the suite passes exactly once per database and fails for
  every later iteration on a checkout nobody touched. Anchor the pattern on `${PREFIX}%` (no
  separator) or make every written name carry the separator. This is why the DATABASE is state a
  Ralph iteration inherits: a green suite on a fresh database says nothing about the fifth run.
- **A test suite failing before you have written a line is proved pre-existing by finding its
  CAUSE, not by re-running it.** Query the fixture rows the failing assertion collides with — a
  leaked row whose name predates your change settles it in one query, where a bisect by moving
  files aside costs a 30 s suite run and, for a migration, leaves `pgmigrations` naming a file that
  is no longer on disk. `psql` is denied at the tool level; `node -e` with `require('dotenv')` +
  `require('pg')` against `process.env.DATABASE_URL` is the way to look at `atelier_w4`.
- **A SQL comparison against a NULLABLE column yields NULL, not false, and pg hands that back as
  JS `null`** — so a derived boolean in a projection must be `COALESCE(<comparison>, false)` or a
  caller that wrote `x.overdue === false` silently never matches. The same NULL then makes
  `WHERE NOT <expr>` drop the row instead of keeping it, so the filter and the projection must use
  the ONE expression constant, not two spellings of it.
- **A list whose filter refers to a JOINED table forces the count query to share the FROM clause,
  and that is only safe while no join can multiply a row.** A UNIQUE column is the usual licence
  (`inventory.colourway_id`); a PARTIAL unique index is an equally good one where the join carries
  its predicate (`sample_loans_open_unique` + `ON ... AND returned_at IS NULL` is at most one row
  per sample). State which index licenses it in a comment — a later join added without one inflates
  `meta.total` while every row still looks correct.
- **"Derived at read time, never stored" is only proved by a test that changes the INPUT and
  re-reads.** Reading once and asserting the value passes against a stored column too. Move the
  dependency (the due date, the clock), read again, assert the derived value flipped AND that the
  parent row's `updated_at` did not — that pair is what a stored flag cannot satisfy.
- **A ROUTE story in this workstream cannot ship without `src/app.js`, which is out of bounds.**
  There is no plugin auto-loader here: every route module is an explicit
  `api.register(<module>, { pool })` inside `buildApp`, so `src/routes/admin-samples.js` is dead
  code until someone edits `src/app.js`. Standing up a bare Fastify instance in the test instead
  does not rescue it — the route needs `app.guards.requireRole('backoffice')` and `guards` is
  decorated onto the instance by `buildApp` (`src/app.js:60`), so a hand-rolled app proves the
  handlers work and proves nothing about the authorisation every other `/admin/*` route carries.
  This hits US-005, US-006 and US-007 identically; see `BLOCKED.md`. Do not write a route file
  and leave it unregistered — check `grep -n "routes/" src/app.js` FIRST.
- **`src/lifecycle/registry.js` has no `sample` entry and `deleteOrExplain` 500s on an unknown
  name.** `requireEntity` throws a plain Error rather than answering 404 (deliberately — so an
  `:entity` wired from a URL fails loudly), so any samples DELETE story is blocked on that entry
  existing. The registry's own header comment (line 27) and `atelier-api/CLAUDE.md` both say the
  workstream that creates the tables adds it; this loop's file list says E2 owns `src/lifecycle/`.
  That contradiction is a human decision, not a tidy-up.
- **`src/seed/legacy-import.js`'s `LEGACY_TABLES` is the canonical declaration of what every
  `legacy_*` table holds**, so "no legacy table gained a column" is a real assertion: compare
  `information_schema.columns` against the map plus `imported_at`. One pre-existing exception —
  `legacy_sales_orders.owning_business_unit` is staged by the migration and never imported.

- **Learnings:**
  - Patterns discovered (general and reusable only): see the two entries added to
    `## Codebase Patterns` above — a prefix cleanup must match every name a suite WRITES (a rename
    that drops the separator leaks a row carrying a literal uuid, so the suite passes once per
    database), and a pre-existing failure is proved by finding its cause with a `node -e` query
    rather than by moving files aside (`psql` is denied; moving an APPLIED migration aside also
    leaves `pgmigrations` naming a file that is gone).
  - Gotchas:
    - **`showroom_id` is NOT NULL + RESTRICT here while `samples.showroom_id` is SET NULL, and the
      asymmetry is deliberate.** A sample with no home is still a sample on a shelf; an ORDER with
      no destination is a request nobody can fulfil. Consequence for the fixtures: every sample
      order hangs off a showroom, so a suite can clean the whole table with
      `WHERE showroom_id IN (SELECT id FROM showrooms WHERE name LIKE $1)` and needs no prefix
      column of its own.
    - **Cleanup order gains a THIRD shape**: `sample_orders` must go before `showrooms` (RESTRICT)
      AND before `brands` (its `colourway_id` is RESTRICT, so it stops a brand cascade dead exactly
      as `samples.colourway_id` does). A suite touching both lifecycles deletes
      `sample_orders` + `sample_loans` -> `samples` -> `brands` -> `suppliers` -> `showrooms`.
    - **The six transition stamps are the table's reason to exist and must not be collapsed.** One
      `status_changed_at` is overwritten by the next move; `status` answers "where is it now" and
      the stamps answer "when did it move", which is what a showroom chasing a house asks. A NULL
      stamp is readable as "has not been there" without consulting `status`, so US-004/US-007 need
      no CASE over the status to date a transition.
    - **The state MACHINE is not in the schema and must not be added there.** A CHECK sees one row
      at a time and cannot see which state a row is moving FROM, so it can hold the vocabulary and
      never the transitions — `ALLOWED_TRANSITIONS` is US-007's, in a module the CRM mirrors. There
      is deliberately also no CHECK tying `status = 'cancelled'` to `cancelled_at IS NOT NULL`: a
      back-dated correction must stay possible.
    - **There is no quantity column, deliberately.** The row is one requested item; nothing derives
      a figure from it, and the first number on a samples table is what a later reader mistakes for
      stock. If the office needs "three hangers" that is three rows or a note, until somebody
      ratifies a line grain.
    - `archived_at` IS here (unlike `sample_loans`, which is append-only history): US-007 refuses a
      hard delete of anything past `requested`/`cancelled`, so archiving is the only way a finished
      order leaves the CRM list.
  - Context:
    - The spec is `_bmad-output/planning-artifacts/architecture.md` § *Samples domain* ("Showroom
      stocking — `showrooms` + `sample_orders` advancing requested -> ordered -> in_transit ->
      received -> displayed | cancelled") and the delete-policy table above it, whose `sample order`
      row is "409 unless requested/cancelled".
    - The inline `check:` is emitted unnamed and Postgres auto-names it `sample_orders_status_check`
      — the name the `rejects.toThrow(...)` anchors on and the name US-007's `rethrowConflict`-style
      mapping would key on.
    - **`src/lifecycle/registry.js` is STILL not in this workstream's allowed files** and now has
      three probes owing to it, not two: `sample` -> `sample_loans`, the open-loan guard on
      `sample loan`, and `sample order` -> the requested/cancelled guard (plus a `samples` probe on
      `product`/`colourway`). Same ownership question US-001 and US-002 flagged (E2 owns lifecycle);
      do not edit the registry silently.
- **Needs human verification:** none — schema only, no screen and no route. A human should confirm

  its own copy.
- Overdue is one expression constant, `COALESCE(ol.due_back_at < now(), false)`, used by both the
  projection and the filter; the `returned_at IS NULL` half rides on the open-loan join predicate.
  Nothing is stored and no column exists to store it in.
- Repos and files changed: atelier-api only — `src/samples/admin-samples.js` (new),
  `test/samples-read-models.test.js` (new, 25 tests), plus the bookkeeping (`prd.json`,
  `sprint-status.yaml`, `progress.txt`, `CLAUDE.md`).
- Gates: `( cd atelier-api && npm run lint && npm test )` -> 0 (55 files, 1237 tests);
  `( cd atelier-crm && npm test && npm run build )` -> 0 (37 files, 567 tests) — no CRM file was
  touched, run only to prove the branch is clean.
- **Learnings:**
  - Patterns discovered (general and reusable only): see the three entries added to
    `## Codebase Patterns` above — a nullable comparison derives NULL rather than false (so one
    COALESCE'd expression constant must serve the projection AND the filter), a count query sharing
    a FROM needs every join to be non-multiplying (a PARTIAL unique index licenses one), and
    "derived at read time" is only proved by moving the input and re-reading.
  - Gotchas:
    - **The open loan is a plain `LEFT JOIN`, not a lateral, and that is deliberate.**
      `sample_loans_open_unique` guarantees at most one open loan per sample, which is exactly what
      lets the count query reuse `SAMPLE_FROM` — and it must reuse it, because the `overdue` filter
      names `ol`. A lateral with `LIMIT 1` would work and would hide the fact that the invariant is
      what makes it correct.
    - **`loan_count` is a correlated scalar subquery in the projection, never an aggregate join.**
      An aggregate join would need a GROUP BY over every selected column and would put the count
      into the count query, where it is dead weight.
    - **`overdue` is tri-state as a filter**: absent leaves the list alone, `true` is the chase
      list, `false` is "not late back" (out on time OR on the shelf). `false` is not the same as
      "on the shelf" and a screen must not treat it as such.
    - **`q` deliberately does NOT search `holder_name`.** "What has Kedgley got out" is a question
      about loans, and a loan list is its own read model; folding it in here would make a register
      search return samples whose own fields match nothing the user typed.
    - The by-id and by-barcode reads do NOT filter `archived_at` — house rule for every by-id admin
      read, and for the scanner it is load-bearing: a scanned object exists whatever the CRM list is
      currently showing.
    - `status` and `include_archived` answer different questions and both are needed. A `retired`
      sample is a LIVE row (`archived_at IS NULL`) and appears in the default list; a test asserts
      exactly that, because collapsing the two is the obvious wrong simplification.
    - Test fixture cleanup is anchored on `${PREFIX}%` (no separator) per the pattern above, and the
      order is `sample_loans` -> `samples` -> `brands` -> `suppliers` -> `showrooms`.
  - Context:
    - The AC "no sample code path reads or writes inventory" is covered twice now: the static source
      scan in `test/samples-schema.test.js` already globs `src/samples/**`, and
      `test/samples-read-models.test.js` adds the runtime counterpart — a recording stub pool
      (`{ query }` only, four lines) asserting no statement these read models issue names
      `qty_available`/`qty_reserved` or puts `inventory` in a SQL position.
    - US-005 owns `src/routes/admin-samples.js`. It should spend `MAX_LIMIT` as the query schema's
      `maximum` (an over-large limit is a 400 there; the module still clamps because it is also
      called directly), `SAMPLE_STATUSES` as the `status` enum, and build
      `{ samples, meta: { total, page, limit } }` from `{ samples, total }` — the shape
      `src/routes/admin-suppliers.js` already uses.
    - `getSampleByBarcode` is written and tested here rather than in US-005 because it is a read
      model; US-005 only has to wire the route and turn null into a 404.
    - **`src/lifecycle/registry.js` is STILL not in this workstream's allowed files** and still owes
      three probes (`sample` -> `sample_loans`, the open-loan guard on `sample loan`, the
      requested/cancelled guard on `sample order`, plus a `samples` probe on `product`/`colourway`).
      US-005's "DELETE is blocked by sample_loans" is the story that finally collides with it: E2
      owns `src/lifecycle/`, so that is an ownership question for a human, not a tidy-up. The
      alternative a reviewer may prefer is that US-005 relies on the RESTRICT FK's 23503 rather than
      a probe — but the house rule is that the probe is the primary defence and the catch is the
      backstop, so this needs deciding rather than assuming.
- **Needs human verification:** none — no route and no screen yet, so nothing is reachable from a
  browser. A human should confirm the register list's search fields are the ones staff actually

- **Learnings:**
  - Patterns discovered (general and reusable only): see the two entries added to
    `## Codebase Patterns` above — a route story here cannot ship without `src/app.js` because
    there is no auto-loader AND `guards` is decorated by `buildApp`, and `deleteOrExplain` 500s
    rather than 404s on an entity the registry has never heard of.
  - Gotchas:
    - **US-006 and US-007 are route stories too and hit the `src/app.js` wall identically.** They
      are NOT marked BLOCKED — the loop's rule is one story per iteration and a human may clear
      all three with one decision — but an iteration picking US-006 next should check
      `grep -n "routes/" src/app.js` before writing anything, and block on the same ground if the
      file list has not been widened. Do not write `src/routes/admin-samples.js` and leave it
      unregistered to make a story look finished; it ships nothing.
    - **The 23503 workaround was considered and deliberately refused.**
      `sample_loans.sample_id` is RESTRICT, so a bare `DELETE FROM samples` really does raise
      23503 while a loan points at it, and catching that inside `src/samples/` would satisfy the
      criterion's literal words in-bounds. It is wrong twice over: `atelier-api/CLAUDE.md` states
      the probe is the primary defence and the catch only the backstop, and the 409 envelope
      (`{ message, blockers: [{ relation, label, count, capped }], archivable }`) is a shared
      contract the CRM's `describeBlockers`/`ConfirmDialog` kit consumes — a second, divergent
      implementation of it in a domain folder is a decision for a human, which is what US-004's
      entry already said ("this needs deciding rather than assuming").
    - **`sprint-status.yaml` has a `blocked` value** — line 6 declares
      `# Values: pending | in_progress | done | blocked`. It does not need a new state inventing.
  - Context:
    - The delete policy is `_bmad-output/planning-artifacts/architecture.md` § *Delete policy*:
      `sample` → blocked by sample loans; `sample order` → 409 unless requested/cancelled;
      `sample loan` → 409 while still open. All three, plus a `samples` probe on the existing
      `product` and `colourway` entries, are owed to `src/lifecycle/registry.js`.
    - The read models US-005 would have wired are already written and tested
      (`src/samples/admin-samples.js`, W4-US-004): `listSamples`, `getSample`,
      `getSampleByBarcode` (exact match on the unique column — the route only has to turn null
      into a 404) and `listSampleLoans`, plus `DEFAULT_PAGE`/`DEFAULT_LIMIT`/`MAX_LIMIT` and
      `SAMPLE_STATUSES` for the query schema. The route work itself is small; only the two
      out-of-bounds files stand in the way.
    - `src/routes/admin-suppliers.js` is the shape to copy when this is unblocked — same
      `{ suppliers, meta: { total, page, limit } }` envelope built in the route, `MAX_LIMIT` as
      the schema `maximum`, `rethrowConflict` for the 23505, and `deleteOrExplain`/`replyDelete`
      with the entity name as a single-quoted literal.
