# Ralph progress log — Atelier — August 6th updates — W5 Reporting

## Codebase Patterns

General, reusable findings only. A Ralph iteration reads this block FIRST, before anything else.
Story-specific detail belongs in the per-story entries below, not here.

- **`atelier_w5` was migrated BEFORE it was seeded, so every data-seeding migration matched
  nothing.** `test/featured-rank.test.js` therefore failed out of the box with
  `expected null to deeply equal 1` — nothing to do with the story being worked on. The repair is
  to run the migration's OWN exported statements against the database (that migration exports
  `FEATURED_BRANDS`/`FEATURED_COLLECTIONS`/`brandFeatureSql`/`collectionFeatureSql` precisely so a
  caller need not retype them), never a hand-written UPDATE. Already done once; if another
  data-seeding migration surfaces the same shape, fix it the same way and do NOT edit the test.
- **`psql` and absolute-path `git -C <abs>` are refused by the tool permission layer.** Query the
  database with `node -e` through `loadConfig()` + `createPool()`, and run git from inside the repo
  directory (`cd atelier-api` once; the Bash cwd persists between calls).
- **A gate failure that your diff cannot reach is environment, not code.** Prove it by naming the
  files you touched and the ones the failing test reads, fix the environment, re-run the full
  suite — do not "fix" the test.
- **A migration that seeds or backfills must EXPORT its statement.** node-pg-migrate reads only
  `up`/`down`, so anything else exported is free — and `atelier_w5` holds almost no rows, so a
  backfill's UPDATE matches nothing here and the migration alone proves nothing. The test inserts
  its own fixtures and runs the migration's OWN exported SQL against them. Retyping the statement
  in the test is how the two drift. Established by `1786593600000_featured-rank.js`, followed by
  `1786680000000_reporting-finance-access.js`.
- **A vocabulary copied to a code boundary needs a drift test that parses the LIVE
  `pg_get_constraintdef`, not a literal list.** A boundary copy of a CHECK exists so an unknown
  value is a 400 instead of a 500; the cost is that the two can drift silently, and comparing the
  copy against another hand-written list proves nothing. `test/admin-reports.test.js`'s
  `checkValues(pool, constraint)` extracts every `'value'::text` out of the constraint definition —
  the posture `DISCOUNT_METHOD_ENUM` and `suppliers-product-category.test.js` already take. Where a
  frozen JS list ALREADY exists (`ORDER_STATUSES` in `src/orders/admin-orders.js`), import it
  instead of copying, and still drift-test it.
- **A pure module's unit test may not touch the pool, so anything only the database can confirm
  belongs in the DB-backed suite beside it.** `test/report-filters.test.js` takes no pool, runs no
  migration and stubs nothing; the schema agreement lives in `test/admin-reports.test.js`. Splitting
  the two is what keeps the pure suite honest — the moment it needs `loadConfig()` it is no longer
  proving the module is pure.
- **A masking rule that SUBTRACTS a list can only remove what somebody remembered to declare;
  one that PROJECTS onto the survivors cannot leak a key nobody declared.** `maskReport`
  (`src/reports/access.js`) rebuilds each row from the surviving column keys rather than deleting
  the finance ones out of it. The cost is real and is the right way round: an undeclared key
  silently disappears, which surfaces as a missing value in the report's own test, where a leaked
  cost figure is invisible. The same choice applies to any future response built from a declared
  column list.
- **A default population that a filter can override must be REPLACED by it, never intersected with
  it.** `buildRevenueScope` omits its own `status = ANY('paid','shipped')` clause entirely when the
  caller supplied a `status` filter. Intersecting would answer `status=requested` with zero rows,
  which a reader parses as "no trade" rather than "outside the default" — the same failure mode as
  a filter that silently matches nothing.
- **A UNION seam is checked positionally at module load or it is not a seam.** `assertScopeSource`
  compares each source's column list to `SCOPE_COLUMNS` joined in order, because a UNION ALL lines
  its branches up by POSITION: two sources agreeing on the names while disagreeing on the order
  file one house's revenue under another's heading, and nothing raises. Same posture as
  `assertEntity` (`src/lifecycle/registry.js`) and `assertStorable`. Export the assertion so the
  unit tests can prove it rejects a drifted source — a load-time check nothing exercises is a
  comment.
- **A figure that cannot be added is ABSENT from a totals row, never summed into one.** A fabric is
  metres and a finished good is units; `order_lines.unit_price_cents` is denominated in the
  PRODUCT's currency and `orders` carries none of its own. So `productPerformanceReport` omits `qty`
  from its totals outright and omits `value_cents` whenever the population quotes more than one
  currency — a projected row simply has no such key, which the CRM renders as a dash and the CSV as
  an empty cell. Checkout already refuses a mixed-currency cart for the same reason ("picking a
  winner would silently mis-charge"), and the CRM's own by-design view drops its quantity column on
  the same argument. Any future aggregate over `order_lines` inherits both hazards.
- **Totals are computed over the POPULATION, never over the rows that survived a limit.** A total
  that added up only the visible page agrees with everything on screen and is wrong, which is the
  kind of error nobody checks. `product-performance.js` runs a second aggregate over the same scope
  CTE and puts `rows_total`/`truncated` in `meta` so the table admits which of the two it is.
- **A route's rate limiting is provable from a response HEADER, not by spending the bucket.**
  @fastify/rate-limit puts `x-ratelimit-limit` on a metered route and nothing else does, so
  `expect(response.headers['x-ratelimit-limit']).toBeDefined()` (paired with the same assertion
  being UNDEFINED on an unmetered admin route) proves the opt-in in two requests instead of sixty.
- **`src/routes/*.js` body schemas are OUTSIDE this workstream's file list, so a new writable
  column is inert over HTTP until its route file's owner adds the property.** Ajv runs
  `removeAdditional: true`, so an unlisted key is silently STRIPPED, not 400'd — the PATCH
  succeeds and writes nothing. Add the column to the domain module's whitelist (which is what the
  acceptance criteria mean by "the PATCH whitelist"), then say so in this log; do not reach into
  the route file.

## 2026-08-06T18:35:00Z - W5-US-003 - Report filter layer
- `src/reports/filters.js` (new, pure, no pool and no query) is the one place a reporting
  querystring becomes SQL. `FILTER_COLUMNS` is the frozen name -> trusted-column whitelist for the
  seven filters (`from`, `to`, `brand`, `product_type`, `collection`, `kind`, `status`);
  `parseReportFilters(query)` validates values into a canonical frozen object, ignoring an
  unrecognised key and throwing a 400 naming the filter for a value it cannot use; and
  `buildReportFilters(filters, { params, names })` emits the WHERE fragments with every value bound
  as `$n`. `brand` is the multi-valued one (repeated params or one comma-separated value, blanks
  dropped, de-duplicated, bound as `= ANY($n::text[])`). `PRODUCT_TYPES` and `ORDER_KINDS` are
  boundary copies of the schema CHECKs; `ORDER_STATUSES` is re-exported from
  `src/orders/admin-orders.js` rather than retyped.
- Repos and files changed: atelier-api — `src/reports/filters.js` (new),
  `test/report-filters.test.js` (new, 33 tests), `test/admin-reports.test.js` (+ a `checkValues`
  helper and 3 drift tests), `ralph/w5-reporting/prd.json`, `ralph/w5-reporting/progress.txt`,
  `_bmad-output/implementation-artifacts/sprint-status.yaml`, `CLAUDE.md`. atelier-crm — untouched.
- Gates: `npm run lint` -> 0, `npm test` -> 0 (53 files, 1214 tests); CRM baseline run untouched:
  `npm test` -> 0 (567), `npm run build` -> 0.
- **Learnings:**
  - **The column literals fix the table aliases every Epic 5 query must use** — `o` orders,
    `b` brands, `p` products, `col` collections, which is what the order and catalogue read models
    already use. US-004's scope CTE, US-005's product performance and US-007's two reports have to
    alias their FROM the same way or the clauses this module emits will not resolve.
  - **`to` is exclusive on the NEXT day (`< ($n::date + 1)`), never `<= $n::date`.** `created_at` is
    `timestamptz`, so `<= to::date` cuts the range at that morning's midnight and silently drops
    everything the office did on the last day of its own report — a wrong answer that looks like a
    quiet day. The date bounds resolve in the database session's timezone; nothing here pins one.
  - **`names` is how a report declines a filter it cannot honour.** A stock report has no `orders`
    in its FROM, so a `status` clause there is a broken query rather than a narrowing. An unknown
    name in `names` throws a plain Error (a 500) because it is a code literal, exactly as
    `requireEntity` does — a client can never reach it.
  - Gotcha: a filter value is validated for SHAPE, so `brand=Pierre Frey` is a 400 rather than a
    report that matches nothing. Slugs are `[a-z0-9-]` by construction (`src/seed/slugify.js`), so
    that is safe — but any future filter over free text (a product name, an order number) must NOT
    reuse `parseSlug`.
  - Gotcha for whoever writes the route: `parseReportFilters` throws `statusCode: 400` errors, which
    Fastify serialises as `{ statusCode, error, message }` — so the handler needs no try/catch, in
    the same posture as `src/checkout/checkout.js`. The route's own querystring schema should NOT
    declare `additionalProperties: false` expecting rejection; Ajv's `removeAdditional: true` strips
    unknown keys, and ignoring them is this module's stated behaviour anyway.
  - Context: `src/reports/` now exists and holds `filters.js` alone. `access.js`,
    `revenue-lines.js`, `product-performance.js`, `stock.js`, `not-invoiced.js` and
    `src/routes/admin-reports.js` are still unwritten (US-004 onward). `src/lib/csv.js` from US-001
    is the export writer US-006 will use.
- **Needs human verification:** none. No route, no response shape and no screen changed — the module
  is not wired to anything yet.

- **Learnings:**

    intersected by its filter — both promoted to Codebase Patterns above, as is the positional

  - Context: `src/reports/` now holds `filters.js`, `revenue-lines.js` and `access.js`.
    `product-performance.js`, `stock.js`, `not-invoiced.js` and `src/routes/admin-reports.js` are

  - Every assertion there scopes itself with a `brand` filter over the two fixture houses —
