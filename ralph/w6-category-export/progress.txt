# Ralph progress log — Atelier — August 6th updates — W6 Category export

## Codebase Patterns

General, reusable findings only. A Ralph iteration reads this block FIRST, before anything else.
Story-specific detail belongs in the per-story entries below, not here.

- **`src/` and `scripts/` may import each other freely** — one package, plain relative specifiers,
  no bundler, no `files` field. `src/seed/price-lists.js` already imports `scripts/lib/price-template.js`;
  `scripts/lib/text.js` now imports back the other way. A shared module belongs wherever its owner
  lives, and the other side re-exports.
- **`incoming/pricing-templates/` does not exist in a worktree** (gitignored, main checkout only),
  so `npm run convert:pricing` cannot run here at all and the byte-identity gate cannot be run as
  written. Verify a converter-adjacent change with a hand-made fixture instead:
  `node scripts/convert-price-lists.js <in-dir> <out.json>`, filename matching
  `^(.+?)(?:\s+(FABRIC|WPPR|TRIMMING))?\s+PL\b`, then compare the emitted record against the
  matching line of the committed `src/seed/data/price-lists.json` (line 2 is its first record;
  strip the trailing comma). `test/price-template.test.js`'s byte-pin block names the exact cells
  behind that line.
- **`atelier_w6` was seeded AFTER `1786593600000_featured-rank` ran**, so the migration's UPDATE
  matched nothing and `test/featured-rank.test.js` failed on a database defect, not on any code.
  Repaired once by running the migration's own exported `brandFeatureSql`/`collectionFeatureSql`
  against the seeded rows (a migration may export more than `up`/`down`, and here that is what
  makes the repair the exact statement rather than a retyped copy). If a featured assertion fails
  again after a reseed, this is why — do not chase it into `src/`.
- **A W6 gate run is both repos** even for an api-only story: `( cd atelier-api && npm run lint && npm test )`
  and `( cd atelier-crm && npm test && npm run build )`. The CRM has no ESLint, so `build` is its
  only compile check.
- **A new route plugin has to be registered in `src/app.js`, and that file is nobody's exclusive
  property.** It is not on W6's MUST-NOT list, and a route file no `api.register` line names is
  dead code — so the edit is one import plus one registration, appended, never a restructure. Every
  workstream adding a route makes the same two-line change, so keep it additive and adjacent to
  the existing block or the human merge turns into a conflict for no reason.
- **`npm test -- <file>` and `npx vitest` are both blocked at the tool level here; `npm test` is
  not.** Budget for the whole suite (~33 s, 52 files) on every check rather than trying to narrow
  it — the narrowing attempt costs a denied call and tells you nothing.
- **A 4xx that has to carry structured detail must be RETURNED, never thrown.** Fastify's error
  serializer emits exactly `{ statusCode, error, message }` and drops every custom property, so a
  thrown error cannot carry `errors`/`blockers`/counts. `reply.code(422); return { ... }` is the
  house shape (`src/routes/orders.js` does it, `src/lifecycle/` returns its refusals for the same
  reason). `Object.assign(new Error(m), { statusCode })` stays correct for a message-only refusal.
- **A route that takes an uploaded FILE registers its own content-type parser inside its plugin.**
  `app.addContentTypeParser([...types], { parseAs: 'buffer', bodyLimit }, (req, body, done) =>
  done(null, body))` — parsers are ENCAPSULATED to the plugin scope, so no other route's body
  handling changes (same posture as the Stripe webhook and `admin-legacy-import.js`). There is no
  multipart parser in this API and adding one is a dependency, so the client posts raw bytes. Set
  `bodyLimit` on BOTH the parser and the route; Fastify's default is 1 MB. Do NOT register
  `text/plain` or `application/json` — the root instance already parses both, and re-registering an
  inherited type throws at boot. The consequence: a caller posting JSON to a file route arrives with
  an OBJECT body, so the handler must check `Buffer.isBuffer` rather than assume bytes.
- **A read model takes `db` — a pool OR an open client — and that is what lets a write step run
  the SAME read inside its own transaction.** `src/lifecycle/archive.js` and
  `src/email/recipients.js` already take that shape; anything a later story has to apply should be
  written that way from the start rather than duplicated. Where the read decides what the write
  will do, it needs `FOR UPDATE` in the transactional case and must NOT take locks in the dry-run
  case, so the lock is an option on the shared function, not a second copy of it. Lock in a
  deterministic order (`ORDER BY id`) or two concurrent callers with overlapping row sets deadlock
  instead of queueing.
- **Ajv applies a querystring `default` only when the key is ABSENT.** `?brand=` sends the empty
  string, which is present, so it meets the `pattern` instead and 400s. That is the right answer
  for an export (the caller asked for a house and named none) and the opposite of the CRM list
  rule, where `buildListQuery` drops an empty filter precisely so it never reaches the API.

## 2026-08-06T18:38:28+12:00 - W6-US-003 - Re-import parse and validate
- `POST /admin/product-sheet/validate` (backoffice-only) takes the filled-in sheet back as the raw
  file and reports what WOULD happen. It writes nothing at all — US-004 applies. `parseProductSheet`
  (pure) and `validateProductSheet` (one read query) live in `src/products/product-sheet.js`, beside
  the export that wrote the file, so the header contract has exactly one definition.
- Contract: a structural failure is 400 (not a Buffer, empty file, a header this API never wrote);
  row-level failures are 422 `{ message, errors: [{ row, message }], error_count, summary }`; a clean
  sheet is 200 `{ summary: { rows, skipped, repeats, unchanged, changed }, changes }`. When there are
  no errors the file balances: `rows === skipped + repeats + unchanged + changed`.
- Rules: the row number in every message is `csvRows`'s own line number, so it counts the header and
  points at the line Excel shows. A blank Category is `skipped` (the row nobody touched). A category
  is trimmed and lower-cased before matching the shared `CATEGORIES` set. A repeated Product ID
  saying the same thing collapses (`repeats`); saying two different things is an error naming both
  rows. An id that matches no product, or matches an archived one, is reported — never resolved
  through the House/Design cells beside it. Blank lines are ignored. A header line ending in a stray
  comma is accepted (trailing EMPTY header cells are dropped, as in the pricing pipeline). The
  upload is deliberately NOT brand-scoped: `products.id` is unique across the catalogue.
- Repos and files changed: atelier-api — `src/products/product-sheet.js` (import half added),
  `src/routes/admin-product-sheet.js` (content-type parser + the validate route),
  `test/product-sheet.test.js` (+21 tests), `CLAUDE.md` (`## Category export`),
  `ralph/w6-category-export/{prd.json,progress.txt}`,
  `_bmad-output/implementation-artifacts/sprint-status.yaml`.
- Gates: `npm run lint` (atelier-api) -> 0, `npm test` (atelier-api) -> 0 (52 files, 1206 tests),
  `npm test` (atelier-crm) -> 0 (37 files, 567 tests), `npm run build` (atelier-crm) -> 0.
- **Learnings:**
  - A 4xx carrying structured detail must be RETURNED through `reply.code(...)`, not thrown —
    Fastify's serializer drops custom error properties. Promoted to Codebase Patterns.
  - An upload route registers its own `parseAs: 'buffer'` content-type parser inside its plugin
    scope, and must then check `Buffer.isBuffer(request.body)`: the ROOT instance still parses
    `application/json` and `text/plain`, so a caller using either arrives with a parsed object or a
    string and `decodeText` would throw a TypeError (a 500) on it. Promoted to Codebase Patterns.
  - `products.id` is int4, so a typed-in digit string past 2147483647 reaches the `ANY($1::int[])`
    cast and surfaces as a 500 from Postgres. It is refused in the parser as what it is — not a
    Product ID — which is the general shape: range-check anything that will be cast to `int` before
    it reaches SQL.
  - Two suites in one test file may each own an app + fixtures, and that is cheaper than sharing
    them: `/auth/register`'s 10-per-15-min bucket is per app INSTANCE and per route, so a second
    `buildApp()` starts with a fresh bucket. Vitest runs suites in a file sequentially, so the two
    `beforeAll`s cannot interleave — they only need different fixture prefixes and email domains
    (`sheet-test-` / `sheet-import-test-`; note the second is NOT matched by the first's
    `LIKE 'sheet-test-%'` cleanup).
  - `decodeText` is proved end to end rather than in isolation: the unmatched-row error quotes the
    file's own Design cell, so the cp1252 test (`é` = 0xE9, `’` = 0x92 — the second byte is what
    distinguishes cp1252 from latin-1) asserts a decoded name coming back out of an HTTP response.
  - Do not write a literal U+FEFF into source to strip a BOM — it is invisible in the file and in
    every diff. `String.fromCharCode(0xfeff)` + `startsWith` says the same thing visibly.
  - Context: the header contract, the parser and the matcher are all in
    `src/products/product-sheet.js`; the vocabulary is `CATEGORIES` in `scripts/lib/price-template.js`
    (imported, never retyped — `products.category` and `price_list_items.category` are one set);
    `validateProductSheet` returns an `updates` array that is deliberately NOT served, and is the
    seam US-004 applies.
- **Needs human verification:** no screen exists yet (US-005 builds the panel), so a person should
  drive the round trip once by hand from a signed-in back-office session: download
  `/admin/product-sheet/export.csv?brand=<house>`, open it in Excel, type a category into a few
  rows, save as "CSV (Comma delimited)" — which is cp1252 on Windows — and POST the file to
  `/admin/product-sheet/validate` with `content-type: text/csv`. Confirm the counts match what they
  typed and that the categories in the database are unchanged afterwards.

## 2026-08-06T18:47:00Z - W6-US-004 - Apply validated categories
- `POST /admin/product-sheet/apply` (backoffice-only) writes the filled-in sheet. One transaction:
  either every category the office typed lands or none does. It takes the FILE again rather than
  the validate step's report — a list of updates handed back by a client is a list the client could
  have edited — so the counts are recomputed at write time and returned, never echoed.
- Contract: 200 `{ applied, summary: { rows, skipped, repeats, unchanged, changed }, changes }`,
  where `applied` is the UPDATE's own `rowCount` (the database's count, not the report's
  prediction). A row-level failure is the SAME 422 body the dry run returns, built by one shared
  `refusalBody(report)` in the route file, and the transaction is rolled back — "Nothing has been
  written" is a statement about a rollback there, not about a route that cannot write. A file that
  is not a product sheet at all is a 400 thrown by the parser BEFORE a connection is taken.
- Re-uploading the same file changes nothing: a stated category equal to the stored one is
  `unchanged`, never a write, so the second run reports `applied: 0, changed: 0` and touches no row.
- Repos and files changed: atelier-api — `src/products/product-sheet.js` (`matchProductSheet` split
  out of `validateProductSheet`, `applyProductSheet` added), `src/routes/admin-product-sheet.js`
  (`refusalBody` + the apply route), `test/product-sheet.test.js` (+10 tests, third suite),
  `CLAUDE.md` (`## Category export`), `ralph/w6-category-export/{prd.json,progress.txt}`,
  `_bmad-output/implementation-artifacts/sprint-status.yaml`.
- Gates: `npm run lint` (atelier-api) -> 0, `npm test` (atelier-api) -> 0 (52 files, 1216 tests),
  `npm test` (atelier-crm) -> 0 (37 files, 567 tests), `npm run build` (atelier-crm) -> 0.
- **Learnings:**
  - The dry run and the apply must not be two implementations of one decision. `validateProductSheet`
    was split into the pure `parseProductSheet` (already there) plus a private
    `matchProductSheet(db, parsed, { lock })`; `validateProductSheet` is now two lines over it and
    the apply calls the same function inside its transaction with `lock: true`. Promoted the general
    shape to Codebase Patterns.
  - `FOR UPDATE` on the matching read is what makes the report true at write time: without it a
    product could be archived or hard-deleted between the decision and the UPDATE, and the office
    would be told a row was written that was not. `ORDER BY id` beside it is the deadlock rule —
    two overlapping sheets applied at once take the same locks in the same order.
  - A backstop still earns its place after the lock: `rowCount !== updates.length` throws a 409 and
    rolls back, because the alternative is reporting a count the database did not do. Same posture
    as `src/lifecycle/delete.js`'s 23503 catch — unreachable by an ordinary request, correct anyway.
  - A write suite needs a `beforeEach` that resets only the FIXTURE ROWS, never the users: this file
    now has three suites, and re-registering would spend the 10-per-15-min bucket. Each suite owns
    its own `buildApp()` (fresh limiter store), its own slug prefix and its own email domain — and
    the prefixes must not be prefixes OF each other: `sheet-test-%` does not match
    `sheet-apply-test-house`, which is the only reason three cleanups can coexist.
  - Asserting the two routes' refusals are `toEqual` is what keeps one CRM renderer serving both;
    asserting each separately would let the messages drift apart and both tests stay green.
  - Context: the header contract, the parser, the matcher and the apply all live in
    `src/products/product-sheet.js`; the four legal values come from `CATEGORIES` in
    `scripts/lib/price-template.js` and are never retyped.
- **Needs human verification:** no screen exists yet (US-005 builds the panel), so a person should
  drive the whole round trip once from a signed-in back-office session: download
  `/admin/product-sheet/export.csv?brand=<house>`, type categories into a few rows in Excel, save as
  "CSV (Comma delimited)", POST it to `/admin/product-sheet/validate` (content-type `text/csv`),
  read the counts, then POST the SAME file to `/admin/product-sheet/apply` and confirm the products
  carry the categories in the CRM — then POST it a third time and confirm `applied` is 0.
