# Ralph progress log — Atelier — August 6th updates — W7 Featured

## Codebase Patterns

General, reusable findings only. A Ralph iteration reads this block FIRST, before anything else.
Story-specific detail belongs in the per-story entries below, not here.

- **The local database `atelier_w7` IS SEEDED** (41 brands, the full collection set). So a migration's
  data-correction UPDATE actually matches rows here, unlike CI. Do not assume an empty database.
- **A migration may export more than `up`/`down`.** node-pg-migrate only reads those two, so extra
  named exports (frozen data literals, SQL builders) are free — and are how a test exercises the
  exact statement the migration ran without duplicating it. `test/featured-rank.test.js` imports
  `migrations/1786593600000_featured-rank.js` directly.
- **A migration builder takes statements, not parameters** (`pgm.sql(text)`), so any seeded value is
  interpolated rather than bound. Validate every interpolated value at module load — slug regex,
  positive-integer check — so a typo throws while the file loads instead of reaching the database.
  Same posture as `assertEntity` in `src/lifecycle/`.
- **`( cd atelier-api && npm test )` runs the WHOLE suite in ~27s** (907 tests, 47 files). There is
  no need to try to run one file; `npm test -- <file>` needs an extra approval anyway.
- Do NOT `cd` inside a Bash call and then rely on the next call's path — the working directory
  persists between calls, so a later relative path silently resolves somewhere else.
- **`unnest($1::text[]) WITH ORDINALITY AS v(slug, rank)` is how an ordered list becomes ranks
  without interpolating anything** — one bound parameter, position is the rank, and it works as a
  from_item of `UPDATE … FROM` (multi-column too: `unnest($1::text[], $2::text[]) … AS v(a, b,
  rank)`). An unknown key matches nothing and raises nothing, so `RETURNING` is the only evidence
  of a drop; compare its set against what was asked for.
- **A suite that mutates a column GLOBALLY must snapshot and restore it.** `fileParallelism: false`
  means test files share one database serially, so whatever a file leaves behind is what the next
  file's assertions see. Snapshot `(id, <column>)` in `beforeAll`, restore in `afterAll`.
- **A route schema and a column whitelist must be edited in lockstep.** Ajv runs
  `removeAdditional: true`, so a whitelist entry with no matching `properties` key is inert — the
  key is stripped before the handler ever sees it — and a schema entry with no whitelist entry is
  ignored. Neither half fails loudly on its own.
- **An ordering test must be built so no assertion can pass by accident.** Rank the row whose NAME
  sorts LAST first (otherwise a plain `ORDER BY name` passes), give two rows the SAME rank (or the
  tie-break is never exercised), and archive the LOWEST-ranked row (or an implementation that
  treats rank N as slot N passes). Assert the same list twice, too — a non-total ORDER BY is free
  to return a different permutation each time and a single call cannot see that.
- **A reseed test must use a row the seed ACTUALLY upserts, and prove it did.** The seed only
  touches rows from the vendored catalogue, so a prefix-namespaced fixture is never visited and
  "the column survived a reseed" passes vacuously — including against a set list that clears it.
  Feature a real seeded slug, and in the same test overwrite a column the seed DOES refresh
  (`story`): its return is the proof the row was upserted rather than skipped.
- **Assert the SET LIST, not the file.** A file-wide `includes('<column>')` cannot tell an INSERT
  column from a refreshed one, and those are two different mistakes. Parse each
  `INSERT INTO <t> (<cols>) … ON CONFLICT (…) DO UPDATE SET <list>` out of the source, keep
  `DO NOTHING` as a distinct (null) case, and assert the extraction found every table first — a
  regex that matches nothing passes every per-statement check.
- **Filter a shared-database assertion to the fixture's own prefix and assert RELATIVE order.**
  `atelier_w7` is seeded and the migration already featured real rows, so any absolute position or
  `toHaveLength` over a public listing is asserting about the seed as much as the fixture.

## 2026-08-06T16:40:00Z - W7-US-002 - Admin patch support and whole-list reorder endpoints

- `featured_rank` joined both admin update whitelists (`BRAND_UPDATE_COLUMNS`,
  `COLLECTION_UPDATE_COLUMNS`) and both PATCH route schemas, and is now carried by every admin
  brand/collection read model (`BRAND_COLUMNS`, `COLLECTION_SELECT`, `toBrand`, `toCollection`,
  and the create / update / archive RETURNING projections). It is deliberately ABSENT from both
  create schemas and both INSERT column lists — a house is not featured at birth.
- Two whole-list reorder endpoints, backoffice-only:
  - `PUT /admin/brands/featured` — body `{ slugs: [...] }`, returns `{ brands }` in rank order.
  - `PUT /admin/collections/featured` — body `{ collections: [{ brand_slug, slug }, ...] }`,
    returns `{ collections }`. The PAIR, never the slug alone.
  - **Position in the array IS the rank.** The caller never computes a number, which is what makes
    a swap expressible without a rank collision — and is why the column has no unique index.
  - Each is ONE transaction: `UPDATE … SET featured_rank = NULL WHERE featured_rank IS NOT NULL`,
    then one applying `UPDATE … FROM unnest($1::text[]) WITH ORDINALITY`. An empty list is legal
    and features nothing (how the office turns a strip off).
  - An entry that matched no row is a **422 naming it** — detected from the applying UPDATE's
    `RETURNING` set, because an unknown slug simply matches nothing and raises nothing. The throw
    happens inside the transaction, so a refusal rolls the clear back and the previous list stands.
  - A slug (or pair) listed twice is a 422 too: `UPDATE … FROM` picks one matching source row
    non-deterministically rather than raising, so a duplicate would resolve to an arbitrary rank.
  - `FEATURED_LIMIT = 12` caps both lists as `maxItems` (a 400). Boundary sanity, not a product
    rule — the homepage leads with three and its latest row shows four. **US-005's CRM ordering
    module must cap at the same number.**
- Repos and files changed: atelier-api only — `src/catalogue/admin-brands.js`,
  `src/routes/admin-catalogue.js`, `test/featured-admin.test.js` (new, 17 tests), `CLAUDE.md`
  (`## Featured`), `ralph/w7-featured/prd.json`, `ralph/w7-featured/progress.txt`,
  `_bmad-output/implementation-artifacts/sprint-status.yaml`.
- Gates: `npm run lint` -> 0, `npm test` -> 0 (924 passed, 48 files). The two untouched repos were
  run as well: `( cd atelier-crm && npm test && npm run build )` -> 0,
  `( cd atelier-storefront && npm run lint && npm test && npm run build )` -> 0.

- **Learnings:**
  - Patterns discovered (general and reusable only) — promoted to `## Codebase Patterns` above:
    `unnest(...) WITH ORDINALITY` is the parameterised way to turn an ordered array into ranks; a
    suite that mutates a GLOBAL column must snapshot and restore it, because `fileParallelism:
    false` means another file's assertions run against whatever it left behind.
  - Gotchas:
    - **`featured_rank` had to be added to the route schema AND the whitelist in lockstep.** Ajv's
      `removeAdditional: true` strips any key the schema's `properties` does not name, so a
      whitelist entry alone is inert and a schema entry alone is silently ignored. This is the
      same trap `products.category` is documented under.
    - `{ type: ['integer','null'], minimum: 1 }` is the right shape for a nullable rank: a
      JSON-Schema `minimum` applies to numbers only, so the null arm still passes and an explicit
      null still reaches `buildUpdate`, which keeps it distinct from an absent key. Rank 0 is
      therefore a 400 at the boundary rather than an opaque 23514 from the column CHECK.
    - `WITH ORDINALITY` yields **bigint**; assigning it to the `integer` column is a legal
      assignment cast, so no explicit `::int` is needed. It arrives from `RETURNING` as a JS number
      because the target column is integer — but a bare `SELECT … WITH ORDINALITY` returns the
      ordinality as a STRING (pg maps bigint to string), which will bite anyone reading it directly.
    - **A `PUT` on `/admin/brands/featured` cannot collide with `PATCH /admin/brands/:id`** —
      different methods entirely — and Fastify prefers a static segment over a parametric one
      anyway. No route-ordering care was needed, but do not add a `PUT /admin/brands/:id` later
      without checking.
    - The reorder clears ranks across the WHOLE table, seeded real rows included. `test/
      featured-admin.test.js` snapshots `(id, featured_rank)` in `beforeAll` and restores in
      `afterAll` so `test/featured-rank.test.js` (which runs after it alphabetically and asserts
      the migration's ranks are still in place on this seeded database) still passes.
    - An archived house or collection is deliberately still featurable: the public read models
      already exclude archived rows, so a featured archived house simply does not appear, and
      restoring it brings its position back. US-003 must make sure that leaves no hole.
  - Context:
    - Reorder functions and the featured read models: `src/catalogue/admin-brands.js`, under the
      `Featured ordering (whole-list reorder)` banner at the foot of the file.
    - Endpoints: `src/routes/admin-catalogue.js` — the two `app.put` calls sit between the brand
      and collection blocks.
    - Whole-list `PUT` precedent this followed: `PUT /admin/shipping-rates`
      (`src/routes/shipping.js` + `src/shipping/rates.js`).
- **Needs human verification:**
  - Nothing renders these endpoints yet — the CRM panel is US-005. A human should eyeball the
    CRM's Brands screen once that lands, and confirm the reorder round-trips.
  - Confirm `FEATURED_LIMIT = 12` is an acceptable cap before US-005 hardcodes the same number.
