# Ralph progress log — Atelier — August 6th updates — W9 Scanner spike

## Codebase Patterns

General, reusable findings only. A Ralph iteration reads this block FIRST, before anything else.
Story-specific detail belongs in the per-story entries below, not here.

- **`BarcodeDetector` is unavailable on iOS, in every browser.** Safari does not implement it and
  every iOS browser is WebKit underneath, so Chrome and Firefox on an iPhone or iPad do not either.
  The constructor is simply absent, so a feature-detect is mandatory and the failure is silent
  otherwise. Any browser-camera scanning in this platform means a WebAssembly decoder, not the
  native API — treat "PWA scanning" as carrying that dependency, never as a free browser feature.
- **W9 was run supervised, not under Ralph, and that is by design.** A research workstream has no
  gates to verify against, so a loop has nothing to stop on and burns its budget. The handoff says
  so explicitly. Consequence for anyone reading this file: the commit landed before the bookkeeping,
  which is the reverse of the Ralph invariant.

- Wrote `_bmad-output/planning-artifacts/research-sample-scanner.md` — four options (A Bluetooth

- **Learnings:**
  - Pattern: an options matrix is only decision-useful if one constraint is hoisted above the list.

## 2026-08-06T03:08:26Z - W9-US-002 - Recommendation
- Same document, `## Recommendation`: start with A (Bluetooth keyboard wedge), keep B as the
  documented fallback, with four numbered reasons and the conditions under which the call holds.
- Each rejected option carries what would have to be true for it to win: B if staff must scan away
  from a counter, C if sample tracking should leave the platform entirely (a strategy decision that
  contradicts W4), D only for offline scanning with no Wi-Fi, which nobody has asked for.
- Names the integration point W4 owns — `GET /admin/samples/by-barcode/:barcode` plus the
  `check-out` / `check-in` verb routes — and notes that A and B both hit it, so choosing A wastes
  nothing if B is added later.
- Records three things needed from Atelier (confirm the showroom device, confirm who prints the
  labels, decide whether loan holders may be named in a third-party system) and one open dependency:
  `SampleScanner.jsx` still refers to a "Dataverse-vs-PWA backend call (§6.1)", which W4 answers for
  this platform by putting the register in Postgres.
- Repos and files changed: atelier-api — `_bmad-output/planning-artifacts/research-sample-scanner.md`.
  Delivered in commit `0fc323e`.
- Gates: `npm run lint` -> 0, `npm test` -> 0.
- **Learnings:**
  - Pattern: a recommendation that also states the falsifying condition for every rejected option is
    re-runnable. When the showroom device is confirmed, the reader checks one line instead of
    re-doing the comparison.
  - Gotcha for W4: the recommendation assumes `by-barcode` returns one deterministic 200 or 404
    rather than a filtered list. A wedge scanner types a code and presses Enter, so an ambiguous
    result has no interaction to disambiguate it.
- **Needs human verification:** the showroom device question (iPad vs laptop) is the single input
  that most changes the answer, and only Atelier can answer it. The ADR is therefore `proposed`,
  not `accepted`.
