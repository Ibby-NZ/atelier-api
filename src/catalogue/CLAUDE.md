# atelier-api — catalogue (public + admin + featured)

Extracted from the root CLAUDE.md (root conventions still apply). Loaded automatically when working in this directory.

## Catalogue (public)

- `GET /catalogue/products` (`src/routes/catalogue.js` + `src/catalogue/products.js`) — public product list, `show_on_website = true` only, paginated (`page`, `limit`; defaults 1/20, max 100). Response: `{ products: [...], meta: { total, page, limit, sort } }`.
- Filters are exact-match strings whitelisted in `FILTER_COLUMNS` (`application`, `composition`, `width`, `price_band`, `lead_time`, `product_type`, `collection`) plus `brand` (matches `brands.slug`). Filter *names* map to trusted columns; filter *values* always go through parameterized placeholders — never interpolate a value into SQL. Unknown query params are simply ignored (the whitelist controls what filters), not rejected.
- **Merchandising fields** (added so the storefront grid is a real shopping grid, not a spec table), all built by one `LEFT JOIN LATERAL` colourway rollup: `image_url` (first colourway image in name order, falling back to the product's `hi_res_asset_url`, else null), `in_stock` (`bool_or` over the colourways' `qty_available - qty_reserved > 0`; no colourways or no inventory rows → false), `colourway_count` (true count) and `colourways` (up to `CARD_SWATCH_LIMIT` = 6 `{ name, sku, hex_tones }` for the card swatch strip). The rollup is an aggregate subquery, so it always yields one row — `cw` is never null.
- **Search**: `q` is a single free-text term ILIKE-matched against product name, house name, composition, application, and (via EXISTS) every colourway name/SKU. `%`/`_`/`\` in the term are escaped and the SQL carries `ESCAPE '\'`, so searching `100%` finds a literal percent. A blank/whitespace term is ignored, not treated as "match nothing". `q` narrows the count query too, so `meta.total` is the search total.
- **Sort**: `sort` ∈ `name` (default) | `price_asc` | `price_desc` | `newest`, mapped through the trusted `SORT_ORDERS` table — never interpolate the raw value. Price sorts order on `DISPLAY_PRICE` (`CASE WHEN b.is_international THEN NULL ELSE p.retail_price_cents END`), **not** the raw column: ordering on a price the shopper is not allowed to see would leak it. Hidden/absent prices sort `NULLS LAST` in both directions.
- Pricing (FR-3), enforced in `toPublicProduct`: international brands (`is_international = true`) get `price_hidden: true` and **no** `retail_price_cents` field; domestic brands get `retail_price_cents` only when non-null, `price_hidden: false`.
- Fastify querystring validation with `additionalProperties: false` does NOT reject unknown params here (extra keys pass through), but `enum`/type constraints (`product_type`, `sort`) DO 400. Rely on the code whitelist for filter safety, not on schema strictness for unknown keys.
- `GET /catalogue/products/:slug` (`src/catalogue/product-detail.js`) — public product detail, `show_on_website = true` only (else 404). Response `{ product }`: list fields + `hi_res_asset_url` + `colourways: [{ name, sku, hex_tones, image_url, in_stock }]`. `in_stock = qty_available - qty_reserved > 0`; a colourway with **no** inventory row (LEFT JOIN → nulls) is out of stock. pg returns `numeric` columns as strings — coerce with `Number()` before arithmetic.
- **Trade pricing** (`trade_price_cents`, integer NZD cents on `products`): added by the `1784605289852_trade-price-cents` migration; precomputed at seed for **fabrics only** from the vendored `src/seed/data/pricing.js` `tradeUnit(design)` (`Math.round(unit * 100)`); finished goods stay null. **Both** the list and detail endpoints reveal it, and only to approved trade users (`effectiveRole(user) === 'trade'`) — never to anonymous/customer/backoffice. (The list used to omit it entirely; that made a signed-in trade shopper see "sign in for trade pricing" on every card in the grid.) `price_hidden` is independent: an international house hides its retail price from everyone, trade included, while still showing the trade figure.
- Optional-auth pattern for public routes that show extra fields to logged-in users: `app.guards.loadOptionalUser(request)` returns the user or null and never blocks (unlike `requireAuth`). Route derives `includeTrade` from it and passes it into the read model; the read model is the single gate that adds the field. Both catalogue routes use it.
- `GET /catalogue/brands` → `{ brands: [{ slug, name, country, currency, is_international, story, website_url, image_url }] }` (all brands, alpha). `GET /catalogue/brands/:slug` → `{ brand: { ...brand, collections: [{ slug, name }] } }`, 404 if unknown (`src/catalogue/brands.js`). `website_url` (migration `1785715200000`) is the house's own site, rendered by the storefront brand page as an outbound link; admin create/PATCH validate it via `websiteUrlFrom` — absolute http(s) only, else 422, so a `javascript:` URL can never reach a public href; explicit null clears it. Seed source is `src/seed/data/brand-websites.js` — **seed-owned, not a vendored snapshot** (a re-copy of `src/seed/data/` must not overwrite it), URLs verified against the live sites before entry — and the brand upsert applies it with `COALESCE(brands.website_url, EXCLUDED.website_url)`: it fills blanks only, a CRM-entered URL survives every reseed (guarded by `test/seed.test.js`).
- **`image_url` on a brand is the house's own photograph, and it is the FIRST rung of the storefront's artwork chain.** Added by `1788926400000_brand-image.js`, written only through the CRM's Houses screen (same `websiteUrlFrom` http(s) gate as `website_url`, so a `javascript:` URL can never reach a public `src`; explicit null clears it) — the seed never writes it. It is on the PUBLIC brand shape because the storefront's house tiles (`/`, `/brands`, `/story`) are a photograph with the maison's mark over it and no caption, so the picture carries the whole tile: without it `houseArtwork()` falls through to a collection hero or a product shot, which is whatever the catalogue happened to photograph rather than what the office chose for that house. Nullable, and most houses have none — consumers fall through the chain and finally paint the weave, never another maison's room.

### Two independent gates — trade PRICE vs trade VISIBILITY

- **`includeTrade` is who may see a price; `includeTradeOnly` is whose products exist at all.** They cover different sets of people and conflating them is the trap: `includeTrade` (FR-3, `trade_price_cents`) is **approved trade ONLY** — staff deliberately never receive it. `includeTradeOnly` (`src/catalogue/visibility.js`, `canSeeTradeCatalogue`) is approved trade **plus backoffice/director**, because the back office has to be able to check the real storefront against what it published. A pending trade application is `effectiveRole` `customer` for both, so an applicant sees exactly what a signed-out visitor sees. `viewerGates(user)` in `src/routes/catalogue.js` resolves the session once and derives both.
- **`brands.trade_only`** (migration `1786161600000_brand-trade-only`, `NOT NULL DEFAULT true`) is the flag. A signed-out visitor browses only houses with `trade_only = false`; the seed opens exactly one, `atelier-textiles-nz` (Atelier's own workroom), and closes all 40 represented maisons. **The default is closed on purpose** — a house created in the CRM mid-negotiation must fail to "not published yet", never to "accidentally published" — and `POST /admin/brands` defaults it to `true` for the same reason.
- **The seed writes it on INSERT only.** `trade_only` is absent from `upsertBrands`'s `ON CONFLICT DO UPDATE` set list (unlike `is_international`, which refreshes), so opening or closing a house in the CRM is operational data that survives every reseed — same posture as inventory and shipping rates, and for the same reason: a reseed silently pulling a maison off the public site would be invisible until someone noticed the grid had shrunk. The migration is what applied the initial values to already-seeded databases.
- **Where the predicate is applied**: the listing and both SKU-resolving transactional paths use it as a WHERE clause (`PUBLIC_BRAND_CONDITION`, `b.trade_only = false`) — a closed house's product must vanish, not read as brandless. **The detail endpoint deliberately does NOT**: it fetches the row, then answers **403** `{ error, message, trade_only: true }` carrying nothing about the product. 404 would be a lie (the URL is shareable and the design is real) and, worse, the storefront's SSR fetch carries no session cookie — so a trade customer's own product page would 404 in the HTML and only appear after the island rehydrated. 404 still means the slug genuinely does not exist.
- **The gate closes the transactional paths too, or it is cosmetic.** The cart and the order request take a bare SKU, so `validateCheckoutLines` and `resolveLine` both apply it; a non-entitled caller gets the **same 422 as an unknown SKU** (a refusal must not confirm what exists). Consequence to know: the guest order-request flow (FR-5/FR-6) now reaches the open houses only. The **Stripe webhook deliberately does NOT apply it** — it re-resolves the cart with its own query, and a session that has already been paid must always produce an order; re-gating there would drop a paid order on the floor if a house were closed between checkout and the callback.
- **Houses and collections stay public for everyone.** `/catalogue/brands`(`/:slug`) lists every maison — the directory is Atelier's marketing and closing it would gut `/brands` for signed-out visitors — and each brand now carries `trade_only` so the storefront can label it and offer the application. Collections are listed for everyone too; only `product_count` moves, counting what THIS viewer can reach (0 for a guest on a represented house) so a tile never promises twelve designs and opens on none.
- `meta.trade_gated` on the listing tells the storefront which of the two libraries it is looking at — without it, the public subset is presented as if it were the whole catalogue. Guarded by `test/trade-catalogue.test.js` (22 tests: the four viewers × listing / detail / brands / collections / order request / checkout / admin PATCH).
- **Every catalogue test fixture must set `trade_only = false`** or it models a house no anonymous request can see; the column defaults closed and 64 tests failed on the migration alone until the fixtures said so.

### Collections (brand → collection → product)

- The hierarchy is `brands 1—N collections 1—N products`, but a product's **brand is a direct FK** (`products.brand_id` NOT NULL), not inherited through the collection; `products.collection_id` is nullable (`ON DELETE SET NULL`). A product with no collection is normal, not broken — **the seed never assigns one**, so every seeded product starts uncollected and membership is staff-assigned in the CRM. `admin-products.js` `requireCollectionInBrand` 422s a collection belonging to another house.
- **A collection slug is unique per brand, never globally** (`collections_brand_id_slug_unique`), so every single-collection lookup is brand-scoped: `GET /catalogue/brands/:slug/collections/:collectionSlug` → `{ collection: { slug, name, product_count, brand } }`, 404 otherwise (`src/catalogue/collections.js`). The house param stays named `slug` because Fastify's router rejects two different parameter names in the same path position — renaming it would break `/catalogue/brands/:slug`.
- `GET /catalogue/collections?brand=` → `{ collections: [...] }` (brand name, then collection name). Unknown brand → **empty list, not 404** — same posture as a product filter that matches nothing. `product_count` counts only reachable products (visible, unarchived, unarchived house), so a non-zero count always yields a non-empty grid.
- Collections carry **tile editorial**: `description` + `image_url` (migration `1785801600000`), seeded from the vendored atelier.co.nz snapshot (`realCatalogue.collections` `description`/`src` — the first seed dropped these) and exposed on both public collection endpoints and the admin reads. `PATCH /admin/collections/:id` now takes any of `name`/`description`/`image_url` (`minProperties: 1`; name no longer required); `image_url` goes through the same http(s)-only `websiteUrlFrom` gate as the brand website (it lands in a public `<img src>`), 422 otherwise. Collection **display names drop the snapshot's redundant house prefix** (`collectionDisplayName`: "Pierre Frey | Cappuccino" → "Cappuccino"; a letterless remainder like "2024" keeps the full name) while the **slug still derives from the full snapshot title** — it is the `(brand_id, slug)` upsert key and changing it on a reseed would duplicate every already-seeded collection.
- **Neither collection route returns products.** The grid is `GET /catalogue/products?brand=&collection=`, so filtering, sorting, paging and the trade-price gate stay in one read model. `collection` alone (no `brand`) matches every house using that slug — pair the two.
- Both product read models expose `collection: { slug, name } | null` via a `LEFT JOIN collections col ON col.id = p.collection_id AND col.archived_at IS NULL`. **The archived check lives in the join condition, not the WHERE clause**: archiving a collection is a soft delete of the grouping only (see `setCollectionArchived`), so its products keep selling and simply read as uncollected — and the `collection` filter can never match an archived collection. The join is in the count query too, or `meta.total` would ignore the filter.
- Guarded by `test/catalogue-collections.test.js` (15 tests), whose fixture gives two houses the *same* collection slug — the regression that brand-scoping exists to prevent.

## Back-office catalogue admin

- `src/routes/admin-catalogue.js` + `src/catalogue/admin-brands.js` (brands + collections) + `src/catalogue/admin-products.js` (products + colourways). All routes `requireRole('backoffice')`. **The client is the CRM, not the storefront** — the storefront's admin islands were deleted in its `6d1e1df` ("move back-office admin out of the storefront") and the screens now live in `atelier-crm` (`src/screens/Admin*.jsx`), calling these endpoints cross-origin from :5273. Nothing to do with the AdminJS panel at `/panel`, which stays as the raw fallback.
- **Endpoints**: `GET|POST /admin/brands`, `PATCH /admin/brands/:id`; `GET|POST /admin/collections` (`?brand_id=` filter, `brand_id` in the create body), `PATCH /admin/collections/:id` (name only); `GET|POST /admin/products` (`?brand_id=`), `GET|PATCH /admin/products/:id`; `POST /admin/products/:id/colourways`, `PATCH /admin/colourways/:id`. Admin reads are separate from the public catalogue ones because they include `id` and unhidden-only filtering does not apply (staff see `show_on_website = false` rows).
- **Slugs are server-generated on create and immutable after** — they are public storefront URLs and the EmDash brand-page match key, so a rename must not break links. `slugFrom` (exported from `admin-brands.js`) wraps `src/seed/slugify.js`: whitespace-only input makes slugify throw and punctuation-only returns `''`; both become **422**, never a 500 or an empty slug. Product slug follows the seed convention in `src/seed/catalogue-data.js` — fabric = `slugify(\`${brand.name} ${name}\`)` using the brand **name** (not its slug), finished good = `slugify(name)`.
- **`product_type` is immutable too** (the colourway's inventory `unit` was derived from it), and creates take no inline colourways — add them one at a time via the nested route.
- **`trade_only` is editable per house** (create + PATCH), because whether a maison appears on the public storefront is a commercial decision the office makes, not a property of the vendored catalogue. Create defaults it to `true`. See the visibility gate under Catalogue (public).
- **`brands.image_url`** (migration `1788926400000_brand-image`) is the house image the CRM's Houses screen sets. It is a **URL to a file hosted elsewhere** (the atelier.co.nz media library), not an upload — this API stores no blobs and has no multipart parser or static route. Create + PATCH run it through the same `websiteUrlFrom(value, 'Image')` gate as `collections.image_url`: absolute http(s) only or 422, blank/null clears. The public `/catalogue/brands` shape carries it too — see the bullet under *Catalogue (public)*; the storefront's uncaptioned house tiles are what wanted it.
- **SKUs are typed by staff, not generated.** The CRM's Brand-Product-Colour generator lives only in the demo app and was deliberately not ported; the API just enforces uniqueness. `sku` *is* editable via PATCH (typo fixes are safe — `order_lines` reference `colourway_id`, never the sku).
- **Duplicates are detected by the database, never pre-checked** (a pre-check races and would still need the handler): `rethrowConflict` maps pg `23505` to a **409** keyed on `error.constraint` (`brands_slug_key`, `collections_brand_id_slug_unique`, `products_slug_key`, `colourways_sku_key`; unknown constraint degrades the message, never the status).
- **Colourway create is the one transaction**: BEGIN → `SELECT product_type` (404 if the product is gone) → INSERT colourway → `INSERT INTO inventory (…) VALUES ($1, 0, 0, $2) ON CONFLICT (colourway_id) DO NOTHING` → COMMIT, unit from `UNIT_BY_PRODUCT_TYPE` (`fabric → metres`, `finished_good → units`). A duplicate SKU rolls the whole thing back, so a failed create leaves no orphan colourway. `hex_tones` must be `JSON.stringify`'d (same trap as the seed).
- `buildUpdate(input, columns)` builds every PATCH's SET clause from a **frozen in-code column whitelist** — column names are never user input, values are always `$n` placeholders. `Object.hasOwn` keeps an explicit `null` (clears `collection_id`) distinct from an absent key (leaves it alone).
- Status codes: 400 schema (incl. empty PATCH via `minProperties: 1`), 404 unknown `:id`, 409 duplicates, 422 business rules (unknown `brand_id`/`collection_id`, a collection belonging to another brand, unsluggable name).
- **Gotcha — `additionalProperties: false` does not reject unknown body keys.** Fastify's bundled Ajv runs `removeAdditional: true`, so extra keys are silently *stripped*, not 400'd (same family as the querystring note under Catalogue). Immutability still holds where it counts: on PATCH the stripped body becomes `{}` and `minProperties` produces the 400, and on create a client-supplied `slug` is discarded so the server's wins. Do not rely on schema strictness to reject a field — leave it out of the whitelist.
- Guarded by `test/admin-catalogue.test.js` (63 tests). Same rate-limit gotcha as admin orders: register the two users **once** in `beforeAll`; fixtures are namespaced `admin-cat-test-*` so cleanup deletes brands by slug prefix and cascades.

## Featured

- **`featured_rank` is a nullable INTEGER on `brands` and `collections`, never a boolean** (`migrations/1786593600000_featured-rank.js`). NULL means not featured. The homepage needs three hero slides *in a chosen order*, and a boolean produces a set with no order. Both columns carry an inline `CHECK (featured_rank IS NULL OR featured_rank > 0)` — Postgres names them `brands_featured_rank_check` / `collections_featured_rank_check`. Rank 0 is refused because it sorts ahead of rank 1 while reading as "unset", which is the ambiguity NULL already covers.
- **No unique index, deliberately.** `ORDER BY featured_rank ASC NULLS LAST, name ASC, id ASC` is already deterministic when two rows share a rank, whereas a partial unique index would make every step of a reorder a potential 409 (swapping ranks 1 and 2 collides halfway unless the whole list is rewritten in one statement). No plain index either: `brands` is 41 rows and `collections` a few dozen, and the public endpoints read both whole.
- **Every collection lookup is a `(brand_slug, slug)` PAIR.** `collections_brand_id_slug_unique` is per brand and never global, so the migration's seeding UPDATE joins through `brands`; a slug-only match features another house's identically-slugged collection as well, or instead. `test/featured-rank.test.js`'s fixture gives two houses the same collection slug — the regression the pair exists to prevent, which a fixture with distinct slugs would pass anyway.
- **`featured_rank` is absent from the seed entirely**, not merely from its `ON CONFLICT DO UPDATE` set lists, so a reseed can never move an office decision — the same posture as `trade_only`, inventory and shipping rates. The consequence to know is that a fresh `npm run seed` leaves every row NULL: the migration is the only thing that features anything, exactly like `1786060800000_client-house-roster.js`.
- **A migration may export more than `up`/`down`, and here that is load-bearing.** node-pg-migrate reads only those two, so `FEATURED_BRANDS`, `FEATURED_COLLECTIONS`, `brandFeatureSql` and `collectionFeatureSql` are exported for the test to run the EXACT statement the migration ran against its own fixtures, rather than a re-typed copy of it that could drift.
- **A migration builder takes statements, not parameters** (`pgm.sql(text)`), so every seeded value is interpolated rather than bound. Each one is therefore checked at module load — slug regex, positive integer, non-empty list — so a typo throws while the file is loading instead of reaching the database. Same posture as `assertEntity` in `src/lifecycle/`.
- **The seeded values are inlined, never imported.** They came from the storefront's hand-edited `FEATURED_COLLECTIONS` / `LATEST_SLUGS` (a different repo) and match the seed snapshot, but a migration is a record of what ran and one importing a file that later changes would rewrite its own past.
- **The seeded ranks are a STARTING POINT, not an invariant, and no test may assert the live list still matches them.** The CRM's reorder clears every rank and re-applies the office's own list, and `1789012800000_larsen-2024-feature.js` prepends Larsen 2024 to the collections list (the client's own choice — it is what the `/brands` featured band shows, and the home follows the same list). A migration that changes the list therefore **shifts what is already there** rather than restating one: `featured_rank + 1` for every featured row, guarded by a `NOT EXISTS` on the row being added, so a re-run is a no-op and an office reorder made in between survives. Restating a list would silently undo it.
- **The database owns the order; the page owns the composition.** The seven seeded collections are ONE ordered list — "the first three are the hero, the next four are the latest row" is the homepage's decision and is not encoded here. Do not add a "slot" or "section" column to make it one.
- **Houses were never hand-picked by the storefront.** `/brands`'s "in focus" strip derives its three from `is_international` + a design count + whether editorial photography exists, and that last input lives in the storefront's own content, so no query here can reproduce it. The migration seeds the three houses behind the hero collections so the two surfaces agree; changing it is a CRM edit, not a migration.

### Back-office writes

- **Two ways to write it, and both matter.** `featured_rank` is in `BRAND_UPDATE_COLUMNS` and `COLLECTION_UPDATE_COLUMNS`, so a single rank is correctable with an ordinary PATCH without restating the whole list; and `PUT /admin/brands/featured` / `PUT /admin/collections/featured` (`setFeaturedBrands`/`setFeaturedCollections` in `src/catalogue/admin-brands.js`) replace the list outright. Both are backoffice-only.
- **It is absent from BOTH create schemas and both INSERT column lists** — a house is not featured at birth. Leaving it out of the whitelist is what enforces that; `additionalProperties: false` would only strip it silently.
- **Position in the submitted array IS the rank.** The body is `{ slugs: [...] }` for houses and `{ collections: [{ brand_slug, slug }, ...] }` for collections — the PAIR, because `collections_brand_id_slug_unique` is per brand and never global, so a slug-only match features another house's identically-slugged collection as well or instead. A caller never computes a rank number, which is precisely what makes a swap expressible without a collision and why the column carries no unique index.
- **Each reorder is ONE transaction that clears then re-applies**: `UPDATE … SET featured_rank = NULL WHERE featured_rank IS NOT NULL`, then one `UPDATE … FROM unnest($1::text[]) WITH ORDINALITY AS v(slug, rank)`. Clear-then-apply (rather than diffing) is what makes the submitted list authoritative — anything absent stops being featured without the caller saying so. An empty array is legal and features nothing; that is how the office turns a strip off.
- **An entry that matched nothing is a 422 naming it, never a silent drop.** An unknown slug matches no row and raises nothing, so the applying UPDATE's `RETURNING` set is the only evidence anything was dropped — compare it against what was asked for. The throw happens *inside* the transaction, so a refusal rolls the clear back and the previous list stands intact.
- **A slug or pair listed twice is also a 422**, checked in JS before the transaction: `UPDATE … FROM` picks one of several matching source rows non-deterministically rather than raising, so a duplicate would resolve to an arbitrary rank instead of failing.
- **`WITH ORDINALITY` yields bigint.** Assigning it to the `integer` column is a legal assignment cast, so no `::int` is needed — but a bare `SELECT … WITH ORDINALITY` hands the ordinality back as a **string** (pg maps bigint to string), which is the usual `Number()` trap in a new place.
- **`FEATURED_LIMIT` (12) caps both lists via `maxItems`, so an over-long list is a 400.** Boundary sanity, not a product rule: the homepage leads with three and its latest row shows four. The CRM's own ordering module keeps its own copy of the number.
- **An archived house or collection is still featurable, deliberately.** The public read models already exclude archived rows, so a featured archived house simply does not appear and restoring it brings its position back — the alternative (refusing, or clearing on archive) would lose the office's ordering over a reversible action.
- **A test suite that exercises a reorder clears ranks across the WHOLE table**, seeded rows included. `test/featured-admin.test.js` snapshots `(id, featured_rank)` in `beforeAll` and restores in `afterAll`, because `fileParallelism: false` means `test/featured-rank.test.js` runs afterwards against whatever it left behind.

### Public reads

- **`ORDER BY featured_rank ASC NULLS LAST, <name>, <id>` is the one ordering, applied in four places**: `listBrands`, `listCollections`, the collections nested in `getBrandBySlug` (all three under `src/catalogue/`), and `listFeaturedBrands`/`listFeaturedCollections` in `admin-brands.js`. It is total without a unique index — two rows may share a rank and still order identically on every request — which is exactly what lets a reorder rewrite the whole list in one statement.
- **The collection list is ordered by rank ACROSS houses, then by the pre-existing `b.name, c.name, c.id` tail.** The hero is one list the office ordered; grouping by house first would scatter it. The tail is unchanged, so the unfeatured majority sits exactly where it always did.
- **`featured_rank` rides along on both public shapes** (and on the collections inside a brand), explicitly null when unfeatured. `/brands` needs it to draw its "in focus" strip from the office's choice rather than re-deriving one, and a client that can read the rank can tell "not featured" from "rank unknown".
- **Featuring is viewer-independent; only `product_count` moves.** Houses and collections stay listed for everyone (a closed house is flagged `trade_only`, not hidden), so featuring a `trade_only` house cannot punch a hole in the strip — a guest and an approved trade viewer get the SAME slug order, and the guest simply sees `product_count: 0` on a closed house's collection. `test/featured-public.test.js` asserts the two orders are equal and the two counts differ.
- **Rank is not a position, and nothing may index by it.** An archived featured row is excluded from every public read, so ranks arrive with gaps in them (and the seeded set starts at whatever survived). A consumer takes the first N rows it is handed; `featured-public.test.js` archives the LOWEST-ranked fixture house precisely so an implementation that treated rank N as slot N fails.
- A fixture that features rows must set the ranks with a direct `UPDATE`, not through the reorder endpoints — those clear every rank in the table, including the migration's seeded ones.

### Seed

- **Two assertions keep `featured_rank` out of the seed, and neither alone covers the regression.** `test/seed.test.js` ("never moves a featured house or collection, on any later reseed") proves the office's decision survives `runSeed`; `test/featured-seed.test.js` parses `src/seed/seed.js` and proves the column is in no INSERT column list and no `DO UPDATE` set list. The behavioural test only sees what the seed did to rows it upserts, so a `featured_rank` added to an INSERT list with a null beside it passes it — and that is exactly the state from which someone later extends the set list. The structural test cannot see whether anything survived.
- **A reseed test must feature a row the seed ACTUALLY upserts, and prove it did.** `runSeed` only visits rows built from the vendored catalogue, so a prefix-namespaced fixture house is never touched and "the rank survived" passes vacuously — even against a set list that clears the column. The test therefore uses `pierre-frey` / `pierre-frey-cappuccino` (the PAIR, as every collection lookup must) and overwrites `story` alongside the ranks: the seed refreshes `story = EXCLUDED.story` unconditionally, so its return is the proof the row was upserted rather than skipped.
- **Snapshot and restore, do not "restore to NULL".** `pierre-frey`'s brand rank is NULL but its `pierre-frey-cappuccino` collection is rank 6 from the migration, which `test/featured-rank.test.js` asserts is still in place. The same applies to any future test that features a seeded row.
- **Assert the parsed SET LIST, never a file-wide `includes`.** A whole-file search cannot tell an INSERT column from a refreshed one, and those are two different mistakes; `DO NOTHING` must stay a distinct case from an empty set list. `featured-seed.test.js` asserts the extraction found all six upserts first — a regex that matches nothing would pass every per-statement check vacuously.
