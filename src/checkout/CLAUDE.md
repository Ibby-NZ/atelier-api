## Checkout (Stripe)

- `POST /checkout/session` (`src/routes/checkout.js` + `src/checkout/checkout.js`) — B2C card checkout for finished goods (FR-4). Body `{ lines: [{ sku, qty }], zone }` plus optional free text `notes` (500) / `client_reference` (200) / `customer_po_number` (200); **no prices accepted from the client** (`additionalProperties: false` on line items). `validateCheckoutLines` resolves each SKU server-side and rejects with **422**: products not sold retail (`products.sell_retail` false — the CRM's Retail tick beside "Show on the website", 1 Oct 2026; such a product can only be quoted through `POST /orders/request`, which takes any listed product; the type used to decide, fabric refused), goods with `retail_price_cents = null`, hidden/unknown SKUs, and insufficient stock (`qty_available - qty_reserved < qty`, pg-numeric strings coerced). Unknown shipping zone → **400**.
- Stripe line items use inline `price_data` (currency/`product_data.name`/`unit_amount` from the DB), never pre-created Price IDs. A shipping line item is appended from `getShippingQuote(zone, totalQty)`. The cart (`[{ sku, qty }]` only) + zone + shipping_cents go into `session.metadata` so the **US-011 webhook** rebuilds the order — this endpoint creates **no** order row. `client_reference_id`/`customer_email` are set when logged in (`loadOptionalUser` — guests allowed). Returns `{ url, session_id }`.
- **The shopper's own words travel as metadata, because this endpoint writes no order row.** `notes` / `client_reference` / `customer_po_number` go into `session.metadata` (`filledMetadata`, trimmed) and the webhook copies them onto the order. A blank one is **dropped, not sent**: Stripe metadata is strings throughout, so an empty value would land as a note that says nothing. The 500/200 schema caps sit under Stripe's own 500-character metadata-value limit — raising them past it makes Stripe, not Ajv, reject the checkout.
- **Delivery details are collected by the STORE, not at Stripe** (Sept 2026). Body carries `customer: { name, email, phone, address: { line1, line2?, city, postal_code } }` (schema in `src/routes/checkout.js`; lengths bounded so each fits a 500-char Stripe metadata value; no country field — Ajv's `removeAdditional` drops one, delivery is NZ-only). The session gets `payment_intent_data.shipping` (name/phone/address, country fixed `NZ`) so the parcel address shows on the payment, `customer_email` from the body (the address the shopper confirmed wins over the login), and flat `ship_*` metadata keys, which is what the webhook persists — it prefers metadata (signed, ours) over `collected_information.shipping_details` (kept as the fallback for sessions created before this). Deliberately **no `shipping_address_collection` / `phone_number_collection`** any more, or Stripe would ask twice; still **no `shipping_options`** — our own zone tiers price the freight as a line item and Stripe adding its own would double-charge. `GET /checkout/prefill` (`requireAuth`) returns the form's starting values for a signed-in shopper: account name/email, then the newest card order's `shipping_address`/`contact_phone`, then the trade application's `business_name` / `delivery_address` (one free-text block → `line1`) / `mobile_phone` → `landline_phone`. Blank strings, never nulls — it is a form draft. Guests get 401 and start blank.
- **GST 15% is charged as its own Stripe line item** ("GST 15%", `src/orders/gst.js` — pure, mirrored by the store's `src/lib/gst.js`, both unit-tested) on goods PLUS freight, and stashed as `metadata.gst_cents` beside `shipping_cents`. The webhook writes it to `orders.gst_cents` (migration `1791292800000_order-gst`) and a checkout order's `total_cents` is subtotal + shipping + gst; a session without the key (created before this) totals as it did. Manual/request orders leave `gst_cents` at 0 and `recomputeOrderMoney` is untouched — Xero adds the tax to those itself (`LineAmountTypes: Exclusive`).
- **Every line item is `STORE_CURRENCY` (`src/catalogue/visibility.js`) — goods, freight and GST alike.** It used to be `tradePriceCents === null ? p.currency : TRADE_CURRENCY`, i.e. a retail line took the SUPPLIER's currency. That column is what Atelier PAYS a house and describes neither price field — both are stored in New Zealand cents — so a house that invoices in US dollars had `unit_amount: 42900` sent to Stripe under `usd` on a card the shopper had read as NZ$429.00, a ~1.8x overcharge. The old **mixed-currency 422** went with it: a cart cannot be mixed once a line's currency no longer comes from its supplier, and that check could never have caught this anyway — a wholly-USD cart looked perfectly consistent to it. The insufficient-stock 422 still names the SKU **and** how many remain, so the store can tell the shopper what to change.
- **`adaptive_pricing: { enabled: false }` on every session.** Stripe's Adaptive Pricing otherwise presents a buyer abroad with a converted local currency (USD, with NZD as a toggle) for a cart the store quoted in NZD — the 15 Sep 2026 audit, run offshore, read that as "USD defaulted". The order and the invoice are NZD whatever the buyer's location. Asserted in `test/checkout.test.js`.
- **Stripe is injected**, not imported globally: `buildApp({ ..., stripe, storeBaseUrl })`. `src/server.js` builds the real client from `STRIPE_SECRET_KEY` (optional env — checkout returns **503** when unset, so the rest of the API boots without it). Tests pass a stub whose `checkout.sessions.create` records params — no SDK/network. Secret comes from env only; `test/checkout.test.js` greps `src/` for an `sk_(live|test)_` literal and asserts none (the pattern is built from fragments so it never self-matches).
- `GET /checkout/session/:id` (public) — the store success page (US-019) verifies a completed session. `retrieveCheckoutSession({ pool, stripe }, id)` retrieves the session from Stripe (unknown/failed → **404**; stripe unset → **503**) and then **looks the order up by `orders.stripe_session_id`**, returning `{ order_number, pending, paid, amount_total_cents, currency, email, lines: [{ sku, name, qty, unit_price_cents }], shipping_address }`. Test stub adds a `retrieve` method alongside `create`; it needs the **pool** now, so a test app for this route must be built with one.
- **The order number is read, never derived.** It used to be `WEB-${session.id}` on both sides so the page could show it without waiting — which put `WEB-cs_test_a1b2c3…` in front of the client (Userback 8367539). The webhook now writes a human `WEB-XXXXXXXX` (`src/orders/order-number.js`), so there is nothing to derive: when the row is not there yet the answer is `pending: true` with `order_number: null`, `lines: []`, `shipping_address: null` and the store polls. `paid` still comes from the session, so a pending answer still confirms the payment — never make the shopper wait for the webhook to be told their card went through, and never invent a number.
- Line money on that response comes off the **order**, not the live catalogue: what the client paid is what they must see afterwards, whatever the price is today. `qty` is coerced (`numeric` → string from pg).
- Errors are thrown as `Object.assign(new Error(msg), { statusCode })`; Fastify serializes `{ statusCode, error, message }`, so handlers stay thin.
