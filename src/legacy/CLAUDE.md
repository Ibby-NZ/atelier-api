# atelier-api — legacy D365 staging + overrides

Extracted from the root CLAUDE.md (root conventions still apply). Loaded automatically when working in this directory.

Covers `src/seed/legacy-import.js`, `src/seed/push-legacy.js`, `src/legacy/*`, `src/routes/admin-legacy-import.js`, `src/routes/admin-legacy-merge.js` and the `/admin/legacy/*` read/override routes.

## Legacy D365 staging

- Two-step pipeline mirroring the price-list one: `npm run convert:legacy` (`scripts/convert-d365-exports.js`, Node with no dependencies) turns the Dynamics worksheet exports in `incoming/data-exports/` (gitignored) into `incoming/data-exports/normalized/*.json`; `npm run import:legacy` (`src/seed/import-legacy.js` → `src/seed/legacy-import.js`) upserts them into the eleven `legacy_*` tables (product_prices, stock_items, item_locations, accounts, contacts, sales_orders, sales_invoices, purchase_orders, purchase_invoices, reserves, cuttings). Full column audit and data findings in `docs/d365-export-analysis.md`.
- **The per-workbook reader is `scripts/lib/d365-workbook.js`** (`readD365Workbook(buffer, name, errors)`, `d365WorkbookEntity`, `exportedAt`), lifted out of the converter unchanged in Sept 2026 so the API's house-pricing upload reads the tracking-options export by the same rule (the converter's `tracking_options.json` was byte-identical before and after). The converter script still runs `main()` on import, so nothing may import IT — import the lib.
- Adding an entity means three edits in lockstep: `ENTITIES` in the converter, a `createTable` in a migration, and a `LEGACY_TABLES` entry (the column map drives the `unnest` casts, so a missing/misnamed column fails the whole import rather than silently nulling).
- Columns pulled from a **related** entity export as `<relationship-guid>.<logical_name>` (e.g. `5c5e1693-….atelier_code`). The GUID changes if the view is rebuilt, so the column map accepts a `*.atelier_code` suffix wildcard; a bare logical name always takes precedence.
- **All four transaction entities are header-only** (sales orders, sales invoices, purchase orders, purchase invoices) — roll-up totals, no lines. There is no export path for the detail rows, so **line-item import is shelved**: legacy sales history stays header-grain and product-grain historical reporting is out of scope. Revenue by customer/owner/period still works off the 7,002 invoice headers.
- **D365 item codes are composed at sales-order time, not catalogued**: `{supplier's colour code}[ {YY}{SUPPLIER_TOKEN}]` (e.g. `F3518-003 23PF`). 74.5% carry the suffix, 62 tokens, years 11–26. The token is the **supplier**, not the brand (`CF` = Colefax & Fowler + Jane Churchill), so the token set doubles as the supplier↔brand roll-up A13 wants. Consequence: Product Prices is the catalogue spine (19,327 designs) and Stock Items is the transacted subset (7,611) — a colourway only exists once sold. The item code's numeric part is the supplier's colour code and does **not** match the price-list code, so never join those on code.
- **Lookup columns export as the target's display name, which destroys the key.** `legacy_stock_items.product_price_list` is the price row's Description: only 52% of stock items resolve to exactly one price row (796 ambiguous, 1,780 no match, 1,064 unset). Same for `legacy_item_locations.item` (7,611 items share 6,315 names). The fix is a related **code** column, as Reserves/Cuttings already have — those join at 88–92%. Re-export those two views before attempting any stock↔price mapping.
- `legacy_reserves` (not the stock item's free-text `Reserve` note) is the source of reserved quantity.
- Portal identity columns on `contact` (`adx_identity_*`, incl. the password hash) are dropped at conversion alongside the supplier bank details.
- **Staging is deliberately separate from the live tables and nothing maps into them yet.** The A1/A2/A3 definitions (cost source, what counts as a sale, stock authority) are unsettled; Atelier runs live on D365 until cutover so the import must re-run; and `orders`/`order_lines` are owned by the Stripe webhook + admin-orders state machine — injecting historic orders there would desync `qty_reserved`.
- Exports must stay **dynamic** worksheets. Each embeds `<entity>:<sig>:<logical_name>=<Display Name>&…` in `sheet.xml` (data is on `sheet2.xml`), so columns are matched by **D365 logical name, never display name or position** — a renamed or reordered view cannot corrupt the import, and a missing required column fails the whole run. Dynamic exports also carry the record GUID and a row checksum; a static export carries neither.
- Upsert key is the D365 GUID → re-import is idempotent and refreshes in place; rows absent from a later export are kept. `validateLegacyRecords` runs before any SQL and rejects duplicate GUIDs (a multi-row upsert cannot hit the same conflict key twice) and unknown columns. `raw` jsonb holds every non-empty source column by logical name — `JSON.stringify` it before binding (pg maps a raw object to a record, not jsonb).
- **Consent polarity trap**: D365 renders `donotemail=false` as the word **"Allow"** and `donotsendmm=false` as **"Send"**. Staging columns keep the source attribute's polarity and name (`do_not_*`, TRUE = do not contact); a column named `send_marketing_materials` would invert every row. Guarded by `test/legacy-import.test.js`.
- Supplier bank-account columns are dropped at conversion time and never reach the database. Normalised JSON lives under `incoming/` (gitignored), not `src/seed/data/`, because accounts and orders are client PII.
- Timestamps are `timestamp` (no zone): the export writes Excel serials rendered in the exporting user's local time, so tagging them UTC would shift every date by the NZ offset.

### Getting the exports onto a server (`push:legacy`)

- **A deploy can never carry this data.** `incoming/` is gitignored (client PII), so `npm run import:legacy` on a server finds an empty directory and the CRM's Orders/Clients/Price-lists screens sit at `total: 0` — 200-with-no-rows, which reads as "broken app" rather than "no data". That is exactly what happened on staging: migrations applied, routes deployed, zero rows.
- `npm run push:legacy` (`src/seed/push-legacy.js`) runs on the workstation that HAS the files and streams them to a remote API: `ATELIER_API_PASSWORD='…' npm run push:legacy -- --api https://api.example.com --email <director>`. Options `--dir`, `--batch` (default 1000), `--only <entity>`, `--dry-run`, `--cookie` (skip sign-in). Password comes from the environment by preference — argv is visible in shell history and `ps`.
- The receiving end is `POST /admin/legacy/import/:entity` (`src/routes/admin-legacy-import.js`), **director-only** — backoffice may browse the staging tables but not bulk-write them. `:entity` uses the export/table names (`product_prices`, `sales_orders`), NOT the read routes' URL vocabulary (`prices`, `sales-orders`).
- **Batching is what makes this work without server access.** The corpus is 125 MB of JSON but ~12 MB gzipped; at 1000 records a batch the largest request is **403 KB compressed** (accounts, the fattest rows), under nginx's 1 MB default `client_max_body_size`. So no nginx edit, no SSH, no panel — an HTTPS session cookie is the whole channel. Raising the batch size past ~2000 breaks that guarantee.
- Body is gzip (`application/gzip`, parsed as a Buffer by a parser **encapsulated in this plugin** — same posture as the Stripe webhook; if it leaked to the root instance every JSON route would start receiving Buffers). A plain JSON array is accepted too, for a hand-made curl. `decodeImportPayload` (`src/legacy/import-payload.js`) caps the DECOMPRESSED size at 32 MB — a gzip bomb is cheap to build, so the compressed body limit alone is not a defence — and rejects batches over 5000 records.
- Status codes: 400 malformed (bad gzip, not an array, empty, unknown entity), 413 oversized batch, 422 field-level (`validateLegacyRecords`: bad GUID, unknown column, duplicate GUID inside one batch), 403 backoffice, 401 anonymous.
- Idempotent and resumable: each batch is one transaction upserting on the D365 GUID, so an interrupted push is re-run, not repaired. The client retries transport failures and 5xx three times with backoff and fails fast on 4xx (retrying a rejected batch only burns the rate-limit bucket, 600 / 10 min).
- `LEGACY_ENTITY_ORDER` (`src/seed/legacy-entities.js`) is shared by the local CLI and the push so both land the catalogue spine (product prices, stock) first. Guarded by `test/legacy-import-api.test.js` (22 tests); verified end to end by pushing all 55,877 records into an empty database over HTTP.

### Correcting the mirror (`d365_overrides`)

- **The staging tables are still read-only; the corrections live beside them.** `migrations/1787025600000_d365-overrides.js` adds `d365_overrides`, and `POST /admin/legacy/:entity`, `PATCH|DELETE /admin/legacy/:entity/:guid` and `POST /admin/legacy/:entity/:guid/restore` write only to it. The reason is the rule above: `importLegacyEntity` upserts every mapped column to EXCLUDED on the D365 GUID and the import re-runs until cutover, so a correction stored on a `legacy_*` row survives until the next `npm run import:legacy` and then vanishes with no error. Same argument `trade_accounts` and the samples register were built on.
- **The NAME is load-bearing, not cosmetic.** `test/samples-schema.test.js`, `samples-loans` and `samples-orders` each assert the count of live `legacy\_%` tables equals `Object.keys(LEGACY_TABLES).length`, so a twelfth `legacy_`-prefixed table turns three green suites red on the migration alone — and the prefix would claim membership of the namespace whose defining property is the one this table exists to escape. Do not "tidy" it back.
- **The incumbent already models this split.** D365's own price rows carry `atelier_setpricesmanually` plus the `atelier_manual*` family — a calculated-value / override-value lane, live on 55 of 19,327 rows (`docs/d365-export-analysis.md`). Corrections beside the source is the source system's own pattern.
- **`entity` holds the READ vocabulary (`accounts | sales-orders | stock | prices`), never the import one.** Both are live and three of the four names differ; a row written as `sales_orders` would match no read config, apply nothing and raise nothing. The inline CHECK pins it (Postgres names it `d365_overrides_entity_check`) and a test parses `pg_get_constraintdef` against `LEGACY_ENTITIES`. Consequence to know: the seven staging tables with no read route have no override capability, and two of those — `legacy_sales_invoices` and `legacy_cuttings` — are what the client portal serves.
- **No FK to `legacy_*.guid`, deliberately.** The staging tables are re-imported wholesale, rows absent from a later export are kept, and an override may legitimately be written **before** its record lands — it stays inert and applies when the record arrives, which is the correct behaviour and is tested. An FK would either block the import or cascade a correction away.
- **The merge is in SQL, not in `mapRow`, and that is the module's whole shape.** `q`, every filter and the `ORDER BY` have to see the corrected value and `meta.total` has to count it; a JS overlay would make a customer renamed here unfindable by the corrected name and would paginate over a different set than it counted.
- **`COALESCE(patch->>'col', t.col)` is the obvious form and is WRONG.** `'{"a":null}'::jsonb->>'a'` IS NULL, identically to an absent key, so a deliberate clear would silently return the D365 value while the CRM reported success — and it would behave *differently per type*, since `''` survives COALESCE for text and `''::numeric` throws. The read therefore tests key PRESENCE: `CASE WHEN jsonb_exists(o.patch, 'col') THEN … ELSE t.col END`. The function form rather than `?` so nothing between here and Postgres can mistake the operator for a placeholder. `revert` (dropping the key) is the only way back to D365's value.
- **`WHERE (o.archived_at IS NULL OR $2)` on the LEFT JOIN must NOT be "fixed" into the ON clause.** `IS NULL` is true for the all-NULL non-matching side, so the join does not degrade to an inner one; moving it to ON would make suppression a silent no-op, because an archived override would simply fail to join and the staging row would be emitted uncorrected. **Only an `IS NULL` test on the nullable side is safe in the WHERE** — any other predicate on `o.*` there turns it into an inner join, which is why `o.entity = $1` is correctly in the ON clause.
- **Both UNION branches are generated in ONE loop over one array.** A UNION ALL lines its branches up by POSITION and takes its output names from the first, so two lists agreeing on names but not order would file a local record's city under `province` and raise nothing — the lesson `assertScopeSource` records in `src/reports/revenue-lines.js`. Here the single loop makes the drift unconstructable rather than merely detected.
- **Every cast type is derived from `LEGACY_TABLES`, never retyped**, and `assertEntities()` (`src/legacy/override-schema.js`) runs at module load — the `assertEntity`/`assertStorable` posture. It also catches two things nothing guarded before: a `search`/`filter`/`ORDER BY` column that is not PROJECTED (those clauses run over the CTE, so the first filter added on an unprojected column is a `column does not exist` 500 — it holds for all four configs today by luck), and a `commercial` column that is not overridable.
- **THREE plpgsql safe-cast functions exist so one bad row cannot take a screen down.** The merged read evaluates the cast for every row before the LIMIT, so a single uncastable value — a restored backup, a hand-written UPDATE, any path that skips the API — would raise 22P02 for all 19,327 price rows on every page and every filter, with the only recovery path being the broken list itself. PG14 has no `pg_input_is_valid` (that is 16), so `d365_override_{numeric,boolean,timestamp}(value, fallback)` catch and return the STAGED value. A NULL input returns NULL, because a JSON null is a deliberate override to null and must not revert.
- **The API also makes POSTGRES ITSELF parse each value at write time**, inside the write transaction (`castProbeSql`). A regex can only police the SHAPE — `2026-02-31` passes the timestamp pattern and then raises 22008 — and here the failure would not surface on the write at all, it would land in the table. The safe-cast functions are the backstop, not the primary defence.
- **A timestamp is a NAIVE local value and a `Z` or an offset is a 422.** Every `legacy_*` time column is zone-less because the export writes Excel serials in the exporting user's local time, and Postgres **discards** an offset on a `::timestamp` cast rather than applying it — so accepting what `toISOString()` produces would move every corrected date 12–13 hours and re-sort a list ordered on it.
- **Numerics are stored in the patch as canonical TEXT, not as JSON numbers.** The columns are `numeric(18,4)`/`numeric(18,6)`, whose range does not survive a double.
- **The route schema deliberately does not type the values.** `additionalProperties: false` would make Ajv's `removeAdditional` strip every key and answer 200 having written nothing; a union type (or its `anyOf` spelling) makes `coerceTypes` match a deliberate `null` against the string branch and deliver `''` — the exact bug the read layer exists to avoid, reintroduced by the schema. The column whitelist and type check in `override-schema.js` are the gate, which is the house rule anyway.
- **The PATCH merge is ONE statement** (`patch = (existing || EXCLUDED.patch) - $revert::text[]`). A read-modify-write in JS loses an update whenever two staff correct different fields of one record within a few seconds — the common case here — and tells neither of them. A column named in both `set` and `revert` is a 422, not a precedence rule nobody can see from the request.
- **DELETE and restore are UPSERTS, and the 404 is decided by whether the RECORD exists.** The common case is a record nobody has corrected, so there is no override row and an `UPDATE` would report `rowCount` 0 — read as either a 404 on a record the user is looking at, or a 200 with the record still fully visible.
- **What suppression is NOT.** It hides a record from `/admin/legacy/*` and survives every re-import, which no `DELETE FROM legacy_accounts` could. It reaches **nothing else**: `src/trade-accounts/viewer.js`, `client-legacy.js` and `admin-trade-accounts.js` each write their own SQL straight at the staging tables, so suppressing a duplicate account does **not** resolve a portal name collision and does not remove anything from a client's invoice history. The DELETE response carries `SUPPRESSION_WARNING` saying so — the success envelope matches `replyDelete`'s shape widened by one additive key, the `REIMPORT_WARNING` precedent.
- **`stock` and `prices` rows carry a DERIVED `category`, computed in `mapRow` and stored nowhere.** It is `categoryForItemType(item_type)` (`scripts/lib/price-template.js`), so the CRM's stock list reads as fabric / towel / cushion / throw / bed-linen rather than as a raw D365 item type, and a corrected item type yields a corrected category for free — `mapRow` sees the value the SQL merge already resolved. There is no `category` column on any `legacy_*` table and there must not be one: the import upserts every mapped column and would overwrite it. This is the one derivation that is deliberately NOT in SQL, and the rule above does not contradict it — that rule is about the override MERGE, which `q`, the filters and the `ORDER BY` must all see. Nothing filters, searches or orders on `category`; `ENTITIES.stock.filters.item_type` is the selective one and it is indexed. `npm run import:item-types` is what corrects the type it derives from (`src/products/CLAUDE.md`).
- **`base` is a snapshot of what D365 said when the correction was made.** Without it an override masks every future upstream correction silently and for ever (staff fix a credit limit here in March, accounts fix it in D365 in June, the import lands the new figure, the override keeps returning March's). The detail read reports `stale_fields`. Both sides use `to_jsonb(<column>)` so the comparison is exact rather than a text rendering disagreeing with itself on numeric scale.
- **`base` is merged PER WRITTEN KEY and must never be assigned wholesale** — the same key-wise discipline `patch` gets on the line above it, and assigning one wholesale beside the other was a real bug. A whole-record snapshot reassigned on every write silently retracts the staleness signal for every *other* corrected column: correct a credit limit, D365 moves it (stale_fields fires correctly), then fix an unrelated typo months later and the refreshed snapshot agrees with D365 again — so the divergence stops being reported while the read still serves the old figure, unrecoverably. The upsert is `base = (base - $revert::text[]) || EXCLUDED.base` with `EXCLUDED.base` restricted to the keys this request writes; reverted keys are subtracted, because a snapshot of a correction that no longer exists means nothing.
- **A local record may not be emptied, at either end.** `createLocalLegacyRecord` refuses values that are all null (counting KEYS is not enough — `{ name: null }` is one key and produces a record with every column null), and `setLegacyOverrides` rolls back a revert that would leave a local record's patch empty. Without both, the row survives with `patch = '{}'`, the merged read's local branch emits a guid with every column null, it counts toward `meta.total`, and **no further revert can remove it** — the emptiness is precisely what makes it unfindable. This is reachable through the manual-merge procedure this section itself prescribes. The refusal is thrown AFTER the upsert and inside the transaction, so the rollback undoes it: the resulting patch is what the merge produced, where a pre-read would be checking a value another transaction is about to change.
- **A suite that creates local records cannot clean up by guid or by patch content.** The guid is minted and the only identifying text lives in the patch, so a row with an empty patch is unfindable by both — `test/legacy-overrides.test.js` cleans on `created_by_user_id` against its own fixture users, with the guid list and patch predicates kept only as a belt for rows a test wrote directly rather than through a route.
- **Two query paths, on purpose.** The merged CTE cannot use the base table's index (it orders on a CASE expression), so a page of `legacy_product_prices` goes from a ~22 ms index scan to a ~120 ms sequential scan, twice over because the count runs it too. Overrides number in the tens against tens of thousands of staging rows, so an entity with no corrections takes the original query unchanged; the gate is one indexed existence check and `meta.merged` reports which path ran. A test asserts the two paths return identical rows — that is what stops them drifting.
- **Privileges split three ways, and the axis is durability, not batch size.** Reads and clerical corrections are `backoffice`; a correction touching a `commercial` column additionally needs `can_view_finance` (a login that may not SEE a cost figure in a report must not SET one here — `backoffice` covers the showroom as well as the accounts desk, which is why that flag exists); raising, suppressing and restoring a record are `director`. A correction is durable in a way the bulk import is not — it survives every re-import and masks the upstream value indefinitely. Consequence to know: `can_view_finance` defaults false, so a director created after `1786680000000_reporting-finance-access.js` must be granted it, exactly as for reports. Reverting a commercial column is gated too — it changes the displayed figure.
- **Not routed through `src/lifecycle/`, and the reason is structural**: `assertEntity` requires a single scalar `idColumn` and a probe with exactly one `$1`, and `deleteOrExplain` takes one id, so a composite `(entity, guid)` cannot be expressed. It is not a hard delete either — no `legacy_*` table has `archived_at` and the staging row is owned by the import.
- **KNOWN GAP, stated rather than papered over**: nothing reconciles a locally raised customer with the same customer later arriving from D365 under its own guid; both appear and merging is manual. A trade account cannot be linked to a local guid at all (`POST /admin/trade-accounts` resolves the account out of `legacy_accounts` first, so it 422s), which is the right answer. The local branch's `NOT EXISTS` against the staging table means one guid can never be emitted twice: if a D365 record ever lands under a minted guid, the local branch stops emitting and the staged branch takes over with the patch applied.
- **Only `sales-orders` carries a timestamp column in its read projection**, so it is the only entity where the naive-timestamp rules can be exercised at all. Aiming those cases at `accounts` makes them pass as "unknown column" while `NAIVE_TIMESTAMP`, `castProbeSql`'s timestamp probe, `proveCastable`'s 22007/22008 mapping and `d365_override_timestamp` all go untested — which is exactly what happened once. Every validation test asserts the REASON in the message, so a case cannot pass on the wrong refusal.
- **Custom fields — the ones D365 has no column for — live in `d365_overrides.extras`, NOT in `patch`** (`migrations/1787112000000_d365-override-extras.js`). `patch` is keyed on D365 COLUMN NAMES and three mechanisms read it that way: `overridden_fields` is `jsonb_object_keys(patch)`, `base` is the staging snapshot taken per written key, and `stale_fields` compares the two. A custom key in `patch` would therefore be reported to the CRM as an overridden D365 field, would make `baseSnapshotSql` throw (it refuses a column outside the whitelist), and would never be projected at all — `mergedProjection` emits the declared columns and nothing else. A custom field is a different KIND of fact, so it gets its own lane; the same argument that put this table beside the staging tables rather than on top of them.
- **`custom` / `revert_custom` are the same two verbs as `set` / `revert`, in the SAME statement.** `PATCH /admin/legacy/:entity/:guid` takes all four and `POST /admin/legacy/:entity` takes `custom` beside `values`; the upsert merges `extras = (extras || EXCLUDED.extras) - $revert_custom::text[]` on the line below `patch`'s, so a correction and a custom field written together are one atomic write and two staff editing different custom fields cannot lose each other's work. `custom: { k: null }` is a field that exists with no value; `revert_custom: ['k']` removes it — one rule, learned once. A key in both is a 422.
- **A custom key may not SHADOW a D365 column** (or `guid`): 422 naming it. Two values under one name cannot be told apart by a reader, `overridden_fields` would disagree with `custom_fields` about what has been corrected, and the meaning would change under the office if D365 ever started exporting that column. Keys are `^[a-z][a-z0-9_]{0,39}$` — the column vocabulary, so one CRM renderer serves both — values are scalar only (string/number/boolean/null; an object or array has no renderer, no search story and no way to be corrected field by field), ≤ `MAX_CUSTOM_VALUE_LENGTH` (2000) chars and ≤ `MAX_CUSTOM_FIELDS` (50) per record. `extras` carries no CHECK: the keys are free-form by definition, so `src/legacy/override-schema.js` is the *only* thing that bounds them.
- **`dropEmptyOverride` must test `extras` as well as `patch`.** It deletes an override row whose `patch` is `'{}'` — without the extras half, reverting the last column correction silently destroys every custom field beside it. Regression-tested directly.
- **`custom_fields` is jsonb in and jsonb out, and that is why it is one free-form column rather than typed ones**: it needs none of the three `d365_override_*` safe-cast functions, so no value stored here can raise 22P02 and take an entity's whole listing down. It is a fourth entry in `MERGED_EXTRAS`, emitted identically by both UNION branches (`COALESCE(o.extras, '{}'::jsonb)` — the staged branch's LEFT JOIN has no `o` row for an uncorrected record) and **defaulted in `mapRow`**, because the fast path selects the staging columns only and the key would otherwise appear and disappear depending on whether anyone had ever corrected that entity.
- **A record may not be identified only by custom fields.** `createLocalLegacyRecord` still demands one non-null DECLARED value: search, the filters and every ORDER BY run over the declared columns, so such a record is a blank row in the list that nothing can find — the same phantom the null-values rule already refuses, arriving by another door.
- **Custom fields are clerical (`backoffice`), and the finance gate deliberately does not reach them.** `touchesCommercial` classifies by declared column name and cannot classify a free-form key, so passing custom keys through it would read as a gate while gating nothing. A custom field carries only what a staff member typed — no D365 cost figure reaches it — so it opens no read path `can_view_finance` protects. Raising a record stays director-only.
- Guarded by `test/legacy-overrides.test.js` (100, parameterised over all four entities — three of the four merged projections were once never executed by any test) and the widened method × entity sweep in `test/price-list-exposure.test.js` — a sweep that enumerated only GET would leave every write route outside the negative-security net that file exists to be. Every payload in it is schema-VALID, or Fastify's pre-preHandler validation makes the assertion pass with the guard deleted.


### The Dynamics archive (`/admin/dynamics/*`)

- `src/legacy/archive-read.js` + `src/routes/admin-dynamics-archive.js`: one config-driven read over ALL twelve `LEGACY_TABLES` entries for the CRM's Archive page — `GET /admin/dynamics` (every entity's columns, types, count and `read_entity`), `GET /admin/dynamics/:entity` (list), `…/facets?column=` (distinct values with counts, text/boolean only), `…/:guid` (one record with `raw`). Backoffice, read-only. Guarded by `test/dynamics-archive.test.js`.
- **The entity vocabulary is the IMPORT one** (`sales_orders`, `stock_items`) — the only one that names all twelve tables. The four entities that also have a curated read config get their corrections applied and their suppressed records hidden through `READ_KEY`, resolved off `ENTITIES[*].importEntity`; the merge is the same `jsonb_exists` + safe-cast shape as `legacy-read.js` (`CAST_FUNCTION` is exported from `override-schema.js` for it). Locally raised records are NOT listed here — the archive is what Dynamics said.
- **Any column, any operator, all bound.** `filter=column:op:value` (repeatable, max 20; the value may contain colons — only the first two split). Column names are whitelisted against `LEGACY_TABLES`, operators per type (`OPS`), and values are shape-checked in JS (`VALUE_SHAPE` + `calendarValid`, because `2025-02-30` passes a regex and raises 22008) so a bad filter is a 400 naming the column, never a 22P02 from inside the CTE. `q` ILIKEs every text column; `sort` any projected column, `guid` as the stable secondary key.
- **Timestamps are formatted in SQL (`to_char`) on the way OUT, after filtering.** pg turns a zone-less `timestamp` into a JS Date in the server's zone and JSON writes it as UTC, so a midnight Auckland order date would come out as the previous afternoon. The CTE keeps native types so filters and ORDER BY are correct; only the outer SELECT formats.

### The cutover merge (`merge:legacy`)

- `npm run merge:legacy [-- --create-houses]` (`src/seed/merge-legacy.js` → `src/legacy/merge.js`) promotes the staging tables into the LIVE ones, in preparation for going live. Four things move, each where the mapping is deterministic: **accounts → `trade_accounts`** (keyed on the D365 guid; `migrations/1790947200000_trade-account-details.js` widened the table with the company details — account number, type, primary contact, email, phone, address, city, country, terms, Xero id, `archived_at` — and those FOLLOW D365 on every run while `account_manager_name` is fill-only, so the office's edit survives; no login linked — that stays manual), **contacts → `trade_account_contacts`** (joined on the account NAME, the only key the export carries, and only where the name is unique among clients), **reserves + cuttings → `reserve_requests`/`reserve_lines`** (one docket per customer + contact + owner + day; `Complete` → `dispatched`, `In Progress` → `confirmed` if a real reserve number else `requested`; CFA words mapped), **stock items → catalogue + `inventory`** (each item through `importColourways` as `{ brand: range_name, design: product_price_list ?? name, colour_code: item_code before its year token }`, then `stock_on_hand` onto the colourway's `qty_available` and `trade_price`/`retail_price` fill-only onto the product, NZD rows only).
- **`POST /admin/legacy/merge` is the same merge behind a request** (`src/routes/admin-legacy-merge.js`), DIRECTOR-only like the import, body `{ create_houses?: boolean }` (default false, the CLI's posture; the CRM sends true, as the deploy script does). It exists because on the deployed API the CLI runs only inside the deploy script: a bundle the office loads through the CRM's import panel AFTER the last deploy sits in the Archive and nowhere else until somebody deploys again, and a failure of that deploy-time run is written to a shell nobody reads. The route answers `{ summary, create_houses, ms }` — `summary` is exactly what `mergeLegacy` returns and the CLI prints — a 409 while a run is already in flight (one at a time, per process), and a 500 whose `message` carries the failure's reason, because each step is all-or-nothing and the reason is what makes a repeat worth trying. The CRM's Archive page runs it (`LegacyMergePanel`, behind "Promote to live"). Guarded by `test/legacy-merge-api.test.js`. The deploy script still runs the CLI; the two are the same function.
- **NOT merged, structurally**: the four transaction entities are header-only and `orders` is the checkout's — a header without lines is not an order there. They stay in the Archive. Suppliers and pricing parameters were already promoted by the two `backfill:*` scripts.
- **Who is a client is NOT `is_customer`.** That checkbox is ticked on 321 of 866 accounts while 515 "Trade" accounts have it clear. `CLIENT` in `merge.js` reads "not ONLY a supplier". (The curated `/admin/legacy/accounts?is_customer=true` filter the order desk uses still narrows to the 321 — worth widening when the desk moves to `trade_accounts`.)
- **Re-runnable, and the staging import refreshes until cutover, so it will be.** `migrations/1790860800000_legacy-merge-keys.js` adds nullable `legacy_guid` (unique) to `trade_account_contacts` and `reserve_lines`; accounts land on `legacy_account_guid`; the catalogue is the colour importer's own idempotent upsert. **Stock quantity is the one column overwritten every run** — D365 is the stock authority until the day this runs for real — and `qty_reserved` is never touched. Prices are fill-only, so a CRM edit survives. Guarded by `test/legacy-merge.test.js` (runs the merge twice over a fixture corpus).
- **`--create-houses` raises a `brands` row for each D365 range that carries stock and has no catalogue house** (Solbiati, Libeco, "STOCK - INTERWEAVE", "ATELIER MISC" …), named exactly as D365 spells it, `trade_only`, NZD. Off by default — the colour importer's rule that a house is never created silently stands — but at cutover the office's own stock lines sit under exactly such names. Zero-stock unknown ranges are reported, never raised.
- The price fill fires W17's capture trigger, so `landStock` runs under `withChangeContext({ source: 'import', sourceFile: 'merge:legacy' })`. A test that edits a product price by hand needs the same.
- **`landCategories` fills a blank `products.category` from REVIEWED item types only** — `src/seed/data/reviewed-stock-item-types.js`, the 381 rows of Atelier's corrected stock workbook, keyed on the D365 guid, the category derived through `categoryForItemType`. It matches on the same SKU `landStock` does (`skuFor`, spelled once). Fill-only (a CRM edit is a later answer and survives); a product whose reviewed items disagree is left blank (`split`), as is one whose category the office has since deleted (`missing` — the FK would refuse it). D365's own type for the other ~7,200 items is NOT used: NULL means nobody looked, and an unreviewed suggestion filled in is an answer nobody gave. It rides the merge rather than a migration because the products it fills are CREATED by the merge — on a database where the merge has not yet run, a one-shot migration would find nothing and never run again. The summary's `categories` is what the CLI and the CRM's Promote to live panel report.
- **Every contact lands** (`migrations/1791033600000_contacts-standalone.js`: `trade_account_contacts.trade_account_id` nullable, FK `SET NULL`, plus `company_name` text). Filed under its account where the export's company name is ONE client's; else unattached with the name as text, for the office to file — 1,373 filed, 736 unfiled, 553 with no company. `/admin/contacts` (`src/routes/admin-contacts.js` → `src/trade-accounts/contacts.js`) is the cross-company book: list (`q`, `filed`, `trade_account_id`), create, PATCH (fields, or `trade_account_id` to file/unfile — filing clears `company_name`, the account IS the company then), DELETE. Backoffice, like the per-account book. Guarded by `test/admin-contacts.test.js`.
- **`PATCH /admin/trade-accounts/:id` takes the company details, DIRECTOR-only** (`DETAIL_COLUMNS`; `touchesDetails` in the handler answers 403 to backoffice, while the account-manager block stays backoffice). The snapshotted `legacy_customer_name` is still NOT patchable — the portal matches invoice history on it. Blanks fold to null, email lower-cased.
- `GET /admin/trade-accounts` is the client roster now: A–Z, `q` over name / account number / primary contact / email / phone, `customer_type`, `include_archived`, each row carrying the details and `contact_count`. The CRM's Clients → Accounts tab reads it. `by-guid`'s `d365_people` leaves out anyone the merge already landed on the book (`legacy_guid`), so it lists only what is still Dynamics-only.
- Measured on the full corpus (`atelier_cutover`): 860 trade accounts, 1,373 contacts (553 contacts name no company, 735 name a non-client, 1 a shared name), 2,855 lines in 1,026 dockets, 5,833 colourways across 3,485 products, 436 colourways carrying stock (7,425 m). Runs in about a second after `import:legacy` + `import:colour`.
