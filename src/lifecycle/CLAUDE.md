# atelier-api — lifecycle (delete/archive foundations + CRUD completion)

Extracted from the root CLAUDE.md (root conventions still apply). Loaded automatically when working in this directory.

## Foundations

The shared delete/archive lifecycle module, `src/lifecycle/`. Every hard delete in this API goes through it.

- **The schema will not stop a destructive delete.** Of the 13 FK edges between the live (non-`legacy_*`) tables exactly ONE is RESTRICT (`order_lines_colourway_id_fkey`); eight CASCADE and four SET NULL. `DELETE FROM brands WHERE id = <a stocked house>` raises nothing and destroys its collections, products, colourways and inventory while returning success — and SET NULL is worse because it is invisible: deleting a user SET NULLs their whole order history into anonymous guest orders with no `guest_email`, silently. So the module **probes first**; the pg 23503 catch is a backstop for the grandchild race and for a future RESTRICT FK whose registry entry someone forgot, never the primary defence.
- **`deleteOrExplain(pool, entityName, id, ctx)` returns its refusal — it never throws it.** Fastify's error serializer emits exactly `{ statusCode, error, message }` and drops custom properties, so a thrown error cannot carry `blockers`, which is the entire point of the 409. Result is `{ deleted: true, entity, id }` or `{ deleted: false, status: 404|403|409, error, message, blockers: [{ relation, label, count, capped }], archivable }`. `replyDelete(reply, result)` sends it; success is **200 `{ deleted: { entity, id } }`**, not 204, because every route here returns a JSON envelope and the CRM's `useMutation` names the result in its toast.
- **Transaction order is `BEGIN` → lock → guard → probe → `DELETE` → `COMMIT`**, and the lock must be `SELECT … FOR UPDATE`, **never `FOR NO KEY UPDATE`**. Postgres takes `FOR KEY SHARE` on a referenced row whenever a transaction inserts a row pointing at it; `FOR KEY SHARE` conflicts with `FOR UPDATE` and with nothing weaker, so the weaker mode would leave the check-then-delete window wide open. Probes and the DELETE share the transaction. No SERIALIZABLE — it would add 40001 retries nothing here handles. Guarded by a stub-pool test asserting the statement order and the lock text.
- **Probes count archived rows.** An archived product still blocks its house: archiving is not deletion, and skipping archived rows would let a delete quietly destroy the archive. All of an entity's probes run as ONE `UNION ALL` round trip, each `LIMIT 101`; past 100 hits a blocker reports `{ count: 100, capped: true }` and the message renders "100+ products" rather than counting 19,000 rows to answer a question whose answer is already "no".
- **Registry keys are code literals used at route registration — never a path parameter.** `requireEntity` throws a plain `Error` (a 500) for an unknown name rather than answering 404, so a caller that ever wired `:entity` from the URL fails loudly instead of letting a client probe which names exist. `assertEntity` runs at import time over every entry (probe body matches `/^SELECT 1 FROM [a-z_ ]/` with exactly one `$1`, relation/table/column match `/^[a-z][a-z0-9_]*$/`, relations unique within an entity), so a malformed probe stops the server booting instead of reaching SQL.
- **`archivable` is a property of the entity, not the row.** `inventory` and `shipping_rates` have no `archived_at` column, so their refusals must not offer "archive instead". Check the column exists before adding an entry with `archivable: true`.
- **`inventory`'s `idColumn` is `colourway_id`, not `id`.** The table has both (`id` is the PK, `colourway_id` is UNIQUE) and every existing caller — `/admin/inventory/:colourwayId`, the order state machine — addresses stock by colourway. An entry keyed on `id` would look right and address the wrong row.
- Guards are for rules that are not "something still points at this", and return `{ status, message }` or null: reserved stock blocks its `inventory` row (409); the last `shipping_rates` tier for a zone is 409, because a zone with no tiers makes `getShippingQuote` answer 400 and stops checkout there; a self-delete is **403** from `ctx.user.id`, not 409 — nothing references the row, the caller simply may not.
- Adding an entity is one registry entry; the tables for suppliers and samples do not exist yet, so those entries belong to the workstreams that create them (the safety test asserts every declared table exists in `information_schema.columns`).
- **`setArchived(db, entityName, id, archived, options)` (`src/lifecycle/archive.js`) is the single soft-archive write**, and takes `db` — a pool *or* an open client — so a caller can join it to its own transaction. `setOrderArchived` does exactly that: its terminal-state guard and the write must be one transaction or a concurrent transition slips between them. All eight helpers (`setBrandArchived`, `setCollectionArchived`, `setProductArchived`, `setColourwayArchived`, `setPriceListItemArchived`, `setOrderArchived`, `setUserArchived`, `setEnquiryArchived`) delegate to it and keep their own wrapper, because three different return conventions are in play (throw 404 / return null / re-fetch through a joined read model) and each one's existing tests assert its shape. What was actually duplicated is four lines: the `now()`/`NULL` fragment, the WHERE on the id column, the RETURNING projection and "no row means unknown id". `extraSets`/`alias`/`from`/`filter`/`returning` cover the rest and are frozen code literals, same posture as `buildUpdate`'s column whitelists.
- **`order` is `archivable: true` with a `guard` and a `beforeDelete`, and it carried `deletable: false` until manual sales orders arrived.** That flag refused EVERY order; the two dangers behind it are real but narrower than it was, so they moved into the entry. `orderGuard` refuses a `checkout` order whatever its status (it is the record of a payment taken at Stripe) and any order past `paid`/`shipped` (money moved, `xero_invoice_ref` names the invoice, and a shipped order is what its stock decrement was justified by); what is left — a request nobody priced, a confirmed order before payment, a declined one, a mis-keyed manual order — destroys nothing. `releaseOrderReservation` is the `beforeDelete`: `order_lines.order_id` is CASCADE, so the reservation must be handed back BEFORE the delete or `qty_reserved` is spoken for by an order that no longer exists, silently and for ever. `holdsReservation` is what stops a double release — a shipped order converted its reservation and a declined one already released it. **The normal protection is still absence** — `requireEntity` throws on an unknown name, so `order_lines`, `webhook_events`, trade applications, trade accounts and every `legacy_*` table need no entry at all. `deletable: false` remains supported and is currently used by nothing; `test/lifecycle-archive.test.js` asserts that, so a flag reappearing is a decision rather than a leftover.
- **`beforeDelete(client, id, ctx)` is the ONE pre-DELETE write, and it runs at (C2) — after the guard and the probes, before the DELETE.** Guards and probes stay strictly read-only, which is what makes "a refusal rolls back and there is nothing to keep" true. It exists for state a CASCADE cannot unwind: the reservation is readable only while the lines are still there, and gone the instant the DELETE runs. `assertEntity` type-checks it, and `test/lifecycle-delete.test.js` pins its position against a stub pool (the release UPDATE after the lock, before `DELETE FROM orders`) — a status-code test cannot see ordering.
- Every column constant used as a RETURNING projection (`BRAND_COLUMNS`, `ROW_COLUMNS`, `USER_READ_COLUMNS`, `ENQUIRY_COLUMNS`) is unqualified, so it is only valid while the statement has no alias — the collection wrapper passes a fully qualified projection because its `FROM brands b` join forces one.
- **Fixture cleanup order matters**: delete `orders` before `brands`. `order_lines.colourway_id` is the one RESTRICT edge, so a brand cascade cannot get past it and the cleanup itself 23503s.
- Guarded by `test/lifecycle-delete.test.js` (23 tests): real-database behaviour plus a stub `pool` (`{ connect: async () => client }` logging SQL text) for the statement order, the lock mode and the 23503 branch, whose real-world trigger is a race. `test/lifecycle-archive.test.js` (7) covers `setArchived`'s own contract. `test/lifecycle-registry.test.js` (79) covers the registry: probe shape, `assertEntity` actually rejecting 14 malformed synthetic entries, agreement with `information_schema` (including `archivable` in **both** directions against the `archived_at` column), and a source scan asserting every `deleteOrExplain`/`setArchived` call outside `src/lifecycle/` passes a **single-quoted literal**.
- **The registry is not an authorisation boundary.** `requireEntity` throwing on an unknown name proves nothing: `'brand'` and `'user'` are both known, so an entity name derived from a path parameter would still let a client pick which table gets written to or deleted from. The scan demands a literal for that reason, and it carries its own "did I find any call sites at all" assertion — a regex that silently matches nothing passes every per-site check vacuously.

## CRUD completion

Hard DELETE routes, wired to the `src/lifecycle/` module described under Foundations.

- **A DELETE route is a one-line handler and nothing else.** `deleteOrExplain` returns its refusal, so the handler pipes it: `async (request, reply) => replyDelete(reply, await deleteOrExplain(pool, 'brand', request.params.id, { user: request.user }))`, registered with the same `{ preHandler: backoffice, schema: { params: idParamsSchema } }` as the archive routes beside it. Nothing goes in the domain module — there is no rule left to put there, because the registry entry already holds the probes and the guard.
- **The entity name is a single-quoted literal at every call site.** `test/lifecycle-registry.test.js` scans `src/` and fails the build on an expression. The registry knows `'brand'` and `'user'` alike, so it is not an authorisation boundary: an `:entity` path parameter would let a client choose which table gets deleted from.
- **`ctx` is `{ user: request.user }`**, passed uniformly even where the entity has no guard (brand, collection). `requireRole` has already loaded `request.user`, the shape costs nothing, and it means adding a guard to an entity later does not silently do nothing at one of the call sites.
- **CORS already allows DELETE** (`allowedMethods` in `src/app.js`). A new DELETE route needs no CORS change — but only a real browser preflight proves that, never `app.inject()`.
- `DELETE /admin/brands/:id` and `DELETE /admin/collections/:id` are the first two (`src/routes/admin-catalogue.js`). Both are what makes archiving meaningful: a house or collection created in error can now be removed outright, while anything with catalogue behind it is refused with the counts. Guarded by 11 tests in `test/admin-catalogue.test.js` — including that a collection holding products comes back 409 **and** its products' `collection_id` is untouched (that FK is SET NULL, so an unprobed delete would report success while silently uncollecting them), and that an *archived* product still blocks its house.
- `DELETE /admin/products/:id` and `DELETE /admin/colourways/:id` complete the catalogue. A product **owns** its colourways and their stock rows — both CASCADE, both go with it — but a product's *grandchildren* are where commerce lives, so the probes reach through the colourways: an order line anywhere under the product blocks it, and so does stock that is on hand **or** reserved. Nothing about the product row itself records that it was ever sold, which is exactly why a bare `DELETE FROM products` is wrong.
- **A fixture that inserts into `orders` must be cleaned up before the brands it hangs off.** `order_lines.colourway_id` is the schema's one RESTRICT edge, so it stops a brand cascade dead and the *cleanup itself* raises 23503 in the next test's `beforeEach`. Delete the orders by order-number prefix first; their lines cascade with them.
- **The 23503 backstop is reachable in a test without stubbing pg.** The probes cover `order_lines` for both product and colourway, so no ordinary request can reach the catch — the only way in is the grandchild window `src/lifecycle/delete.js` documents (the transaction locks the *product*, so an order line inserted against one of its colourways after the probes have run is unopposed). `test/admin-catalogue.test.js` reproduces it deterministically by handing `deleteOrExplain` a pool wrapper whose `query` commits that insert on a second connection when the statement is about to be `DELETE FROM products`. `deleteOrExplain` only ever calls `connect()`/`query()`/`release()`, so the wrapper is four lines — the same trick works for any check-then-write here. The test then runs the ordinary probe path over the same row and asserts the two envelopes match key for key, message included, which is what "the backstop produces the same 409" has to mean; `constraintBlockers` reports `count: 1, capped: true` (a "1+"), because pg says a row exists and nothing about how many.
- **There is no `samples` table yet**, so neither registry entry carries a samples probe and the "samples block a product delete" criterion cannot be met. The workstream that creates the table (E4) adds the probe to the `product` and `colourway` entries — a probe against a non-existent relation would fail the registry's `information_schema` safety test, so stubbing one now is not an option.
- `DELETE /admin/price-list-items/:id` (`src/routes/admin-price-lists.js`) and `DELETE /admin/contact-enquiries/:id` (`src/routes/contact.js`). Neither entity has probes or a guard — nothing in the schema references either table — so 404 is the only refusal either can produce. Hard delete sits **alongside** the archive/restore pair each already had; it does not replace it.
- **A deleted price-list item is the one delete in this API that is not durable, and the response says so.** `npm run import:pricing` upserts on `(supplier, category, code)` and keeps rows absent from later files, so the next import re-creates a deleted rate verbatim while leaving an archived one archived — archive is the removal that survives. Staff cannot infer that from a 200, so the success envelope is `{ deleted: { entity, id }, warning }` (`REIMPORT_WARNING`), and the CRM renders it in the toast. **Refusals still go through `replyDelete` untouched**: the 409/404 shape is what every screen shares, and only the 200 is widened, by one additive key. `replyDelete` calls `reply.send()`, so this is done by branching on `result.deleted` in the handler — post-processing its return value is not possible. The refusal deliberately carries no `warning`: the caveat describes a deletion that happened.
- **`POST /contact` shares the auth routes' 10-per-15-min-per-IP rate-limit bucket**, and `test/contact.test.js` spends most of it in its existing tests. New fixtures must be `INSERT`ed into `contact_enquiries` directly — seeding through the endpoint yields 429s that surface as a destructuring `TypeError` on the absent `enquiry`, not as an obvious rate-limit failure. Same rule the suite already applies to `/auth/register` in `beforeAll`.
- `contact_enquiries.user_id` is SET NULL, so deleting an enquiry never touches its author's account. The mirror case is not symmetric: enquiries **do** block a user delete (the registry's `user` entry probes them).
- `DELETE /admin/users/:id` (`src/routes/admin-users.js`) is the one delete whose refusals are all **invisible damage**, not cascades: `orders`, `trade_applications` and `contact_enquiries` all point at `users` with SET NULL, so a bare `DELETE FROM users` reports success while anonymising an entire order history into guest orders carrying no `guest_email`. Each of the three probes is asserted separately, plus one test proving a doubly-referenced account names both relations in a single 409 (they run as one `UNION ALL`, so reporting only the first would send staff round the loop once per relation).
- **`trade_account_users` is an access grant and deliberately has no probe.** Its `user_id` is CASCADE — one login, one company, and a deleted login must not leave a dangling grant — so a trade client whose only link is that grant deletes cleanly and the `trade_accounts` row (the company, a business record) survives. Anything given a probe here would be claiming to be a record worth keeping; that is the distinction to apply when a new table references `users`.
- **The self-delete guard is a 403 in the registry, while self-archive is a 422 in the handler**, and the two are not inconsistent: archive/PATCH answer 422 because they are refusing a *body* the caller sent, whereas a delete has no body and the caller is simply not permitted. The delete rule cannot live in the handler like the other two — `deleteOrExplain` owns the transaction and the refusal has to travel in the same envelope as a probe's — so it reads `ctx.user`, which is what makes `{ user: request.user }` load-bearing on this route rather than boilerplate.
- **Fixtures that block a delete must be cleaned by their own tag, not via the user.** Those same SET NULL edges mean deleting the fixture users leaves the orders/applications/enquiries behind with a null `user_id`; the next test's probes then count rows an earlier test created. `test/admin-users.test.js` cleans them by order-number / business-name / email prefix *before* the users, in both `beforeEach` and `afterAll`. `trade_applications` needs 24 NOT NULL columns, so the fixture is one frozen object with the INSERT generated from its keys — going through `POST /auth/trade-application` instead would spend the register rate-limit bucket.
- **`trade_accounts.linked_by_user_id` is the SET NULL sibling of that grant, and is likewise unprobed.** The link outlives whoever made it and merely stops naming them, so a staff account stays deletable however many trade clients it linked — probing it would make every back-office login permanently undeletable the moment it did any work. Together the two edges are the test for a new table referencing `users`: CASCADE + no probe when the row is an access grant, SET NULL + no probe when it is an audit trace, a probe only when it is a business record in its own right.

Single-row admin reads, added alongside the deletes because the CRM re-reads a row after every write.

- **`GET /admin/brands/:id` and `GET /admin/collections/:id` carry child counts, and those counts deliberately agree with the delete probes** — `product_count`/`collection_count` on the house, `product_count` on the collection, each counting **archived rows too**. architecture.md § *CRM CRUD kit* forbids a pre-flight "can I delete this" GET (it races the delete and the 409 is already authoritative), so the detail read is the only place a screen can learn in advance that Delete will be refused. A count that filtered `archived_at` would report an empty house and then be contradicted by the 409, because an archived product still blocks its house. `test/admin-catalogue.test.js` asserts the agreement in both directions: archive the only child, read the counts, then DELETE and assert the blocker counts are the same numbers; and a house reading 0/0 really does delete with a 200.
- **A by-id admin read never filters on `archived_at`.** `getAdminProduct` does not and neither do these three: the caller already knows the row exists, the restore screen reads it back, and a 404 there reads as "someone deleted it". Filtering belongs on the LIST, behind `include_archived`. The same holds for embedded children — the brand detail lists archived collections, each carrying its own `archived_at` for the screen to style, exactly as the product detail returns every colourway.
- **`toBrand`/`toCollection` now take a second `extra` argument** (the shape `toProduct` already had) so a detail read can add children and counts to the list shape without a second mapper. That silently breaks a bare `rows.map(toBrand)` — `map` passes the array index as the second argument, and `{ ...1 }` happens to be `{}` — so both list call sites became `rows.map((row) => toBrand(row))` in the same edit. `src/catalogue/brands.js` and `collections.js` are unaffected; those are W7's public read models with their own local mappers.
- `COLLECTION_SELECT` is split into `COLLECTION_COLUMNS` + `COLLECTION_FROM` (mirroring `PRODUCT_COLUMNS`/`PRODUCT_FROM`) because a count subquery has to go between the projection and the FROM. `BRAND_COLUMNS` stays unqualified, so `getAdminBrand`'s query must stay alias-free — it is `FROM brands` with a correlated `WHERE brand_id = brands.id`, and adding an alias later would break the projection.
- `GET /admin/price-list-items/:id` is one route over the already-exported `getPriceListItem`. Going through the shared `toPriceListItem` matters rather than being tidy: `wholesale_rate` is `numeric`, so pg hands back a string and only the mapper coerces it — a hand-rolled detail query would put a string into the CRM's number input.

The colourway browse — `GET /admin/colourways` and `GET /admin/colourways/:id`.

- **The list pages, and it is the only catalogue list that does.** One row per SKU makes `colourways` the largest table in the catalogue (~19k designs once the colour files land), so it copies the price-list ledger's shape exactly: the module exports `DEFAULT_PAGE`/`DEFAULT_LIMIT` (50)/`MAX_LIMIT` (200) and `listAdminColourways` returns `{ items, total }`; the route spends the constants as the query schema's `default`/`maximum` and builds `{ colourways, meta: { total, page, limit } }`. `MAX_LIMIT` as the schema `maximum` is load-bearing — an over-large `limit` must be a 400, because a silent clamp reports a page size the caller did not ask for.
- **Both standalone reads carry the design and the house on every row** (`product_name`, `product_slug`, `product_type`, `brand_id`, `brand_name`). Nothing on a colourway row names its parents, and the whole point of browsing SKUs outside their product is not knowing which design a code off a sample tag belongs to. This is why `COLOURWAY_SELECT` now has a sibling pair — `COLOURWAY_CONTEXT_COLUMNS` + `COLOURWAY_CONTEXT_FROM` — instead of one widened select: the colourways **embedded** in `GET /admin/products/:id` already sit under their parent, so they keep the narrow shape and never pay for the joins. A test asserts the by-id read and the list row are `toEqual`, so one CRM renderer serves both.
- **`toColourway` takes an `extra` second argument now** (the shape `toProduct` and `toBrand` already had), which silently breaks a bare `rows.map(toColourway)` — `map` passes the index, and `{ ...0 }` is `{}`. `getAdminProduct` became `colourways.map((child) => toColourway(child))` in the same edit.
- **Filters are `product_id`, `brand_id`, `q` and `include_archived`.** `q` is one ILIKE term over the SKU, the colour name and the **design** name — the three ways staff arrive at a colourway — with `%`/`_`/`\` escaped and `ESCAPE '\'` in the SQL, so a supplier code containing a percent matches one row rather than the whole house. The house is a filter and deliberately not a search term: one maison's name would return several thousand rows.
- **`include_archived` covers the colourway's own flag and never its product's.** Archiving a product does not archive its colourways, and `GET /admin/products/:id` returns every child regardless, so filtering on the parent here would make the two screens disagree about which SKUs exist. The by-id read filters neither, like every other by-id admin read.
- **The count query shares `COLOURWAY_CONTEXT_FROM` with the row query**, which means it carries the `LEFT JOIN inventory`. That is only safe because `inventory.colourway_id` is UNIQUE — a join that could multiply rows would inflate `meta.total` while the rows themselves looked correct.
- Guarded by 14 tests in `test/admin-catalogue.test.js`. Every one of them scopes itself with `brand_id` or `product_id`: this list spans the whole catalogue, so an unfiltered `meta.total` counts every seeded colourway in the test database alongside the fixtures.

Shipping-rate CRUD — `GET|POST /admin/shipping-rates`, `PATCH|DELETE /admin/shipping-rates/:id`.

- **The bulk `PUT` and the single-row routes are two write paths on one table, and their conflict behaviour differs on purpose.** `PUT` is "make this tier table so" and upserts on `(zone, threshold_qty)`; `POST` is a statement that the row is new, so a collision means a mistyped threshold and answers **409** rather than overwriting a live rate with no trace. The PUT is otherwise untouched by this story.
- **`listShippingRates` now selects `id`, and that is what made the rest possible.** A tier was addressable only by `(zone, threshold_qty)` — the pair a PATCH must never move — so nothing could name one row. Because `upsertShippingRates` returns `listShippingRates(pool)`, the PUT's response gained `id` too: additive, no existing key changed. Anything *renamed* in that projection would break the PUT contract without touching the PUT's own code.
- **`PATCH` accepts `rate_cents` and nothing else, and its schema says `required`, not `minProperties: 1`.** `(zone, threshold_qty)` is the identity key the quote resolves against and the seed upserts on, so moving either is a delete plus a create. With one editable column the house `minProperties: 1` shape is actively wrong: Ajv's `removeAdditional` strips the immutable keys *after* `minProperties` has been evaluated, so `{ zone, threshold_qty }` would arrive at the handler as `{}` and produce an empty SET clause. `required: ['rate_cents']` makes that body a 400. The UPDATE is written inline for the same reason — a one-column `buildUpdate` is indirection over a literal.
- **`DELETE` of the last tier for a zone is a 409 from the registry guard, and the refusal is `archivable: false`.** A zone with no tiers makes `getShippingQuote` answer 400 "unknown zone", which stops checkout for every shopper in it; `shipping_rates` has no `archived_at` column, so the dialog must not offer "Archive instead" — the only way out is to add a replacement tier first, which is what `shippingRateGuard`'s message says. The guard holds on the *last remaining* tier, so emptying a zone one delete at a time is refused at the final one.
- `threshold_qty` is `numeric(12,2)`, so pg returns `'30.00'`; every read here goes through `toShippingRate`, which coerces it. A hand-rolled query would put a string into the CRM's number input.
- Guarded by 22 tests in `test/shipping.test.js`. The file has **no `beforeEach`** and its bulk-PUT tests mutate the shared fixture zone in order, so the CRUD block owns two zones of its own and rebuilds them per test. Every fixture zone name must end in `Test Zone` — `deleteTestData` cleans by `zone LIKE '%Test Zone'` and would leave anything else behind.

Inventory create and delete — `POST /admin/inventory`, `DELETE /admin/inventory/:colourwayId`.

- **The pair is one feature: a stock row is deleted to take a colourway out of circulation, and
  created to put it back.** `createColourway` already makes a row (qty 0), so the only way to reach
  a stockless colourway is the delete this story adds — which is why the create had to arrive with
  it rather than after it.
- **`unit` is derived, never accepted, and that is a correctness rule rather than a validation
  one.** It is what every quantity on the row *means*, so a client-chosen unit does not produce a
  row a check could reject — it silently redenominates 40 metres as 40 units. The column is absent
  from the route schema (Ajv's `removeAdditional` strips a `unit` a client sends rather than 400ing
  it) and `createInventory` reads it from the colourway's product through `unitFor`, now **exported**
  from `src/catalogue/admin-products.js` instead of copied. One map, two callers: a second copy
  would eventually disagree about a colourway created through one path and re-stocked through the
  other.
- **An existing row is a 409, never an upsert.** The row carries staff-corrected counts and a live
  `qty_reserved` the order state machine depends on, so a create that overwrote them with its
  defaults would zero live stock and release a reservation while answering 200. Same posture as the
  shipping `POST` beside its bulk `PUT`. An unknown colourway is a 422 (a business rule, like an
  unknown `brand_id` on a product create); the pre-insert lookup is a nicety and the FK is the rule,
  so a colourway deleted in between raises 23503 and the catch answers with the same 422.
- **Create is the one inventory route keyed on a body field rather than `:colourwayId`** — there is
  no row to address yet, and the colourway is what the create is choosing.
- **The delete's guard refuses `qty_reserved > 0` with 409 and `archivable: false`.** `inventory`
  has no `archived_at`, so the CRM dialog must not offer "Archive instead" (the same shape as a
  shipping tier); the way out is to ship or decline the open orders, which releases the reservation
  and makes the delete succeed. Deleting a reserved row would leave the order state machine's
  release `UPDATE ... FROM order_lines ... WHERE i.colourway_id = ol.colourway_id` matching nothing
  forever — no error, just a reservation that can never be released.
- **A delete must not take the colourway with it.** The CASCADE runs colourway -> inventory and
  never the reverse; a test asserts the SKU is still in the catalogue afterwards, because the
  failure mode is silent and destroys catalogue data rather than stock data.
- **Search a fixture by its namespaced SKU, not by a colour or design name.** `test/admin-inventory.test.js`
  shares the database with the seeded catalogue, and `?q=Jade` matches two seeded colourways as well
  as the fixture. The older `?q=Velvet` / `?q=Sky` assertions are unique only by luck.
