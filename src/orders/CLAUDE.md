Extracted from the root CLAUDE.md (root conventions still apply). Loaded automatically when working in this directory.

## Order requests (fabric / backorder)

- `POST /orders/request` (`src/routes/orders.js` + `src/orders/order-request.js`) — a customer or guest asks the back office to cut and invoice fabric (FR-5/FR-6). Body `{ lines: [{ sku, qty_metres, cut_requirements? }], contact?: { name, email, phone }, accepted_lead_time? }`. Public (guests allowed via `loadOptionalUser`). Returns **201** `{ order: { id, order_number, kind, status, lines } }`.
- **Two-layer validation**: the body schema is structural only (empty `lines`/missing `sku` → **400**). `qty_metres > 0` and email validity are checked in the handler via `validateOrderRequestInput`, which returns **422** `{ message, errors: [{ field, message }] }` with field paths like `lines[0].qty_metres` / `contact.email`. Guests must supply `contact.email`; logged-in users fall back to their session email (order gets `user_id`, `guest_email` stays null).
- **Availability decides the kind**: for every line, `available = qty_available - qty_reserved` (pg-numeric strings coerced). All lines in stock → `kind='order_request'`, `order_number` `REQ-…`. Any line short → requires `accepted_lead_time=true` (else **422** "accept the quoted lead time"); then `kind='backorder_request'`, `order_number` `BO-…`. Both create `status='requested'`.
- **Reservation**: in one transaction each line increments `inventory.qty_reserved` by `qty_metres` (backorder lines reserve too — committed demand). The colourway row is locked `FOR UPDATE OF c` — the inventory row is the nullable side of the LEFT JOIN and **can't** be locked directly ("FOR UPDATE cannot be applied to the nullable side of an outer join"), so locking the colourway serialises concurrent same-SKU requests. Unknown/hidden SKU → **422**.
- Pricing is deliberately **0** on request lines (`unit_price_cents = 0`); the invoice amount is set manually by the back office at confirmation (US-014), not by the client. `contact` name/phone are stored in `orders.notes`.

## Order history + guest lookup

- `GET /orders/mine` (`src/routes/orders.js` + `src/orders/order-history.js`) — auth (`requireAuth`), returns `{ orders: [...] }` newest first, each with `lines`. Ownership is enforced in SQL (`WHERE user_id = request.user.id`), never in the handler, so one user can never read another's orders.
- `GET /orders/lookup?order_number=&email=` — public guest lookup. Returns `{ order }` only when order number AND email match; email matches either `guest_email` or the placing user's `users.email` (case-insensitive `lower()`). No match → **404** (never a 400/enumeration signal). Both query params required by schema (missing → 400).
- Order shape (`toOrder`): `id, order_number, kind, status, subtotal_cents, shipping_cents, total_cents, shipping_zone, xero_invoice_ref, shipping_address, created_at, lines`. Lines carry `sku, product_name, qty, unit_price_cents, cut_requirements`. Internal columns (`stripe_session_id`, `guest_email`) are not exposed. Lines are batch-loaded for all order ids in one query (`ol.order_id = ANY($1::int[])`) then grouped — no N+1.

## Back-office order management

- `src/routes/admin-orders.js` + `src/orders/admin-orders.js` (US-014, FR-7). All routes `requireRole('backoffice')` (director inherits). Handlers stay thin; the state machine + reservation logic live in the module.
- **Lifecycle** (order-request / backorder kinds): `requested --confirm--> confirmed --mark-paid--> paid --ship--> shipped`; `requested|confirmed --decline--> declined`. Any other transition throws **409** via `requireStatus`. `confirm` stores `xero_invoice_ref` from the body (manual Xero, no API call).
- **Reservation model**: only `RESERVING_KINDS` (`order_request`, `backorder_request`, `manual`) touch inventory here; `checkout` orders arrived paid + already-decremented and hold no reservation (`reserves(kind)` guards every inventory write). `reservation_state` per order = `held` (requested/confirmed/paid) → `converted` (shipped: `qty_reserved -=`, `qty_available -=`) or `released` (declined: `qty_reserved -=`). `ship`/`decline` update inventory with a single `UPDATE inventory i ... FROM order_lines ol WHERE ol.order_id=$1 AND i.colourway_id=ol.colourway_id` (no per-line loop). A colourway with no inventory row (short backorder) reserved nothing, so the join simply matches nothing.
- **Endpoints**: `GET /admin/orders` (see the order desk below), `POST /admin/orders` (201), `GET /admin/orders/:id` (404), `PATCH /admin/orders/:id`, `DELETE /admin/orders/:id`, `POST .../confirm|mark-paid|ship|decline|archive|restore`. `:id` is an integer param (Fastify coerces; non-numeric → 400).
- **`kind` is the order's CHANNEL, not its behaviour**, and `manual` (migration `1786939200000_manual-order-kind.js`) is the fourth: a sales order the back office keyed from a phone call, a walk-in, a bespoke enquiry — or from a storefront request that turned into a bigger job. Reusing `order_request` for those would erase the one distinction the office wants in its lists and its reports, and the `SO-` order-number prefix is a string convention rather than a queryable dimension (`src/reports/filters.js` filters on `o.kind`). **Widening the CHECK is half the change**: `RESERVING_KINDS` (`src/orders/order-states.js`), `ORDER_KINDS` (`src/reports/filters.js`) and `INVOICEABLE_KINDS` (`src/reports/not-invoiced.js`) move in the same commit, plus the CRM's `KIND_LABELS`. `test/admin-reports.test.js` parses the live `orders_kind_check` and asserts it equals `ORDER_KINDS`, so a half-done widening fails loudly — that is the tripwire working. A test that retypes one of these sets as a literal will fail on the next kind; assert the exclusion (`not.toContain('checkout')`) or compare against the constant.
- **`src/orders/order-states.js` is a pure, zero-import leaf module** holding `RESERVING_KINDS`/`reserves`, `DELETABLE_ORDER_STATUSES`, `HELD_STATUSES`, `isDeletableOrder`, `holdsReservation` — the `sample-order-states.js` posture, for the same three reasons: `src/lifecycle/registry.js` imports it (and cannot import `admin-orders.js`, which imports `lifecycle/archive.js` → registry: a cycle), the CRM mirrors it so a Delete button is never offered where the API would 409, and it unit-tests with no database. `RESERVING_KINDS` lived in `admin-orders.js` until the delete story needed it; that module now imports it, so there is one source of truth rather than two copies that could disagree about whether a manual order holds stock.
- **`POST /admin/orders` (`createManualOrder`) is a separate module function, not a parameterisation of `createOrderRequest`** — that one is keyed on SKU, prices every line at 0 and applies the storefront's trade-visibility gate. This one takes prices, addresses colourways by id (the CRM picks them out of the catalogue search) and trusts the backoffice guard, because staff key orders against unlisted designs and trade-only houses as a matter of course. Attribution is `user_id` **or** a walk-in's `contact` (422 when neither: an order nobody can be billed for is not a sales order); the contact is packed through the **exported** `buildNotes` from `order-request.js`, so `orders.notes` reads identically however the order was raised. A `guest_email` is written only when there is no account — the account's own address is the one to write to, and a copy here goes stale. Every line is resolved (and its colourway locked) before anything is written, so an unknown colourway refuses the whole order rather than leaving half of one behind.
- **`PATCH /admin/orders/:id` is what turns a storefront quote into an invoiceable sales order.** Body: `lines` (per-line `qty` / `unit_price_cents` / `cut_requirements`, `minProperties: 2` so an id alone is a 400), `add_lines` (`colourway_id`, `qty`, `unit_price_cents`), `remove_line_ids`, plus `notes` / `guest_email` / `contact_phone`; `anyOf` demands at least one key, because Ajv's `removeAdditional` strips unknown ones rather than rejecting them. The old qty-only body still validates. Order of operations is removals → edits → adds → header → **recompute**, and removals go first because they free reservation a re-add in the same request may want back. **The money is always recomputed from the lines** (`ROUND(SUM(qty * unit_price_cents))::int`, once over the whole order — rounding per line multiplies the error by the line count); `shipping_cents` is never touched here and `total = subtotal + shipping`. **An order may not be left with no lines** (422): declining it releases the reservation and leaves a record, where an empty order would keep its number and say nothing.
- **`orders.discount_pct` is the manual pricing override (Rebecca-R2), and it is an INPUT to the one recompute, never a second total.** `subtotal_cents` stays the un-discounted figure; `recomputeOrderMoney` computes `total_cents = ROUND(subtotal * (1 - discount_pct/100))::int + shipping_cents`, so every path that re-totals (line edit, add, removal, the discount change itself) agrees by construction — mirrored by `discountedTotalCents` in `src/orders/discounts.js` and tripwired by `test/order-discounts.test.js`. **0/5/10 are the standard tiers any back-office user may set; anything else is director-only and must carry a non-blank `discount_reason`** (403 / 422 from `checkDiscountWrite` — an in-HANDLER check on `request.user.role`, the admin-users self-protection posture, because the route guard stays `requireRole('backoffice')` and director *inherits* backoffice, so the guard cannot draw this line). The pct and its reason travel as a pair (a reason alone is a 400 via schema `dependencies`; a pct without one clears the stored reason), `discount_applied_by` is stamped from the session and never readable from the body, and a discount is a commercial term — it sits behind the requested/confirmed status guard like a price edit, not with the annotations. The customer-facing `toOrder` deliberately does not expose any of the three columns: the totals already reflect the discount, and who authorised it is the office's business. `discounts.js` is a pure zero-import leaf (the `order-states.js` posture); the CRM mirrors its tiers so Custom is disabled for non-directors rather than discovered as a 403.
- Every inventory write goes through `moveReservation(client, kind, colourwayId, delta)`, gated on `reserves(kind)`; a colourway with no inventory row reserved nothing, so the UPDATE matches nothing. `lockColourway` is the `resolveLine` idiom (`FOR UPDATE OF c` — the inventory row is the nullable side of the LEFT JOIN and cannot be locked), so concurrent edits to one SKU serialise their read-then-reserve.
- Every mutation runs through `withOrderTxn(pool, id, fn)`: `BEGIN`, `SELECT ... FOR UPDATE` the order (404 if missing), run `fn`, `COMMIT`, then return the fresh order via `getAdminOrder`. Admin order shape exposes internal fields customers don't see (`guest_email`, `notes`, `shipping_address`, `contact_phone`, per-line `colourway_id` + `inventory` snapshot + `reserved_qty`).
## The order desk (W12: search, paging, the client's own numbers, creation mail)

- **`GET /admin/orders` is PAGED and returns `{ orders, meta: { total, page, limit } }`** — `DEFAULT_LIMIT` 50, `MAX_LIMIT` 200, both exported from `admin-orders.js` and `MAX_LIMIT` spent as the route schema's `maximum`, so an over-large limit is a **400** rather than a silent clamp reporting a page size nobody asked for (the `src/pricing/admin-price-lists.js` convention). `total` is counted over the same FROM and the same WHERE as the page — a total computed off a second query is one that disagrees with its own list. It used to return `{ orders }` unpaged; a caller reading `.orders` still works, a caller assuming it got the table does not.
- **`src/orders/order-filters.js` is a pure, pool-free leaf module and is NOT `src/reports/filters.js`.** Reports' values are slugs and enums — `[a-z0-9-]` **by construction** (`src/seed/slugify.js`), which is the only reason `parseSlug` can validate a shape and stop. A client reference and a customer PO number are free text somebody typed, so every value binds as `$n` **and** `%`/`_`/`\` are escaped in the pattern with an explicit `ESCAPE '\'` on every clause. Unescaped, a reference of `100%` matches every order in the table and `A_1` matches `AB1` — a wildcard injection whose only symptom is a search quietly answering with the wrong orders. `test/order-filters.test.js` proves the escaping with no database; `test/admin-orders.test.js` proves it against real rows with a `100%_A` reference and a `100XYA` near neighbour.
- **The whitelist is `ORDER_FILTER_COLUMNS`: name → a LIST of trusted `alias.column` literals**, not reports' name → one column, because the free-text filters legitimately span several. It fixes the aliases the caller's FROM must use (`o` orders, `u` the LEFT JOINed account). **`client` and `q` must search `o.guest_email` as well as `u.name`/`u.email`** — a guest order has no `users` row at all, so a client filter over the join alone silently excludes every order placed without a login. An unknown filter name is ignored; an unusable value is a 400 naming it; a blank value is ABSENT, never "match nothing".
- **`orders.client_reference` and `orders.customer_po_number`** (`1787457600000_order-reference-and-po-number.js`) are the CLIENT's two numbers. **`customer_po_number` is the PO number THEY issued to US** — it is not one of our purchase orders, which are W13's `purchase_orders` table with its own sequence. They never join and neither is derivable from the other; the `customer_` prefix is load-bearing. **No index on either, deliberately**: the search is `ILIKE '%term%'` and a btree cannot serve a leading wildcard, so an index would be maintained on every order write and never chosen. `orders.created_at` already carries the btree the date range uses.
- **Both are in `ORDER_HEADER_COLUMNS`, so `PATCH /admin/orders/:id` writes them** — editable rather than create-only because a PO number usually arrives in a later email, and an order nobody can attach one to is one the client's accounts payable will not pay. **A header field clears to NULL, never to `''`**: the CRM's text inputs send back an empty string when a person deletes what they typed, and a stored `''` is an absence every `IS NULL` read misses and every search matches. `applyOrderHeader` folds `''` to null for every header column.
- **Every creation path now alerts the back office** (`notifyBackofficeNewOrder` / `notifyOrderCreated`, `src/email/notifications.js`) at the ONE configured `mailer.backofficeEmail`. Not a per-salesperson routing table — that restriction is the client's actual requirement, and an order landing in one person's inbox is an order nobody covers when they are away. Before this, a paid Stripe checkout mailed the customer only and `POST /admin/orders` notified nobody at all.
- **The client's confirmation fires at CREATION, not at `confirm`.** `order_confirmed` moved onto the creation path; the `confirm` transition sends `order_invoiced` instead, so confirming tells the client something new rather than re-sending the mail they already have. Two events, two messages — do not collapse them back into one template.

- **Test gotcha**: register shares a rate-limit bucket (10 / 15 min / IP). Register staff/customer **once** in `beforeAll` and keep them; per-test `beforeEach` cleans only orders + brand fixtures, never users (re-registering each test 429s and yields no cookie). pg `numeric` qty comes back like `'10.00'` — compare with `Number()`, not string equality.

- **`orders.sales_rep_user_id` is a staff-asserted ANNOTATION** (migration `1790083200000`, A6 groundwork): FK users SET NULL, nullable, movable at ANY status via `PATCH /admin/orders/:id` — back-filling who sold a shipped order is the point — and settable on `POST /admin/orders`. `assertSalesRep` (one check, both write paths) 422s anything not in `USER_SEGMENTS.staff`; the read model joins `rep.name AS sales_rep_name`. NEVER backfilled from the legacy owner column (72% shared logins); checkout/storefront orders stay NULL and report as 'Unassigned'.
- **`GET /admin/orders` `status` takes one value OR a set** (repeated params → array via the schema's anyOf, bound `= ANY(...)`): the dashboard's Open tile means `HELD_STATUSES` at once. Single-status callers are unchanged.
