# atelier-api — orders

Extracted from the root CLAUDE.md (root conventions still apply). Loaded automatically when working in this directory.

## Order requests (fabric / backorder)

- `POST /orders/request` (`src/routes/orders.js` + `src/orders/order-request.js`) — a customer or guest asks the back office to cut and invoice fabric (FR-5/FR-6). Body `{ lines: [{ sku, qty_metres, cut_requirements? }], contact?: { name, email, phone }, accepted_lead_time?, client_reference?, customer_po_number? }`. Public (guests allowed via `loadOptionalUser`). Returns **201** `{ order: { id, order_number, kind, status, lines } }`.
- **Two-layer validation**: the body schema is structural only (empty `lines`/missing `sku` → **400**). `qty_metres > 0` and email validity are checked in the handler via `validateOrderRequestInput`, which returns **422** `{ message, errors: [{ field, message }] }` with field paths like `lines[0].qty_metres` / `contact.email`. Guests must supply `contact.email`; logged-in users fall back to their session email (order gets `user_id`, `guest_email` stays null).
- **Availability decides the kind**: for every line, `available = qty_available - qty_reserved` (pg-numeric strings coerced). All lines in stock → `kind='order_request'`, `order_number` `REQ-…`. Any line short → requires `accepted_lead_time=true` (else **422** "accept the quoted lead time"); then `kind='backorder_request'`, `order_number` `BO-…`. Both create `status='requested'`.
- **Reservation**: in one transaction each line increments `inventory.qty_reserved` by `qty_metres` (backorder lines reserve too — committed demand). The colourway row is locked `FOR UPDATE OF c` — the inventory row is the nullable side of the LEFT JOIN and **can't** be locked directly ("FOR UPDATE cannot be applied to the nullable side of an outer join"), so locking the colourway serialises concurrent same-SKU requests. Unknown/hidden SKU → **422**.
- **Every line carries an INDICATIVE price, not 0** (A2, Userback 8367521). `unit_price_cents` is resolved server-side through `resolveCartLines` (`src/catalogue/line-prices.js`) — the ONE copy of the trade-vs-retail rule, shared with the Stripe webhook, so a request and a checkout can never quote differently for the same SKU. The basis is `canSeeTradePricing(user)`, exactly how `createCheckoutSession` decides `includeTrade`: approved trade is quoted trade, everyone else retail. It is a quote, not a charge — the back office still edits every line before invoicing — but 0.00 on every request read as a bug to the office and made the CRM's order look empty. **A design the catalogue does not price stays at 0**: most fabric is unpriced (quoted per job), and `resolveCartLines` says "no price" by throwing, so `indicativePriceCents` catches and returns 0 rather than refusing a request the client is entitled to make. Safe because `resolveLine` has already proved the SKU exists and is listed, and a query that genuinely failed leaves the transaction aborted and blows up on the next statement. `subtotal_cents` is `Math.round` of `Σ qty × unit_price` — **once over the whole order**, the `recomputeOrderMoney` rule (rounding per line multiplies the error by the line count); `shipping_cents` stays 0 and `total = subtotal`, because nothing is shipped or charged from a request.
- **The phone has a column: `orders.contact_phone`** (A1, Userback 8367511). `contact.phone` is written there and is NOT packed into `orders.notes` any more — a number buried in free text is one the order desk cannot filter on, and one in both places is two that can disagree. `buildNotes` still *supports* a phone and the back office's `createManualOrder` still passes one, because that path has no `contact_phone` write; give it one and the phone leaves notes for good. Name and email stay in notes on both paths — nothing else displays them.
- **A signed-in requester's number is remembered**: the same transaction runs `UPDATE users SET phone = $1 WHERE id = $2 AND phone IS DISTINCT FROM $1` when a non-empty phone was submitted, so a request that rolls back remembers nothing and an unchanged number is not a write. `phone` is in `PUBLIC_USER_COLUMNS`, so `/auth/me` hands it back and the storefront form stops asking every time.
- **`client_reference` and `customer_po_number` are top-level on the request body** (A3, Userback 8367555; the same 200-char columns `PATCH /admin/orders/:id` writes — and it is `customer_po_number`, never `client_po_number`). Blank values fold to NULL, never `''`, the header-column rule the order desk applies: a stored `''` is missed by every `IS NULL` read and matched by every search. Ajv's `removeAdditional` strips unknown keys silently, so the route's **named argument list** — not the schema — is what decides which body fields reach a column.

## Order history

- `GET /orders/mine` (`src/routes/orders.js` + `src/orders/order-history.js`) — auth (`requireAuth`), returns `{ orders: [...] }` newest first, each with `lines`. Ownership is enforced in SQL (`WHERE user_id = request.user.id`), never in the handler, so one user can never read another's orders.
- **`GET /orders/lookup` is gone** (22 Sep 2026). The public order_number + email lookup let anyone who knew (or guessed) both halves read another client's order — a logged-in client already sees theirs under `/account`. Do not bring it back as a "guest" convenience; `test/orders-history.test.js` asserts the route 404s even with a matching pair.
- Order shape (`toOrder`): `id, order_number, kind, status, subtotal_cents, shipping_cents, gst_cents, total_cents, shipping_zone, xero_invoice_ref, shipping_address, created_at, lines`. Lines carry `sku, product_name, qty, unit_price_cents, cut_requirements`. Internal columns (`stripe_session_id`, `guest_email`) are not exposed. Lines are batch-loaded for all order ids in one query (`ol.order_id = ANY($1::int[])`) then grouped — no N+1.

## Back-office order management

- `src/routes/admin-orders.js` + `src/orders/admin-orders.js` (US-014, FR-7). All routes `requireRole('backoffice')` (director inherits). Handlers stay thin; the state machine + reservation logic live in the module.
- **Lifecycle** (order-request / backorder kinds): `requested --confirm--> confirmed --mark-paid--> paid --ship--> shipped`; `requested|confirmed --decline--> declined`. Any other transition throws **409** via `requireStatus`. `confirm` stores `xero_invoice_ref` from the body (manual Xero, no API call).
- **`mark-paid` marks the Xero invoice paid too** (16 Sep 2026 feedback). The route takes `xero` (null when unconfigured) and answers `{ order, xero_payment?: { recorded, amount?, payment_id?, invoice_number?, reason? } }`; the transition itself never fails because of Xero. See `src/xero/CLAUDE.md`.
- **`ship` takes an OPTIONAL `tracking_url`** (A4, Userback 8367567; migration `1790515200000`). `POST /admin/orders/:id/ship { tracking_url? }` — the route schema is `type: ['object','null']` so a body-less ship still works (Fastify validates a missing body as `null`, and declaring only `object` would 400 every ship the CRM sends today), and `pattern: '^https?://'` is the whole validation: the string is put in a client's inbox as a link, so `javascript:…` or a bare `nzpost.co.nz` is a **400** before anything ships. `shipOrder(pool, id, { trackingUrl })` writes it in the SAME `UPDATE` that sets `status='shipped'`, so the order handed to `notifyOrderTransition` already carries the link the `shipped` letter quotes; the office hand-delivers plenty of orders, so null is ordinary and the letter simply drops its tracking line. Exposed as `tracking_url` on the admin order shape.
- **Reservation model**: only `RESERVING_KINDS` (`order_request`, `backorder_request`, `manual`) touch inventory here; `checkout` orders arrived paid + already-decremented and hold no reservation (`reserves(kind)` guards every inventory write). `reservation_state` per order = `held` (requested/confirmed/paid) → `converted` (shipped: `qty_reserved -=`, `qty_available -=`) or `released` (declined: `qty_reserved -=`). `ship`/`decline` update inventory with a single `UPDATE inventory i ... FROM order_lines ol WHERE ol.order_id=$1 AND i.colourway_id=ol.colourway_id` (no per-line loop). A colourway with no inventory row (short backorder) reserved nothing, so the join simply matches nothing.
- **Endpoints**: `GET /admin/orders` (see the order desk below), `POST /admin/orders` (201), `GET /admin/orders/:id` (404), `PATCH /admin/orders/:id`, `DELETE /admin/orders/:id`, `POST .../confirm|mark-paid|ship|decline|archive|restore`. `:id` is an integer param (Fastify coerces; non-numeric → 400).
- **`kind` is the order's CHANNEL, not its behaviour**, and `manual` (migration `1786939200000_manual-order-kind.js`) is the fourth: a sales order the back office keyed from a phone call, a walk-in, a bespoke enquiry — or from a storefront request that turned into a bigger job. Reusing `order_request` for those would erase the one distinction the office wants in its lists and its reports, and the `SO-` order-number prefix is a string convention rather than a queryable dimension (`src/reports/filters.js` filters on `o.kind`). **Widening the CHECK is half the change**: `RESERVING_KINDS` (`src/orders/order-states.js`), `ORDER_KINDS` (`src/reports/filters.js`) and `INVOICEABLE_KINDS` (`src/reports/not-invoiced.js`) move in the same commit, plus the CRM's `KIND_LABELS`. `test/admin-reports.test.js` parses the live `orders_kind_check` and asserts it equals `ORDER_KINDS`, so a half-done widening fails loudly — that is the tripwire working. A test that retypes one of these sets as a literal will fail on the next kind; assert the exclusion (`not.toContain('checkout')`) or compare against the constant.
- **`src/orders/order-states.js` is a pure, zero-import leaf module** holding `RESERVING_KINDS`/`reserves`, `DELETABLE_ORDER_STATUSES`, `HELD_STATUSES`, `isDeletableOrder`, `holdsReservation` — the `sample-order-states.js` posture, for the same three reasons: `src/lifecycle/registry.js` imports it (and cannot import `admin-orders.js`, which imports `lifecycle/archive.js` → registry: a cycle), the CRM mirrors it so a Delete button is never offered where the API would 409, and it unit-tests with no database. `RESERVING_KINDS` lived in `admin-orders.js` until the delete story needed it; that module now imports it, so there is one source of truth rather than two copies that could disagree about whether a manual order holds stock.
- **`POST /admin/orders` (`createManualOrder`) is a separate module function, not a parameterisation of `createOrderRequest`** — that one is keyed on SKU, prices every line off the catalogue (an indicative figure the office edits, see above) and applies the storefront's trade-visibility gate. This one takes prices, addresses colourways by id (the CRM picks them out of the catalogue search) and trusts the backoffice guard, because staff key orders against unlisted designs and trade-only houses as a matter of course. Attribution is `user_id` **or** a walk-in's `contact` (422 when neither: an order nobody can be billed for is not a sales order); the contact is packed through the **exported** `buildNotes` from `order-request.js`, so `orders.notes` reads identically however the order was raised. A `guest_email` is written only when there is no account — the account's own address is the one to write to, and a copy here goes stale. Every line is resolved (and its colourway locked) before anything is written, so an unknown colourway refuses the whole order rather than leaving half of one behind.
- **A manual order may carry a `shipping_address`, and the CRM fills it from the CLIENT'S OWN RECORD.** Same optional body field, same key set and same `addressOrNull` trimmer the storefront's request uses (`SHIPPING_ADDRESS_SCHEMA` is exported from `order-request.js` and imported by both route files, so the two cannot drift), landing in the same `orders.shipping_address` jsonb the Stripe webhook writes — one Delivery block and one packing slip read all three paths. The order desk does not type it: the CRM sends the address off the `trade_accounts` row it picked (835 of the 860 merged clients carry one), and an order for a client with nothing on file simply has none rather than `{}`, which would print an empty Ship-to block.
- **`PATCH /admin/orders/:id` is what turns a storefront quote into an invoiceable sales order.** Body: `lines` (per-line `qty` / `unit_price_cents` / `cut_requirements`, `minProperties: 2` so an id alone is a 400), `add_lines` (`colourway_id`, `qty`, `unit_price_cents`), `remove_line_ids`, plus `notes` / `guest_email` / `contact_phone`; `anyOf` demands at least one key, because Ajv's `removeAdditional` strips unknown ones rather than rejecting them. The old qty-only body still validates. Order of operations is removals → edits → adds → header → **recompute**, and removals go first because they free reservation a re-add in the same request may want back. **The money is always recomputed from the lines** (`ROUND(SUM(qty * unit_price_cents))::int`, once over the whole order — rounding per line multiplies the error by the line count); `shipping_cents` is never touched here and `total = subtotal + shipping`. **An order may not be left with no lines** (422): declining it releases the reservation and leaves a record, where an empty order would keep its number and say nothing. **A patch carrying nothing but `notes` is allowed at ANY status** (A4): the note about a delivery — the courier, the phone call, what the client asked for on the doorstep — arrives once the order is paid or shipped, and a guard that refuses it there sends it to somebody's notebook instead. It rides ALONE rather than joining `ANNOTATION_COLUMNS`, because `notes` is also the header field an ordinary edit carries alongside lines and money: one key means the annotation, `notes` in company with anything else is an edit and keeps `requireStatus(['requested','confirmed'])` exactly as it was. Money, lines and the reservation stay frozen.
- **The delivery details are editable until the order ships** (23 Sep 2026, the CRM order page's Edit delivery). `PATCH /admin/orders/:id { shipping_address }` takes the same `SHIPPING_ADDRESS_SCHEMA` and stores through the same `addressOrNull`; **sent ALONE it is accepted at `requested`/`confirmed`/`paid`** (`DELIVERY_EDIT_STATUSES`, 409 once shipped or declined) and skips the line checks and `recomputeOrderMoney` entirely, because a paid card checkout's total is what Stripe charged and a new address must not re-derive it. In company with any other key it is an ordinary edit behind the requested/confirmed guard (the notes-only posture). `null` clears it; an address naming neither `line1` nor `city` is a **422** here, where the create paths silently store none, because somebody pressed Save on a delivery they meant to record. The shape grew two OPTIONAL keys, `phone` (whoever receives it, often not the client) and `instructions` ("Mark parcel: Lounge"), which `addressOrNull` stores only when given, so a webhook or storefront address keeps exactly its seven keys. The packing slip prints both in its Deliver-to block.
- **An admin order line carries `composition`, `width`, `size` and `description` off its product** (null where the record is unfilled) so the packing slip can print the product's description, Contents and Width under the design, as the D365 slip did. Admin shape only; the customer `toOrder` is unchanged.
- **`orders.discount_pct` is the manual pricing override (Rebecca-R2), and it is an INPUT to the one recompute, never a second total.** `subtotal_cents` stays the un-discounted figure; `recomputeOrderMoney` computes `total_cents = ROUND(subtotal * (1 - discount_pct/100))::int + shipping_cents`, so every path that re-totals (line edit, add, removal, the discount change itself) agrees by construction — mirrored by `discountedTotalCents` in `src/orders/discounts.js` and tripwired by `test/order-discounts.test.js`. **0/5/10 are the standard tiers any back-office user may set; anything else is director-only and must carry a non-blank `discount_reason`** (403 / 422 from `checkDiscountWrite` — an in-HANDLER check on `request.user.role`, the admin-users self-protection posture, because the route guard stays `requireRole('backoffice')` and director *inherits* backoffice, so the guard cannot draw this line). The pct and its reason travel as a pair (a reason alone is a 400 via schema `dependencies`; a pct without one clears the stored reason), `discount_applied_by` is stamped from the session and never readable from the body, and a discount is a commercial term — it sits behind the requested/confirmed status guard like a price edit, not with the annotations. The customer-facing `toOrder` deliberately does not expose any of the three columns: the totals already reflect the discount, and who authorised it is the office's business. `discounts.js` is a pure zero-import leaf (the `order-states.js` posture); the CRM mirrors its tiers so Custom is disabled for non-directors rather than discovered as a 403.
- Every inventory write goes through `moveReservation(client, kind, colourwayId, delta)`, gated on `reserves(kind)`; a colourway with no inventory row reserved nothing, so the UPDATE matches nothing. `lockColourway` is the `resolveLine` idiom (`FOR UPDATE OF c` — the inventory row is the nullable side of the LEFT JOIN and cannot be locked), so concurrent edits to one SKU serialise their read-then-reserve.
- Every mutation runs through `withOrderTxn(pool, id, fn)`: `BEGIN`, `SELECT ... FOR UPDATE` the order (404 if missing), run `fn`, `COMMIT`, then return the fresh order via `getAdminOrder`. Admin order shape exposes internal fields customers don't see (`guest_email`, `notes`, `shipping_address`, `contact_phone`, per-line `colourway_id` + `inventory` snapshot + `reserved_qty`).
- **`confirm` and `mark-paid` refuse while any line is at $0.00** (422 naming the count, from `unpricedLineCount(lines)` in `order-states.js` — the zero-import leaf, so `src/xero/service.js` applies the SAME predicate to the invoice push and the CRM mirrors it to disable the buttons). A storefront request arrives with every line at 0 meaning "not priced yet", and the 15 Sep 2026 audit confirmed and Xero-invoiced one at nil. `requirePriced` reads the lines inside the order's own transaction because `withOrderTxn` selects only `id, kind, status`. `ship` is deliberately NOT gated: a PATCH may still zero a line at `confirmed`, but money is frozen from `paid` on, so once mark-paid refuses an unpriced paid order cannot exist. No director override — an unpriced order is priced, not confirmed at nil. Consequence for tests: `placeRequest` in `test/admin-orders.test.js` prices its line through the real PATCH before handing it back; pass `{ unitPriceCents: 0 }` for the raw storefront state. Admin lines also carry **`unit`** (`'metres' | 'units'` from `inventory`, null when never stocked, like `inventory`); the customer shape does not, because its lines have `product_type`, which decides the unit.
## The order desk (W12: search, paging, the client's own numbers, creation mail)

- **`GET /admin/orders` is PAGED and returns `{ orders, meta: { total, page, limit } }`** — `DEFAULT_LIMIT` 50, `MAX_LIMIT` 200, both exported from `admin-orders.js` and `MAX_LIMIT` spent as the route schema's `maximum`, so an over-large limit is a **400** rather than a silent clamp reporting a page size nobody asked for (the `src/pricing/admin-price-lists.js` convention). `total` is counted over the same FROM and the same WHERE as the page — a total computed off a second query is one that disagrees with its own list. It used to return `{ orders }` unpaged; a caller reading `.orders` still works, a caller assuming it got the table does not.
- **`src/orders/order-filters.js` is a pure, pool-free leaf module and is NOT `src/reports/filters.js`.** Reports' values are slugs and enums — `[a-z0-9-]` **by construction** (`src/seed/slugify.js`), which is the only reason `parseSlug` can validate a shape and stop. A client reference and a customer PO number are free text somebody typed, so every value binds as `$n` **and** `%`/`_`/`\` are escaped in the pattern with an explicit `ESCAPE '\'` on every clause. Unescaped, a reference of `100%` matches every order in the table and `A_1` matches `AB1` — a wildcard injection whose only symptom is a search quietly answering with the wrong orders. `test/order-filters.test.js` proves the escaping with no database; `test/admin-orders.test.js` proves it against real rows with a `100%_A` reference and a `100XYA` near neighbour.
- **The whitelist is `ORDER_FILTER_COLUMNS`: name → a LIST of trusted `alias.column` literals**, not reports' name → one column, because the free-text filters legitimately span several. It fixes the aliases the caller's FROM must use (`o` orders, `u` the LEFT JOINed account). **`client` and `q` must search `o.guest_email` as well as `u.name`/`u.email`** — a guest order has no `users` row at all, so a client filter over the join alone silently excludes every order placed without a login. An unknown filter name is ignored; an unusable value is a 400 naming it; a blank value is ABSENT, never "match nothing".
- **`orders.client_reference` and `orders.customer_po_number`** (`1787457600000_order-reference-and-po-number.js`) are the CLIENT's two numbers. **`customer_po_number` is the PO number THEY issued to US** — it is not one of our purchase orders, which are W13's `purchase_orders` table with its own sequence. They never join and neither is derivable from the other; the `customer_` prefix is load-bearing. **No index on either, deliberately**: the search is `ILIKE '%term%'` and a btree cannot serve a leading wildcard, so an index would be maintained on every order write and never chosen. `orders.created_at` already carries the btree the date range uses.
- **Both are in `ORDER_HEADER_COLUMNS`, so `PATCH /admin/orders/:id` writes them** — editable rather than create-only because a PO number usually arrives in a later email, and an order nobody can attach one to is one the client's accounts payable will not pay. **A header field clears to NULL, never to `''`**: the CRM's text inputs send back an empty string when a person deletes what they typed, and a stored `''` is an absence every `IS NULL` read misses and every search matches. `applyOrderHeader` folds `''` to null for every header column.
- **Every creation path now alerts the back office** (`notifyBackofficeNewOrder` / `notifyOrderCreated`, `src/email/notifications.js`) at the ONE configured `mailer.backofficeEmail`. Not a per-salesperson routing table — that restriction is the client's actual requirement, and an order landing in one person's inbox is an order nobody covers when they are away. Before this, a paid Stripe checkout mailed the customer only and `POST /admin/orders` notified nobody at all.
- **The client's confirmation fires at CREATION, not at `confirm`.** `order_confirmed` moved onto the creation path; the `confirm` transition sends `order_invoiced` instead, so confirming tells the client something new rather than re-sending the mail they already have. Two events, two messages — do not collapse them back into one template.

- **Test gotcha**: register shares a rate-limit bucket (10 / 15 min / IP). Register staff/customer **once** in `beforeAll` and keep them; per-test `beforeEach` cleans only orders + brand fixtures, never users (re-registering each test 429s and yields no cookie). pg `numeric` qty comes back like `'10.00'` — compare with `Number()`, not string equality.

- **`orders.sales_rep_user_id` is a staff-asserted ANNOTATION** (migration `1790083200000`, A6 groundwork): FK users SET NULL, nullable, movable at ANY status via `PATCH /admin/orders/:id` — back-filling who sold a shipped order is the point — and settable on `POST /admin/orders`. `assertSalesRep` (one check, both write paths) 422s anything not in `USER_SEGMENTS.staff`; the read model joins `rep.name AS sales_rep_name`. NEVER backfilled from the legacy owner column (72% shared logins); checkout/storefront orders stay NULL and report as 'Unassigned'.
- **`orders.notify_emails` is the order's Emails list** (migration `1791552000000`, 23 Sep 2026): extra addresses that receive every status letter on top of the client and the sales rep (who are read off the order, never copied into the list, so re-assigning the rep moves their letters with them). `text[] NOT NULL DEFAULT '{}'` — `[]` is the one spelling of "nobody extra", so the PATCH schema takes an array and never null. An ANNOTATION like the rep: writable at any status via `PATCH /admin/orders/:id { notify_emails }`, which REPLACES the list (the CRM sends it whole on every add/remove). Shape and count (`NOTIFY_EMAIL_PATTERN`, `NOTIFY_EMAILS_MAX` = 10) are the route schema's, from the pure leaf `src/orders/notify-emails.js`, which the CRM mirrors; `uniqueEmails` stores one spelling per address. The admin shape also carries `sales_rep_email` (NULL for an archived rep). Who receives what is in `src/email/CLAUDE.md`.
- **`POST /admin/orders/:id/email { letter: 'details'|'status' }`** (24 Sep 2026) — the CRM Emails panel's Send buttons: the whole order, or the current status letter again, to the client, rep, list and the standing `ORDER_COPY_EMAIL` copy. Refusals and recipients in `src/email/CLAUDE.md`.
- **`orders.price_type` is the basis the order was priced off — `trade` or `retail`** (migration `1791120000000`, `PRICE_TYPES` in `admin-orders.js`, spent as the route schemas' `enum` so the CHECK and the vocabulary cannot drift). **Stated, never derived**: `canSeeTradePricing(user)` answers what the STOREFRONT quotes, and the office routinely charges the other one — trade terms on a walk-in job, retail on a one-off to a trade client — so an account-derived read model would quietly contradict the invoice. NOT NULL, default `retail`, backfilled to `trade` for approved-trade accounts (the rule the storefront actually priced by at the time), which is why the schema declares `string` + `enum` and **not** `['string','null']`: a null would reach Postgres as a 23502 and surface as a 500 where the enum answers 400. It is a COMMERCIAL TERM, not an annotation — it sits in `ORDER_HEADER_COLUMNS` behind the requested/confirmed guard like a price edit or the discount, so it freezes once the invoice is out. Settable on `POST /admin/orders`.
- **`GET /admin/orders` `status` takes one value OR a set** (repeated params → array via the schema's anyOf, bound `= ANY(...)`): the dashboard's Open tile means `HELD_STATUSES` at once. Single-status callers are unchanged.

## Userback 15 Sep 2026 (order numbers, GST, line identity, discount to the client)

- **`migrations/1790601600000_legacy-order-numbers.js` renumbered the pre-#56 card checkouts** from `WEB-cs_test_…` (70 chars of Stripe session id) to `WEB-XXXXXXXX` — deterministic (`md5(old)` first 8 hex, upper) so a re-run is a no-op and a collision aborts on the unique index. Nothing keyed on the old string (Xero gets the PO/client reference, the webhook ledger keys on the event, the success page looks up by `stripe_session_id`); letters already sent carry the old number, which is why `down` is a no-op. New numbers come from `src/orders/order-number.js`, never from a Stripe id.
- **GST is derived, never stored** (`src/orders/gst.js`, Userback 8367857). Every `/admin/orders*` response carries `order.gst = { basis, rate, gst_cents, total_incl_gst_cents }`, added by ONE `preSerialization` hook in `adminOrderRoutes` rather than in each handler, from `total_cents` and the same `XERO_LINE_AMOUNT_TYPES` the invoice push uses (`buildApp({ lineAmountTypes })`, default `Exclusive`: GST on top; `Inclusive`: 3/23 of the total; `NoTax`: 0). Do NOT add a tax column: the figure is a function of the total and the basis, and a stored copy would only let the two drift. The customer read model (`/orders/mine`) has no derived GST block (it does expose the stored `gst_cents` a card checkout charged) — the client sees the indicative total; the invoice states the tax.
- **Admin order lines carry `product_id`, `product_slug`, `colourway_name`** (Userback 8367841) so the CRM can open the stock row behind a SKU. The customer read model already had `slug`/`colourway_name` for reorder; the admin one lagged.
- **`/orders/mine` exposes `discount_pct` and nothing else about the discount** (Userback 8367809): the client sees why the total is under the subtotal; `discount_reason` and `discount_applied_by` stay in the back office (`src/orders/admin-orders.js` header comment).
- **A request carries the client's own `notes` and an optional `shipping_address`** (Userback 8373461). `orders.notes` used to hold only the packed `Name: … | Email: …` line for every request, so the office opened a note field full of contact details and no note. Now: the client's note first, then `Name: <guest name>` ONLY for a guest (no account row to carry it) — `guest_email` and `contact_phone` are columns, so neither is packed any more. `buildNotes` is unchanged for the back office's manual create. The address is validated to the webhook's key set, trimmed, stored only when it names a `line1` or `city` (a name alone is not an address), and `JSON.stringify`'d into the jsonb column.
