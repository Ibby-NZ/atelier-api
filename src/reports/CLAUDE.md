## Reporting

- **`src/lib/csv.js` is the one CSV writer in this API — `csvCell` and `csvRow`, and nothing else.** It was extracted verbatim from `src/pricing/trade-price-lists.js` (formula guard, RFC 4180 quoting and the comments explaining both), because a second copy is how the formula-injection guard stops being applied everywhere: the reporting export writes the same staff-typed free text into the same Excel. `test/price-list-exposure.test.js` is the proof the extraction was a MOVE — it was not edited, and it exercises the escaping through `toTradePriceListCsv`, so a behaviour change fails it on the `= + - @` lead-ins and on `"Linen, ""washed"""`.
- **The module owns one cell and one row; the caller owns the header, the row order and the line terminator.** `toTradePriceListCsv` keeps its own `CSV_HEADER`, its `\r\n` join and its trailing newline. That split is what lets a report with a different header, a different terminator or a streamed body reuse the escaping without inheriting a file format — and it is why `csvRow` deliberately does not append a line ending.
- **`FORMULA_PREFIXES` stays module-private.** Nothing imports it, and exporting a mutable array of the security rule invites a caller to extend it locally instead of here. Widen the guard in one place or not at all.
- **Every value written through `csvCell` is neutralised, including a number.** Do not pre-format a cell into a string "to save a conversion" and then bypass the helper — a product name beginning `=` reaching a file unguarded is the exact regression this module exists to prevent, and it is invisible until the client opens the file.

### Schema (`1786680000000_reporting-finance-access.js`)

- **`orders.created_at` carries a plain ascending btree, and that is the whole choice.** Every report here is a date range first and a filter second, while the two pre-existing indexes (`user_id`, `status`) are the account and lifecycle access paths and neither helps a range predicate. Not DESC — a btree range scan is direction-agnostic, so `ORDER BY created_at DESC` uses it anyway. Not a composite `(status, created_at)` — the status filter is overridable, so the column that is ALWAYS in the predicate is the one to index.
- **`users.can_view_finance` is `boolean NOT NULL DEFAULT false`, because finance visibility must fail CLOSED.** A nullable column turns "nobody has decided yet" into a third value every reader has to interpret, and the interpretations drift. Role alone will not do the job either: `backoffice` covers the showroom and the accounts desk alike, which is exactly why a second explicit permission exists. The migration backfills `true` for directors — the role that already sees every cost figure in the CRM, so the grant changes nothing about what they reach and everything about what a `backoffice` login can.
- **The backfill statement is EXPORTED (`DIRECTOR_BACKFILL_SQL`) and guards itself with `AND can_view_finance = false`.** node-pg-migrate reads only `up`/`down`, so the export is free and lets `test/admin-reports.test.js` run the exact statement that ran rather than a retyped copy — the posture `1786593600000_featured-rank.js` established, and the only way to prove a backfill at all on a database whose `users` table is empty. The guard is what makes a second run a genuine zero-row no-op the test can assert.
- **`can_view_finance` joins `USER_UPDATE_COLUMNS` under the same discipline as `trade_approved`: a role moved off `backoffice`/`director` clears it.** The flag only means anything on a staff row, so leaving it set strands a `true` where nothing displays it and hands finance visibility straight back on a later re-promotion, with no review — the identical shape of the `trade_approved` regression. An explicit `can_view_finance: true` in the same body LOSES: the role is the stronger statement, and the two together are a contradiction rather than an instruction. Enforced in `updateUser`, so it holds for every caller.
- **It is not yet writable over HTTP.** `patchBodySchema` in `src/routes/admin-users.js` does not list the property, and Ajv's `removeAdditional: true` STRIPS an unlisted key rather than 400ing it — so a CRM PATCH carrying it answers 200 having written nothing. The live write paths today are the migration's backfill and the AdminJS panel (`users` is an editable resource and `@adminjs/sql` picks the column up by introspection). Adding the schema property is the one edit needed, and it belongs to whoever owns that route file.
- `USER_READ_COLUMNS` now carries it, which widens `createUser`/`getUser`/`listUsers`/`setUserArchived` at once. That was safe only because `test/admin-users.test.js` asserts with `toHaveProperty` and never an exact `toEqual` on a user — check that before widening it again.

### The filter layer (`src/reports/filters.js`)

- **One pure module turns a reporting querystring into SQL, and every Epic 5 report goes through it** — the table and its CSV export share one query builder (US-006), so a second parsing path is how the file and the screen start disagreeing about what was filtered. It takes no pool, issues no query and stubs nothing, which is what makes `test/report-filters.test.js` able to prove the whitelist and the placeholder discipline on their own. The moment it needs `loadConfig()` it has stopped being that proof.
- **`FILTER_COLUMNS` is the frozen name -> trusted-column whitelist and it also FIXES the table aliases every report query must use**: `o` orders, `b` brands, `p` products, `col` collections — the same letters the order and catalogue read models already carry. A report that aliases its FROM differently gets clauses that do not resolve. `from` and `to` are two bounds on one column, which is why the map is name->column and the clause shape lives in `buildReportFilters`.
- **An unknown filter NAME is ignored; an unusable filter VALUE is a 400 naming it.** Ignoring is the posture the public catalogue listing already takes — the whitelist is what controls which filters exist, never a schema's strictness (Ajv's `removeAdditional: true` strips unknown keys rather than rejecting them, so a route schema could not reject one anyway). A recognised name carrying a bad value is the opposite case: it is a typo whose only other symptom is an empty report, which reads as "no trade".
- **`to` is exclusive on the NEXT day (`< ($n::date + 1)`), never `<= $n::date`.** `orders.created_at` is `timestamptz`, so `<= to::date` cuts the range at that morning's midnight and silently drops the whole last day of the office's own report. The bounds resolve in the database session's timezone; nothing here pins one.
- **`brand` is the one multi-valued filter** — the office compares houses against each other, and one house at a time is a different question. Repeated params (`brand=a&brand=b`) and one comma-separated value are both accepted (the CRM sends the first, a hand-typed URL the second), blanks are dropped, the list is de-duplicated and it binds as `= ANY($n::text[])`. A wholly blank value is ABSENT, never "match nothing".
- **Values are validated for SHAPE, so `brand=Pierre Frey` is a 400 rather than a report matching nothing.** Slugs are `[a-z0-9-]` by construction (`src/seed/slugify.js`), which is what makes that safe — a future filter over free text (a product name, an order number) must not reuse `parseSlug`.
- **`names` is how a report declines a filter it cannot honour**, and an unknown entry throws a plain Error (a 500), not a 400: it is a code literal, exactly like a lifecycle registry key, so a client can never reach it. The stock report has no `orders` in its FROM, so a `status` clause there is a broken query rather than a narrowing.
- **`buildReportFilters` copies the caller's `params` array and never appends to it**, so a report can bind its own placeholders first and hand them in. Clauses come out in `REPORT_FILTER_NAMES` order rather than the caller's key order, so one filter set is always one SQL string.
- **`PRODUCT_TYPES` and `ORDER_KINDS` are boundary copies of the schema CHECKs; `ORDER_STATUSES` is re-exported from `src/orders/admin-orders.js` rather than retyped.** A boundary copy exists so an unknown value is a 400 instead of a 500, and its cost is silent drift — so `test/admin-reports.test.js` parses the LIVE `pg_get_constraintdef` for all three and asserts the sets match, the posture `DISCOUNT_METHOD_ENUM` takes. Where a frozen JS list already exists, import it: architecture.md § Reporting says the revenue default becomes a change to one frozen constant when the client settles A2, and a second copy is how that turns into two decisions.

### The revenue scope (`src/reports/revenue-lines.js`)

- **Every money report answers a question about ONE population, so the population is declared once and each report selects out of it.** `buildRevenueScope(filters, { params })` returns `scope AS ( … )` plus its bound params; a report writes `WITH ${cte} SELECT … FROM scope`. US-005 groups it by house and design, US-006 exports the same query and US-007's not-invoiced narrows it — which is the point: the table and its CSV cannot disagree about what revenue means if neither restates it.
- **`REVENUE_STATUSES` (`paid`, `shipped`, all kinds) is the default population and is ONE frozen constant**, because architecture.md § Reporting says settling A2 ("what counts as a sale") is a change to that constant and nothing else. Only checkout orders carry money — the Stripe webhook inserts them `paid` with every price re-resolved from `retail_price_cents`. `confirmed` is deliberately absent: on this platform a confirmation is a Xero reference typed by a human and carries no amount.
- **A `status` filter REPLACES the default population rather than narrowing it.** The clause is omitted entirely when the caller supplied one; intersecting the two would answer `status=requested` with zero rows, which reads as "no trade" rather than "outside the default".
- **A request-kind line is IN the population and contributes its QUANTITY at zero value.** Those lines are created at `unit_price_cents = 0` and nothing ever fills them in, so every scope row carries `unpriced` and a report counts them (`COUNT(*) FILTER (WHERE unpriced)`). Dropped, they understate the metreage sold; counted as money, they understate the average price — the count is what lets a reader tell the two apart.
- **`line_value_cents` is `numeric`, not an integer.** `qty` is `numeric(12,2)`, so 2.5 m at NZ$19.99 is 4997.5 cents. Round at the AGGREGATE (`ROUND(SUM(…))`, as `summariseRevenue` does), never per line, or the rounding error is multiplied by the row count — and pg then hands the sum back as a string, so coerce with `Number()`.
- **`SOURCES` is the union seam, and it is checked positionally at module load.** One source today (live order lines); when legacy line data exists it becomes a second entry unioned into the same CTE rather than a rewrite of each report. Nothing can be unioned yet — all four D365 transaction entities are header-only — which is exactly why the seam is built before there is anything to put through it. `assertScopeSource` compares each source's column list to `SCOPE_COLUMNS` **in order**, because a UNION ALL lines its branches up by position: two sources agreeing on the names but not the order would file one house's revenue under another's heading and raise nothing. It is exported so the unit tests prove it rejects a drifted source.
- **Archived ORDERS are excluded; archived products and brands are deliberately not.** An archived order is one the back office took out of its own lists and must stop contributing to revenue, but the sale of an archived design still happened — a catalogue tidy-up must never rewrite last quarter's figures.
- `listRevenueLines` is bounded (`REVENUE_LINE_LIMIT`) on purpose: a report aggregates in SQL, and this is the one read that does not, so nothing here streams the ledger into memory by accident. It also carries `client`, a COALESCE over the scope's own `user_id`/`guest_email` — the same read not-invoiced makes of the same two columns, and the reason neither report needs a second join tree.

### The orders behind the numbers (`revenue-lines`, the report — Userback 8287873)

- **`GET /admin/reports/revenue-lines` is the population itself, one row per line**, and it exists because the office's next question after every aggregate is which orders that figure is made of. It lives in `src/reports/revenue-lines.js` beside the scope rather than in a file of its own: the report IS `listRevenueLines` in the envelope, and a second module named after the same thing is how a reader ends up editing the shared population while meaning to edit one report. Everything above the readers in that file is the population — a report edit must not reach it.
- **It is the ONE report whose export is still capped.** `limit: null` is the every-row contract everywhere else in this library, and honouring it here would be an unbounded line-grain read of the whole order ledger — precisely what `REVENUE_LINE_LIMIT` exists to prevent. `limit: null` therefore resolves to that bound (and `listRevenueLines` re-applies it regardless, so the cap holds even if `MAX_ROW_LIMIT` and `REVENUE_LINE_LIMIT` ever part company). The honesty mechanism is the same one the tables use — `meta.rows_total`, `meta.truncated`, `meta.row_limit` — plus `coverage.row_cap` and a coverage note that states the ceiling **in the file**, because a truncated CSV read as a complete one is the failure this would otherwise ship.
- **`value_cents` is not a `finance` column, matching product performance.** A sell value is money and is not a cost; marking it finance here would contradict the policy the CRM already applies and would mask a figure its neighbour serves openly. Masking still runs (`meta.masked_columns` is `[]`), which is what makes the day this report gains a cost column a one-line change.
- **A row's `value_cents` is NOT rounded; the totals row is.** `line_value_cents` is numeric because `qty` is `numeric(12,2)`, so one line can be worth 4997.5 cents — the rule is round at the AGGREGATE, and here the row IS a line, so the exact figure is the honest one and `ROUND(SUM(…))` happens once over the population.
- The two totals rules its neighbours live by apply unchanged: no `qty` while the population holds both metres and units, no `value_cents` while it quotes more than one currency. `meta.statuses` states the lifecycle window, because a `status` filter REPLACES the paid/shipped default rather than narrowing it.
- Every filter it honours is already in the route's `FILTER_PROPERTIES` — it honours the whole of `REPORT_FILTER_NAMES` through the shared scope, and the two lists match today. A filter added to `src/reports/filters.js` and not to that object answers 200 having filtered nothing (Ajv's `removeAdditional` strips it), so the filter assertions for this report go through the ROUTE and not through the builder.
- Guarded by 23 tests in `test/admin-reports.test.js`, sharing the module-scoped order fixture and adding one finished good sold to an ACCOUNT — which is what makes the client name, the mixed-unit totals rule and the guest/account COALESCE provable at once.

### Report access and masking (`src/reports/access.js`)

- **Access is derived from `request.user` and nothing else.** `reportAccess(user)` takes the user record — not a request, so there is no query param, header or body value that can reach it — and returns a frozen `{ reports, finance }`. `reports` is the derived statement `/auth/me` hands the CRM in US-008; the real gate is still the route's `requireRole('backoffice')`, so a drift in `REPORT_ROLES` can only mis-describe a route, never open one.
- **Finance visibility is the `can_view_finance` column, never the role — that is what makes it revocable.** `director` is not ORed in: a role-derived answer can be granted and never taken back, so an explicit revocation would be silently ineffective. Consequence to know: a director created AFTER `1786680000000_reporting-finance-access.js` starts closed, because the migration backfilled the directors that existed and the column defaults false.
- **A finance column is DELETED — from `columns`, from every row and from `totals`.** Not nulled and not blanked: a key that survives with an empty value still tells the reader which figures exist. `meta.masked_columns` carries the dropped columns' **labels** only; a key is the machine name of a figure this caller may not have.
- **Rows are PROJECTED onto the surviving columns, not subtracted from.** Subtraction can only remove what somebody remembered to declare; a projection cannot leak a key nobody declared. The cost is the right way round — an undeclared key silently disappears, which surfaces as a missing value in the report's own test, where a leaked cost figure is invisible. Consequence: anything a screen needs (a `brand_slug` behind a link) must BE a declared column, though not one the table has to render.
- **A report that is finance end to end answers 403 with a reason, never 200 with an empty table** — "no rows" and "you may not see this" are indistinguishable on a screen, and only the second is something a person can act on. Both the structural case (every column `finance`) and a report's own `finance_only` declaration raise it. The error is `Object.assign(new Error(msg), { statusCode: 403 })`, which Fastify serialises as `{ statusCode, error, message }`, so a handler needs no try/catch — the posture `parseReportFilters` and `src/checkout/checkout.js` already take.
- **A totals row that masking emptied becomes `null`, not `{}`** — an empty object renders as a totals row with nothing in it, which is the "silently short" table a masked view must never be.
- `defineColumns` validates a report's `{ key, label, kind, finance }` declaration at module load (unique snake_case keys, a non-empty label, a known kind), so a malformed report throws while its file is loading rather than as a response. Columns come out in declaration order and rows are built in that same order, so the CSV writer takes its header and its cells straight off the masked envelope with no second ordering rule.

### Product performance, and the report envelope (`src/reports/product-performance.js`, `src/routes/admin-reports.js`)

- **`GET /admin/reports/product-performance` is the first report served over HTTP, and its shape is the one every later report copies.** The payload IS the envelope — `{ report, title, columns, rows, totals, meta }` at the top level, not wrapped in a named key like the list routes: a report is one document and its own name is already the `report` field the CRM keys its renderer on. `columns` carries the labels and kinds, every row is keyed by column key in column order, and `totals` is a row of the same shape — which is what makes it consumable by the CRM's `buildReport` cell pipeline without rewriting `reportBuilders.js`.
- **The handler is three lines and `maskReport` runs on the way out of every route here**, including a report that declares no finance column: masking is what puts `meta.masked_columns` on the payload, and a route that skipped it would be the one that ships a finance column silently the day its report declares one. `parseReportFilters` throws a 400 and `maskReport` a 403, both as `{ statusCode }` errors Fastify serialises, so there is no try/catch anywhere in the route file.
- **Nothing in this report is a `finance` column, deliberately.** A sell value is money and is not a cost — the distinction `access.js` draws, and the one the CRM's own `REPORT_POLICY` already applies (R-05's sell "Value" is open to every staff login; R-10's "Landed /m" is masked). The first report where masking actually deletes a column is the stock report, whose landed cost IS a cost. Marking "Sales" finance here would contradict the policy the CRM consumes.
- **A figure that cannot be added is ABSENT from the totals row, never summed into one.** `qty` is omitted outright — a fabric is metres and a finished good is units, so one number adding the two has no unit — and `value_cents` is omitted whenever the population quotes more than one currency (`meta.mixed_currency` says which). A projected row simply has no such key, which renders as a dash and exports as an empty cell.
- **`orders` carries no currency column and `order_lines.unit_price_cents` is denominated in the PRODUCT's currency**, which varies across the catalogue (the seeded products are EUR, USD, GBP and NZD). Nothing foreign can be bought today — `validateCheckoutLines` refuses a product with a null `retail_price_cents` and only the domestic house has one — so every paid line is NZD in practice. That is a property of the checkout path, not of the schema, which is why `currency` is now a scope column and every money aggregate groups by it. Checkout refuses a mixed-currency cart for exactly the same reason.
- **Totals and the coverage window are computed over the POPULATION, never over the rows that survived the limit.** A total that added up only the visible page agrees with everything on screen and is wrong. A second aggregate over the same scope CTE answers it, and `meta.rows_total`/`meta.truncated` make the table admit which of the two it is.
- **`meta.coverage` states what the figures are OF, in the payload rather than in a screen's footnote** — the CSV is the copy that leaves the building, and a file that does not say what it covers is read as covering everything. It carries the observed window (`from`/`to`, null for an empty population), the range that was asked for (`requested_from`/`requested_to`), and `COVERAGE_NOTE`: live platform orders only, historic Dynamics sales staged **header-only**, so no pre-launch sale is included at any grain and a house sold for years before the platform opened reads as nil.
- **`limit: null` means every row and is the contract the CSV export uses**; the route's schema caps at `MAX_ROW_LIMIT`, so an over-large limit is a 400 rather than a silent clamp reporting a page size nobody asked for. One builder serves the table and the file, which is what stops them disagreeing about what a sale is.
- **These are the only admin routes in this API that opt into the rate limiter.** Everywhere else the backoffice guard is the gate (the limiter is `global: false`), but a report is an unbounded aggregate over the order ledger — the one back-office surface where a stuck screen is a database problem rather than a permissions one. A metered route is provable from its `x-ratelimit-limit` response header, so a test needs two requests rather than sixty.
- The querystring schema is a shape check, not the whitelist: `src/reports/filters.js` decides which filters exist (an unknown name is ignored, an unusable value is a 400 naming it). `brand` is declared `anyOf` string-or-array, because a repeated param arrives as an array and declaring only `string` would 400 the multi-house filter before `parseReportFilters` ever saw it.
- Guarded by 26 tests in `test/admin-reports.test.js` and 6 in `test/report-filters.test.js`. The order fixture there (two houses, three designs, six orders spanning every status the population has an opinion about) is module-scoped and shared with the revenue-scope block; every assertion scopes itself with a `brand` filter, because the database also carries the seeded catalogue.

### The CSV export (`src/reports/export.js`)

- **`GET /admin/reports/<report>/export.csv` and its table are registered off ONE declaration.** `registerReport(path, build)` in `src/routes/admin-reports.js` takes a single builder and registers both routes from it, so "the export shares one query builder with the table" is structural rather than a convention two handlers have to keep — a second report is one more `registerReport` line, not a second pair of handlers. The export differs in exactly three declared ways: it asks for every row, it does not declare `limit` in its querystring vocabulary, and it has its own tighter bucket.
- **`.csv` is its own path segment, never a suffix on a param** — Fastify folds it into the preceding `:param` otherwise and every lookup 404s. The same rule the trade price-list download follows.
- **`limit: null` is the every-row contract, and it is unreachable from the table route.** The table's schema caps at `MAX_ROW_LIMIT` (an over-large limit is a 400, not a silent clamp), and the export's schema does not declare `limit` at all — Ajv's `removeAdditional` strips one a caller sends, which is the right outcome because the export's answer is every row either way. That is what makes "the export is not the current page" true while both share a builder.
- **`maskReport` runs BEFORE the writer sees a row and before either header is set.** It throws 403 for a report the caller may not have, and a refusal raised after `reply.header('content-type', 'text/csv')` leaves as JSON wearing a CSV content type and an `attachment` disposition — the browser saves the error instead of showing it. The rule generalises to every route that sets headers before returning a body.
- **The header row IS the masked envelope's columns**, and every cell is read by that column's key in that order, so a finance column masking deleted has no header here and no value anywhere in the file. There is no second list of what a report contains. The totals row is a row — its label travels as data — so the writer appends it with no second rule, and a figure the totals deliberately lack comes out as an empty cell rather than a zero.
- **Every value goes through `csvCell`.** Nothing may pre-format a cell into a string and hand it over already joined: a design name a staff member typed as `=SUM(…)` reaching Excel unguarded is the exact regression `src/lib/csv.js` exists to prevent, and it is invisible until the client opens the file.
- **A `money` column is written in UNITS at 2dp, never in cents.** `kind` is declared once for the table and the file alike (`src/reports/access.js`), and `100000` under a heading of "Sales" is a wrong figure to every human who opens it. Consequence to know: `csvCell` neutralises a leading `-`, so a negative money figure is written `'-50.00` and Excel shows it as text — the formula guard working as designed, deliberately not special-cased here. No report emits a negative today.
- **The file states its own coverage, its filters and any withheld columns, in a notes block BELOW the table.** A CSV is the copy that leaves the building: one that says nothing is read as covering everything, and a masked one is read as complete. The notes go after the data because line 1 has to stay the header for anything reading the file mechanically, and in a spreadsheet a footnote under the table is where a reader looks anyway. Withheld columns are named by LABEL only, because that is all `meta.masked_columns` carries.
- **The filename comes from the report's own name** (`atelier-<report>.csv`), a module constant checked against `^[a-z][a-z0-9-]*$` — it reaches a `Content-Disposition` header, and a code literal that has stopped being filename-safe is a plain Error (a 500), the posture `requireEntity` takes for a registry key. It carries no date range today, so two exports of different windows share a filename.
- **The export's bucket is tighter than the table's** (10/min against 60): it runs the same aggregate with no row limit and then serialises the whole of it, and it is a download a person clicks rather than a screen that re-reads on every keystroke. Assert the relationship, not the number — compare `x-ratelimit-limit` on the two routes.
- Guarded by 24 pure tests in `test/report-filters.test.js` (the file format, including a synthetic report with a `finance` column, since product performance declares none) and 13 in `test/admin-reports.test.js`. **A test block against the export fetches ONE response in `beforeAll` and asserts against it** — a per-test request would spend the 10/min bucket and surface as a 429 in an unrelated assertion.

### Stock and not-invoiced (`src/reports/stock.js`, `src/reports/not-invoiced.js`)

- **`src/reports/limits.js` owns `DEFAULT_ROW_LIMIT` (200), `MAX_ROW_LIMIT` (1000) and `clampLimit` for every report and for the route schema.** Three reports spend them now; a per-report copy is how one of them would quietly start answering with a different page than its neighbours. `limit: null` is still the export's every-row contract and is still unreachable from a table route.
- **The stock report is the one report NOT built on the revenue scope, and it could not be**: the scope starts at `orders`, and a holding exists whether or not anybody ever bought it. It starts at `inventory` and joins the catalogue outwards, which is also why it honours only `brand`, `product_type` and `collection` — it has no `orders` in its FROM, so the date and lifecycle filters are the ones `STOCK_FILTERS` declines.
- **NOTHING IN THIS SCHEMA HOLDS A LANDED COST, so the stock report carries no valuation and no `finance` column — and no placeholder is written.** `products`, `colourways` and `inventory` have no cost column; `price_list_items.wholesale_rate` is the only cost data Atelier holds and its `(supplier, category, code)` key has no path to a colourway (the supplier colour code must never be joined to `price_list_items.code`, and `products` carries no supplier code at all). A1 (the cost source) is still open. The consequence to know: the CRM's `REPORT_POLICY.stock` masks 'Landed /m' and 'Value', and those columns now have no live source to mask — so **masking still deletes nothing anywhere in Epic 5**. Adding a cost is a decision about A1, not a report change.
- **A snapshot report states `as_at`; a range report states the window it observed.** `inventory` holds current quantities and no history, so "stock as at last month" is unanswerable and a date filter is declined rather than silently narrowing nothing.
- **A zero row is not a holding.** Atelier runs an indent model and most colourways carry an inventory row at zero, so the report lists only `qty_available > 0 OR qty_reserved > 0` and says so in its coverage note; the catalogue is where a design with no stock is looked up. An ARCHIVED design's stock is listed — archiving is a catalogue decision, not a stock movement, the same argument that keeps an archived product's sales in the revenue scope.
- **`available` is legitimately NEGATIVE and must stay so.** A backorder request reserves stock that has not arrived, so a colourway can be allocated past what is on hand; clamping at zero would hide exactly the over-allocation the report exists to surface, and `meta.over_allocated` counts it. This is the first report in the API to emit a negative number of any kind: `csvCell` neutralises a leading `-`, so the CSV writes `'-2.00` and Excel shows it as text. That is the formula guard working as designed — widen it in `src/lib/csv.js` or not at all.
- **A DEFAULT is overridable by a filter; a DEFINITION intersects with it.** `buildRevenueScope(filters, { statuses })` lets a report state its own lifecycle window — not-invoiced covers `requested`/`confirmed`/`paid`/`shipped`, because an order is awaiting an invoice from the moment it is placed — and a `status` filter still REPLACES whichever default is in play. `INVOICEABLE_KINDS` is the opposite case: a card checkout is paid at Stripe and is never invoiced through this platform, so `kind=checkout` intersects to zero rows rather than opening the population back up, and `meta.kinds` states the population so the empty answer is legible. Counting checkouts would report every web sale as an unbilled receivable.
- **The invoice queue cannot state a value, and that is a property of the platform rather than an omission.** Request-kind lines are inserted at `unit_price_cents = 0` (with `subtotal/shipping/total_cents` at 0 beside them), `PATCH /admin/orders/:id` edits quantities only, and the invoice amount is typed into Xero by hand at confirm (FR-8 forbids calling Xero). A "Value" column would therefore be a column of zeros under a money heading — a wrong figure to every human who reads it — so there is none and `meta.unpriced_lines` says how many lines carry no price. Giving it one means pricing the confirm path, not changing the report.
- **The scope carries `user_id`, `guest_email` and `invoice_ref` so the queue reads out of the SHARED population** rather than a second join tree a future D365 source would then have to be unioned into twice. `client` is a COALESCE of the account's name, its email and the guest email — an order is placed by one or the other and never both.
- **A report that cannot honour a filter declares it.** `partitionFilters(filters, names)` splits what was supplied into `meta.filters` and `meta.ignored_filters`, and `src/reports/export.js` writes a `Filters ignored` note under the table. Declining is deliberately not a 400 — the CRM drives every report from ONE filter bar, so a date range left in the bar would otherwise refuse the stock report the moment it was selected — but an ignored filter echoed into `meta.filters` would be read from the CSV as one that had narrowed the file.
- **A figure that is one row's snapshot repeated across many is ABSENT from the totals row**, alongside the metres-plus-units and mixed-currency cases: several not-invoiced lines can name one colourway, so summing their `on_hand` gives a number that exists nowhere. `qty` is totalled only while the population is one `product_type`, and the stock report's three quantities only while it is one `unit`.
- `COALESCE(array_agg(DISTINCT x), '{}')` needs its `FILTER (WHERE x IS NOT NULL)`, or a nullable column puts a null INTO the array, which reads as a second unit and silently switches the totals row off.
- Guarded by 29 pure tests in `test/report-filters.test.js` and 26 in `test/admin-reports.test.js`. **A test asserting on a `timestamptz` must compare against the row the database holds, never a transcribed literal** — the fixtures write wall-clock times, so `2026-03-12 09:00` comes back as `2026-03-11T20:00:00.000Z` under a NZ session and the same test would pass in UTC and fail here.

### `report_access` on `/auth/me` (`src/routes/auth.js`, `src/auth/user-columns.js`)

- **`GET /auth/me` carries a DERIVED `report_access` — `{ reports, finance }` — and it is never stored on the session.** The cookie holds a user id and nothing else, so the statement is recomputed from the row on every read: a finance grant given or taken away in the back office reaches the CRM on its next page load rather than at the account's next sign-in, which is what makes it a revocation rather than a note for later. Nothing a caller sends can reach it — `reportAccess(row)` takes the row the session id resolved.
- **The payload states what the login may SEE and withholds the flag behind it.** `SESSION_USER_COLUMNS` selects `can_view_finance` and `publicUser(row)` projects it back out, so the body carries one statement of the rule rather than two that can be read against each other. Projection, not deletion — the same posture `maskReport` takes: a key that was never declared public cannot survive a projection, where a `delete` only removes what somebody remembered to name. `PUBLIC_USER_KEYS` is split out of `PUBLIC_USER_COLUMNS` itself, so a column added there needs no second edit.
- **`loadReportAccess(db, user)` exists because `src/auth/guards.js` loads `request.user` through `PUBLIC_USER_COLUMNS`, which carries no `can_view_finance`.** A route calling `reportAccess(request.user)` therefore read the flag as `undefined` and answered `finance: false` to everyone, for ever. Nothing showed it — no Epic 5 report declares a finance column — but the moment `/auth/me` publishes a statement to the CRM, a payload saying "you may see costs" beside a report route masking as though you may not is exactly the drift this layer exists to prevent. So the report layer fetches the one column it needs, keyed on the id the SESSION resolved, and **a record that already carries the flag is used as-is** — which is how the extra lookup disappears of its own accord if the guard's projection ever widens. It fails closed: a row that has gone has no finance.
- The lookup is a primary-key read beside an unbounded aggregate, so it costs nothing worth optimising. Do not "fix" it by widening `PUBLIC_USER_COLUMNS` — that list is what every login, register and session response returns, and the flag has no business in any of them.


### The W21 reporting dimensions (`src/reports/coverage.js`, `1788408000000_reporting-codes.js`)

- **`brand_code` and `range` are the first FREE-TEXT filters in `FILTER_COLUMNS`, and they must never reuse `parseSlug`.** That parser is safe only because slugs are `[a-z0-9-]` by construction; a brand code is `CF` and a range is `RAMM, SON & CROCKER`, so reusing it would 400 every real value the office holds. `parseFreeText` validates the SHAPE instead — non-empty, ≤100 characters, one line of printable text — and the control-character check is load-bearing rather than tidy: `meta.filters` is echoed into the CSV's notes block, so a newline in a filter breaks the file out of the row the reader is looking at.
- **The `%…%` wrapping happens in `BINDINGS`, never in the parser, and the two halves of the escape are one rule.** The parsed value is what `meta.filters` echoes back and what the CSV's notes print, so a parser that returned `%c \& c milano%` would tell the office it typed something it did not. `escapeLike` neutralises `%`, `_` and `\`, and the clause carries a matching `ESCAPE '\'` — without the clause half, Postgres uses no escape character at all and the backslashes are matched literally, so `100%` finds nothing instead of everything. `FREE_TEXT_FILTERS` is the list, checked against the whitelist at module load.
- **Both columns are in the revenue SCOPE, not in each report.** `product_range` and `brand_code` are scope columns because every report that reaches `p`/`b` can filter on them and because each report states how much of ITS OWN population carries them — a count that would otherwise be a second join per report. Adding them moved `SCOPE_COLUMNS`, which `assertScopeSource` checks POSITIONALLY.
- **`src/reports/coverage.js` holds the two statements a report has to make about the new dimensions, and they reach the FILE.** `dimensionCoverage()` states the constraint that makes an empty range report legible: all four D365 transaction entities are staged **header-only**, so no historic sale is attributable to a product, a brand code or a range at any grain, and the platform has been taking orders for weeks. The counts beside it are what turn a caveat into a measurement — 0 of 40 lines carrying a range is a backfill that has not run, not a quarter with no trade. `src/reports/export.js` writes both statements as their own notes rows, because the CSV is the copy that leaves the building and `notesOf` previously carried `coverage.note` alone.
- **Every stock figure names the table it came from, and nothing picks a winner between the two staged D365 totals.** `legacy_stock_items.stock_on_hand` totals 5,332.8 (its own `xero_stock_on_hand` agrees at 5,421.8) against `legacy_item_locations.total_stock_on_hand` at 14,157.9 — **2.65×** — and the disagreement is not even diagnosable until Item Locations is re-exported with the item code, because its `item` column is a display-name lookup and stock-item names repeat (7,611 items over 6,315 names). `stockSource('inventory')` is on the stock report's three quantities and on the not-invoiced report's `on_hand`; an unknown key is a plain Error (a 500), the posture `requireEntity` takes for a registry key.
- **No report gained a `brand_code` or `range` COLUMN** — FR-278 asks for filters, and adding columns would change `PRODUCT_PERFORMANCE_COLUMNS`, which the CRM's renderer and the CSV header are both built from. Grouping BY range is a new report, not a widened one.
- `brands.brand_code` is deliberately absent from `src/catalogue/brands.js`'s `BRAND_COLUMNS`. `test/price-list-exposure.test.js` scans COST vocabulary only, so a code leaking into a public house response is a regression it would not catch — `test/reporting-codes.test.js` asserts the absence against the read model and scans the serialised body for the VALUE as well as the key.

- **`sales-by-rep`** (`src/reports/sales-by-rep.js`): order-grain attribution over the SAME revenue scope (the rep columns ride the scope: `sales_rep_user_id` + `rep.name AS sales_rep`). NULL reps are an explicit **'Unassigned' row, never dropped**; grouped by the ID, displayed by the name (two Rebeccas stay two rows). The `rep` filter (`FILTER_COLUMNS.rep`, `parseId` — a positive integer id, never free text) narrows every scope-backed report. Coverage note carries the A6 caveat: attribution is staff-asserted, never derived from the Dynamics owner field.
