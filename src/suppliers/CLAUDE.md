## Suppliers

- **A supplier is who INVOICES Atelier; a brand is what a customer buys.** One supplier sells several brands (Rubelli sells Dominique Kieffer, Jim Thompson sells No.9 Thompson), so they can never be the same row. `suppliers` + `supplier_aliases` land in `migrations/1786334400000_suppliers.js`, with `brands.supplier_id` and `price_list_items.supplier_id` added beside them.
- **`suppliers.currency` is the supplier's INVOICING currency, never the country's default** — Jim Thompson is Thailand and invoices USD, C&C Milano is Italy and invoices EUR. It is deliberately **nullable**: a NOT NULL forces a value at create time, and the only value to hand is the country, which is exactly the wrong answer. Blank means "no invoice on file yet"; the backfill fills it from `price_list_items.currency`, which every rate row already carries.
- **No cost column may ever be added to `brands`.** `src/catalogue/brands.js` serves brand rows to anonymous visitors, so a discount, rate or markup parked there ships to the public storefront. `brands` gains exactly one integer (`supplier_id`); commercial terms live on their own tables, which no client-facing read model joins. `test/suppliers-schema.test.js` asserts no `brands` column matches the cost vocabulary, at the schema layer, ahead of `test/price-list-exposure.test.js` at the response layer.
- **`price_list_items.supplier` free text STAYS.** It is part of the `(supplier, category, code)` unique key `npm run import:pricing` upserts on, so dropping it would rewrite the upsert target and make every re-import insert duplicates instead of refreshing. `supplier_id` sits beside it and is backfilled; the free text remains the row's identity and its traceability to the source file.
- **The two FK policies differ on purpose.** `brands.supplier_id` is **RESTRICT** — a house pointing at a supplier is a live commercial relationship, and deleting the supplier must be refused loudly rather than silently unlinking houses (this is the 23503 backstop the delete route exercises). `price_list_items.supplier_id` is **SET NULL** — the rate ledger is history that must survive the supplier record being tidied away.
- **`supplier_aliases` is unique on `lower(btrim(alias))` GLOBALLY**, not per supplier: the price lists spell one house several ways (`JV`, `JWALL`, `C&C MILANO` — see `SUPPLIER_OVERRIDES` in `scripts/convert-price-lists.js`) and an alias that resolved to two suppliers would make the backfill pick one at random. `supplier_id` is CASCADE — an alias is a lookup key belonging to the supplier, not a business record.
- **`suppliers.d365_token` is the token D365 composes into an item code** (`F3518-003 23PF` → `PF`). It identifies the SUPPLIER, not the brand (`CF` covers Colefax & Fowler *and* Jane Churchill), so it is the roll-up key back into the `legacy_*` corpus. Partial-unique (`WHERE d365_token IS NOT NULL`), as is `short_code`, so the optional columns stay repeatably NULL.
- `discount_method` is `CHECK IN ('averaged','per-brand')`, matching the vendored `src/seed/data/suppliers.js` vocabulary: `averaged` is the one supplier-level net discount (the 9 Jul rule), `per-brand` the complex houses excluded from averaging and handled brand by brand.

### Commercial terms (`supplier_brand_terms`, `supplier_discount_tiers`)

- **A discount chain is MULTIPLICATIVE, which is why `discount_chain` is `numeric(6,4)[]`.** JV Fabrics is "40% off, then 40% off the result" — `{0.4, 0.4}` nets to **×0.36**, not −80%. Summing a chain into one rate undercharges Atelier by 44% of list on every metre, so no reader may reduce it to a single percentage. `src/suppliers/discount-chain.js` (`chainMultiplier`, `applyDiscountChain`, `resolveTermsChain`) is the only evaluator; it is pure, and it is a deliberate re-implementation of the vendored `src/seed/data/discounts.js` rather than an import, so re-copying `src/seed/data/` can never change API behaviour.
- **Three shapes, and a row may hold only one.** `discount` is the flat per-brand rate (the JV sister brands, −50%), `discount_chain` the compounded sequence, `supplier_discount_tiers` the rates that differ by what is bought (Janelli Volpi: 45% new collections / 40% wallpapers by the metre / 50% everything else). `supplier_brand_terms_discount_shape_check` (`discount IS NULL OR cardinality(discount_chain) = 0`) enforces it at write time — carrying both would leave the net rate depending on which reader's precedence rule ran. `resolveTermsChain`'s precedence (chain → tier → flat) mirrors the snapshot's `resolveDiscount`.
- **The fallback tier is a flag, not the string `'All other collections'`.** `is_fallback` carries it, with a partial unique index (`supplier_discount_tiers_fallback_unique … WHERE is_fallback`) so at most one exists per brand: two fallbacks make the unmatched case — the common case — non-deterministic. Tier labels are matched case-insensitively against the line's category, so they are unique per terms row on `lower(btrim(label))`, same posture as `supplier_aliases`.
- **Terms are UNIQUE per brand** (`brand_id` UNIQUE, not part of a composite): one house has one set of terms, whoever invoices it.
- **Both FKs are CASCADE, deliberately.** A terms row describes a live supplier–brand relationship, not a record that outlives it. It also keeps US-005's supplier DELETE story intact — `brands` (RESTRICT) and `price_list_items` (SET NULL) stay the only two blockers a caller is counted, rather than a third RESTRICT edge surfacing as an uncounted 23503. A brand is effectively never hard-deleted anyway (archivable, and `deleteOrExplain` refuses one with any product or collection), so the cascade only ever reaches a stub house.
- **Neither table may be joined into a client-facing read model.** A discount off a maison's list price is that maison's confidential term. `test/suppliers-terms.test.js` walks every `src/**/*.js` (skipping the vendored `src/seed/data/`) and asserts the tables are named only under `src/suppliers/` or `src/routes/admin-suppliers.js` — the schema-layer counterpart to `test/price-list-exposure.test.js`. They are also **not** registered as AdminJS panel resources.
- **pg parses `numeric[]` into JS numbers but a scalar `numeric` into a string**, so a chain and a flat rate arrive from the same column family as different types. The house "coerce with `Number()`" rule is about the scalar; the module coerces either.
- A `CHECK` cannot contain a subquery, so per-element range validation of `discount_chain` is impossible in SQL — that lives in `rateFrom`. A NULL element *is* catchable (`array_position(discount_chain, NULL) IS NULL`) and is checked, because one NULL nulls the whole computed net rate.

### `products.category`

- **`products.category` and `price_list_items.category` are ONE vocabulary** (`fabric | wallpaper | trimming | accessory`), which is the entire point of the column: it is the axis on which the catalogue and the supplier rate ledger become joinable. Added by `migrations/1786507200000_product-category.js` with the same inline CHECK text as `1785110400000_price-list-items.js`. **Widening the set is a one-line migration on BOTH tables** — a value added to one side never raises anything, it just silently stops matching, so `test/suppliers-product-category.test.js` compares the two live `pg_get_constraintdef` definitions to each other rather than to a literal list.
- **It is NOT `product_type`.** `product_type` is `fabric | finished_good`, is create-only, and is what derives the colourway's inventory unit (metres vs units). `category` is a merchandising axis: a wallpaper and a trimming are both finished goods, and both are bought on rates filed under their own category. Conflating them would strand stock in the wrong unit.
- **Nullable, with no default.** Every product predating the column is uncategorised, not wrong; the only defensible default is `fabric`, which would assert a category for rows nobody has looked at while reading as populated. The Epic 6 spreadsheet round trip is the fill-in path. No index either — four values over a table of hundreds is not selective, and the joins are aggregate.
- **Nothing exposes it yet.** `FILTER_COLUMNS` (`src/catalogue/products.js`) and `PRODUCT_UPDATE_COLUMNS` (`src/catalogue/admin-products.js`) do not list it, and adding it to either alone would be inert: Ajv's `removeAdditional: true` strips any key the route schema's `properties` does not name, so `src/routes/catalogue.js` (`listQuerySchema`) and `src/routes/admin-catalogue.js` have to be edited in lockstep with the whitelist.
- An inline column `check:` — in `createTable` or `addColumns` — is emitted unnamed, and Postgres auto-names it `<table>_<column>_check`. That is the name a `rejects.toThrow(...)` assertion and a `pg_constraint` lookup both use; no `addConstraint` is needed to get it.

### Back-office admin module (`src/suppliers/admin-suppliers.js`)

- **Every field this module serves is cost-bearing or commercially sensitive**, so nothing here may be joined into a client-facing read model: `discount_method` states how the house is rated, `agent`/`incoterm` are the negotiated freight terms, `po_email` is an internal ordering address, and `getSupplier` embeds the per-brand terms outright. `test/suppliers-admin.test.js` asserts this against the REAL `/catalogue/*` bodies — the response-layer counterpart to the source scan in `test/suppliers-terms.test.js`, and now load-bearing in a way it was not before: `brands.supplier_id` exists, so every public brand response is one careless `SELECT *` away from carrying it.
- **The exposure suite asserts BOTH directions.** A test that only proves a field is absent from `/catalogue/*` keeps passing after the admin read model quietly stops returning it, which is a regression wearing a green tick. Each absence assertion is paired with one that the back-office model DOES carry the field, and the raw response BODY is scanned for the fixture's secret VALUES as well as its keys — a renamed column passes a key scan while still shipping the freight agent and the PO address.
- Shape follows `src/pricing/admin-price-lists.js` exactly: limits + `httpError` + `rethrowConflict` + a frozen `SUPPLIER_UPDATE_COLUMNS` fed to `buildUpdate` + a frozen `toSupplier` mapper. `listSuppliers` returns `{ suppliers, total }` — the ROUTE builds the meta envelope.
- **The list search reaches `supplier_aliases` via a correlated EXISTS**, not just the canonical name. The price lists spell one house several ways (`JWALL`, `C&C MILANO`) and those spellings live ONLY as aliases, so a name-only search answers "no such supplier" for exactly the strings staff have in front of them. The query uses the bare table name rather than an alias (`WHERE supplier_aliases.supplier_id = suppliers.id`) so the one unqualified `SUPPLIER_COLUMNS` constant stays valid in the SELECT, the INSERT RETURNING and the UPDATE RETURNING alike.
- **`slug` is server-generated on create and is NOT recomputed on rename.** It is the stable key the backfill and any later import address a supplier by; a rename is a correction, not a new supplier. `discount_method` is writable, but its vocabulary is the database's CHECK rather than a JS list, so the two cannot drift.
- Four unique constraints can raise a 409, so `rethrowConflict` is keyed on `error.constraint` (`suppliers_name_key`, `suppliers_slug_key`, `suppliers_d365_token_unique`, `suppliers_short_code_unique`); an unknown constraint degrades the message, never the status. A duplicate is always detected by the database — a pre-check races and would still need the handler.
- **`listSupplierBrandTerms` (`src/suppliers/supplier-terms.js`) batch-loads tiers for every terms row in ONE query** (`WHERE supplier_brand_term_id = ANY($1::int[])`) and groups them in JS, the posture `src/orders/order-history.js` already takes for order lines. It resolves each row's `net_multiplier` through `discount-chain.js`, so the ×0.36 rule reaches the read model rather than being re-derived by a caller.
- **A bad `discount_chain` element is reported on the row, not thrown.** A CHECK cannot validate array elements, so the chain is the one place an out-of-range rate can reach the database, and `rateFrom` throws on it. Failing the whole supplier read for one bad row would hide the other thirty-nine, so the row carries `net_multiplier: null` plus `invalid_reason` and the CRM badges it.
- **`Number(null)` is 0**, which on a discount or markup column reads as "free" / "sell at cost". Every nullable numeric goes through `value == null ? null : Number(value)`; the house "coerce numeric with `Number()`" rule is about a value already known to be present.
- Archived brands are included in `getSupplier`'s `brands` deliberately: `brands.supplier_id` is RESTRICT, so an archived house still blocks the delete, and hiding it would show a supplier that looks unlinked and then refuses to go.
- Test-fixture order: delete `brands` before `suppliers` (RESTRICT), or the supplier delete 23503s inside cleanup. `supplier_brand_terms` needs no cleanup line — it CASCADEs from both sides.

### Routes (`src/routes/admin-suppliers.js`)

- **`GET|POST /admin/suppliers`, `GET|PATCH|DELETE /admin/suppliers/:id`, `POST /admin/suppliers/:id/archive|restore`** — all `requireRole('backoffice')` (director inherits). There is no viewer below staff: the record carries the freight agent, the Incoterm, the internal PO address and how each house is discounted. The guard test is parameterised over the whole surface, so a route added later without one fails.
- **DELETE is the first route in this API wired to `deleteOrExplain`/`replyDelete`.** `supplier` is a **code literal**, never `:entity` from the URL — the registry is not an authorisation boundary, so a name taken from the path would let a caller choose which table gets deleted from (`test/lifecycle-registry.test.js` enforces the literal by source scan).
- **Both blockers are probes, and the SET NULL one is the reason probes exist.** `brands.supplier_id` is RESTRICT so the database would at least refuse, but `price_list_items.supplier_id` is SET NULL: without its probe, deleting a supplier silently unlinks the entire rate ledger and returns 200. Each blocker reports its own count, and the refusal carries `archivable: true` — which is what makes `POST /:id/archive` the answer a blocked supplier needs, since a house pointing at it can never be unlinked without destroying who invoiced it.
- **`brands_supplier_id_fkey` is registered in `CONSTRAINT_BLOCKERS` (`src/lifecycle/delete.js`)** — the second RESTRICT edge in the schema after `order_lines_colourway_id_fkey`. The probe normally reports it first; the entry is what keeps a lost race (a house inserted between the probe and the DELETE) saying "houses" rather than the generic "related records". Exercised against a stub pool, as the lock-mode assertions are — its real trigger is a race.
- **`DISCOUNT_METHOD_ENUM` in the route file is the boundary copy of `suppliers_discount_method_check`.** Without it a typo reaches the CHECK and surfaces as a 500 instead of a 400; with it the two can drift, so `test/suppliers-routes.test.js` parses the live `pg_get_constraintdef` and asserts they are the same set. Same posture as `CATEGORY_ENUM` in `admin-price-lists.js`, with the drift test added.
- The route builds `{ suppliers, meta: { total, page, limit } }`; the module returns `{ suppliers, total }`. `limit` past `MAX_LIMIT` is a **400 by schema** here, not a silent clamp — the module still clamps, because it is also called directly.
- Admin routes in this API do **not** opt into `config.rateLimit` (the limiter is `global: false`), and these follow that: the backoffice guard is the gate. Only the public and `/account/*` routes are metered.

### Backfill (`npm run backfill:suppliers`)

- **`npm run backfill:suppliers`** (`src/seed/backfill-suppliers.js` CLI → `src/suppliers/backfill.js` → the pure `src/suppliers/backfill-plan.js`) populates `suppliers`, `supplier_aliases`, `price_list_items.supplier_id`, `brands.supplier_id` and the per-brand terms from the two sources the office already holds: `SELECT DISTINCT price_list_items.supplier` (40 filename-derived spellings) and the vendored `src/seed/data/suppliers.js` (9 houses with the country, currency, agent, Incoterm, PO address and discount method). **Run it after `npm run import:pricing`** — on an empty rate ledger it can only see the 9 snapshot houses. Real corpus: 42 suppliers, 4 aliases, 40 name matches, 15 house links, 6 terms rows.
- **The apply layer lives in `src/suppliers/`, not `src/seed/`, and must stay there.** It names `supplier_brand_terms` and `supplier_discount_tiers`, and `test/suppliers-terms.test.js`'s ownership scan is a plain `source.includes(table)` that allows those names only under `src/suppliers/` or `src/routes/admin-suppliers.js`. `src/seed/backfill-suppliers.js` is a CLI wrapper for that reason alone.
- **Match, then report — never guess.** Two spellings become one supplier only by an exact `lower(btrim(name))` match or by an alias saying so, and **name beats alias**: while a supplier row of that exact name exists, an alias pointing elsewhere is ignored. So merging `Jannelli Volpi` (the rate ledger, 2,516 rows) into `Janelli Volpi` (the snapshot spelling, which holds JV's tiers and its ×0.36 chain) is a human act — add the alias, DELETE the duplicate (`price_list_items.supplier_id` is SET NULL, so the rates survive it), re-run. The planner reports the pair and never collapses it: a guessed merge is a wrong discount on every metre.
- **Currency comes from the price list, never the snapshot and never the country.** A rate row is evidence of an invoice; the snapshot is a note of intent, and the two disagree (Manuel Canovas: rates say GBP, snapshot says EUR). The snapshot fills only a supplier with no rates, a disagreement is reported, and a name quoting two currencies is left NULL rather than resolved.
- **What it may overwrite and what it may not.** `price_list_items.supplier_id` is derived, has no screen and its only truth is the free text beside it, so it is re-pointed whenever the resolved supplier differs — that is how an alias hands 2,516 orphan rows over. `suppliers` columns and `brands.supplier_id` are staff-curated and are filled **only where NULL**, the same COALESCE posture as `brands.website_url` in the seed: a backfill that overwrote what it found would undo an office correction every time someone re-ran it.
- **Re-running changes nothing, and every statement carries its own guard**: the supplier upsert fires its `DO UPDATE` only when a row comparison shows COALESCE would actually fill something (so `updated_at` does not creep), aliases are `ON CONFLICT DO NOTHING`, both link updates carry `IS DISTINCT FROM` / `IS NULL`, and terms are inserted only where the brand has none. `(xmax = 0)` in the `RETURNING` is what separates a created row from an enriched one.
- **`SUPPLIER_ALIAS_SOURCES` is a boundary copy of `SUPPLIER_OVERRIDES`** in `scripts/convert-price-lists.js`, which does not export it — `test/suppliers-backfill.test.js` scans that file and asserts the two agree, the posture `DISCOUNT_METHOD_ENUM` takes against the database CHECK.
- **The snapshot's catch-all tier is a LABEL there and a FLAG here.** `resolveDiscount` in the vendored `src/seed/data/discounts.js` falls back on the literal `'All other collections'`; the backfill translates it into `is_fallback` so the string never reaches the schema, and reports a tier set that has no catch-all.
- **The snapshot names houses that were never catalogued** — all seven of JV's (`Altagamma`, `JWall`, `JV Design`, `Armani` vs the catalogue's `Armani Casa`, `Missoni` vs `Missoni Home`, `JV Fabrics`, `Janelli Volpi` itself). They are reported, never created: inventing a `brands` row would put a maison on the storefront that Atelier holds nothing from. Consequence today — `supplier_discount_tiers` and `discount_chain` stay empty on a real run, and the 6 terms rows that do land are Fabricut's retail markups.
- **A price-list `supplier` is often a BRAND, not a supplier** (`Altagamma`, `S Harris`, `Jane Churchill`, `Kieffer` are all somebody else's house), because the value comes from a filename prefix. The backfill creates a row per distinct name anyway — the story is "nobody retypes 40 names", and merging is a CRM act with the alias + delete flow above.
- Test posture: the real-data assertions run through the **pure planner** against the committed `src/seed/data/price-lists.json`, so they cost no writes to the shared test database; the apply layer is exercised against prefixed fixtures with an **injected** snapshot and alias list, so a test run can never create the nine real houses.
