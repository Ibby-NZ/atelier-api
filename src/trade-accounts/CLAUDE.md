# atelier-api — trade client portal

Extracted from the root CLAUDE.md (root conventions still apply). Loaded automatically when working in this directory.

## Trade client portal (`/account/*`)

- The approved-trade client's own view: dashboard, sample history, invoice record, price lists, account manager. `src/routes/account.js`, read models in `src/trade-accounts/` + `src/account/summary.js`. **Every route is `requireRole('trade')` and nothing else** — `GRANTING_ROLES.trade` is `['trade']` and `effectiveRole` collapses an unapproved trade account to `customer`, so that one preHandler already means "approved trade, not a customer, not staff". Staff are excluded deliberately (they have the CRM and `/admin/legacy/*`, unscoped); re-deriving the predicate per handler is how the archived-user and CORS-methods regressions happened. All routes opt into `config.rateLimit` — the limiter is `global: false`, so a route without it is unmetered.
- **`users` is a login (a person); a trade client is a company.** Nothing joined them, so `trade_accounts` + `trade_account_users` (migration `1786248000000_trade-accounts.js`) is the link, deliberately **outside** the `legacy_*` namespace: `importLegacyEntity` upserts every mapped column to EXCLUDED, so anything stored on a legacy row would be destroyed by the next `npm run import:legacy`.
- **The key is the D365 GUID; the NAME is a snapshot.** The transaction exports carry the customer as the target's **display name**, not a key (`legacy_sales_invoices.customer` is text), so `trade_accounts.legacy_customer_name` is snapshotted at link time and is what the reads match on. **Account names are not unique** — 866 rows, 865 distinct names ("Peter Kedgley Architects" twice, 2 invoices between them) — and a name-equality predicate returns the UNION of every account sharing it, i.e. cross-client disclosure by construction.
- **The collision check is LIVE, in `VIEWER_CTE`, not the stored flag.** `name_is_ambiguous` is computed once at link time, but `npm run import:legacy` re-runs until cutover — upserting `legacy_accounts.name` and inserting new rows — so the flag can be falsified afterwards. Two drifts, both closed by the CTE's join to `legacy_accounts`: a NEW account appearing with an already-linked company's name (its invoices would join straight onto that viewer while the flag still said false), and a linked account being RENAMED with its old name later taken by someone else (here the collision count is legitimately 1, so recomputing the flag would not help — requiring the snapshot to still equal the LINKED GUID's current name is what does). `toClientTradeAccount`'s `linked` is the live `resolves`, so the dashboard can never promise history the reads will refuse. The stored flag remains the CRM's warning. Verified against the real corpus: the colliding link reports `coverage.invoices: 2` to staff and serves the client `linked: false` and zero rows; both drift cases are regression-tested.
- **`UNIQUE (user_id)` on `trade_account_users`** — one login, one company. Without it a back-office mis-click links a person to a second firm and a single-row viewer query starts returning a non-deterministic one (intermittent cross-company disclosure). Several logins per company IS allowed and is the common case (the trade application collects a design contact and an accounts contact).
- **The scoping key is never a function argument.** `VIEWER_CTE` (`src/trade-accounts/viewer.js`) derives it inside SQL from `$1 = the authenticated user id`, the same posture as `/orders/mine`. No read model here accepts a customer name — a helper that did is one a future route could bind from a query param. An unlinked or ambiguous viewer resolves to zero rows, so the reads **fail closed** rather than degrading to `= ''` (which matches every legacy row with an empty customer field).
- Linking is **manual, backoffice, and never automatic** (`/admin/trade-accounts`, `src/trade-accounts/admin-trade-accounts.js`). **No screen calls those routes yet** — they belong on the CRM's Users → Applicants tab, which is another repo — so `trade_accounts` and `trade_account_users` are registered as editable AdminJS resources as the stopgap. Without one of the two, nothing can create a link and the samples/invoices/account-manager panels are unreachable for every client. `GET /admin/trade-accounts/suggestions` ranks candidates by exact account email then name — suggestions only. An auto-link on email match is the tempting shortcut and is wrong: 171 contact emails are shared by 2-4 contacts and 385 are free-mail, so it would eventually show one designer another's invoices. `GET /admin/trade-accounts/:id` carries `coverage` (invoice + cutting counts) because a link resolving to zero is almost certainly the wrong company, and this is the only place a human sees that before the client does.
- **Invoices are header-only, forever, and carry no payment state.** All four D365 transaction entities export header-grain and line import is shelved, and `status_reason` is 'Sent to Xero' on all 7,002 rows — a dispatch state, not a payment one — while FR-8 forbids calling Xero. So the screen is an invoice **record**, never a statement: no balance, no aging, no "paid" badge. `POST /account/invoices/:id/copy-request` is what replaces the missing PDF (mails the back office + the client). Its `:id` is **re-resolved through the caller's own scoped query** — a D365 GUID is not a secret, and without that check the back office would receive "client X wants invoice <guid>" with no way to tell it was not theirs, and would post it. A non-owned id is **404, not 403** (403 confirms existence).
- Sample history is `legacy_cuttings`, not `legacy_reserves`. The staged export starts 2025-04-08 and has no due-back date, so the panel says what window it is showing rather than implying it is everything. **`legacy_cuttings.comments` is NOT served** — it looks client-safe and is not: 1,757 of 1,886 rows carry one and they are the back office's scratchpad, holding staff names, handling instructions and in several current rows a third party's name, email, phone or home address. Serving it would put one client's contact details in another client's JSON.
- **Account manager is a staff-set field on `trade_accounts`, never derived from `legacy_accounts.owner`** — 72% of that column is a shared login ('Atelier Sales' 491, 'Showroom #' 135) and A6 (salesperson vs owner vs account holder) is still open. Null degrades to a generic showroom contact block.
- **`GET /orders/mine` is now paged** (`page`/`limit`, `{ orders, meta }`). It used to return every order a user had ever placed plus every line of all of them, which the dashboard then sliced to three — and a long-standing trade client is exactly the account that breaks that. Order lines now also carry `slug`/`product_type`/`brand_name`/`colourway_name`/`lead_time`, which is what reorder needs.
- **Client price lists are the SELL side and must never touch `price_list_items`** (`src/pricing/trade-price-lists.js`). That table is Atelier's BUY side — 19.5k supplier rates, mostly discount-inclusive, so the rate IS the net cost; divide it into the trade price and the margin falls out, and the lists are the maisons' confidential documents. Do not widen the guard on `/admin/price-list-items`, do not reuse `toPriceListItem` (no field-level redaction), and do not point the portal at `/admin/legacy/prices` (its `:guid` route returns the whole `raw` jsonb, bypassing every column whitelist). The client list is built from `products.trade_price_cents` alone — cost-free by construction — and `test/price-list-exposure.test.js` asserts all of it, parameterised over every `LEGACY_ENTITIES` route plus a property check that no client-facing key matches `/wholesale|landed|duty|freight|cost|margin|markup|credit_limit|payment_terms/`.
- **Price lists ship DISABLED** (`TRADE_PRICE_LISTS_ENABLED`, off unless exactly `'true'`; the routes are simply not registered, so a probe 404s). `trade_price_cents` is still the demo snapshot — 8 of 12 seeded fabrics share NZ$187.76, no finished good has one — and a per-house list is a document a designer quotes a job from. Turning it on is a decision about the numbers.
- CSV export escapes RFC 4180 **and** neutralises formula lead-ins (`= + - @ TAB CR` get an apostrophe): every column is staff-typed free text via `PATCH /admin/products` and the file is built to open in Excel, where `=HYPERLINK`/`=WEBSERVICE` exfiltrate. The `Content-Disposition` filename comes from the brand **slug** (`[a-z0-9-]` by construction), so nothing typed can reach the header.
- Guarded by `test/account-portal.test.js` (20), `test/trade-accounts.test.js` (18), `test/price-list-exposure.test.js` (15). The portal fixture gives two different legacy accounts **the same name** — the regression the ambiguity flag exists to prevent, which a fixture with distinct names would pass anyway.

## The contact book (`trade_account_contacts`)

- **A contact is NOT a login.** `trade_account_users` grants portal access; `trade_account_contacts` (migration `1789996800000`) is the staff-kept book of people at the company — name, role, email, phone, note — none of whom needs a password ("Zomia is Jenny, Viv, Haike"). CASCADE off `trade_accounts`; never served to clients (`viewer.js` / `client-legacy.js` write their own SQL and know nothing of it).
- **`user_id` is now OPTIONAL on `POST /admin/trade-accounts`**: a bare create upserts the company row and grants nobody anything (the viewer CTE keys off the grant and fails closed), so the contact book can exist before any login does. A later real link upserts onto the SAME row — the GUID is unique — and contacts survive it.
- **`GET /admin/trade-accounts/by-guid/:guid`** bridges the CRM's mirror screens (keyed by D365 GUID) to the company row; its 404 is the screen's "enable contacts" branch. Contact CRUD lives under `/admin/trade-accounts/:id/contacts(/:contactId)`, backoffice; writes fold `''` to null, scope child rows in the WRITING statement, and answer with the fresh account via `getTradeAccount`.
- **`getTradeAccount` also serves `d365_people`**: the `legacy_contacts` rows whose `company_name` matches the snapshotted name (same match the coverage counts use — a shared name unions same-named companies, which the ambiguity flag already warns about). The projection is a WHITELIST — `full_name, job_title, email, mobile_phone, business_phone` — never the credit / do-not-contact / GDPR columns; `test/trade-account-contacts.test.js` scans the serialised body for the keys AND a fixture value.

- **A trade client edits their own application from the portal** (16 Sep 2026):
  `GET /account/trade-application` (404 when the office created the login by hand)
  and `PATCH /account/trade-application` over `APPLICATION_EDITABLE_COLUMNS` —
  everything on the form EXCEPT the consent block (terms, who signed, as what,
  the signature), which is the record of what was agreed. The patch is merged
  over the stored row and the whole thing re-run through
  `validateTradeApplication`, so a client can no more blank their NZBN than they
  could have on the day (422 naming the field). Both routes are `requireRole('trade')`.
